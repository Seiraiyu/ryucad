## Inserts and deleted bodies (decided in ryucad phase 25)

The design is document 521 in the Coxswain planning project `ryucad-ryukei`; this is its plan 25.A (phases 1 to 4, issue #41).

- **Solid keys.** A solid's key is an `Id` that may hold `/`: a founder's ID, or an inserted solid's `<insert>/<source key>` (`Id::solid_path`, read by `Id::solid_key`; `Id::parse` still refuses `/`). Every field naming a solid reads it through `doc::solid::SolidRef` (`targets`, `target`, `tools`, a mirror's `solid`, a split's `target` and `tool.body`, the tweak family's `target`, `delete_body`'s `solids`; sheet metal's `target` stays a founder). A reference into an inserted solid is `{feature: <insert>, solid: <source key>, name}` in files, `<part>/<insert>/<source key>/<name>` in text; in memory `Reference::feature` is the key. What reads a key as a feature (list order, the graph, `has_dependents`, renumbering) reads its founder (`Id::founder_str`). Feature format 21 holds inserts, deletes and any path key or `solid`; every other file keeps its bytes (`tests/corpus.rs` writes every committed feature file back byte for byte).
- **Inserts.** `insert` (`doc::insert::Insert`: `part`, `rev` as an instance's, `project` beside it for another project's, `placement` a primitive's, the identity unwritten) founds a *family* (`solid::Solids`): any key below it is its, chain `[insert]` until a feature acts on it; which keys exist is the source's model at the pin. Parts that insert read parts (`assembly::reads_parts`): built after their sources, keyed by the sources' model hashes, never in the leaf batch, never evicted as leaves; Tarjan takes inserts as edges, and a cycle through one is `insert_cycle`. An inserted solid is the source's body moved (`Body::transformed`), its hash BLAKE3 of the source's hash and the pose (`insert::inserted_hash`), the source's own `Arc` at the identity; it carries `Built::moved` so its mesh is the source's moved (`mesh::make`), and the source lineage moved (`Lineage::moved`) so a source split is followed as `Carrier`. Not on disk. Refusals: `not_found`, `wrong_part_kind` (an assembly, question 625), `insert_cycle`, `label_not_found`, `label_not_official`, `insert_source_empty`; warnings `insert_source_failed` (the source's model as it shows) and `insert_obsolete`, under the insert in the report and in the part's warnings. An inserted reference is refused `reference_body` with the hint `ryucad import convert <source part>/<source key>`: it is converted where it was imported.
- **Pins.** A new insert with no `rev` takes the newest official label, else `working` (question 624; the answer's `took`); another project's part takes the lock's newest label, else the fetched dependency's (`release::newest_official`). A request or a proposed part reading a label no file reads yet looks it up (`Session::model`, `Session::rebuilt_as`). `insert.update` (`ryucad insert update <part> <insert> [--to working|label:L|newest] [--dry-run]`, two arguments as `feature edit` takes them) moves it as one logged change, answering the inserted solids `added`, `removed`, `changed` and the features that fail after. `insert_behind` (doctor and check, a warning) has the repair `insert_update`; an insert whose source part is gone is doctor's `not_found` (an error, no repair). Another project's inserted part is locked as a placed one is (ryupdm's `lock::wanted`, `deps::keep_lock`).
- **Deletes.** `delete_body` (`doc::body::DeleteBody`: `solids`, keys or an insert's ID for its family, each once) ends chains as a boolean ends its tools': features before it read them, after it `body_deleted` (`solid`, `by`); deleting a solid twice, a consumed one or one that isn't there is refused at write (`check_delete` runs the build against the current rebuild). It builds to nothing, keyed by its fields, kept in memory; its report's `delete_body.solids` expands an insert's ID to its keys. The CLI's `--solid` repeats: one goes as `solid`, several as `solids`. The model, meshes, exports, mass and check leave deleted solids out.
- **Git and PDM.** Textconv `insert = pcb @ label B` and a placement line, a reference with `solid` as `<feature>/<solid>/<name>`; a merge takes an insert's `rev` and its `placement` as one value each and a delete's `solids` as one; renumbering an insert rewrites every key and reference it begins; `merge_broke` blames a reader of an inserted solid on the side that changed the source (validate's `places` holds inserts). `part.delete` of a part inserted at working is `has_dependents` (`inserted_by`). Releasing a part needs its inserts at official labels that aren't obsolete (`insert_not_released`). Where-used lists inserting parts as `{kind: insert, part, feature, rev}`, working and released (any part's release, not only assemblies'); `deps uses` lists foreign inserts under its own `inserts` key, beside the rows the service indexes by assembly; BOMs never count an insert. `check` doesn't check an inserted solid nothing acted on again: it is its source's.
- **Testing.** Unit tests per module; `tests/inserts.rs` (issue #41's workflow against an exact volume, pins followed and held, a source split followed, a flattened reference refused and converted, two and nested inserts, cycles, a failing source); `tests/deps.rs`' foreign insert, its where-used and `deps uses`; `tests/recompute.rs`' `inserts_and_deletes_recompute_as_from_nothing`; `inserts_and_deletes_from_the_cli` both ways; the `inserts` and `body_deletes` golden sections (`deletes` was already face deletes'); the `feature` fuzz target's `insert.json` and `delete-body.json` seeds (built in a project of `src` and `fz`) and the `merge` target's `0xe6` mode; `tests/insert_bar.rs` (`RYUCAD_PCBA`: 1,201 inserted reference bodies of the owner's ES-10092 board, a warm rebuild after a placement edit 1.159 s with nothing meshed again, on cox-worker-4's Opteron 6380 at load ~50 without `RYUCAD_BARS`; the 1 s bar wants a quiet box). The mesh cache evicts moved meshes before any the kernel made, so a board's sources outlive their moved copies at the default 256 MiB.
- **Left for 25.C.** Instance patterns driven by features and points. 25.B (inserts and deletes in the app, a flattened part's tree collapsed per file) is in `ryucad-app.md`'s "Inserts in the app".

## Meshes shared across placements (decided in ryucad phase 33, #813)

- **The definition.** A flattened import's body (an import with `place`) is meshed as an inserted solid is: as its file body, unplaced, moved by its place. `import::build` keeps that body and gives the placed `Built` a `moved` whose source is it, hashed by `import::shape_hash` (BLAKE3 of `Body::dump_unnamed`, the first 32 hex digits): copies of one component, whatever features name them, have one shape hash and one mesh. An unflattened import carries no `moved` (question 1074).
- **Healed once under a shape key.** ryukei's healer breaks ties by names (`heal/orient.rs`, `sew.rs`, `collapse.rs`, `seamed.rs`, `unseam.rs`, `build.rs`), and names follow the key, so copies healed under their own features' keys came out different (the block in `assembly.stp`: flipped face senses; 4 of 12 seeded copies). So a placed import heals its file body under `import::shape_key` (from the file's path, the product's ID, name and ordinal and the body, never the feature or the file's bytes), kept in a process cache of `HEALED_BODIES` (1,024) slots by file hash, body, mode, key and heal budget (a budget other than the default may refuse what the default heals; #955's review). Copies rebuilt side by side (a part's features rebuild in parallel) wait on their shape's slot rather than heal it again; a failed heal's slot is dropped, so a later request heals again and a waiter heals itself. The heal runs in a rayon pool of one thread of its own (`shape_heal`), started from a scoped thread and joined: every parallel task of the heal (`Meter::par_map` over face groups and sewn pieces) runs on that one thread, where the recording sees it, and nothing else runs there, on any machine or thread count; the join blocks the waiting worker without running other tasks (a worker waiting in `install` on another pool runs its own pool's tasks meanwhile, and one could be a copy waiting on this very slot: the deadlock the first version of the wait hit). What it gives up is parallelism inside one heal, once per shape. The owner chose healing per shape on 33.C (task 01M7N0FQE41MQMZ8K9G83SH99Y).
- **Names kept (stable names).** The heal runs under `ryukei::name::record::recording`, which notes every `Name::derive` and `OpKey::from_bytes` on the healing thread (thread-local, no lock; result-neutral), the heal's own pool thread. Should a name it left not be recorded (a pool that couldn't be made heals unrecorded), the shape isn't shared and each copy heals under its own feature's key, as before shape keys (`a_heal_not_all_recorded_is_not_shared`); `a_shape_heal_of_many_tasks_is_alike_on_any_thread_count` heals a reference of eight seamed pieces twenty times on eight threads, every name recorded, and rebuilds it flattened twice cold on 1 thread and 8 to the same hashes and one shared shape. Otherwise each name is then derived again under the feature's key (`Derivations::rekey`: a recorded name from its parents so derived, under its key so mapped; the shape key is the feature's, a key that is a name or was made from bytes holding the shape key's is made again; geometry hashes and ordinals stay), in the body (`Body::renamed`), journal (`Journal::renamed`), instance map and reference report. So a flattened body has the names ryucad 0.9 gave it: exactly today's body where both heals break their ties alike, and otherwise the same names on the same faces turned the same way, only ordered or sensed otherwise (ryukei's `names_derived_again_under_another_key_are_that_keys` on seamed and plain primitives; ryucad's `a_reference_into_a_flattened_body_from_before_shape_keys_still_resolves`, every face, edge and vertex of `assembly.stp`'s three bodies, faces measured by reference). Saved references into flattened bodies (fillets, holes, connectors, mates, dimensions) keep resolving.
- **The proof.** `tests/shared_meshes.rs` checks, on OCCT's `assembly.stp` (the block twice, the pin once; reference and solid) and a seeded board of 4 components placed 12 times, that copies' unplaced bodies are equal under `dump_unnamed` (whose lines carry each entity's index, so equal entity ids) and that one mesh's faces and edges are each copy's live ones. No copy is alone.
- **Meshing.** `mesh::Cache` resolves every body to its root (the end of its `moved` chain: an inserted flattened body moves from a flattened body, which moves from its file body), makes each root not held once (`Cache::made` counts roots), keeps it as the kernel's, and moves the rest (`moved_in`, kept as `derived`, evicted first). `Pending` makes roots only; moving happens when the request runs. The display chord comes from the root's diagonal, so a turned copy has an unturned one's chord. Exports (`export_all_for`) do the same at the export's parameters, which fixed the old split where display moved an insert's mesh and exports meshed the placed body; files stay flat (one mesh per placed body in STL, 3MF and USD, not instanced). A reference's `mass` reads the moved mesh (`mass::reference::normal_mesh`). Interference still meshes the placed body.
- **On disk.** A placed import's results entry ends with its solids' sources (the unplaced body, the shape hash, the pose) behind the marker `cache::results::SOURCES` (eight 0xff bytes, which no length is); `decode_made_for` joins them again with the feature, an older ryucad reads such an entry as a miss, and a placed import's entry without them (an older ryucad's) is a miss here, healed once. Other entries keep their bytes (question 1075).
- **What moved.** No name. The `flatten` golden line: its three body hashes (each body's entities in the order and senses the shape key's ties set; the same names, faces the same way) and the STL bytes (moved meshes); its part and feature files, counts and STEP bytes didn't, compared item by item against the base. `external_imports`: the box's hash and dump in its answer, for the same reason; the pins' are unchanged. Display meshes of flattened imports, re-keyed by shape on disk. A flattened reference's mass on `assembly.stp`: the block's copies 6.000000000000001e-6 and 5.999999999999997e-6 m³ before and after, bounds equal to the last bit or one ulp; the pin 9.418050609140581e-7 m³ ± 4.956443558149821e-9 before, 9.418050609140593e-7 ± 4.9564435581498224e-9 after: within the bounds.
