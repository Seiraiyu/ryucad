## Scripting: the connection (decided in ryucad phase 31)

The design is document 603 in the Coxswain planning project `ryucad-ryukei`; this is its phase 1, plan 31.A (#810).

- **`ryucad session --stdio`.** A script's one connection (`ryucad::stdio`). It reads one JSON-RPC 2.0 request a line on stdin (`{"jsonrpc":"2.0","id":…,"method":…,"params":…}`, `proto`'s methods and params, as `--json` help and these docs name them) and writes each answer on stdout, with the same `id`, in request order, one at a time (a script that wants two at once runs two sessions). Blank lines are skipped. EOF on stdin ends the session after the last answer, exit 0. It is the CLI's requests over a pipe, not an MCP server; when one arrives is still an open decision.
- **One process, one hello.** It connects to the project's daemon once (starting it, or replacing one of another build, as the CLI does) and says `session.hello` once as the agent `--as` / `RYUCAD_PARTICIPANT` (`agent` by default); every request after is that participant's, so its writes are logged as its activity entries and `undo` takes back its latest. A script's own `session.hello` line is forwarded and renames it (its cancels and reconnections then use the new name). A refused hello at the start is one refusal with a null id and the CLI's exit code.
- **Answers.** Raw JSON-RPC, written as the daemon writes them: a `result` keeps its own `warnings` (there is no envelope), a refusal is `error` with the stable code in `error.data.code`, and an answer that announces `binary: {encoding, length}` (`mesh.get` with `transfer`, `render`, `drawing.render`, an `export`, `drawing.export` or `release.package` without `out`) is followed by exactly that many bytes before the next line. Exit codes don't apply per request. Notifications come only after the script's own `subscribe`; `progress` lines only for a long request that asks with `progress: true`, before its answer. A line that isn't JSON is `invalid_json` with a null id, one that isn't a JSON-RPC 2.0 request or names an unknown method `usage`, bad params `invalid_document`, as the daemon answers them; the session goes on. Only stdin or stdout failing ends it. `--pretty` and `--progress` don't apply.
- **Paths.** Relative paths mean the script's folder, never the daemon's: before a line is sent, `client::absolute_params` makes absolute, against the folder the session runs as (`-C`'s, else the current one), the params `client::PATH_PARAMS` names by method (`import`'s `path` and `search`, `export`'s and `drawing.export`'s `out`, `release.package`'s `out` and `into`, `release.package.verify`'s `file`, `bom.where_used`'s `in`) and the worktree paths in any method's `rev`, `from`, `to`, `against`, `compare` and `frame` (`worktree:../arm`), a trailing separator kept. The CLI uses the same function (`client::absolute`) for every command, so the command arms no longer make paths absolute themselves, and with `-C` a relative `--out` now means `-C`'s folder, as `worktree:` revisions did (#447).
- **`-C` changes where output lands (a behaviour change, 31.A).** Before 31.A the command arms made a relative output or input path (`export --out`, `drawing export --out`, `release package --out`/`--into`, `release package verify`, `import` and its `--search`, `where-used --in`) absolute against the process's folder, whatever `-C` said. Since 31.A they mean `-C`'s folder, as `-C` promises ("Run as if started in this folder", #447): `ryucad -C sub export p --out p.stl` writes `sub/p.stl`, where it wrote `./p.stl`. Without `-C`, nothing changed. (The CLI's own `--out` for bytes it writes itself, `mesh` and `render`, is unchanged: still the process's folder.)
- **No daemon.** With `--no-daemon` / `RYUCAD_NO_DAEMON=1`, or when no daemon can be had at the start, one `Session` in the process answers every request through `server::handle_job_raw`, in the same framing, byte for byte: same answers and caches, no live participants (`session.hello`, `subscribe`, `undo` are `no_live_session`) and no activity log, as the CLI in process. What it built goes to the shared cache before it exits (`REMOTE_FLUSH`). A warning on stderr says it runs in process.
- **Reconnecting.** A daemon that closed the connection between requests (idle past `RYUCAD_IDLE_TIMEOUT`, `daemon stop`, replaced) is connected to again, with a new hello, before the next request is sent. When none can be had, or a request can't be written, that request and the rest of the run are answered in process, with a warning on stderr. A connection that closes after a request was sent answers it `daemon` ("the request may have been applied"), never retried.
- **Cancel.** A long request (`daemon::LONG`) is given a token unless the script gave it one (`stdio-<pid>-<n>`). The first Ctrl+C sends `request.cancel` for the running long request on a connection of its own (in process, sets its job's flag); another request finishes. Once that answer is out the session exits 130. With nothing running, or on the second Ctrl+C, it exits 130 at once. SIGTERM needs nothing of its own: a killed session drops its connection, and the daemon cancels a hung-up connection's request (#437).
- **No wire change in 31.A.** 31.A added no method; 31.B's `batch` moved `PROTOCOL_VERSION` to 3. `ryu_session::client` gained `Connection::hello`, `Connection::into_halves` and `hello_connection` (the CLI's `request` goes through it).
- **Testing.** Unit tests in `stdio` (lines, tokens, framing, `Frame::of`, `Stop`, the loop in process with progress and binary answers), `client` (`absolute_params`, `absolute`) and `ryu_session::daemon` (hello and halves). `tests/cli.rs`: `stdio_session` both ways (order, refusals, bytes, a long request's own token), `stdio_session_through_the_daemon` (relative `out`, hello renaming, undo), `stdio_session_outlives_its_daemon`, `stdio_session_ends_on_ctrl_c` (Unix), `stdio_session_outside_a_project`, and `relative_paths_mean_dash_cs_folder`.

## Scripting: batches (decided in ryucad phase 31)

Design 603's phase 2, plan 31.B (#810). Protocol 3.

- **`batch`.** `batch {ops: [{method, params}], expect?, dry_run?, rebuild?}` runs many model edits as one checked, logged, undoable change (`ryucad::batch`). The ops are `batch::BATCHABLE`: `annotation::PROPOSABLE`'s 25 model edits plus `part.create`, `part.delete` and `part.ensure` (31.C); anything else is `invalid_param` at `/ops/<i>/method` before anything runs. CLI: `ryucad batch <file | ->`, whose JSON is the same object or a bare array of ops; `--expect`, `--dry-run`, `--rebuild` and `--no-rebuild` override it. It is a long request (`daemon::LONG`): a token, Ctrl+C, a cancel between ops.
- **Running.** The ops run in order through `server::dispatch` in one capture session over the working files (`Session::capturing`), as `annotation.propose` runs one: each sees what the ones before it wrote, with the same checks a single request makes, and its own `expected_revision` is checked against those files. `expect` is the project's revision (`Session::project_revision`) before the batch: a hash of the project's own settings (the manifest, PDM, materials, the lock, project parameters), so a part's edit leaves it; each op's own `expected_revision` covers its part. The first refusal stops the batch with nothing written: its own code, with `op` and `method` in the details and a pointer into its params made `/ops/<i>/params…` (a pointer into a file, beside `path`, is left alone). A capture session never touches the folder: `part.delete` there leaves the part's folder alone (`Session::captures`), and `Project::reload_from` asks its source whether a part's folder is there (`Source::is_dir`: files in memory hold a folder while a file lies in it; on disk it is `Path::is_dir` as before), so a captured `part.create` has its part and a captured `part.delete` hasn't.
- **Writing.** The captured files that differ from the working files are written in one pass through `Session::write_bytes`/`remove_file`: content files, then parts' `part.json` lists, then root files, then deletions, the lists last (`batch::ordered`, undo's order reversed). Each file is atomic, so a crash leaves complete files: at worst feature files no list names yet, or a list naming the old set; `doctor` reports them and running the batch again finishes. No journal. A deleted part's folder then goes with any stray file in it, as `part.delete` alone removes it. Then `reload` and `deps::keep_lock`. A write that fails part way answers `io`, and what it wrote stays and is logged (`answer_live` logs a `batch` whatever it answers), so `undo` takes it back.
- **Log and undo.** One request, so one activity entry (`method: batch`, every file before and after) and one `undo`. A batch that writes nothing logs nothing.
- **Answer.** `{ops: [{method, result}], parts: {<part>: {status, revision}}, written, revision, dry_run?, rebuild?}`. Each op's result is what it would have answered alone, its warnings in it. `parts` holds each part an op names in `part` and each part whose files changed: `created`, `updated`, `unchanged` or `deleted`, judged from the bytes (an op writing the same bytes again leaves its part `unchanged`; a deleted part's revision is null). `written` counts the files written (or that would be, dry). `revision` is the project's after, for the next `expect`.
- **Dry run and rebuild.** `dry_run` runs every op and answers, writing nothing and rebuilding nothing. Otherwise (unless `rebuild: false`) each `created` or `updated` part, then each assembly placing it at working (`mate::reached`), is rebuilt once: `rebuild: {parts: [<part report>…], failed}`. A part that fails to build is reported, never a refusal.
- **Mates.** A batch solves each assembly once, at its end (31.C): its capture defers (`Session::defer_solves`), so `mate::current` notes the part, `mate::refuse_overconstrained` notes the assembly and `mate::failing_warnings` says nothing. Before the write pass, `batch::solve_deferred` solves every assembly the noted parts reach whose poses held in the working files (or that the batch made) and writes its poses in the capture (`mate::keep_current`); one the batch wrote instances or mates to, whose mates held and now can't, refuses the batch `assembly_overconstrained`; failing mates' warnings are the batch's `warnings`, the solves' reports its `assemblies` (an op's own answer has none). A one-op batch writes what the op alone writes; several ops solve once from the working poses. 31.B measured about 0.3 s an op on the 1,000-mate assembly without this; 31.C's measurement is in PR <n>.
- **Paths.** `client::absolute_params` makes each op's params absolute by the op's own method, so relative paths in a batch mean the caller's folder, through the CLI and `ryucad session --stdio` alike.
- **Testing.** Unit tests in `batch` (BATCHABLE, refusals, ops in order, every batchable request writing in a batch what it writes alone, many ops against one by one, the write order, statuses, dry run, expect, rebuild, one entry and one undo, a part-way write undone, cancel) and `server::tests::part_create_and_delete_run_captured`; `tests/cli.rs`: `batch_from_the_cli` (both ways, stdin, undo through the daemon) and `batch_through_a_stdio_session`.

## Scripting: ensure, prune and the bar (decided in ryucad phase 31)

Design 603's phases 3 and 4, plan 31.C (#810).

- **`part.ensure`.** `part.ensure {part, kind?, params?, features: [{id, type, …feature.add's params}], props?, expected_revision?}` (`server::ensure`) makes a part exactly as declared, writing only what differs. `features` is the whole ordered list (one left out is deleted); every feature names its `id` (`invalid_param` at `/features/<j>/id` otherwise: a made-up id would differ between runs and rename its faces and edges) and has no `after`, `first`, `part`, `expected_revision` or `dry_run`. A sketch carries `sketch.edit`'s `ops`, applied after its add. `params` is the whole parameters file (left out: left alone; `{}`: none, the file removed); `props` goes to `props.set`. `kind` left out keeps an existing part's kind and makes a new part a `part`; another kind than the part's is `invalid_param` at `/kind`. A part holding an `import` isn't ensured. `expected_revision` is checked against an existing part (`conflict` for one that doesn't exist). An assembly is a part whose features are instances, so this is #810's `assembly.ensure` too.
- **How.** In a capture session: the part made if missing; the parameters file written whole; when it didn't change, the longest prefix of the list that `feature.add` (and for a sketch its ops and solve, `server::ensure::predicted`) would write again byte for byte is kept (`kept`, through `server::feature::built`, `feature.add`'s build split from its checks); the rest is taken out of the list and folder unchecked and the declared rest added in order through `feature.add`, each checked against the declared features before it, so the end state is what is checked (a feature and its reader may go together); then the properties. A mated instance whose declared placement isn't its solved pose ends the kept prefix and is added again and solved; it is still `unchanged` when the bytes match.
- **Statuses.** The answer is `{part, kind, status, revision, features: {<id>: created | updated | unchanged | deleted}, params?, props?, warnings?}`, each judged from the bytes of its file before and after (a reorder: every feature `unchanged`, the part `updated`). Alone, `part.ensure` is a one-op `batch` (one write pass, one activity entry when it writes, one `undo`, the rebuild of what it changed), its answer the op's own with the batch's `status`, `revision`, `rebuild`, `assemblies` and `warnings`, its refusals its own (no `op`, pointers from `/features/…`). It is a long request (`daemon::LONG`). CLI: `ryucad part ensure <part> --from <file | ->` (a file naming another part is `usage`; `--expect`).
- **`prune`.** `batch {prune: true}` (`ryucad batch --prune`) deletes, after the ops, every part no `part.ensure` or `part.create` op named, through `part.delete` in the capture, a part no other part places or inserts at working first; when none left can go, the first one's `has_dependents` refuses the batch with `prune: true` and `pointer: /prune`. Off by default.
- **Paths.** `client::absolute_params` makes an ensure's features absolute as `feature.add`'s params (an instance's `rev: worktree:…`).
- **The bar.** `tests/script_bar.rs` drives `tests/common/scripted.rs`'s `Script::new(56, 209)` (56 leaves of plates less 14 holes, sketch extrusions and revolves; modules `m0`–`m3` and `top`: 209 instances; about 1,000 single requests) through one `ryucad session --stdio` from the release binary: from scratch ≤ 10 s with one activity entry, again ≤ 1 s with nothing written, one constant ≤ 2 s, #810's review round (one constant, 16 nuts and washers, a part gone with `prune`, two materials) ≤ 3 s, each case's statuses exact, its second run unchanged and the round undone. With `RYUCAD_BARS=1` as they are (Linux, 8 cores), else ten times looser. Measured in PR <n>: <the printed line>. The Windows number (#810's 60 s) is the release e2e's on Windows.
- **Guards.** Golden section `script` (`Script::new(8, 24)` built by one batch and request by request, the same bytes, its parts' files and rebuild hashes); fuzz target `batch` (`tests/batch_bytes/mod.rs`, also seeded in `tests/batch_props.rs`): up to eight ops from a menu as a batch and one by one, the same files or the same refusal at the same op with nothing written; `scripts/smoke.sh`'s stdio session (a batch of ensures, the same again with nothing written, undo).
- **Protocol.** 3, as 31.B left it (no release had shipped protocol 3 without `part.ensure`).
