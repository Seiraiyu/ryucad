## Scripting: the connection (decided in ryucad phase 31)

The design is document 603 in the Coxswain planning project `ryucad-ryukei`; this is its phase 1, plan 31.A (#810).

- **`ryucad session --stdio`.** A script's one connection (`ryucad::stdio`). It reads one JSON-RPC 2.0 request a line on stdin (`{"jsonrpc":"2.0","id":…,"method":…,"params":…}`, `proto`'s methods and params, as `--json` help and these docs name them) and writes each answer on stdout, with the same `id`, in request order, one at a time (a script that wants two at once runs two sessions). Blank lines are skipped. EOF on stdin ends the session after the last answer, exit 0. It is the CLI's requests over a pipe, not an MCP server; when one arrives is still an open decision.
- **One process, one hello.** It connects to the project's daemon once (starting it, or replacing one of another build, as the CLI does) and says `session.hello` once as the agent `--as` / `RYUCAD_PARTICIPANT` (`agent` by default); every request after is that participant's, so its writes are logged as its activity entries and `undo` takes back its latest. A script's own `session.hello` line is forwarded and renames it (its cancels and reconnections then use the new name). A refused hello at the start is one refusal with a null id and the CLI's exit code.
- **Answers.** Raw JSON-RPC, written as the daemon writes them: a `result` keeps its own `warnings` (there is no envelope), a refusal is `error` with the stable code in `error.data.code`, and an answer that announces `binary: {encoding, length}` (`mesh.get` with `transfer`, `render`, `drawing.render`, an `export`, `drawing.export` or `release.package` without `out`) is followed by exactly that many bytes before the next line. Exit codes don't apply per request. Notifications come only after the script's own `subscribe`; `progress` lines only for a long request that asks with `progress: true`, before its answer. A line that isn't JSON is `invalid_json` with a null id, one that isn't a JSON-RPC 2.0 request or names an unknown method `usage`, bad params `invalid_document`, as the daemon answers them; the session goes on. Only stdin or stdout failing ends it. `--pretty` and `--progress` don't apply.
- **Paths.** Relative paths mean the script's folder, never the daemon's: before a line is sent, `client::absolute_params` makes absolute, against the folder the session runs as (`-C`'s, else the current one), the params `client::PATH_PARAMS` names by method (`import`'s `path` and `search`, `export`'s and `drawing.export`'s `out`, `release.package`'s `out` and `into`, `release.package.verify`'s `file`, `bom.where_used`'s `in`) and the worktree paths in any method's `rev`, `from`, `to`, `against`, `compare` and `frame` (`worktree:../arm`), a trailing separator kept. The CLI uses the same function (`client::absolute`) for every command, so the command arms no longer make paths absolute themselves, and with `-C` a relative `--out` now means `-C`'s folder, as `worktree:` revisions did (#447).
- **`-C` changes where output lands (a behaviour change, 31.A).** Before 31.A the command arms made a relative output or input path (`export --out`, `drawing export --out`, `release package --out`/`--into`, `release package verify`, `import` and its `--search`, `where-used --in`) absolute against the process's folder, whatever `-C` said. Since 31.A they mean `-C`'s folder, as `-C` promises ("Run as if started in this folder", #447): `ryucad -C sub export p --out p.stl` writes `sub/p.stl`, where it wrote `./p.stl`. Without `-C`, nothing changed. (The CLI's own `--out` for bytes it writes itself, `mesh` and `render`, is unchanged: still the process's folder.)
- **No daemon.** With `--no-daemon` / `RYUCAD_NO_DAEMON=1`, or when no daemon can be had at the start, one `Session` in the process answers every request through `server::handle_job_raw`, in the same framing, byte for byte: same answers and caches, no live participants (`session.hello`, `subscribe`, `undo` are `no_live_session`) and no activity log, as the CLI in process. What it built goes to the shared cache before it exits (`REMOTE_FLUSH`). A warning on stderr says it runs in process.
- **Reconnecting.** A daemon that closed the connection between requests (idle past `RYUCAD_IDLE_TIMEOUT`, `daemon stop`, replaced) is connected to again, with a new hello, before the next request is sent. When none can be had, or a request can't be written, that request and the rest of the run are answered in process, with a warning on stderr. A connection that closes after a request was sent answers it `daemon` ("the request may have been applied"), never retried.
- **Cancel.** A long request (`daemon::LONG`) is given a token unless the script gave it one (`stdio-<pid>-<n>`). The first Ctrl+C sends `request.cancel` for the running long request on a connection of its own (in process, sets its job's flag); another request finishes. Once that answer is out the session exits 130. With nothing running, or on the second Ctrl+C, it exits 130 at once. SIGTERM needs nothing of its own: a killed session drops its connection, and the daemon cancels a hung-up connection's request (#437).
- **No wire change.** 31.A added no method; `PROTOCOL_VERSION` stays 2. `ryu_session::client` gained `Connection::hello`, `Connection::into_halves` and `hello_connection` (the CLI's `request` goes through it).
- **Testing.** Unit tests in `stdio` (lines, tokens, framing, `Frame::of`, `Stop`, the loop in process with progress and binary answers), `client` (`absolute_params`, `absolute`) and `ryu_session::daemon` (hello and halves). `tests/cli.rs`: `stdio_session` both ways (order, refusals, bytes, a long request's own token), `stdio_session_through_the_daemon` (relative `out`, hello renaming, undo), `stdio_session_outlives_its_daemon`, `stdio_session_ends_on_ctrl_c` (Unix), `stdio_session_outside_a_project`, and `relative_paths_mean_dash_cs_folder`.
