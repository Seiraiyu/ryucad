## The daemon at scale (decided in ryucad phase 7)

The design is document 192 in the Coxswain planning project `ryucad-ryukei`; this is its plan 7.A.

- **The benchmark project.** `ryucad::bench::scale` (the `bench` feature, which brings in `ryukei-testkit`; never in a release build) writes a project from a seed: `Spec::full()` is 200 subassemblies of 50 distinct parts and 500 occurrences each (a fixed base plate, 13 more plates, 10 brackets fastened to it, 10 shafts on revolutes, pins on sliders repeated along x by instance patterns, and 2 or 3 parts importing `ryukei_testkit::race` bodies from one STEP file), 20 modules of 10 and a root: 10,000 parts, 221 assemblies, 100,000 occurrences, about 97,000 features in 107,500 files. Fillets and chamfers name their edges by building each part's first features in memory. Files are written plainly (not synced), in about 8 s; the race file takes about a minute to make and is kept beside the project (`race-<n>.step`). `Spec { races: false, .. }` leaves the imports out (debug builds). Its golden is `tests/golden/scale.txt`, a hash of two subassemblies' files. `cargo run --release -p ryucad --features bench --example ryucad-bench-gen -- <folder> [--parts N]` writes one.
- **Measuring.** `tests/scale_bar.rs` (ignored, its own command: `cargo test -p ryucad --features bench --release --test scale_bar -- --ignored --nocapture`, `RYUCAD_SCALE_PARTS` for a smaller one) generates the project and measures it through a daemon with `session.max_memory` at 4 GiB: a cold rebuild of the root, a daemon over the warm cache (twice), a request that builds nothing, subscribing, one feature edited until a subscriber hears and the request after, the window's open (the root's report and every body's mesh), interference from nothing and after one move, and the daemon's peak memory and session state. It asserts no bars: plan 7.D records them. The app's `tests/first_frame.rs` (ignored; `cargo test -p ryucad-app --release --test first_frame -- --ignored --nocapture`) measures the drawing bars over the same project: a window over an empty cache warms it, a second over the warm cache is timed to its first full frame (the root's report, every body's coarse mesh, the picker, levels, every body uploaded, drawn and read back), then 240 frames orbit and close in; `RYUCAD_BARS=1` asserts 20 s, 60 fps and no frame over 50 ms on a hardware adapter. Without an adapter it stops before drawing, timing a frame's CPU work.
- **The disk cache.** Entries are written to a temporary file and renamed, not synced: syncing each made a cold rebuild of the benchmark I/O bound (about 9 minutes against 1). An entry a crash leaves short fails its hash and is a miss. Everything a daemon writes through `write_atomic` (its project's files, and its exports' `--out` files and `preferences.json` too) is renamed into place and synced behind on a thread of its own (`ryu_doc::source::defer_syncs`): a killed daemon loses only writes not yet synced, never tearing a file; `daemon status` gives `unsynced`, and `stop` waits for them (#235). A power cut can also leave a new file not yet synced empty, and under writeback pressure the unsynced window can last seconds. Writes in process sync first, as before.
- **File events.** A daemon's session watches its folder (`ryu_session::fresh::Watch`, over the `notify` crate: inotify, FSEvents, ReadDirectoryChangesW), keeping events under the root files, `parts/`, `releases/` and `imports/`, ignoring reads. Before a request takes the paths events named, the watch writes a marker file in a folder of its own beside the daemon's log (`<hash>.watch`), watched by the same watcher, and waits for its event: events arrive in order, so every change made before the request has been reported (two rounds on Windows, where each folder has its own queue). Only the named paths are checked (`Stamps::scan_under`: a file, or a folder's files, and stamps under them that are gone); everything is checked at the start, on overflow, failure, late events (2 s) or the project folder itself changing, and every `daemon.rescan_s` (60). What a full check finds that events missed is counted (`missed`) and logged once. A folder that can't be watched, or `RYUCAD_NO_WATCH`, checks every file on every request (`watch_unavailable` in `daemon status` and the log). `daemon status` gives the session's `watch` and `budget` (`Serve::status`, read without waiting on a request). Reasons for a full check don't stack: the first pending one stands until taken (FSEvents may report the project folder made just before the watch started, #198). A session also checks every path its own process wrote or removed (`ryu_doc::source::note_written`, taken by the watch with `take_written`), whatever events said, since FSEvents can hand over a marker's event before a write's (#263).
- **What a request that changes nothing does.** The session counts the times its files change (`Session::epoch`); `publish` works out release states and parts' keys only when that or the release branch's refs moved, and every assembly's key in one rebuild (`Session::assembly_keys`). A subscription's own settling tells nothing: an assembly noted while nobody watched, whose files haven't changed, isn't news. `model.changed` gives an assembly's report without its `occurrences` (`occurrence_count` instead): a window asks for those of the assembly it shows (`rebuild`). The session keeps the project's cycles of assemblies by epoch and pins (`Rebuild::with_cycles`; about 20 ms to find at 10,000 parts), and each leaf part's and assembly's model by the key it was built from (`Store::models`), so a root of 100,000 occurrences isn't gathered again per request.
- **The memory budget.** `session.max_memory` (bytes; a quarter of the machine's memory, from 512 MiB to 8 GiB, by default) bounds what a daemon holds of leaf parts' rebuilds and display meshes between requests (`ryucad::budget`). A part's rebuild is counted by its results' disk entries' sizes (`Made::encoded`, else the codec's lengths) times `budget::RESIDENT` (3, measured). Past it, whole parts' rebuilds go (results and caches), least recently used first, in a rebuild once an assembly's children are placed and after each request; a part's model (the solids it shows) is kept, and counted. A part asked for comes back from the disk cache, the same bits. Parts a request asks for are pinned until it answers; a revision's session lets go of its parts first. What must be held past the budget is `memory_budget_too_small` (in `daemon status` and the log, once). Learnt names and origins share their values (`rebuild::Origins`, `session::Known`): as JSON objects each took about 1.6 KB, and the benchmark has about 7.7 million. Since v0.8.1 (#236, #400) the budget also counts what the session holds besides (`budget::Fixed`, `fixed` in `daemon status`): its files and the project read from them, the imported STEP files kept open, assemblies' occurrences, learnt names and verdicts, by sizes measured over the benchmark (about 0.6 GiB there); and ryucad turns off transparent huge pages on Linux (`PR_SET_THP_DISABLE`), inside which mimalloc's freed memory stayed resident. The peak still passes the budget by the requests' own working memory (the root's report about 0.5 GiB while it is built) and the allocator's overhead over live data (RSS about 1.2 to 1.35 times it), which no count of held data bounds: at 10,000 parts and 4 GiB, 4,670 MiB (main 4,995) on cox-worker-2. So design 192's bar on the daemon's peak at 10,000 parts is `session.max_memory` × 1.15 (4,710 MiB at 4 GiB; the owner's choice, v0.8.2, closing #236), and with the window open that plus a render's quarter of the budget and 256 MiB, #400's bound as before (5,990 MiB): `tests/scale_bar.rs`'s `PEAK_OVER`. On cox-worker-3 (Intel Core Ultra 5 250K Plus, 18 threads, in a `MemoryMax=10G` scope, load under 3.5) with `RYUCAD_BARS=1`: peak 4,686 MiB, the window's open 4,855 to 4,866 MiB.
- **Paged trees and summaries.** `assembly.tree` takes `path` (instance IDs: start at that subassembly) and `depth` (levels listed; a subassembly below says `more`); CLI `ryucad assembly tree <asm> [--path P] [--depth N]`. `part.list` gives each part built at its revision `hash` and `failed` (kept when its rebuild goes, `Store::summaries`), and `model`: the parts a window shows when it isn't told.
- **The window.** A project of at most 200 parts (`LOAD_WHOLE`) loads whole as before; a larger one lists every part from `part.list` (`Model::listed`) and loads the report of what it shows (its focus, else `model`) and of each part whose row opens (`Workspace::load_part`; a subassembly under an instance too). Notifications update the list and reload only what is loaded or shown. Meshes are indexed by body hash and parts' solids by ID, so 100,000 occurrences cost no quadratic scans. `display.gpu_memory` (2 GiB) bounds what the window draws (`lod::within`): past it, the farthest bodies drawn finer than the display quality are drawn at it, then the farthest go undrawn, and no finer level is asked for.
- **Meshes by the batch.** `mesh.get` takes `features` (several of an assembly's occurrences, meshed side by side outside the daemon's lock and answered together; CLI `ryucad mesh <asm> --occurrence PATH`, repeated); the window asks for an assembly's bodies 256 to a request (`MESH_BATCH`). Each body is copied once, and only those the mesh cache lacks.
- **The compact encoding.** `mesh.get` with `transfer: compact` (CLI `ryucad mesh --out FILE --compact`) answers `ryucad.mesh.2`: `ryucad.mesh.1`'s layout (version 2) with indices in two bytes where what they index numbers at most 65,536 and corner normals octahedral in two `i16`s (within 1e-4 rad), about half the bytes; `mesh::decode` reads both. The window asks for it; `binary` stays `ryucad.mesh.1`, which the hosted viewer decodes (its schema can't change under it).
- **Coarse first.** A view drawing more than `lod::COARSE_FIRST` (2,000) occurrences of solids fetches each body's first mesh coarse (`Model::fetch_level`), and levels of detail fetch finer ones where they show, as before; design 72's 1,001 occurrences stay under it. A mesh's level is read from its angle (`lod::level_of`); picking and painting read the user's display quality once the window has it. On the GPU a body is a vertex per corner and its triangles as `u32` indices (`lod::gpu_bytes` counts them so): non-indexed, the benchmark's coarse meshes alone took about 2.4 GB against the 2 GiB budget.
- **A frame at 100,000 occurrences.** Parts index occurrences by path (`Part::by_path`) and the picker its bodies by key; it boxes each distinct mesh once and finds an entity in its body's own mesh (`Picker::slot`), never naming every entity of every occurrence. `lod::choose` walks the picker's bodies (`Picker::seen`: each occurrence's meshes, pose and box), in parallel, culled through its box tree, a node wholly in view (`nav::Sight::In`, from a `nav::Cull` worked out once a frame) taken without judging its bodies; `lod::within` returns at once when all the window holds fits (`Model::held_bytes`). A level other than the display quality doesn't bump the model's generation, so it makes no new picker. The scene draws one run per mesh and keeps its instance buffer while nothing drawn moves.
- **Interference at scale.** `Occurrence::within` keeps an occurrence's pose in each assembly along its path, and `interference` relates two occurrences through the deepest assembly both are in (`relative`), so a pair is to the bit what it is in its subassembly wherever that is placed, and its verdict is the cached one. Pairs come from a grid of cells about twice the median box (boxes over four cells met by brute force), each body's box worked out once.
- **Imported files and rayon.** `import::opened` never waits for another thread's opening (two that ask at once both open the file; the first kept): `ryustep::open` works on rayon, and a worker waiting in it could run another import part's rebuild that waited on the same file. `Rebuild::build_parts` opens its parts' files first, on its own thread (`open_ahead`).
- **Measured.** On cox-worker-2 (8 cores, AMD Ryzen 7 9700X; other sessions sharing it; `RAYON_NUM_THREADS=4`), over three runs of the benchmark after this plan: a cold rebuild of the root 59 to 113 s (before: about 9 minutes, syncing cache entries); a daemon over the warm cache 9.0 to 18.2 s; a request that builds nothing, through the CLI, 51 to 68 ms (before: 1 to 2 s); subscribing 0.6 s (18.8 s); one feature edited 0.6 to 1.3 s, heard at once, the request after it 49 to 129 ms; the window's open, before coarse first and the compact encoding: every body's normal mesh made in 120 to 209 s, or from the disk cache by a new daemon in 184 to 282 s (7.8 GB); after them, every body's coarse mesh made in 23.4 s, or from the cache in 14.7 s (355 MB), and `tests/first_frame.rs` without an adapter: the root's report over the warm cache in 9.3 to 20.7 s, every mesh 3.5 s after it, the picker 0.12 s, a frame's levels 6 ms (before Task 20 of the plan: the picker 6.5 s, a frame 24 s); interference from nothing 295 to 336 s for 93,707 pairs, after one move 0.5 to 0.9 s; the daemon's peak memory 4.7 to 4.8 GB with `session.max_memory` at 4 GiB (before: 11.9 GB). At 1,000 and 3,000 parts the same requests take 5 and 14 ms, the meshes from the cache 1.8 and 4.3 s, and interference 1.6 and 14.5 s.
- **Left for 7.D.** Interference's cost per pair grows with the project (0.17 ms at 1,000 parts, 0.5 at 3,000, 3 at 10,000), which neither the grid nor exact relative poses explained. A request that builds nothing is over design 192's 20 ms. The first full frame over a warm cache is mostly the new daemon's rebuild of the root, which varied from 9 to 21 s on a shared machine. The drawing bars are unmeasured: `tests/first_frame.rs` hasn't run on a hardware adapter, so the upload and draw of the first full frame and the frame rate are unknown (cox-worker-2 has no GPU; issue #192 runs it on cox-worker-3's).
- **Testing.** `ryu_session::fresh` tests (a write then at once the question, 200 times; renames; a folder replaced; a folder that can't be watched; narrowed scans), session tests (watched and forced to scan), the budget's unit tests and `a_budget_lets_parts_rebuilds_go_and_they_come_back_the_same`, `tests/recompute.rs` with a session whose budget holds nothing beside the incremental one, subscription tests, `assembly.tree` paging, `part.list` summaries, `mesh.get` with `features`, interference's grid against a brute force and a subassembly placed far out, the generator's golden, the app's `lod` tests (the budget, coarse first, the box tree's culling against every box judged) and `tests/lazy.rs` (release only, its own CI step: 1,000 parts and 10,000 occurrences meshed, coarse, only the root loaded); `mesh` tests of the compact encoding (the same mesh in about half, wide indices, octahedral normals) and the `mesh_wire` fuzz target reading both encodings.

## The shared cache (decided in ryucad phase 7)

The design is document 192 in the Coxswain planning project `ryucad-ryukei`; this is its plan 7.B.

- **The server is ryupdm-service's.** The owner decided on 2026-10-29 that the shared cache server is paid: ryucad holds the protocol, the client and a fake server for its tests (`crates/ryucad/tests/fake_cache`), and `ryucad cache serve` lives in the private `Seiraiyu/ryupdm-service` (ryupdm phase 6, design 21), which must answer as the fake does.
- **Identity.** `cache::build_identity`: a release (`cache::is_release`: a stamped version not starting `0.0.0`, built with `RYUCAD_COMMIT` given, which `build.rs` records as `RYUCAD_COMMIT_GIVEN`) is keyed by `cache::released_identity` (BLAKE3 of `ryucad.identity.1` and the ryucad, ryukei and `ryustep::VERSION` versions and the commit), the same on every platform, and is `shared`; any other build keeps its executable-keyed identity, never shared. `RYUCAD_CACHE_IDENTITY` (64 hex) claims a shared identity, for tests of development builds. The golden `cache` section of `tests/golden/rebuild.txt` pins a release's identity, a key of each kind, and the bytes of every entry a rebuild and its meshes write (sorted by their bytes: a feature's key holds the stamped versions, its payload doesn't), on every CI platform: what makes one platform's entries another's.
- **Entries.** Format 2 (`ryucad.cache.2\n`): the header, the 32-byte identity that wrote it, the payload's BLAKE3, its length, the payload (`cache::entry`, `cache::check`, `HEADER_LEN`). An earlier build's (`ryucad.cache.1\n`) is a miss, removed without a note. `Disk::get_entry` and `put_entry` move whole entries by key; `Disk::keys_of(kind, identity)` reads headers, so a push sends only this build's.
- **The protocol.** `ryucad.cache.1` over HTTP/1.1 (`cache::wire`): `GET /v1/info`, `GET` and `PUT /v1/<kind>/<key>`, `POST /v1/has` (up to 10,000 names `<kind>/<key>`, answered with those held) and `POST /v1/get` (up to 256, answered as 8-byte little-endian lengths and bytes, `u64::MAX` for one not held); Bearer tokens, 401 for none or an unknown one, 403 for a read token writing, 400 for a bad key or an unsound entry, 413 past 256 MiB.
- **The remote tier.** `cache::remote::Remote` (ureq, the review client's rustls): reads are checked (header, this build's identity, hash) before the disk cache stores them; a local miss asks it (`Disk::get`); `Disk::prefetch` asks a batch (`has`, then `get`) for a depth of a part's rebuild (`rebuild_part_in`) and for a request's meshes (display and export), and keys a prefetch found absent aren't asked for again one by one before they are built. What this machine writes is queued (`send_later`, at most `MAX_QUEUED`, 64 MiB, the oldest dropped with one note) for a writer thread; a request run in process (`--no-daemon`) waits up to 30 s for its queue before it exits, and not at all once the remote is skipped. A remote that doesn't answer within `cache.remote_timeout_ms` or answers 5xx is skipped for 2 s doubling to 5 minutes, a refused token (401) for 5 minutes, each with one warning on stderr (the daemon's log); a 403 on a write stops writing and goes on reading; an entry that fails its checks, or doesn't decode (`Disk::discard` of one the remote gave), is counted `bad` and never used. A remote never fails a request.
- **Settings and the token.** `cache.remote` (a URL as `review.url` takes, `""` for none), `cache.remote_write` (true) and `cache.remote_timeout_ms` (2,000). The token is `RYUCAD_CACHE_TOKEN`, else the file `cache-token` beside `preferences.json`, owner-only (`cache::token`); the preferences never hold it. A daemon's cache takes a new remote when a `cache.remote*` setting is set or the token stored. A development build never uses a remote, and `cache.stats` says why.
- **Commands.** `cache.stats` gains `shared` and `remote` (`url`, `token`, `reachable`, `write`, `hits`, `misses`, `bytes_in`, `bytes_out`, `puts`, `bad`, `problem`, `queued`, `queued_bytes`, `dropped`; or `enabled: false` with `url` and `note`). `cache.login` (`ryucad cache login [--token T]`, stdin without it) stores the token and asks the server (`GET /v1/info`) what it allows (`server: {write, entries}` or `{error}`; `overridden_by` when the variable is set); `cache.logout` removes it (`removed: true`, so the app says a token `RYUCAD_CACHE_TOKEN` gives is still sent). `ryucad cache push [--kind K]` (CLI only, no project) sends this release's entries the remote lacks, in parallel, and fails on the remote's errors (`invalid_param` for no remote or a development build, `cache_remote_refused` exit 1, `cache_remote_unreachable` exit 4). `cache.warm` (`ryucad cache warm [<part>]`) rebuilds a part (an assembly with what it places) or every part through both tiers and answers `built`, `fetched` and `fetched_bytes`; it builds what the remote lacks (a feature's key needs the results it reads, so nothing can be fetched before what it reads is). New codes: `cache_remote_unreachable`, `cache_remote_refused`, `cache_entry_bad`.
- **The app.** Preferences gain a Shared cache section: the server (`cache.remote`), Send what I build (`cache.remote_write`), a Token field with Save token and Forget token (`cache.login`, `cache.logout`), and the remote's state (`ui::dialogs::shared_text`, `token_text`).
- **Testing.** Unit tests per module against the fake (`cache::remote`'s reads, refusals, backoff, timeouts, batches and the queue; `cache`'s read-through, prefetch and bad entries; `cache::token`; `cache::wire`); `tests/cache.rs` (an empty cache filled a depth at a time; the CLI's stats, settings, login, push and warm; a second machine building nothing the first shared, through daemons and in process); the app's `tests/settings.rs` and a window test; `scripts/smoke.sh` checks `cache stats` says `shared: true` for a tag's release build on every platform (`RYUCAD_SMOKE_RELEASE`, set by release.yml) and that `cache push` is refused with none set.
- **Limits.** No server is in this repo: the release e2e reading one server all three platforms fill, and the design's bars over a remote (a cold daemon over a warm remote), wait for the ryupdm-service stage that hosts it. HTTP/2 isn't spoken (ureq is HTTP/1.1). A daemon that exits before its queue drains loses what was queued (`cache push` sends it later). Development builds never share, so CI's caches help only release builds.

## Agents on branches (decided in ryucad phase 7)

The design is document 192 in the Coxswain planning project `ryucad-ryukei`; this is its plan 7.C.

- **Worktrees.** Each agent works in a worktree of its own (`git worktree`), a project folder with its own daemon; every daemon shares the machine's disk cache, whose keys don't depend on the folder. Git's worktree list is the registry (`git::Repo::worktrees`: the main worktree first, then Git's, those whose folder is gone or whose checkout holds no project at the same place left out). `ryucad worktree add <path> [-b BRANCH] [--from REV] [--no-warm]` (CLI only, as `git install` is) runs `git worktree add` (a branch only with `-b`, else the revision detached), the one place ryucad runs a Git command that writes the repository; it says when the repository lacks ryucad's drivers or hooks (`git_drivers_missing`, repaired by `ryucad git install`, which every worktree shares), records the global `--as` name in the worktree's private Git folder (`ryucad-as`, which Git removes with it), and rebuilds the new folder in process (`cache.warm`), which builds nothing a worktree already built. `ryucad worktree remove <path> [--force]` stops its daemon and runs `git worktree remove`; project changes from its head (or Git's refusal) are `worktree_dirty`, and the main worktree and the current one can't go.
- **`worktree.list`.** Each worktree holding the project (`ryucad worktree list`): its project folder and work tree, branch, head, `main`, `current`, `locked`, commits `ahead` and `behind` this worktree's head, the project files its working files change from its own head (`changes`, `dirty`; kept by head and digest), a digest of them (`state`, 16 hex), the recorded `as`, and `daemon`: `null` unless one is running (none is started), else its pid, version, participants and `last_activity` from `daemon.status`, which now gives both (`busy` instead while a request holds the lock, so two daemons listing each other never wait on each other); this daemon answers for its own worktree from its live session.
- **Another worktree as a revision.** `worktree:<path>` (absolute: its work tree or the project folder in it; the CLI makes `rev`, `from`, `to`, `against`, `compare` and `frame` values absolute against where it runs) is a revision everywhere a request takes one: `Session::at` answers from a frozen session over that worktree's working files, read directly (never through its daemon) through stamps of their own, checked as the session's own files are, one session per worktree kept with the revisions and made again when its files change. This worktree's own is the working files; any other path is `worktree_not_found`. `diff` names it `{rev, worktree, branch, head}`.
- **Compare with a worktree.** `ryucad compare --worktree PATH` is `compare.set` with `worktree:<path>`, stored by the worktree's project folder (`compare.get` gives no commit). While anyone is subscribed, the daemon checks each worktree a participant compares with and sends that participant `compare.changed` (`{participant, rev, state}`) when its files move; the window reads the diff again.
- **`merge.preview`.** `ryucad merge preview <REV|--worktree PATH>` merges a revision, or another worktree's working files, into this worktree's working files in memory and reports what `merge.status` would after the merge (`schema: 1`; `ours`, `theirs` and `base` with their commits, `clean`, `conflicts`, `already_failing`, `unmerged`, `warnings`), writing nothing. The base is the merge base of the two heads; each file merges as Git with the drivers would (`merge::files_merged`: one side's change taken, the driver where `.gitattributes` sends a file there (`merge::driven`), lines for the rest, an imported file ours and unmerged, a delete against a change keeping the change), and the merge rebuilds in a session over the merged files (`Session::over`). Merge status's findings work over the files they judge (`validate::findings`; repair IDs hash those files, `doctor::basis_of`, not the disk), so the preview's conflicts, repairs and IDs are a real merge's: `tests/merge.rs` previews before thirteen of its merges and checks `merge status` after a `git merge --no-commit` finds the same. Git's rename following isn't previewed, and a clone without `merge.renames=false` or the merge driver gets a warning. A session keeps the last four previews by what they were made from.
- **The Branches tab.** Beside Releases (`core::branches`, `ui::panels::branches`): every other worktree's branch, who is attached (else the recorded name, `(expected)`), ahead, behind and uncommitted, its last change, and its merge preview, read every five seconds while shown and after this project changes, previews made again when either side's head or state moves, one at a time. Open (`client::open_app`: a new window of this app, or the windows already on it), Compare (with `worktree:<path>`) and Show preview (its conflicts as the conflict panel lists them, read only).
- **Testing.** `git.rs` (worktrees, ahead and behind, a worktree named by either folder), `session.rs` (another worktree read as a revision and followed), ryu-session's `daemon.rs` (participants and the last activity in the status), `doctor.rs` (`basis_of`), `merge.rs` (files merged as Git and the driver would), `tests/worktrees.rs` (add, list with and without daemons, remove, a dirty one, drivers missing, compare and diff against a worktree with `compare.changed`, a preview with uncommitted work on both sides, eight daemons rebuilding one project over one cache), `tests/merge.rs`'s previews, the app's `core::branches` unit tests, `tests/branches.rs` against real daemons, and a window test of the tab.
- **Limits.** A worktree compared with, or listed, is checked by its files' sizes and times on every look (every `daemon.poll_ms` while a compare is on): at the benchmark's 107,500 files that is a full stat of the other folder each time. `worktree.list` reads every other worktree's changes from its head once per head and state. A preview of a worktree whose branch has no commits is refused.

## Corpus and bars (decided in ryucad phase 7)

The design is document 192 in the Coxswain planning project `ryucad-ryukei`; this is its plan 7.D.

- **The corpus.** `crates/ryucad/tests/corpus/`: three projects made through the CLI by scripts beside them (`radial_engine.py`, `gearbox.py`, `printer_frame.py`, over `model.py`, standard library only), committed as they make them: a nine-cylinder radial engine (14 parts, 592 primitive features), a two-stage gearbox (sketches, fillets, holes, patterned tooth gaps, revolutes and fastened gears) and a printer frame (parameters, sweeps, brackets and instance patterns of bolts, 52 occurrences). The scripts run `ryucad` in process with private runtime, config and cache folders, in a temporary folder outside every Git repository (`ryucad init` inside one installs drivers and hooks there), and copy the project out. `manifest.json` holds what each part builds (features, which fail with which code and how many only through another, each solid's hash, counts and shown feature, each assembly's occurrences and solve) and `check`'s findings by code.
- **Pinned assemblies.** `tests/corpus/pinned.txt`: VoronDesign's Voron 2.4r2, Voron 0.2r1 and Switchwire STEP assemblies (GPL-3.0, fetched, never committed), by commit and SHA-256, fetched with ryustep's pinned files by `scripts/fetch-corpus.sh` into `target/corpus/voron/`. `builds <n> <file>` is how many parts must build, raised when a change builds more; `slow` lines (an import over half an hour on cox-worker-3) run by name only (`RYUCAD_PINNED` keeps the files whose path holds it); `roundtrip <part> #<issue> <file>` names a part that builds but doesn't come back through STEP, for that open issue. Since ryukei 15.F all three are `builds` lines (the Switchwire 324 parts, the Voron 0.2 381, the Voron 2.4r2 1,291, each importing in under half an hour; no file is `slow`), so full.yml's devcontainer job's pinned step (`cargo test -p ryucad --release --test corpus pinned`) imports and round-trips every one of them. ## The edit at scale (decided in release 8)

The design is document 312 in the Coxswain planning project `ryucad-ryukei`; this is its plan 8.A (issue #235).

- **Where the time went.** After v0.7.1 took the wait on synced writes off an edit's answer, a 10,000-part edit was CPU work finding again, on every call, what the session already knew (about 390 ms of the daemon's, on a loaded davids-m4):
  - a copy of the whole project, made before finding nothing to lock;
  - every feature scanned for labels and placements;
  - the root's 100,000 occurrences gathered only to be counted;
  - every assembly's children walked to check a cached result;
  - the cycles found again;
  - every part's release state derived again.

  On ext4, the disk cache's unsynced entries were a second cause.
- **What is kept.** Each is kept or skipped while nothing it reads has moved:
  - `deps::keep_lock` looks for an instance at another project's label before copying anything.
  - `Session::pins` reads whether any instance names a label once per epoch.
  - `Rebuild::result` takes a part found current at the session's epoch and its pins' key (`Store::verified`) without walking what it places. `Rebuild::stamp` is `None` for a proposed edit and for `check`.
  - The cycles are found again only when the instances' edges change.
  - `mate::reached` finds who places whom in one pass.
  - A report counts an assembly's occurrences (`Model::count_of_assembly`) and gathers them only when it gives them.
  - `Session::list` steps past each folder.
  - `pdm.changed`'s release states are kept by part revision while the refs, the manifest, the project's parameters, ryupdm's settings and the records stand (`release::States`).

  No answer changed: no golden hash moved, and `tests/recompute.rs` still finds incremental equal to a rebuild from nothing.
- **The cache's writeback.** On ext4 (data=ordered) a journal commit, which the deferred syncs of an edit's files start, first writes every dirty page of the files in it. After a cold rebuild, 350 to 450 MB of the disk cache's entries were still dirty when the edits ran, and an edit's creates and renames waited 0.4 to 0.9 s behind them.
  - The fix: on Linux, `cache::write_entry` queues each new entry's path for a thread (`ryucad-writeback`). Once the cache's writes have been quiet for 250 ms, that thread hints them oldest first with `sync_file_range(SYNC_FILE_RANGE_WRITE)`. This starts their writeback without waiting for it; nothing is synced. At most 131,072 paths wait.
  - Variants measured on cox-worker-3 and dropped:
    - The hint on the writer's thread doubled a cold rebuild, because `sync_file_range` waits when the disk's queue is full.
    - On its own thread but during the rebuild, the hint made a cold rebuild 45% longer.
    - Draining on eight threads left more dirty at the edits, not less.
  - Other platforms are unchanged.
- **The bar.** `tests/scale_bar.rs` holds the first edit after a warm daemon's rebuild (with a new subscriber) to design 192's 300 ms, beside the median of three. Measured with `RYUCAD_BARS=1` at 10,000 parts:
  - **cox-worker-3** (Intel Core Ultra 5 250K Plus, 18 threads, ext4, quiet). Three runs at d9299adb gave first edits of 119, 287 and 149 ms, medians of 119, 287 and 149 ms, and cold rebuilds of 87.4, 83.2 and 83.5 s (80.6 to 83.1 s without the writeback hint).
  - **davids-m4** (Apple M4, 10 cores, macOS 26.6.2, loaded). Three runs at 5f14eed4 gave first edits of 174, 174 and 155 ms and medians of 124, 123 and 123 ms. One run at 97ca951c gave 172 and 133 ms.
- **Left.**
  - The second of `scale_bar`'s edits after a cold rebuild still stalls 0.46 to 1.05 s on ext4, while about 150 MB of the cache drains at the disk's pace (#362, v0.8.1).
  - What remains of an edit otherwise: placing the edited part's assemblies again (the root's 100,000 occurrences), the watch's marker round trip in the save, and the CLI's own start.
  - Interference from nothing grew from 3.4 s to about 71 s on cox-worker-3 between 7.D and 349138b4 (#356).
  - #236 closed with the bar above (v0.8.2); #237 and #238 stay open.
  - Where an orbiting frame of 100,000 occurrences goes now (#237; v0.8.2, `tests/first_frame.rs` prints each step): on cox-worker-3's RTX 5060 at 1280×800, a median of 54 to 57 ms (18 to 19 fps, from 7.D's 86 ms), worst 196 to 212 ms. Levels 8.6 to 12.4 ms, `sync_drawn` 12.5 to 15.6 ms, the render's submission 12.2 to 12.7 ms (wgpu's submit about 6.7, the runs' instances 2.9, encoding about 3), the GPU 16.5 ms; the worst frames are the pump's Picker made again (135 to 138 ms). At the whole view the GPU draws 53.1M triangles and 18.5M edge segments: 32.5 ms a frame with edges and 22.0 without. Grouping `sync_drawn`'s runs in parallel by a sort, and looking each run's upload up once, didn't move its time (the occurrences' Arcs and placement dominate), so neither landed. What's left is drawing less (edges and triangles of occurrences a few pixels across, one draw for many small runs) and the Picker off the frame.

## The frame at scale (decided in release 8, 0.8.x)

Issue #237: orbiting the 10,000-part benchmark (100,000 occurrences) ran at 19 fps, its worst frames over 200 ms.

- **The picker taken in place.** A body's mesh at the user's display quality arriving bumped the model's generation, so the view made a new picker over every occurrence inside a frame (135 to 147 ms). It is now logged in `Model::reindexed` without a new generation, and `Picker::refresh` swaps those bodies' meshes and boxes and refits the box tree in one pass (`Tree::refit`): the same bodies, picking what a new picker would. `View::picker` refreshes before it uses one; `Picker::stale` says when only a new one will do.
- **Drawing less of small bodies.** `lod::choose` leaves out an occurrence whose box spans under a pixel (`lod::DRAWN_FROM`) and draws one under 6 pixels (`lod::EDGES_FROM`) without its edges (`Drawn::edges`): each run's occurrences with edges come first in the instance buffer, and its edges are drawn at those alone. At the benchmark's whole view 99,509 occurrences are under a pixel. Their faces hardly ever cover a sample, so the first frame differs from before only where their edges drew one-pixel specks; by the faces alone, culling them changed 177 pixels of 1,024,000.
- **Measured** on bc2 (NVIDIA GeForce RTX 5060, Intel Core Ultra 5 250K Plus, 1280×800, `tests/first_frame.rs` over a kept project, `RYUCAD_SCALE_KEEP`, load 6 to 10 from other sessions): before, a median of 52 to 66 ms (15 to 19 fps) and worst 202 ms in two runs; with the picker taken in place, worst 69 ms; with small bodies drawn less as well, four runs with `RYUCAD_BARS=1` gave medians of 4.0 to 4.3 ms (235 to 250 fps) and worst frames of 14.7 to 15.3 ms, no picker made again. The frame bars (60 fps, no frame over 50 ms) hold at the test's camera path, which starts at the whole view and closes in to a tenth of its distance; a view in which most occurrences are several pixels across still draws them all. The first full frame took 9.3 s in the run that printed it; three runs while the box was loaded failed its 20 s bar, which is the new daemon's rebuild of the root, untouched here (#238's).
- **Views where most occurrences are several pixels across** (v0.8.2). `tests/first_frame.rs` then stops at three views and turns or flies there, every frame counting towards the bar. In this benchmark the race bodies dominate any wide view: at the whole view 99,509 occurrences are under a pixel, and framing a module draws at most 288. A subassembly's own parts framed draws 501, all with edges; a low flight along a module's subassemblies draws up to 1,699. On bc2's RTX 5060, with `RYUCAD_BARS=1`, the stops' worst frames were 11.5 to 12.9 ms, and the whole run's median was 2.1 to 2.2 ms and its worst 15.6 to 15.9 ms.
- **Testing.** `pick`'s `a_mesh_at_the_display_quality_is_taken_in_place`, `lod`'s `small_bodies_lose_their_edges_and_those_under_a_pixel_go`, and `tests/first_frame.rs`, which counts pickers made while orbiting, occurrences left out and drawn without edges, and writes the first frame with `RYUCAD_FRAME_PNG=<file>`.

## The warm daemon (decided in release 8, 0.8.x)

Issue #238: davids-m4 (Apple M4, 10 cores) missed the warm daemon's bar (12.9 to 18.2 s against 10 s) and the first full frame's (24 s against 20 s), both mostly a new daemon's rebuild of the root over the warm disk cache. Profiled in process on bc2 (Intel Core Ultra 5 250K Plus, 4 rayon threads, a 4 GiB budget, sampled with gdb since `perf` isn't allowed there). Under mimalloc, opening the session, the root's rebuild and its report took about 7.3 s on main and about 3.75 s after these changes. Every change keeps every answer: no golden hash moved.

- **Opening.** `Session::open` loaded the project from the folder and then scanned the folder, reading every file twice, one at a time. The scan now reads the files, listing the part folders and reading the untrusted files in parallel and building its maps whole on the first scan. The project then loads from the stamps (`Project::load_par`, parts parsed in parallel, the first error in listing order as `load_from` gives it). A full check hashes its listed paths rather than ordering them. Open went from 1.9 to 0.42 s, a full refresh from 0.47 to 0.18 s.
- **Names.** A warm daemon learns every name of every part it rebuilds. `names_of` now groups names by state of each solid, finds origins through a 32-byte buffer rather than a string per name, and builds a new solid's map whole; parts are worked out in parallel and learnt in order. 1.3 to 0.6 s.
- **The budget's count.** `Budget::total` meets the rebuilt parts and the measured sizes in one pass: 221 counts a warm rebuild, 0.45 to 0.31 s.
- **Decoding cache entries.** Origins are read as raw JSON text, each distinct text parsed once (`Origins::from_raw`), where every name's was parsed and written out again to share it. ryukei's `check_topology` checks names by one sorted list against the index, not a list per name, and a cached body's decode runs it. An entry is read, dated and touched through one handle. Decoding went from 4.3 to 2.6 s of CPU and reading from 2.07 to about 1.7 s.
- **mimalloc on macOS.** The same in-process warm rebuild took 6.4 to 6.5 s under glibc's allocator and 4.9 to 5.2 s under mimalloc; macOS's own allocator is slower than glibc's at this work, so macOS builds of `ryucad` use mimalloc as Linux's do. Windows keeps its own.
- **Through the daemon.** On bc2 (RTX 5060, 4 rayon threads), `tests/first_frame.rs`'s warm root report went from 8.0 and 8.2 s on main to 5.4 and 6.8 s, and its first full frame from 9.7 s to 7.0 and 8.8 s. A daemon's first read of entries an hour old also touches each one (`TOUCH_AFTER`), which made a cold-start CLI rebuild of the root take 7.9 s against 4.6 to 5.9 s once touched. `tests/scale_bar.rs` on bc2 (4 rayon threads, back to back, each with its own build): a daemon over the warm cache 8.2 and 8.0 s on main, 5.7 and 5.2 s after; the window's open from the cache, the root's report 7.7 against 5.0 s and every coarse mesh 9.4 against 6.7 s; peak memory 4,643 against 4,554 MiB.

## The whole project's rebuild answer (decided in release 8, 0.8.x)

Issue #533: `ryucad rebuild` with no part named answers every part's report (89 MB of JSON for the 10,000-part benchmark), which the daemon built as a `serde_json::Value` tree and then cloned into its response line, peaking near 9.7 GB with `session.max_memory` at 4 GiB.

- **Answers as text.** `ryu_session::rpc::Answer` gains `raw: Option<Raw>`: a result (`Raw::Result`) or a failure (`Raw::Error`: code, message and details) already written as JSON text, `result` then null. The daemon writes its response line around the text (`rpc::write_raw_response`, through a buffered writer under the write lock), never copying it; the bytes are those `rpc_response` gives for the same `Value` (sorted keys, compact), so clients, the CLI's envelope and the hosted review service see no change. A raw failure is a failure: settling a cancel leaves it as it leaves an `Err`. `Answer::into_json` reads raw text back, for callers that read answers rather than send them: `handle_live`, `handle_job` (the CLI in process, tests) do; only the daemon calls `handle_job_raw`.
- **The rebuild's report.** `server::rebuild` writes `{commit?, parts, placed?, warnings?}` part by part, each part's report serialized as it is made, an assembly's occurrences apart from its report and written one at a time into it in their sorted place (`object_text`), so the largest `Value` held is one part's report less its occurrences. `rebuild <part>` takes the same path.
- **Measured.** `tests/answer_peak.rs` (release, `--features bench`, its own step in full.yml) counts live bytes with a global allocator over a generated 1,000-part project (races off) on a warm second rebuild: the answer 8.6 MiB, held 18.7 MiB as text (2.2 times: the `String`'s doubling), against 342 MiB through a `Value` as before (39.9 times: the tree, its clone in the response and the line), on cox-worker-2 (AMD Ryzen 7 9700X). It asserts under 4 times, and that the line is the `Value`'s, byte for byte. The CLI still parses the line into a `Value` in its own process.
