## Catalogues and items (decided in ryuplm 0.A, design 734)

The design is document 734 in the Coxswain planning project `ryucad-ryukei`; this is its plan 0.A (design phases 1 to 3).

- **The crate.** `crates/ryuplm` (library and binary) is the third product on ryupdm's product-neutral core. It depends on `ryu-doc`, `ryu-session`, `ryu-git`, `ryueda-parts` (AML names and lifecycles) and `ryupdm` with `default-features = false`, never on the kernel or another product; `tests/deps.rs` checks the manifest.
- **A catalogue.** A folder with `ryuplm.json` (kind `ryuplm.catalogue`, format 1: `project`, `forked_from: {commit, project}` as ryueda writes it, `default_unit`, `classes`) and one canonical JSON file per item at `items/<ab>/<id>.json` (kind `ryuplm.item`). `Catalogue::load` reads every item and keeps each file's fault beside the rest (a misplaced file names the path it belongs at in `details.expected`), so one bad file never hides the others.
- **Item IDs.** 64 random bits as 13 characters of Crockford's lowercase base32 (`0123456789abcdefghjkmnpqrstvwxyz`): bits 63..4 five at a time, then the low four, so the first two characters (the shard) take all 1,024 values. `RYUPLM_ID_SEED` makes them a fixed sequence (`blake3("ryuplm.id.1\0" ‖ seed ‖ k)`), the same in any process, daemon or not. BOM line IDs are the same form.
  - `ids::generated` accepts any 13 characters of the alphabet, not only those ending `0`-`f` that `random` makes: the plan's own example `k3v9q2m8x4c1p` (design 734's) ends in `p`, and an ID written by hand must still read. An item file whose name is any valid `Id` of two characters or more at its shard reads.
- **Item fields as ryupdm properties.** `Product::properties_from` (new in ryupdm, `None` by default) reads a part's properties from its own file. ryuplm maps `number`, `name`, `description`, `make_buy`, `unit` (as ryupdm's `uom`) and every entry of `properties`, so `props::check`, `Pdm::of_for`'s duplicates, `record::revising` and release readiness work unchanged on items. `properties_path` is the item file. ryuplm never calls ryupdm's property writers; items are edited by `item edit`.
- **`unit`.** One of ryupdm's units of measure (`each`, `m`, `m2`, `m3`, `kg`, `l`), absent meaning `each`. The manifest's `default_unit` (a length unit) is what bare numbers of quantity-typed declared properties take.
- **Content hash** (`ryuplm.content.1`): BLAKE3 over length-prefixed pieces, the tag first, then the item's canonical JSON without `source`, `extra` and `previous_numbers`. Provenance and old numbers never make a released item modified.
- **Numbering schemes.** `ryupdm.json` at format 5 holds `part_number: {schemes: [{name, class?, pattern, next?}]}`, exclusive with format 1's `{pattern}`. ryupdm parses, validates and writes them (`config::NumberScheme`, `Template`) and gives each a textconv line (`part_number.schemes.<name>`); `props::check` raises nothing for them. ryuplm judges: a number matching no scheme whose class is the item's or absent is `part_number_unschemed`, a warning, so legacy numbers stay as written. `next` has one `{seq:N}` (N 1 to 12); `item create --next [<scheme>]` fills it with one more than the highest sequence in use reads back: any item's number or previous number, and any number a release record holds, so the number of an item released and then deleted is never offered again. With one scheme that has `next` no name is needed; with several, `--class` picks its scheme, else the name is required (`usage`).
- **Uniqueness.** In a catalogue, live items sharing a number are `part_number_duplicate` (an error), and so is a live item whose number a release record of another item names, so an obsolete or deleted item's number stays taken while a record names it. Elsewhere: catalogues under `check --in` folders, the `pdm.dependents` preference and the catalogue's Git work tree are compared, `part_number_duplicate_elsewhere` a warning naming the other catalogue's project and item. Writes judge the catalogue's own files only and never read other folders.
- **Renumbering.** `item renumber` moves the old number to the front of `previous_numbers` (no duplicates, the new number leaving it). `item show` and `item list --number` find by current number first, then previous ones.
- **Classes.** Declared in `ryuplm.json` as `classes: {<name>: {properties?: [...]}}`. An undeclared class is `item_class_unknown` (an error). A class with a list allows only those declared properties (`property_unknown` at `/properties/<name>`) and needs only its required ones for release; no list, or no class, takes every declared property.
- **AML.** Entries `{manufacturer, mpn, status, preferred?}`, the names of `ryueda_parts::record::Record`; `status` is `active`, `nrnd`, `obsolete` or `unknown`, mapped from a parts lifecycle by `aml::Status::from_lifecycle` (not recommended and last time buy are `nrnd`, none known `unknown`). At most one preferred; `(manufacturer, mpn)` pairs unique as written; faults are `invalid_document` at the entry.
- **`links`, `bom`, `documents`, `source`, `extra`.** Read in their design shapes and judged for shape only; their meaning is 0.B's and imports' 0.C's. `source` and `extra` are opaque objects by import name.
- **Severity and writes.** Findings are `Fault { severity, error }` as ryueda's. Warnings never fail `check` and never refuse a write. A write that would add an error of the catalogue's own files is refused with the first new fault's own code and `details.faults` listing them (`write::commit`). `check` reports `{schema: 1, faults, errors, warnings, release?}` and fails `check_failed` with the report in `details.report`.
- **Releases.** Through ryupdm's core as ryueda's: records at format 2 (`built_with.product: ryuplm`), states, tags, `release check` and `sync`. Readiness is the item's error faults plus each required property it lacks as its class allows, the latter written as ryueda writes them (`property_invalid`, `missing: true`).
- **Daemon and CLI.** ryu-session's, as ryudfm's: `RYUPLM_NO_DAEMON`, `RYUPLM_RUNTIME_DIR`, `RYUPLM_IDLE_TIMEOUT`, `RYUPLM_CONFIG_DIR`, `RYUPLM_PARTICIPANT`; every command answers the same JSON in process and through the daemon (`tests/cli.rs` runs each both ways), and every protocol method has a command. `BULKY` is empty: items are small and kept in the activity log inline. Preferences are `daemon.poll_ms` and `pdm.dependents`.
- **Git.** `.gitattributes` gets ryuplm's block (manifest, `ryupdm.json`, items and records merged and diffed by ryuplm). ryu-git registers the driver as `ryuplm git merge-driver %O %A %B %P` and textconv as `ryuplm git textconv`. The merge goes field by field, an item's lists entry by entry (`aml` by maker and part number, `links` by product, `bom` by line ID), `previous_numbers` as one value, records whole. ryu-git's shared hook lists `ryuplm` too; its header names `ryuplm git install`, and a hook written with the two-product header before is still read as the shared one. `ryuplm merge status --hook` runs the commit guard and refuses files a merge left with a conflict record or Git's markers.
- **Diff.** `ryuplm diff [<from>] [<to>]` (`HEAD` and the working tree by default) answers items added, removed and changed, each change its textconv lines removed and added, reading a revision through `ryupdm::history::files_for::<Plm>`.
- **Golden.** `tests/determinism.rs` hashes a seeded 300-item catalogue (`testing::catalogue`): its files, `check`'s faults, the next numbers, content hashes and textconv. It carries its own FNV-1a helper (`tests/golden/mod.rs`) rather than ryu-board's, so the dependency test can forbid every other product. The seeded catalogue shares thirteen numbers out among some items, so duplicates are in the golden (the plan's generator gave none).

## Links and BOMs (decided in ryuplm 0.B, design 734)

The design is document 734 in the Coxswain planning project `ryucad-ryukei`; this is its plan 0.B (design phases 4 and 5).

- **Readers.** ryucad's representations are read in process through ryupdm's structure reader (`ryupdm::bom::tree`, depth 1) behind ryuplm's default feature `cad` (`ryupdm/cad` and an optional `ryucad-doc`). `ryucad-doc` depends on `ryukei` and `ryusketch` itself, so with `cad` the kernel is in ryuplm's build transitively; CI's `ryuplm-core` job proves `--no-default-features` reaches neither. ryueda's are read through the `ryueda` executable (`RYUEDA_EXE`, else `ryueda` on PATH): `ryueda -C <dir> --no-daemon bom <design> [--rev <commit>]`, schema 1, each line's `part`, `quantity`, `value`, `footprint` and `refdes` (`reps::eda_answer`); ryueda's `tests/pdm.rs` pins those fields. ryuplm never depends on the `ryueda` crate. Without `cad`, a ryucad link's lines are `item_link_unresolved`. Whatever a product's reader refuses with (its own not-found, a file that doesn't read, ryueda's answer) is the link's `item_link_unresolved`, the reader's error kept under `details.cause`, so `check` reports a missing part once.
- **Links.** `links: [{product, project, part}]` on the item, `product` `ryucad` or `ryueda`. At most one per product and one item per representation (`item_link_duplicate`, an error a write refuses). `item link <item> <product> <project> <part>` takes a project ID or the project's folder (its manifest's `project`) and replaces the item's link of that product; `item unlink` removes it.
- **Where representations are found.** The catalogue's Git work tree (else its folder), then `--in` folders, then `pdm.dependents`, scanned for `ryucad.json` and `ryueda.json`; the first folder holding a project ID wins (`reps::Index`). A part exists when `parts/<id>/part.json` (ryucad) or `designs/<id>.json` or `library/components/<id>.json` (ryueda) is there. `check` reports a project or part not found as `item_link_unresolved` and a representation whose `number` property isn't its item's as `item_number_mismatch`, both warnings.
- **Own lines.** `bom: [{line, item, quantity, unit?, find?, refdes?, notes?}]`; `bom add|edit|remove`. A quantity is a positive decimal as written (`4`, `0.5`; no sign, exponent or unit) and `unit` one of the item units (`invalid_quantity`). A child this catalogue lacks is `bom_item_missing` and a loop of own lines `bom_cycle`, both errors a write refuses (so an item a line names can't be deleted). Another catalogue's child (`<project>:<id>`) is judged by `check` only: a warning when no catalogue searched holds it.
- **The joined BOM.** Own lines, then each link's lines in product order (`bom::of`), each representation line's child resolved to the item linking it. One level: an unlinked child is `bom_unlinked` (one warning per item, `details.unlinked` listing them), nothing is pulled up through it; `bom show --depth N` follows this catalogue's child items. An own line naming an item a representation also places is `bom_line_twice`. A cycle closed only by representation lines is `bom_cycle`, an error, found by `check`. Writes judge own files only and never read representations.
- **Revisions.** Reading the catalogue at a Git revision, a representation inside its work tree is read at the same commit (ryucad through `history::files_for::<Cad>`, ryueda with `--rev <commit>`, its design looked for at that commit); one in another checkout at its working files, and its lines say `"rev": "working"`.
- **Diff and where-used.** `bom diff [<item>] [--from R] [--to R]` (`HEAD` and working by default) keys own lines by line ID and representation lines by product, representation and key, and compares the child, quantity, unit, find number, designators and notes as written. `where-used <item>` answers rows from this catalogue, every other catalogue in the work tree, `--in` or `pdm.dependents` (rows naming the item as `<project>:<id>`), and each one's official releases read at the commit that made them official; a representation that can't be read is a problem, never a failure. Shapes are `bom::SCHEMA` 1.
- **Codes.** New: `item_link_duplicate`, `item_link_unresolved`, `item_number_mismatch`, `bom_unlinked`, `bom_line_twice`, `bom_cycle`. `bom_item_missing` (ryucad's, an assembly placing a part with no item number) also names a ryuplm line whose child can't be found. Import codes are 0.C's.
- **Golden.** `tests/determinism.rs`'s `structure_answers_the_same_everywhere` hashes `testing::structure` (300 items, ryucad and ryueda links, lines held in memory): files, own faults, joined findings, every BOM, a diff against an edited copy and where-used of forty items, in `tests/golden/structure.txt`.

## Imports (decided in ryuplm 0.C, design 734)

The design is document 734 in the Coxswain planning project `ryucad-ryukei`; this is its plan 0.C (design phases 6 and 7). The code is `crates/ryuplm/src/import/`.

- **No new outside crate** (the owner's answer to question 1150). CSV and its four encodings are written here; XLSX's zip is read by `ryupdm::package::zip::read` (bounded, already used for release packages) and its XML by `roxmltree` 0.21 (ryudfm's); mapping regexes use `regex-lite` 0.1 (ryupdm's). `calamine`, `csv` and `encoding_rs` would be three crates (and calamine's four more) for a few hundred lines.
- **The row model.** A reader knows only its file format and yields a `rows::Table`: column names from the header row (`reader.header_row`, 1 by default; rows above it skipped), then each row's cells exactly as written with its row number in the source (a CSV record's first line, an XLSX row's number). Rows whose cells are all empty are skipped, short rows padded, a row wider than the header refused. A blank header is `#<column number>`, a repeated one gets ` #2`, ` #3`, so a mapping can still name it. A record is a row seen through a mapping. No vendor's layout is built in: an Altium- or KiCad-shaped BOM is a CSV with its own mapping.
- **XLSX cells** read as the text a person sees stored: a shared string's text (rich-text runs joined, phonetic runs left out), an inline string's, a formula's cached value, a number's `<v>` as written (`1E-3`), booleans `TRUE`/`FALSE`, errors as their text. Dates are numbers with a date style and read as their serial number: 0.C has no date transform. Sheets are chosen by name (the first when none is named); elements are matched by local name so transitional and strict OOXML both read; roxmltree refuses DTDs.
- **Encodings.** `utf-8` (a BOM dropped), `utf-16le`/`utf-16be` (BOM required), `latin1` (`iso-8859-1`) and `windows-1252` (`cp1252`; its five undefined bytes map to the C1 controls, as browsers do). Unnamed, the reader sniffs: a BOM, else valid UTF-8, else Windows-1252. Bytes that don't decode are refused at their line. The CSV delimiter, unnamed, is the most frequent of `,` `;` tab `|` outside quotes on the first line, `,` on a tie. CSV is RFC 4180 in any one-character delimiter; text after a closing quote is kept, as spreadsheet programs do.
- **Mapping files** are `imports/<name>.json` (kind `ryuplm.import`, format 1, name 1 to 63 of `a-z0-9_-`): `reader` (`type` csv or xlsx, `file` a `*`/`?` pattern the file's name must match, `encoding`, `delimiter`, `sheet`, `header_row`), `key` (the column that identifies a row across imports), `fields` by target (`number`, `name`, `description`, `unit`, `make_buy`, `properties.<declared>`, `aml.<0-9>.manufacturer|mpn|status`), `class` (one class, or `{when, class}` rules, first match wins), `bom` (`quantity`, and `parent` or `level` or `root`, `find`, `refdes`) and `numbers` (`keep`, or `assign` with an optional `scheme`). Transforms run in a fixed order: `trim`, `regex` (the first capture group, else the whole match; no match leaves the field empty), `values` (exact matches; others pass through), `case`, `unit` (appended to a bare number). A field empty after them isn't set. Declared properties are coerced and judged by ryupdm (`props::coerce`, `props::fits`).
- **Provenance** is `source.<import> = {key, digest, values, lines?}` (question 1151): `values` are the mapped values as last imported, by target, beside the design's `key` and `digest`, because a digest can't give back the values the three-way rule needs as its base, and reading the item at the commit of the last import is slow at 100,000 items. The digest is BLAKE3 over the mapped values and the row's unmapped cells, so a change to an unmapped column lands too; equal digests skip the row without comparing values. `extra.<import>` holds the unmapped cells as read, replaced whenever the row changes.
- **Re-import, field by field.** Base = `values` at the last import, current = the item now, new = the row's. New equals base: nothing. Current equals base: take new (an empty new removes the field). Current equals new: the base moves. Otherwise `import_conflict` (a warning with all three values): the field is left alone and its base is *not* moved, so every run reports it again until `--prefer source|catalogue` or an edit settles it, and the stored digest is the stored values', so a row with a conflict left is never skipped as unchanged. A renumber goes through `Item::renumber`, keeping the old number. Keys gone from the source, and lines gone, are `import_missing` warnings; nothing is ever deleted.
- **BOM rows** are items and lines at once. Each row's key is a child item (the first row with that key gives its values; a later row with other values is refused), and each row with a parent (the `parent` column's key, the nearest row one `level` up, a dotted outline's depth being its parts, or `root`, an item's number or ID) is an own line of the parent, matched through the parent's `source.<import>.lines` (`[{child, find?, line, quantity}]`) by (parent key, child key, find number); the same triple twice is refused. The quantity follows the three-way rule; `refdes` is the source's own data, set on a new line and replaced on a changed one. A parent that is only a `root` carries provenance with an empty key, never matched to a row and never missing.
- **Adoption by number** (question 1152). With `numbers: keep`, a key this import has never seen whose number is an untouched item's current number adopts that item instead of making a duplicate the write would refuse: provenance is added and each field judged as a re-import with no base (empty takes the source's, equal is fine, different is `import_conflict`). A structure-only file naming items another mapping made is a second key space, which this doesn't join.
- **All or nothing.** A row that doesn't read fails the run with `invalid_document`, every refusal in `details.refusals` (`{row, column, message}`); a mapping that doesn't read, names a missing column, or an undeclared property, class or scheme is `import_mapping_invalid`; a plan whose writes add an error (a duplicate number inside the source, a BOM cycle) is refused by `write::commit` with its faults. Conflicts and missing rows are warnings. A run is planned as a pure function over the catalogue (`run::plan`) and written through `write::commit`; `--dry-run` answers the same report, `written: 0`, and `would_refuse` (`write::would_add`).
- **Commands.** `import guess <file> [--sheet] [--delimiter] [--encoding] [--save NAME]`, `import check <name> <file> [--limit]` (refusals fail it with `check_failed`, its report in `details.report`), `import run <name> <file> [--dry-run] [--prefer source|catalogue] [--limit] [--expect]` and `import list` (methods `import.guess|check|run|list`). The CLI makes `<file>` absolute so a daemon reads the same file. `--limit` (100) caps the per-row lists in an answer (`created`, `adopted`, `updated`, lines, `shown`); counts, conflicts and missing rows are never capped. `guess --save` refuses an existing mapping (`conflict`) and an unfinished proposal (a BOM with no parent, level or root: `invalid_param`, `details.todo`).
- **Guessing** has no vendor table: a column name is lower-cased and stripped to letters and digits (`Mfr. Part #` is `mfrpart`) and matched to generic spellings of each target, exactly first, then within one edit for names of five letters or more; a trailing number is an AML group (`Manufacturer 2` is `aml.1.manufacturer`); declared properties match their own names. The key is a column spelled like an ID, else the number, else an MPN, else the first column. Every proposed field is trimmed; a number column means `keep`, none `assign`. The answer gives each column's target, or none, and why.
- **Mapping files are catalogue files.** The session tracks `imports/*.json` (undo, the activity log and `project.changed` see them), `ryu_git::Layout` counts them (`pdm::FOLDERS`, `project_file`), and `check` reports one that isn't a mapping, doesn't read, or names an undeclared property, class or scheme as `import_mapping_invalid`, an error a write never adds.
- **Limits.** A source over 256 MiB, an XLSX part over 256 MiB unpacked, more than 2,000,000 rows or 16,384 columns is refused.
- **Large writes.** `write::commit` writes 64 files or more on up to eight threads with syncs deferred (`ryu_doc::source::defer_syncs`), then on Linux syncs the whole file system once (`syncfs` on the catalogue's folder, through `libc`, already in the build by ryu-session) and waits for the queued syncs (`flush_syncs`), which then find nothing to write, before answering. Deferring alone still fsyncs each file: on a network disk (cox-worker-1's Ceph RBD) 100,000 fsyncs took 34 s even on sixteen threads. Elsewhere the queued syncs do it file by file, as ryueda's package export does (#270). Once deferred, later small writes in that process sync behind on the sync thread too, as a ryueda daemon's do.
- **Bars** (`tests/bar.rs`, release only, a step in `full.yml`; `RYUPLM_BARS=1` strict, else ten times looser): 100,000 items loaded by a cold daemon in 2 s; `check` over them in 1 s; a 100,000-row first import in 20 s; re-importing it unchanged in 5 s, writing nothing; where-used over ten checkouts of 10,000 items in 1 s. What they made change, every answer bit for bit the same: where-used opens the other checkouts on threads, the answer in folder order; `Catalogue::load` reads files in order and parses them on threads; `import run` checks its item texts on threads; `tracked` lists the item shards on threads; and a session opened for a request skips that request's refresh (`Session::opened_now`), since opening has just read every file. The bar's catalogue is the seeded one with each repeated number given a suffix: `part_number_duplicate` lists every other item holding its number, so the seed's thirteen shared numbers make gigabytes of faults at 100,000 items. Seeded catalogues take their IDs from `ids::Seeded`, the same IDs `random_from` gives in one pass (it retries every earlier draw first, which is quadratic at 100,000); the import bar runs unseeded for the same reason.
- **Fixtures** (`tests/imports/`, written by `tests/imports.rs` with `UPDATE_FIXTURES=1`, byte-exact, `-text` in Git): an Altium-shaped and a KiCad-shaped BOM, an indented BOM, an item master workbook (a sheet chosen past a notes sheet, legacy numbers in three schemes, its structure by a parent column) and a Latin-1 spreadsheet, each with its mapping; made-up parts, nothing from a customer or vendor. ryupdm has no mass dimension, so the master's weight is declared a number. Each imports, and imports again writing nothing.
- **Golden and fuzz.** `imports_answer_the_same_everywhere` hashes `testing::import_source` (400 rows, a third adopted, then a second source with changed descriptions and quantities, rows gone and rows new) through `records::map` and `run::plan` twice, in `tests/golden/imports.txt`. The `plm` fuzz target's modes 6 to 9 read mappings (canonical round trip), CSV and XLSX on any bytes, and plan a small source through the seeded import.
- **Codes.** New: `import_conflict` and `import_missing` (warnings in a run's report) and `import_mapping_invalid` (an error).

## Releases (decided in ryuplm 0.A)

- **Its own line.** ryuplm is released apart from ryucad, ryueda and ryudfm, as they are:
  - Tags are `ryuplm-vX.Y.Z` (pre-releases `ryuplm-vX.Y.Z-pre.N`), taken only by `.github/workflows/ryuplm-release.yml` (`ryuplm-v[0-9]+.[0-9]+.[0-9]+*`).
  - `crates/ryueda/tests/release.rs` matches all four workflows' tag patterns as GitHub does and checks that no workflow takes another line's tags.
  - Tags follow the `ryuplm-release` roadmap; nothing is tagged until its stage 1.
- **The workflow.** ryudfm's made ryuplm's: the version from the tag (`scripts/stamp-version.sh` takes `ryuplm-vX.Y.Z` and refuses `ryuplm-X.Y.Z`), `full.yml` the gate, per target the golden hashes, a build with `RYUPLM_COMMIT`, `ryuplm version` checked, `scripts/smoke-ryuplm.sh`, then an archive. `workflow_dispatch` is a dry run.
- **What a release holds.** `ryuplm-<version>-<target>` archives holding `ryuplm`, `LICENSE` and `NOTICE`, with `SHA256SUMS`, `install-ryuplm.sh` and `install-ryuplm.ps1`. Never GitHub's latest release (`--latest=false`), never `install.sh` or `install.ps1`; the test checks both, and that the workflow reads no secret and publishes no Python package.
- **Installers.** `install-ryuplm.sh` and `install-ryuplm.ps1` are ryudfm's made ryuplm's: they install to `~/.ryuplm/bin`, take `RYUPLM_VERSION`, `RYUPLM_HOME`, `RYUPLM_NO_MODIFY_PATH` and `RYUPLM_DOWNLOAD_BASE`, and with no version take the newest `ryuplm-v` release that is neither a draft nor a pre-release, never `releases/latest`.
- **Smoke test.** `scripts/smoke-ryuplm.sh <ryuplm>`: a catalogue in a throwaway repository, a scheme and a class, items by the scheme's next number and by a legacy number with an AML, edited, renumbered, found by an old number and by text, `check` (the legacy number a warning), a duplicate refused, a delete undone and redone through the daemon, the activity log, `diff`, the daemon's status and stop, and `check` in process.
- **Testing.** full.yml's installers job builds ryuplm, runs shellcheck and PSScriptAnalyzer over the new scripts, the smoke test on Linux, macOS and Windows, and `scripts/test-install-ryuplm.sh` and `.ps1` (Windows PowerShell 5.1 and PowerShell 7) against a fake release. Its golden-hashes job takes `-p ryuplm` at every CPU level, and the nightly fuzz runs the `plm` target.
