## Catalogues and items (decided in ryuplm 0.A, design 734)

The design is document 734 in the Coxswain planning project `ryucad-ryukei`; this is its plan 0.A (design phases 1 to 3).

- **The crate.** `crates/ryuplm` (library and binary) is the third product on ryupdm's product-neutral core. It depends on `ryu-doc`, `ryu-session`, `ryu-git`, `ryueda-parts` (AML names and lifecycles) and `ryupdm` with `default-features = false`, never on the kernel or another product; `tests/deps.rs` checks the manifest.
- **A catalogue.** A folder with `ryuplm.json` (kind `ryuplm.catalogue`, format 1: `project`, `forked_from: {commit, project}` as ryueda writes it, `default_unit`, `classes`) and one canonical JSON file per item at `items/<ab>/<id>.json` (kind `ryuplm.item`). `Catalogue::load` reads every item and keeps each file's fault beside the rest (a misplaced file names the path it belongs at in `details.expected`), so one bad file never hides the others.
- **Item IDs.** 64 random bits as 13 characters of Crockford's lowercase base32 (`0123456789abcdefghjkmnpqrstvwxyz`): bits 63..4 five at a time, then the low four, so the first two characters (the shard) take all 1,024 values. `RYUPLM_ID_SEED` makes them a fixed sequence (`blake3("ryuplm.id.1\0" ‖ seed ‖ k)`), the same in any process, daemon or not. BOM line IDs are the same form.
  - `ids::generated` accepts any 13 characters of the alphabet, not only those ending `0`-`f` that `random` makes: the plan's own example `k3v9q2m8x4c1p` (design 734's) ends in `p`, and an ID written by hand must still read. An item file whose name is any valid `Id` of two characters or more at its shard reads.
- **Item fields as ryupdm properties.** `Product::properties_from` (new in ryupdm, `None` by default) reads a part's properties from its own file. ryuplm maps `number`, `name`, `description`, `make_buy`, `unit` (as ryupdm's `uom`) and every entry of `properties`, so `props::check`, `Pdm::of_for`'s duplicates, `record::revising` and release readiness work unchanged on items. `properties_path` is the item file. ryuplm never calls ryupdm's property writers; items are edited by `item edit`.
- **`unit`.** One of ryupdm's units of measure (`each`, `m`, `m2`, `m3`, `kg`, `l`), absent meaning `each`. The manifest's `default_unit` (a length unit) is what bare numbers of quantity-typed declared properties take.
- **Content hash** (`ryuplm.content.1`): BLAKE3 over length-prefixed pieces, the tag first, then the item's canonical JSON without `source`, `extra` and `previous_numbers`. Provenance and old numbers never make a released item modified.
- **Numbering schemes.** `ryupdm.json` at format 5 holds `part_number: {schemes: [{name, class?, pattern, next?}]}`, exclusive with format 1's `{pattern}`. ryupdm parses, validates and writes them (`config::NumberScheme`, `Template`) and gives each a textconv line (`part_number.schemes.<name>`); `props::check` raises nothing for them. ryuplm judges: a number matching no scheme whose class is the item's or absent is `part_number_unschemed`, a warning, so legacy numbers stay as written. `next` has one `{seq:N}` (N 1 to 12); `item create --next [<scheme>]` fills it with one more than the highest sequence in use reads back: any item's number or previous number, and any number a release record holds, so the number of an item released and then deleted is never offered again. With one scheme that has `next` no name is needed; with several, `--class` picks its scheme, else the name is required (`usage`).
- **Uniqueness.** In a catalogue, live items sharing a number are `part_number_duplicate` (an error), and so is a live item whose number a release record of another item names, so an obsolete or deleted item's number stays taken while a record names it. Elsewhere: catalogues under `check --in` folders, the `pdm.dependents` preference and the catalogue's Git work tree are compared, `part_number_duplicate_elsewhere` a warning naming the other catalogue's project and item. Writes judge the catalogue's own files only and never read other folders.
- **Renumbering.** `item renumber` moves the old number to the front of `previous_numbers` (no duplicates, the new number leaving it). `item show` and `item list --number` find by current number first, then previous ones.
- **Classes.** Declared in `ryuplm.json` as `classes: {<name>: {properties?: [...]}}`. An undeclared class is `item_class_unknown` (an error). A class with a list allows only those declared properties (`property_unknown` at `/properties/<name>`) and needs only its required ones for release; no list, or no class, takes every declared property.
- **AML.** Entries `{manufacturer, mpn, status, preferred?}`, the names of `ryueda_parts::record::Record`; `status` is `active`, `nrnd`, `obsolete` or `unknown`, mapped from a parts lifecycle by `aml::Status::from_lifecycle` (not recommended and last time buy are `nrnd`, none known `unknown`). At most one preferred; `(manufacturer, mpn)` pairs unique as written; faults are `invalid_document` at the entry.
- **`links`, `bom`, `documents`, `source`, `extra`.** Read in their design shapes and judged for shape only; their meaning is 0.B's and imports' 0.C's. `source` and `extra` are opaque objects by import name.
- **Severity and writes.** Findings are `Fault { severity, error }` as ryueda's. Warnings never fail `check` and never refuse a write. A write that would add an error of the catalogue's own files is refused with the first new fault's own code and `details.faults` listing them (`write::commit`). `check` reports `{schema: 1, faults, errors, warnings, release?}` and fails `check_failed` with the report in `details.report`.
- **Releases.** Through ryupdm's core as ryueda's: records at format 2 (`built_with.product: ryuplm`), states, tags, `release check` and `sync`. Readiness is the item's error faults plus each required property it lacks as its class allows, the latter written as ryueda writes them (`property_invalid`, `missing: true`).
- **Daemon and CLI.** ryu-session's, as ryudfm's: `RYUPLM_NO_DAEMON`, `RYUPLM_RUNTIME_DIR`, `RYUPLM_IDLE_TIMEOUT`, `RYUPLM_CONFIG_DIR`, `RYUPLM_PARTICIPANT`; every command answers the same JSON in process and through the daemon (`tests/cli.rs` runs each both ways), and every protocol method has a command. `BULKY` is empty: items are small and kept in the activity log inline. Preferences are `daemon.poll_ms` and `pdm.dependents`.
- **Git.** `.gitattributes` gets ryuplm's block (manifest, `ryupdm.json`, items and records merged and diffed by ryuplm). ryu-git registers the driver as `ryuplm git merge-driver %O %A %B %P` and textconv as `ryuplm git textconv`. The merge goes field by field, an item's lists entry by entry (`aml` by maker and part number, `links` by product, `bom` by line ID), `previous_numbers` as one value, records whole. ryu-git's shared hook lists `ryuplm` too; its header names `ryuplm git install`, and a hook written with the two-product header before is still read as the shared one. `ryuplm merge status --hook` runs the commit guard and refuses files a merge left with a conflict record or Git's markers.
- **Diff.** `ryuplm diff [<from>] [<to>]` (`HEAD` and the working tree by default) answers items added, removed and changed, each change its textconv lines removed and added, reading a revision through `ryupdm::history::files_for::<Plm>`.
- **Golden.** `tests/determinism.rs` hashes a seeded 300-item catalogue (`testing::catalogue`): its files, `check`'s faults, the next numbers, content hashes and textconv. It carries its own FNV-1a helper (`tests/golden/mod.rs`) rather than ryu-board's, so the dependency test can forbid every other product. The seeded catalogue shares thirteen numbers out among some items, so duplicates are in the golden (the plan's generator gave none).

## Releases (decided in ryuplm 0.A)

- **Its own line.** ryuplm is released apart from ryucad, ryueda and ryudfm, as they are:
  - Tags are `ryuplm-vX.Y.Z` (pre-releases `ryuplm-vX.Y.Z-pre.N`), taken only by `.github/workflows/ryuplm-release.yml` (`ryuplm-v[0-9]+.[0-9]+.[0-9]+*`).
  - `crates/ryueda/tests/release.rs` matches all four workflows' tag patterns as GitHub does and checks that no workflow takes another line's tags.
  - Tags follow the `ryuplm-release` roadmap; nothing is tagged until its stage 1.
- **The workflow.** ryudfm's made ryuplm's: the version from the tag (`scripts/stamp-version.sh` takes `ryuplm-vX.Y.Z` and refuses `ryuplm-X.Y.Z`), `full.yml` the gate, per target the golden hashes, a build with `RYUPLM_COMMIT`, `ryuplm version` checked, `scripts/smoke-ryuplm.sh`, then an archive. `workflow_dispatch` is a dry run.
- **What a release holds.** `ryuplm-<version>-<target>` archives holding `ryuplm`, `LICENSE` and `NOTICE`, with `SHA256SUMS`, `install-ryuplm.sh` and `install-ryuplm.ps1`. Never GitHub's latest release (`--latest=false`), never `install.sh` or `install.ps1`; the test checks both, and that the workflow reads no secret and publishes no Python package.
- **Installers.** `install-ryuplm.sh` and `install-ryuplm.ps1` are ryudfm's made ryuplm's: they install to `~/.ryuplm/bin`, take `RYUPLM_VERSION`, `RYUPLM_HOME`, `RYUPLM_NO_MODIFY_PATH` and `RYUPLM_DOWNLOAD_BASE`, and with no version take the newest `ryuplm-v` release that is neither a draft nor a pre-release, never `releases/latest`.
- **Smoke test.** `scripts/smoke-ryuplm.sh <ryuplm>`: a catalogue in a throwaway repository, a scheme and a class, items by the scheme's next number and by a legacy number with an AML, edited, renumbered, found by an old number and by text, `check` (the legacy number a warning), a duplicate refused, a delete undone and redone through the daemon, the activity log, `diff`, the daemon's status and stop, and `check` in process.
- **Testing.** full.yml's installers job builds ryuplm, runs shellcheck and PSScriptAnalyzer over the new scripts, the smoke test on Linux, macOS and Windows, and `scripts/test-install-ryuplm.sh` and `.ps1` (Windows PowerShell 5.1 and PowerShell 7) against a fake release. Its golden-hashes job takes `-p ryuplm` at every CPU level, and the nightly fuzz runs the `plm` target.
