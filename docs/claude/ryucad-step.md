## STEP import (decided in ryucad phase 6)

The design is document 120 in the Coxswain planning project `ryucad-ryukei`; this is its plan 6.A.

- **Files.** A STEP file an import reads is committed in the project as `imports/<id>.step` (an input, not derived data), shared by every part made from it; the same bytes are stored once. `doc::project::Project::imports` holds them by path, read with the project (`ImportFile`: bytes and BLAKE3), and each `Part::imports` the files its listed imports read; a part's revision hashes those files' BLAKE3 (tagged, so parts without imports hash as before), so a file replaced by hand rebuilds the part. Sessions track `imports/`, revisions read it from Git, and `.gitattributes` gains `imports/** binary` once a project has a file there (`drivers::IMPORT_LINE`, `missing_for`, `with_lines_for`): Git must keep the bytes exactly, or Windows checkouts would change their hash.
- **The feature.** `import` (feature format 5, `doc::import`): `file` `{path, blake3}`, `product` `{id, name, ordinal?}` (the `PRODUCT`'s, and its place among definitions with both equal) or none for a body no product reaches, and `body` (from 0, in instance order). It founds one solid (its `combine` is `new`, always); `feature.add` and `feature.edit` refuse it (`invalid_param`): imports are written by `import`. Rebuild (`crate::import::build`) heals the body with `ryustep::Opened::body` under the feature's own `OpKey`, so names follow the feature and a new version of the file keeps the names of unchanged geometry; files are opened once per process by BLAKE3 (1 GiB of source kept, least recently used first). Origins give each entity its STEP instance (`{feature, step: "#n"}`); the rebuild report gives the feature `import` (file, product, body and the heal report's counts). The input hash adds the file's BLAKE3 as it is; the disk cache keeps the report with the solid.
- **Refusals.** `import_file_missing`, `import_file_changed` (with `expected` and `found`), `step_unreadable` (ryustep's reason, line and column), `import_product_missing` (with the file's `products`), `import_body_missing` (with `bodies`), `import_failed` (the `ImportError` or `HealError` variant in snake case, the STEP instances it names as `#n` in `step`, and import names healing made in `names`). `import_failed` for faces overlapping (or shells crossing) in two different solids of one representation names them in `solids` and says they touch (#208).
- **The command.** `import` (`ryucad import <file> [--part ID] [--into PART] [--product ID] [--dry-run] [--expect REV]`) reads a file the daemon can read (the CLI sends an absolute path), refuses what isn't STEP before writing anything, and makes a part of each product's bodies (`body`, `body-2`, …), then one of the bodies no product reaches, named from the product's id, else its name, else the file's stem (`import::id_from`, the first free `-<n>` past existing and retired IDs); `--part` names the one part a file makes; `--into` adds one product's bodies (`--product` by id, else name, when the file has several) to an existing part (not an assembly) after its features. Where `ryupdm.json` exists a new part's `properties.json` gets `name` and `description` from the product, never `number`. One logged, undoable change guarded by the project's revision (`--into`: that part's); the answer lists the stored file (`reused` when the bytes were there), each part and each feature's result (counts and heal counts, or the error), with `import_failed` and `import_mapped_skipped` warnings. A dry run heals every body in memory and writes nothing. A product's mapped items aren't imported.
- **Doctor, diff, check.** Doctor reports `import_file_missing` (an error, no repair: restore from Git or import again) and `import_file_changed` (an error; 6.B's `import_update` repair), `import_unused` (repair: delete) and `import_large` (over 100 MB); other names under `imports/` are `unknown_file`. `diff` lists imported files that differ at the top (`imports`: path, status, BLAKE3s), only when there are any; an import feature diffs by value and textconvs one line per field. `check` reports both doctor's findings and the features' failures. Doctor also reports `import_misplaced` (a warning): a fixed imported instance whose pose isn't where its file's bytes place its usage, with the repair `place`, which writes the file's poses (#206).
- **ryustep.** `ryustep::open` parses, decodes and reads the product tree once (`Opened`, its `held` representations); `Opened::body(k, opts)` heals one exactly as `read` does, which is now `open` and every body in parallel. `products::Definition` gains `description`.
- **Testing.** `import.rs` unit tests (selection, failures, rebuild, names following geometry, the command, dry runs, `--into`, PDM, undo, revisions and diffs through Git, check), `project.rs` (imports load, reload and define parts), `doctor.rs`, `drivers.rs`, `diff.rs`; `tests/cli.rs`'s `imports_from_the_cli` both ways; `tests/step.rs` (the committed corpus imports as ryustep reads it, bit for bit, per the manifest; the OCCT files import and `check` clean).

## STEP assemblies and re-import (decided in ryucad phase 6)

The design is document 120 in the Coxswain planning project `ryucad-ryukei`; this is its plan 6.B.

- **Placements.** `ryustep::Opened::placement(parent, k)` gives where a usage puts its child: a `Rigid` taking the child's coordinates into its parent's, in meters, each placement read in its own representation's units (`products::Occurrence::representations`, the relationship's, the child's first), an operator inverted where the file related the representations the other way, a scale other than 1 `Malformed`; the identity where the file says nothing.
- **Assembly files.** `import` (`crate::import::plan`) makes a part of each product with bodies, an assembly of each product with children that make something (an `instance` per usage, fixed, at the file's placement, `Pose::snapped`), and for a product with both an assembly placing a part `<id>-body` of its own bodies at its origin; a product several usages place is one part. Instance IDs are the usage's id made an ID, else the child's part's, numbered on collisions. `--part` names the file's one root (a part or an assembly; several roots: `invalid_param`). The plan is file writes (`import::Writes`): a dry run rebuilds them in a session over the proposed files (`Session::proposed`), and parts heal side by side (`Session::rebuild_parts`).
- **Imported instances.** `instance` gains `import` (feature format 5 when present): `{file, product, usage?, ordinal?}`, the file's path, the product it is used in (the assembly's own), and the `NEXT_ASSEMBLY_USAGE_OCCURRENCE`'s id with its place among that product's usages of the same child with that id; no usage is the instance placing the product's own bodies. `feature.edit` keeps it while the instance places the same part.
- **Label pins.** `Session::pinned_part` loads, with a part's files at its release's commit, the imported files its import features name there.
- **Re-import.** `import --update <imports/…> <file>` (proto `update`; `crate::import::update`) replaces the file's bytes and plans from the project's files alone: products matched by PRODUCT id, name and ordinal, then id, then name, in order among equals; a matched product's import features take the new hash and its product as it is now, and one with more bodies gains import features where a part holds all its old ones; new products make parts and assemblies as importing does, but only for a file imported whole: a file only ever imported `--into` a part makes no new parts (an assembly file that left no imported instances, unless two of its products are each in a part it founded: a flat file imported whole whose new version adds an assembly over its parts; or a flat one some of whose products aren't in parts it founded), nor do the same bytes again, and new products such an update makes no part for are warned of (`import_products_skipped`, naming them, and the bodies no product reaches where no feature held them: import them `--into` a part, or delete the file's parts and import it again). The limits, without the old bytes: products taken `--into` empty parts read as a whole import (a flat file's one root, or two products of an assembly file each in a part of its own), and a new version makes parts for the rest; a flat file of one root imported whole whose new version adds an assembly over it reads as `--into`, and the assembly is only warned of; a vanished product's features take the new hash and fail `import_product_missing`. Usages are matched within their assembly by id, child product and ordinal: a fixed instance takes the file's pose, a new usage is a new instance, an instance whose usage vanished is deleted unless a mate or pattern reads it (then kept, `import_usage_missing` in the answer and in that assembly's rebuild warnings). A part whose product now has children can't place them (`import_kind_changed`). The answer lists the parts written, `vanished` products, `kept` instances, and `failing`: the features that build now and wouldn't after, from a rebuild of the proposed files. One logged, undoable change; assemblies current before are written back solved (`assemblies`). `part`, `into` and `product` don't apply (`usage`); a path the project hasn't imported is `not_found`.
- **Doctor, diff, merges.** `import_file_changed` has the repair `import_update`: the same plan from the bytes in place (`import::update_in_place`; assemblies aren't solved again by it). `diff --model` gives each imported file that differs `products`: `added`, `removed` and `changed` (with whether its `bodies`, healed under one key for the file, and its `usages` did), matched as an update matches them. Git leaves conflicting imported bytes unmerged (binary): `merge.status` lists them as `merge_unparsed` with each side's BLAKE3, taken with `--ours`/`--theirs` (theirs taken is settled; ours stays listed until staged); the import features' hashes conflict by value; bytes and hashes left disagreeing fail the import `import_file_changed`, which `merge_broke` blames, counting the imported file among what the feature reads.
- **Testing.** `ryustep`'s `tests/read.rs` (XDE's placements, an operator either way, a scale refused) and `tests/write.rs` (placements written and read back); `import.rs` and `import/update.rs` unit tests (XDE's assembly, a frame with its own plate, a shared pin, a second root and usages with one id, a label pin, an unchanged file, a new version moving, adding and removing, freed and mated instances, refusals, undo, names surviving and a fillet failing with `removed_by`, the products diff, doctor's repair); `tests/merge.rs` (two branches re-importing differently, settled either way, and the merge breaking the import between); `tests/cache.rs` (alike features of different parts); a CLI scenario both ways.

## STEP export (decided in ryucad phase 6)

The design is document 120 in the Coxswain planning project `ryucad-ryukei`; this is its plan 6.C.

- **ryustep.** `write::Product` gains `description` and `revision` (the `PRODUCT_DEFINITION_FORMATION`'s id, empty for none), and `write::Child` an `id`, the usage's (empty: its place among its parent's, from 1, as before); `products::Definition` gains `revision`, read from the formation. Golden hashes for `read` and `write` don't change.
- **The method.** `export` (`ryucad export <part> --out FILE [--rev REV] [--schema ap242|ap214] [--unit mm|m] [--time-stamp T]`; `crate::export`) answers the file as bytes after the response line (`binary: {encoding: "step", length}`), and the CLI writes `--out` atomically, its file name in the header. `rev` is `working` (the default), a Git revision (through `Session::at`), or `label:<L>`, the part's release as an instance would place it (`Session::node`, which looks the label up even when no instance places it). The answer gives each product written (`product`, `name`, `part`, `rev`, `bodies`, `children`, `revision` at a label) and the `commit` read.
- **Products.** A part is one product of its solids as shown, in model order (consumed solids aren't); an assembly a product placing each instance's product at its solved pose and each instance pattern's copies at theirs, subassemblies products of their own; a part at two revisions is two products. A product's id is its PDM `number`, else the one product its import features (or, for an assembly, its imported instances) all name, else its part ID; its name the `name` property, else that product's name, else the ID; its description the `description` property; its revision the label it is read at. A usage's id is its instance's `import.usage` where an import made it, else the instance's ID (a copy's `<pattern>:<i>`). An imported assembly's instance of its own bodies (an import with no usage, at the origin) writes those bodies as the assembly's own. So a file exported as it was imported, with its header's options, is the same bytes, and `import --update` with a project's own export changes nothing but the file's hash and renames nothing.
- **Refusals and determinism.** A feature failing anywhere in what the export places is `export_failed` (`failing`: part, revision, feature, code); a face STEP can't describe is `export_unrepresentable` with its part, solid and entity. The time stamp is `--time-stamp`, else the commit's time when exporting a commit (a Git revision, or the commit where the release became official; `Repo::commit_time`), else now, in UTC to the second (`export::utc`). Exports are rebuilt from the session's results each time and never cached.
- **Testing.** `export.rs` unit tests (a part's solids, PDM names, an assembly's poses and usage ids, labels and revisions with their commits' times, failures, options, an imported assembly file exported byte for byte and updated with itself); ryustep's `tests/write.rs` (descriptions, revisions and usage ids written and read back); `tests/cli.rs`'s `exports_from_the_cli` both ways; the `exports` section of `tests/golden/rebuild.txt` (an assembly, a blended part and a swept one, AP242 in millimetres and AP214 in meters, one thread and four); `tests/step.rs` (release only): every part the corpus and the OCCT files make that builds, exported and imported again, to the same topology and volume; `ryukei-bench`'s `step` test (devcontainer, with ryucad a dev-dependency): OCCT reads parts and an assembly ryucad exports, a solid per lump and occurrence, of ryucad's volumes. `heal::seamed` reads a loop through a cone's apex across it (`across_poles`), so a countersink's lune between two rulings needs no seam (issue #146).

## STEP in the app and at scale (decided in ryucad phase 6)

The design is document 120 in the Coxswain planning project `ryucad-ryukei`; this is its plan 6.D.

- **The app.** File > Import STEP… and Update import… (enabled when the tree's chosen feature is an import, for its file) open a dialog: a `STEP file` typed or found with Browse… (rfd, once the frame is done), its dry run's plan as lines (`core::step::Plan`: parts and assemblies made or changed, each import's body with its counts and heal counts or why it fails, an update's features that would fail and products gone, warnings), then the same `import` an agent sends, one undoable change. File > Export… (plan 8.D; see `ryucad-formats.md`) exports the shown part in any format, STEP with its schema and unit, the daemon writing the file. Answers reach only the dialog for their file. An import feature's row reads `body (import: bracket.step / BRK-100)`, and the property panel shows its file, BLAKE3, product, body and heal counts, read only. The rebuild report gives every import feature `import: {file, blake3, body, product?}`, failing or not, and its heal counts when it built. The panel says `none raised` for a tolerance healing didn't raise.
- **Side by side.** `import::plan::apply` and undo (`ryu_session::activity`'s revert) write their files in parallel (each `write_atomic` waits on a sync), deletions after. `assembly::Rebuild::build_parts` builds the parts an assembly places (and `Session::rebuild_parts`'s) in parallel before walking them; an export reads every node from one rebuild (`Session::nodes`). `import::usage_warnings` indexes each file's products and usages once.
- **Shared contents.** `ryu_session::fresh::Files` holds `Arc<[u8]>` (`Bytes`), so snapshots, dry runs and frozen sessions share the stamps' bytes; `ryu_doc::source::Source::read_shared` loads imported files without copying them. The activity log counts each distinct content once, files in the product's bulky folders (`Product::BULKY`, ryucad's `imports/`) against `MAX_BULKY_BYTES` (1 GiB), the rest against `MAX_BYTES` (64 MiB).
- **The bars.** `tests/step_bar.rs` (release only, its own CI step): the race's bodies (`ryukei_testkit::race`, which `ryukei-bench`'s race uses too), each its own product, placed three times on a 40 × 40 grid 10 m apart (ryukei-bench's race along x leaves the size box), the two that don't come back through STEP left out: 1,598 parts, 125.8 MB of AP242 in millimetres. On cox-worker-2 (8 cores, AMD Ryzen 7 9700X): over six runs on a worker other sessions shared, ryustep read it in 37 to 55 s and wrote it in 18 to 22 s; a daemon started cold over an empty disk cache rebuilt the root in 1.01 to 1.25 times the read (bar 1.25; one run while the worker was busiest took 1.41 and failed), one over the warm cache answered in 0.89 to 1.7 s (bar 2 s), and `ryucad export` took 0.94 to 1.11 times the write (bar 1.25). The cold bar has little margin on a shared machine: record it on a quiet one. With `RYUCAD_BARS=1` asserted as they are, else ten times looser. `cargo bench -p ryucad --bench step`: importing `nist_ctc_01` into a new project 84 ms, re-importing it unchanged 0.6 ms, exporting it 8.8 ms.
- **Testing.** Unit tests (`core::step`, the panel's rows, the form, `import::written`, `plan::apply`, `build_parts`, the log's budgets, shared snapshots, `race`); the app's `tests/step.rs` against a real daemon and window tests for both menus; the `imports` section of `tests/golden/rebuild.txt` (OCCT's files imported, every import's body and the assembly's placements, one thread and four); the `feature` fuzz target's parts import `s1` of eight race bodies ryustep wrote (`imports/seeded.step`), which fuzzed imports select from, and the `merge` target reads `0xfe` as an import feature and `0xff` as an imported instance (two re-imports conflict at `/file`).

## The STEP bug finder (decided in ryucad phase 12)

The design is document 277 in the Coxswain planning project `ryucad-ryukei`; this is its plan 12.A.

- **What it is.** `crates/step-hunt` (never released) splits the sources in `crates/step-hunt/sources.txt` into cases: every body of every file as its own canonical STEP file (the representation's closure, renumbered breadth first, a fixed header), identical bodies one case by BLAKE3, and files whole where a source says `whole` or a file can't be split. Each case runs through a `ryucad` binary given by path, as an agent does: `import`, `check`, `export`, `reimport` (the same counts), `volume` (within both bounds), `fixpoint` (exported in meters, imported and exported again: the same bytes), and for a whole file `whole_import`, `whole_export` of each root that built, `whole_reimport`. Every command is a process of its own, in process (`RYUCAD_NO_DAEMON`), on one rayon thread, with private folders, killed at `--timeout` (900 s). It links no ryucad, so it runs on any branch's build or a release.
- **Findings.** A failure is signed `<stage>/<code>[/<reason>][/<kinds>]`: the kinds are the STEP surface or curve entities the instances an `import_failed` names lie on. A round trip that differs is `<stage>/<what>`, a crash `<stage>/crash/<exit>`, a timeout or a stage over `--slow` (30 s) `<stage>/timeout|slow/<faces>/<surfaces>`. A failed import is tried once more under another part ID (`key_dependent`). Signatures group mechanically; which group is one root cause is the filer's call, and the tool files nothing.
- **The ledger.** `crates/step-hunt/known.txt` judges each finding by case and signature: `#<issue>`, `file` (the file is wrong) or `limit` (a limit the kernel keeps on purpose). A run's report says `new`, known, or `fixed` (a line whose case now passes; never for a case that timed out). Slow and timeout findings are `timed`: reported, never judged by a test.
- **Running it.** From the workspace: `cargo build --release -p step-hunt -p ryucad`, then `target/release/step-hunt run --ryucad target/release/ryucad --out <dir> [--source NAME]… [--jobs N] [--timeout S]`; `step-hunt rerun <dir>/report.json …` runs only what failed (a fix checked, or `main` against `release/0.7`); `step-hunt extract <case> --out body.step` makes one case's file again from the pinned sources, which is how an issue's reproducer is given without publishing third parties' bytes; `step-hunt report <dir>` writes the report of a stopped run, `--resume` goes on with it. Pinned sources need `scripts/fetch-corpus.sh` and `scripts/fetch-kicad.sh` first. Campaigns run niced on a named worker nobody is building on, never cox-worker-2.
- **Testing.** Unit tests per module; `tests/hunt.rs` against `fake-ryucad` (each stage's failure, a crash, a hang, both mismatches, a rerun) and, in release, the committed corpus through the real `ryucad` (no `new` and no `fixed` finding but timed ones) and one job against four; `tests/split.rs` (release) every committed body split out heals as in its file. `full.yml`'s `release-suites` runs both on Linux x64: about 31 minutes on cox-worker-1 (Intel Xeon E5-2650, 8 threads given; hunt 1,357 s, split 490 s, release build already made) when executed.
- **The committed corpus.** 53 cases (28 bodies, 25 files whole); its findings are the ledger's: two NIST PMI sheets (`limit`, phase 9), OCCT's folding `offset_sheet` (`file`), and #285, `nist_ftc_10` not healing from its own export under its product's part ID. Timed: `nist_ctc_05`'s `check` over 600 s on one thread, `mass` 30 to 75 s on one thread for small curved bodies (12.B files what a quiet worker confirms).
