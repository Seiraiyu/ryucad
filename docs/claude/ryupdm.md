## PDM data model (decided in ryupdm phase 0)

The design is document 44 in the Coxswain planning project `ryucad-ryukei`. ryupdm phase 1 built it, with the refinements in Local PDM below.

- **Identity.** A part is (project ID, part ID): the project ID is 128 random bits in `ryucad.json` (`project`, manifest format 2), kept across moves and forks (since phase 5 `pdm new-id` gives a fork an ID of its own: see Multi-repo below); the part ID is the folder ID, which never changes. A part number is a property, never identity. A deleted part's ID stays reserved while any release record names it (`part_id_retired`).
- **Files.** `ryupdm.json` at the root (kind `ryupdm.config`: `revisions` scheme, `release_branch`, `part_number.pattern`, custom property schema) and `parts/<part>/properties.json` (kind `ryupdm.properties`): core properties `number`, `name`, `description`, `material`, `uom`, `make_buy`, plus declared custom ones with a `type`, `required` and `revising` (default true). Undeclared keys, bad values and duplicate numbers are per-part faults; a part with one still rebuilds but can't be released.
- **Revisions.** Per part, labelled by the project's scheme (`letters` per ASME Y14.35, `numeric`, `numeric2`), never typed. States: released and obsolete are recorded, superseded and `modified` are derived; work in progress is just commits. Editing a released part is work towards the next revision.
- **Release records.** `releases/<part>/<label>.json` (and `<label>.obsolete.json`), append-only, naming the content hash, the revising properties' values, the rebuilt body hashes and the build, never a commit. A record can be written on any branch and is official from the first commit on the release branch's first-parent chain whose tree holds it (`origin/<branch>` if it exists, else the local branch). Tags `ryupdm/<part>/<label>` are derived from records; `release sync` makes and repairs them locally, ryucad's only Git write. Signing is left to Git.
- **Content hash.** BLAKE3 (64 hex) over length-prefixed pieces: `ryupdm.content.1`, the manifest's `default_unit`, `part.json`, each listed feature's ID and bytes, then `parameters.json` if present, then (since ryucad plan 10.E) the tag `ryucad.project_parameters` and each project parameter the part reads or shadows (one of its own parameters' names), by name, with its text, only when there is any, so the hashes of parts reading none don't change, and a change to one a part reads makes its release `modified`. A part reading a name it lacks while the project's file doesn't read has no hash. It excludes the rest of the manifest, `properties.json` and `ryupdm.json`, so none of those make a released part look modified.
- **Repo and service.** The repo is the source of truth for releases and (phase 4) approvals; the service keeps review state, comments, its audit log and rebuildable indexes. Derived data, release packages included, is a content-addressed cache, never Git or LFS.
- **Code.** A `ryupdm` crate over a new `ryucad-doc` crate (ryucad's file format split out of `ryucad`); `ryucad` depends on both and exposes PDM as `proto` methods and CLI commands. ryupdm never calls the kernel, daemon or app.

## Local PDM (decided in ryupdm phase 1)

The design is document 57 in the Coxswain planning project `ryucad-ryukei`; its plans are 1.A to 1.E. It builds design 44's model, offline, in a plain clone: only `release sync` writes to Git (local tags), and nothing commits, stages, pushes or fetches. Since phase 5 `deps add`, `deps fetch` and `deps update` fetch other projects' repositories, and nothing else does (see Multi-repo below).

- **Crates.** `ryucad-doc` holds the file format (`doc`, `units`, `expr`, `error`; `error::Code` stays one enum for all three crates). `ryupdm` holds `config`, `props`, `label`, `record`, `content`, `history`, `state`, `check` and `merge` over `ryucad-doc` and `gix`, and never calls the kernel, a session, the daemon or the app: its library API (every function takes a `Source`, and where history matters a `gix::Repository` and the project's place in it) is what the service will link, follows the workspace's version, and is tested against a bare repository (`tests/api.rs`). ryucad exposes it as `proto` methods and CLI commands (`pdm`, `props`, `release`), each write one logged, undoable change guarded by a revision.
- **Settings and properties.** `ryupdm.json`: `revisions` (`letters`, `numeric`, `numeric2`; locked once a record exists, `revision_scheme_locked`), `release_branch`, `part_number.pattern` (`regex-lite`, anchored, ASCII classes), and declared properties (`string`, `text`, `integer`, `number`, `quantity` with one of ryucad's dimension names, `boolean`, `enum`; `required`; `revising`, true by default). `properties.json` is a defining file of its part (it counts in the part revision); the project revision covers the manifest and `ryupdm.json`. Faults (`property_unknown`, `property_invalid`, `part_number_invalid`, `part_number_duplicate`) are found on load and are doctor errors, so `check` fails on them; a write is refused when the project, judged whole after it, has a fault it hasn't now (`pdm.configure` takes `force`). `props.set` reads text as the declared type. The first PDM write gives the project its ID (manifest format 2); `pdm.init` is idempotent; a part ID a record names is `part_id_retired`; doctor's `project_id_missing` writes the ID a record names, else one derived from the folder.
- **Labels and records.** `letters` is bijective base 20 over ASME Y14.35's letters (A to Y, then AA), `numeric` 1, 2, 3, `numeric2` 01 to 99 then 100; each reads only labels it writes, at most 12 characters. Records are design 44's, format 1; `approvals` and `attestations` are reserved for a later format, which this build reads as `format_too_new` and a state of `unknown`; phase 4 put approvals in release tags instead (see Approvals below). A part is its release when its content hash and every property revising under the current settings equal the record's.
- **Propose and obsolete.** `release.propose` refuses in order: `not_a_git_repo`, `not_found`, `conflict`, an unreadable record's own error, `release_pending`, `release_not_ready` (every load, rebuild and property fault and missing required property, in `problems`), `nothing_to_release` (only while released); `dry_run` (CLI `--dry-run`) writes nothing and answers the label and `problems`. `released_by` is Git's author identity and the participant. `release.obsolete` takes only the latest official label, refuses while anything is proposed, and works on a deleted part, which may be released again after.
- **History and states.** The release branch is `origin/<branch>` if it exists, else the local branch. One first-parent walk compares `releases` tree IDs; a record is official from the oldest commit of the unbroken run that ends at the tip and holds it, and a later change is `release_modified`; a shallow clone stops at its boundary (`shallow`). The branch as read is cached by its tip and every `ryupdm/` tag. States: `in_work`, `released`, `modified`, `obsolete`, `unknown`, each with any proposal; outside a repository nothing is official.
- **Tags.** `release.sync` creates `ryupdm/<part>/<label>` at each official release's commit and moves tags that point elsewhere (gix ref edits, `MustNotExist`/`MustExist`); it never pushes or deletes (an orphan is a finding) and is logged as a `refs` activity entry, not undoable. Since phase 4 it leaves records under approval rules to the service (see Approvals below).
- **Checks.** `release.check` and `ryucad check` report design 44's codes plus `release_tag_orphaned`, as `schema: 1` findings `{code, severity, source, part?, label?, message, details?}` (adding a field or code isn't a new schema). `release_result_changed` rebuilds only with `--results`, cached by content hash; `check <part>` keeps that part's; `release_project_mismatch` waits while the manifest has no ID.
- **Commit guard.** The hook line is unchanged. On every commit it reads the index, `HEAD` and the release branch's tip, rebuilding nothing: `release_stale` for a proposal that doesn't describe its staged part, `release_sequence` and `release_project_mismatch` for staged records, `release_modified` for an official record changed or deleted. Withdrawing a proposal (deleting its record) is allowed.
- **Merges.** `merge.status`'s `pdm_broke` lists PDM faults the merged files have that neither side had (duplicate numbers, values the merged settings refuse, proposals made stale or out of sequence), keyed by code, part and property or label, and blamed on the side that changed what the faulty file depends on (not counting a side holding it as merged). IDs are `<file>#pdm_broke/<code>[/<property>]`; a property's takes `merge resolve --value`, a proposal's the repair `withdraw`. Settings a merge left conflicted judge nothing.
- **Diff and textconv.** `diff` gives a part whose PDM differs a `pdm` block: `properties` (`{from, to, revising}`), `records` (`added`, `removed`, `changed`, each `{label, kind}`) and `state` (`{from, to}`, both read against the release branch as it is now); `ryupdm.json` changes are top-level `pdm.changes` by pointer, compared with defaults filled in. textconv gives each declared property one line and a record's author one line, its `results` last.
- **Events.** `pdm.changed` (topic `pdm`) carries `{parts: [{part, state, tags}]}` for parts whose state or tags moved, computed only while someone subscribes.
- **App.** Each part's line shows its state (`p (B modified, C proposed)`), and in a compare the records it adds (`[proposes C]`) and its PDM lines under Changes. The Part section (under the parameters, for the chosen feature's part) edits every property with a control for its type through `props.set`, reloading on a conflict, and offers Set up PDM. The Releases tab (beside History) lists records and findings, and proposes (after a dry run), obsoletes and syncs tags, each confirmed. `pdm_broke` shows in the conflict panel with its titles and hints.
- **Testing and limits.** Unit tests per module, `ryupdm`'s bare-repository API test, Git scenarios in `ryucad/tests/merge.rs` (the guard, the hooks, `pdm_broke`), CLI scenarios both ways, the app's `tests/pdm.rs`, `tests/compare.rs` and window tests, the `pdm` section of `tests/golden/rebuild.txt`, the `pdm` fuzz target and the `merge` target's properties and record modes. Limits: two branches that each make a project's first PDM write give it two IDs (the manifest conflicts at `/project`); `merge resolve --expect` is ignored for a record's conflict; quantity properties have length and angle dimensions only.

## Structure and BOMs (decided in ryupdm phase 3)

The design is document 180 in the Coxswain planning project `ryucad-ryukei`; these are its phases 1 to 3, plan 3.A.

- **Structure.** `ryupdm::structure` reads what an assembly places from files alone: nothing is rebuilt, so a BOM answers in milliseconds and on a model whose features fail. `Reader::node` reads a part at a revision with its properties: at `working` from the files it is given, at a label from the commit where its record became official (only that part's files and the project's root files, `history::part_files`). Nodes read at commits are kept by commit and part (`structure::Cache`, which the session keeps as `Session::structure` and copies into frozen sessions), and the release records are read once per reader, at its first label. The label rule moved here from ryucad: `structure::lookup` reads the record (`label_not_found` without one), then `structure::pin` gives the official commit, else the working files while the proposed record describes them. ryucad's rebuild (`release::pinned`) calls both, so the rebuild and the BOM resolve a label alike. `occurrences` lists each instance, then each instance pattern's copies of each seed (`<pattern>:<i>/<seed>`), leaving out the seed's own place and skipped copies; a feature that can't be read is a problem naming it.
- **Amount.** `amount` is a new core property: how much of the part's `uom` one occurrence uses, so a quantity is occurrences × amount, and no instance file changes. `properties.json` format 2 holds it (`props::FORMAT`); a file without one stays at 1. It is a core `string`, revising, not required. `props::amount` reads it against `uom`: a positive number, bare in the unit of measure or in a unit from a fixed table (`m`: `m, cm, mm, um, in, ft`; `m2`: `m2, cm2, mm2, in2, ft2`; `m3`: `m3, l, ml, cm3, mm3, in3, ft3`; `l`: `l, ml, m3, cm3, mm3`; `kg`: `kg, g, lb`), snapped to its shortest decimal (`600 mm` is 0.6 m). ryucad's quantities aren't used: they read only lengths and angles. An amount on a part counted `each`, or in a unit its `uom` doesn't take, is `property_invalid`; `props::missing` asks for one before a release when `uom` isn't `each`.
- **BOMs.** `bom::tree` is the indented BOM: each assembly's children by part and revision, with how many their parent places and the instances and copies that place them, to `depth` levels (`truncated` below). `bom::flat` is every leaf by part and revision with its total, sorted by part number (parts without one last), then part, then revision in the scheme's label order (`rev_order`: `9` before `10`, `B` before `AA`). A leaf is a part, or an assembly bought whole (`make_buy: buy`): the indented BOM lists its children marked `bought`, and the flat BOM doesn't sum them. A quantity is `{count, uom, value?, text?}`. A BOM fails only for its root. A child that can't be read is a row with its `problem`: `not_found`, `instance_not_released` (an instance at `working` inside a part read at a label, which the rebuild refuses too), `assembly_cycle` (a child that closes a cycle), or its record's error. `bom::problems` lists them with each assembly's unreadable features.
- **Diff.** `bom::diff` compares two whole BOMs, either of which may be missing. Flat rows pair by part (equal revisions first, then the rest in the scheme's label order) and are `added`, `removed` or `changed`: revision, quantity, item numbers, and properties, each marked `revising` by the settings. `tree` holds each assembly both sides have whose children changed, `assemblies` those only one side has, and `summary` the counts. A BOM against itself is empty.
- **Where-used.** `where_used::where_used` gives `working`, each assembly the files have as they are whose structure reaches the part, and `released`, each official release of an assembly that does, read at its commit, with its label, its state (`released`, `superseded` by a later official one, or `obsolete`) and the commit. Each has `count` and `uses`: `via` (the parts from the assembly down to the one placing it), the revision placed, and how many. A `Query` takes one revision (a label, or `working`) and `direct` (only assemblies that place it themselves). Releases that can't be read are `problems`; with no release branch read, `released_note` says none was searched.
- **Protocol and CLI.** `bom.get` (`ryucad bom [part] [--rev REV] [--flat] [--depth N] [--format json|csv] [--out FILE]`), `bom.diff` (`ryucad bom diff [part] [--from REV] [--to REV]`, `HEAD` and `working` by default) and `bom.where_used` (`ryucad where-used <part> [--label L | --working] [--direct]`) read through `crate::bom`, over the session's files or a revision's (`Session::at`), with labels against the release branch as read (none outside a repository). A revision may be `label:<L>`, the part's release `L`. With no part, a BOM is of the project's one root assembly (one no instance places); several or none is `invalid_param` with `roots`. Each answers `"schema": 1` (`bom::SCHEMA`, under design 65's rule): `bom.get` `{schema, root, rev, commit?, tree | flat, csv?, columns, problems, findings}`, a row `{part, rev, kind, make_buy, uom, properties, quantity, instances, item?, state?, commit?, obsolete?, bought?, problem?, children?, truncated?, problems?}` (a flat row has `items` for `item`, and no `instances`, `children`, `truncated` or `problems`); `bom.diff` `{schema, root, from: {rev, commit}, to, summary, flat, tree, assemblies}`; `bom.where_used` `{schema, part, rev?, direct?, working, released, problems, released_note?}`. `ryucad bom` takes its subcommands before its arguments (`args_conflicts_with_subcommands`), so `bom diff` is always the diff; `--out` implies CSV.
- **CSV.** RFC 4180 (a field holding a comma, a quote or a line break is quoted, quotes doubled). The columns are `level, item, number, name, part, revision, quantity, uom, make_buy, material, description`, then each declared custom property in the settings' order (`bom::columns`, which `bom.get` answers whatever the format). Item numbers fill `level` and `item` (see Item numbers below). A BOM holding another project's rows adds a last column, `project` (see Multi-repo below).
- **Check.** `check` reads every part's BOM in the working files and adds each finding once, as `source: bom`: `bom_amount_missing` (a warning: a part counted in anything but `each` with no `amount`), `bom_mixed_revisions` (a warning: an assembly placing one part at two revisions) and the item numbers' faults (see Item numbers below). `check <part>` keeps those naming that part.
- **Testing.** Unit tests per module; `tests/structure_props.rs` (seeded projects from `ryucad_doc::doc::fixtures::structure`: flat totals are the sums along every path, a diff lists exactly the rows that differ, where-used counts what the flat BOM counts); `tests/api.rs` against a bare repository (BOMs and where-used at commits and labels); CLI scenarios both ways; BOMs of an imported STEP assembly; the `boms` section of `tests/golden/rebuild.txt` (64 seeded projects: JSON, CSV both ways, where-used); the `structure` fuzz target, and `amount` in the `pdm` target.
- **The bars.** Timed on the methods, not through `server::handle`, whose freshness check over the 2,021 files of `tests/bar_project` costs more than the BOM. ryucad's `tests/assembly_bar.rs` gives the flat BOM of 1,001 occurrences in 6.8 ms and a pin's where-used in 6.1 ms (bars 50 ms each). ryupdm's `tests/api.rs` (release only, in full.yml) gives where-used over 100 released assemblies in 135 ms cold and 3.9 ms read again (bars 1 s and 10 ms). Recorded on an Intel Xeon E5-2650 (8 cores); with `RYUCAD_BARS=1` the bars are asserted as they are, else ten times looser.

## Item numbers (decided in ryupdm phase 3)

The design is document 180 in the Coxswain planning project `ryucad-ryukei`; this is its plan 3.B.

- **Files.** An assembly's `part.json` keeps its item numbers (find numbers) as `items`, by placed part ID (another project's part by `<project ID>:<part>`, part format 4, since phase 5: see Multi-repo below), each a whole number from 1 to 99,999 (`files::MAX_ITEM`); part format 3 holds them (`part_format` gives 3 only with `items`), so an assembly without them stays at 2 and an older build refuses one with them as `format_too_new`. A part (not an assembly) with `items` doesn't read. Numbers are labels, not identities: two parts sharing one, or a placed part without one, still read, and are the BOM's faults. `part.json` is in the content hash, so a release pins its numbers.
- **Assigned by writes.** `ryupdm::items::assigned`: a write (`server::save`, so `feature.add`, `edit`, `delete`, `move` and everything else that saves a part, and `import` and `import --update` through `import::writes`) that makes an assembly place a part it didn't gives that part the next number, one past the largest (past 99,999 the smallest free), counted before anything leaves, so a part replacing another in one write never takes its number; a part it no longer places loses its entry, unless a listed feature doesn't read (it may still place the part); nothing else moves. Instance patterns copy instances and assign nothing. Doctor's list repairs (`missing_part_index`, `listed_feature_missing`, `orphan_feature`) keep the numbers.
- **Renumbering.** `bom.renumber` (`ryucad bom renumber <asm> <part>=<n>… [--expect REV]`, or `--compact` alone) sets numbers together (so two may swap), refusing a part the assembly doesn't place (`not_found`), a number out of range (`invalid_param`) and a number a set part would share (`bom_item_duplicate`); `--compact` numbers the placed parts 1 to n by their current numbers, unnumbered ones after in list order, and drops the rest. A part is `wrong_part_kind`. One logged, undoable change guarded by the assembly's revision; it answers `{part, revision, items}`.
- **Faults.** `ryupdm::items::faults`: `bom_item_missing` (warning; the placed parts without one), `bom_item_duplicate` (error; one per shared number, its parts in list order) and `bom_item_unused` (warning; judged only when every listed feature reads), each a new `error::Code`. `doctor` reports them on `parts/<asm>/part.json` with the repairs `assign_items`, `renumber_items` (the later part in list order takes the next number) and `remove`. `bom.get` and `check` give them as `source: bom` findings for assemblies read at `working` (a release's numbers are what it released), and `check` leaves out doctor's copies. `release.propose` of an assembly lists missing and shared numbers among `release_not_ready`'s problems; unused ones don't block.
- **BOMs.** A tree row has its parent's number for its part (`item`); a flat row its number in each assembly that places it (`items`: `{assembly, rev, item}`, as first met); CSV's `item` is the row's number (a flat row's distinct numbers joined by `;`), and an indented row's `level` is the path of item numbers (`1.20.5`), its place among its siblings where it has none. `bom diff` gives a changed number as `item` (tree) or `items` (flat), `{from, to}`. Rows' revisions sort and pair in the scheme's label order (`9` before `10`, `B` before `AA`; `bom::rev_order`), not as text.
- **Git.** Textconv gives each item a line after the features, in number order (`item 3 = bolt`). `diff` gives a part whose either side has items an `items` block (`added`, `removed`, `changed` by part ID). The merge driver merges `items` per part, as `part.json`'s other keys; one part numbered differently on each side is a `value` conflict at `/items/<part>`. Two parts each side numbered alike merge cleanly and `merge.status` lists `item_collision` (`parts/<asm>/part.json#item_collision/<n>`, `validate::KINDS`), blamed on both, with the repair `renumber`: theirs' part (the one theirs numbered so and ours didn't) takes the next free number; every collision's repair writes the file with all of that assembly's collisions settled, so they agree. Feature IDs renumbered by `id_collision` don't touch items, which are keyed by part; part IDs are never renumbered.
- **Testing.** `ryupdm::items` unit tests (assignment, faults, repairs, renumbering, collisions), `bom` tests (items in JSON, CSV and diffs, findings), `structure_props`' `every_placed_part_has_its_item_number_in_the_bom` (the seeded fixtures number their parts), ryucad tests of writes and undo, imports and re-imports, doctor's repairs, release readiness, textconv and diff, the merge rule and `item_collision` (`validate`, and through Git in `tests/merge.rs`), `boms_from_the_cli` both ways, the `boms` golden section, and the `merge` fuzz target's list mode, which now edits items. The `structure` fuzz target checks flat totals against the generator's sums (`fixtures::Structure::totals`).

## The app's BOM tab and where-used (decided in ryupdm phase 3)

The design is document 180 in the Coxswain planning project `ryucad-ryukei`; this is its plan 3.C.

- **The tab.** A BOM tab beside Activity, History and Releases shows the BOM of the window's focus, else the project's one root assembly (`bom.get` with no part); several roots are offered as Show buttons that set the focus. Indented, or flat with the Flat box; its columns are the CSV's, which `bom.get` now answers as `columns` (`ryupdm::bom::columns`: the core columns, then declared properties in the settings' order), so the table and the file never disagree. Findings sit above the table, each line's problem beside it, lines inside a bought assembly weak. It is read once opened, and again on `model.changed` for any part it reads (or a removed part), `project.changed`, `pdm.changed`, a focus or compare change and a reconnect, one reading on its way at a time; the flat BOM follows the indented one, whose lines give it its occurrences.
- **Choosing a line.** A line knows its occurrences: its instances under every occurrence of its parent (`<root>/<instance>/…`, a pattern's copies as `<pattern>:<i>/<seed>`); a flat line those of every indented line of its part and revision. Choosing it makes them the window's selection (`selection.set`) and frames them.
- **Item numbers.** An indented line whose parent is read at `working` has its number as a button; pressed, it is typed and set with `bom.renumber` (that part only) against the revision of the parent the window last saw. A number outside 1 to 99,999 is refused in the window with the text kept; a `conflict` reads the BOM again and says `Someone changed <asm>'s item numbers while you edited: <part> is now <n> (you typed <m>)`. Lines under a label, and flat lines, aren't editable (a release's numbers are what it released).
- **Export CSV.** Export CSV… writes the BOM as the tab shows it, indented or flat, from `bom.get`'s `csv`, atomically where Save as says (Browse… opens the OS's dialog with a CSV filter): the bytes `ryucad bom --out` writes.
- **Where used.** The Part section's part (the chosen feature's, else the first) has a Where used section under its properties (`bom.where_used`): each working assembly that reaches it with how many one holds and each path on hover, a Show button setting the focus, then each official release of an assembly that does with its label and state, or why none was searched. It is read again on `model.changed`, `project.changed` and `pdm.changed`.
- **Compare.** While the window compares, the tab reads `bom.diff` from the compared revision to the working files after each reading and says `Compared with <rev>: n added, n removed, n changed`: lines its parent's children added (and what an added assembly places) in the new colour, chosen and numbered like any other line, changed cells as `<new> (was <old>)` in the changed colour (an item number stays a button), and lines removed listed in the removed colour after their parent's last line (in the flat BOM, last).
- **Tiles.** What the tab and the section know is `core::bom` (`BomTab`, `BomExport`) and `core::where_used`, apart from egui; `ui::bom::{tab, where_used, export}` each draw in the `Ui` they are given, and every action is a `Workspace` method (`load_bom`, `set_bom_flat`, `save_item`, `open_bom_export`, `run_bom_export`, `show_where_used`), so ryucad 11's tiles and commands can host them unchanged.
- **Testing.** `core::bom` and `core::where_used` unit tests (lines, levels and cells, occurrences, flat lines, editing, conflicts, roots, marks), `Model::occurrence_bodies`, ryucad's `a_bom_names_the_csvs_columns_declared_properties_last`, the app's `tests/bom.rs` against real daemons (following changes, roots and focus, renumbering and a stale save, the CSV against the CLI's, where-used, a compare) and window tests for the tab (choosing a line, renumbering, flat) and for where-used and a compare.

## Approvals (decided in ryupdm phase 4)

The design is document 261 in the Coxswain planning project `ryucad-ryukei`; these are its phases 1 to 3, plan 4.A. The service's side is Approvals on pull requests in `ryupdm-review.md`. Approvals live in the annotated release tag the service signs, not in records, which stay at format 1: design 261's deviation from designs 44 and 57, since the service never pushes to a PR's head or a base.

- **Rules.** `approvals` in `ryupdm.json` (`ryupdm::approvals`): `rules`, a non-empty ordered list of `{parts, count, from}` (`parts` globs over part IDs, `*` and `?` only; `count` from 1 to the length of `from`, or to 100 when `from` names a team; `from` unique GitHub logins and, since phase 6, teams, compared without regard to case), and `keys`, key IDs (16 hex, the start of the BLAKE3 of the key's 32 bytes, `attest::key_id`) to Ed25519 public keys (64 hex), trusted besides the hosted ones. Every rule whose `parts` match a part applies, and each must be met: at least `count` distinct logins of its `from` approved, never the proposer; one approval counts towards every rule naming it. A part no rule matches needs nothing, and a file with no `approvals` requires nothing. Rules apply to release and obsolete records alike. `ryupdm.config` format 2 holds `approvals`, and since phase 5 `dependencies.bump` (format 3 when `approvals` names a team or a revoked key, phase 6); a file without either is written at 1, and `approvals` in a format 1 file is `invalid_document` at `/approvals`. Other faults are `approval_rule_invalid` at the field's pointer (`/approvals/rules/1/count`); since phase 6 a rule may name a team (`@org/team`), and an entry of `keys` may be a revoked key (see Teams and revoked keys below). Doctor reports them as `invalid_document` on `ryupdm.json`, an error, so `check` fails, and a write that adds one is refused.
- **Which file counts.** A proposal is judged by `ryupdm.json` at the release branch's tip; an official record by the file at its official commit's first parent (`rules_at`), the release branch as it stood when the record arrived, so a PR that loosens the rules is judged by the old ones.
- **Judging.** `approvals::judge(rules, reviews, proposer)` gives `{met, counted, missing, blockers}` (and since phase 6 `via` and `unreadable`; it is `judge_with` knowing no team): a login's last review stands, the proposer's never count, and a change request from a login a rule names blocks until it is replaced. It is the one ryupdm rule the service links, so its verdict on a PR and a clone's verification of the tag agree by construction.
- **Attestations.** `ryupdm::attest`: `ryupdm.attestation` format 1 (format 2, phase 6, adds an approval's `via` and is written only when one has it), canonical JSON of `{approvals: [{at, commit, github: {id, login}, review, via?}], commit, format, kind, label, missing?, outcome, part, project, proposed_by, pull?, record, record_kind, rules, rules_at, signed_at}`. `record` is the BLAKE3 of the record's bytes at the official commit; `outcome` is `approved`, or `unapproved` with `missing` (each unmet rule and how many more it needed), and a direct push has no `pull`. The tag `ryupdm/<part>/<label>` (`….obsolete` for an obsolete record, which has a tag only under rules) is annotated, its tagger `ryupdm[bot]`, its message the canonical JSON, then `-----BEGIN RYUPDM SIGNATURE-----`, `{"ed25519": "<128 hex>", "key": "<16 hex>"}` and `-----END RYUPDM SIGNATURE-----`. The signature is Ed25519 (`ed25519-dalek` 2, pure Rust) over `ryupdm.attestation.1\0` and the canonical bytes, so the same attestation and key give the same tag. Messages are read up to 64 KiB (`attest::MAX_MESSAGE`). Signing (`attest::sign`) is built only under `ryupdm`'s `testing` feature (its key is `TEST_SEED`) and in the service; `examples/keygen.rs` made the hosted key, the seed to stdout for `gh secret set` and the `HOSTED_KEYS` line to stderr, nothing on disk.
- **Keys.** `attest::HOSTED_KEYS` holds the hosted service's public keys and never loses one, since old tags must still verify; a new key needs a ryucad release before the service signs with it. A tag is judged against those and `approvals.keys` at `rules_at` (`attest::trusted`), so a key added later can't vouch for older tags.
- **Verification.** `ryupdm::history` reads each ryupdm tag's object as well as its target, and gives each official record under rules an `Approval {rules, rules_at, verdict}`. `attest::verify_message` judges the message against what the clone reads (`Expect`: project, part, label, record kind, official commit, the record's hash there, the rules, `rules_at`, the trusted keys and the revoked ones): `Approved`, `Unapproved`, `Invalid(Clause)`, `Missing`, or since phase 6 `Revoked` and `Unknown`. A clause is `lightweight`, `no_attestation`, `too_large`, `unreadable`, `unknown_key`, `bad_signature`, a field that doesn't match (`project`, `part`, `label`, `record_kind`, `commit`, `record`, `rules`, `rules_at`), `not_met`, `proposer_approved` or (phase 6) `via`. A tag at another commit is `release_tag_moved` as before, and its attestation isn't judged. Verdicts are memoised by the tag object, the record's path, bytes and official commit, and the keys revoked at the tip, and the session's release cache follows tag objects. Nothing is fetched, and states don't change: an unapproved or invalid release is still official, and its finding is the mark.
- **Findings.** `release check` and `ryucad check` (`source: release`) add `release_unapproved` (error, with `approvers` and `missing`), `release_attestation_invalid` (error, its `clause` in `details`; for a lightweight tag the message says an older ryucad's `release sync` may have made it and how to replace it) and `release_attestation_missing` (warning: not fetched, or not tagged yet, with `git fetch origin 'refs/tags/ryupdm/*:refs/tags/ryupdm/*'`, `check::FETCH_TAGS`). Each names `tag`, `official`, `rules` and `rules_at`. A record no rule covered at `rules_at` is judged as before (`release_tag_missing`, `release_tag_moved`).
- **Protocol and CLI.** `pdm.configure` takes `approvals` (`ryucad pdm configure --approvals JSON`, or `--no-approvals`), one logged, undoable change guarded by the project revision. `release list` (still `schema: 1`) gives each official record under rules `approval: {status, rules, rules_at, clause?, outcome?, approvers?: [{login, id, at, via?}], proposed_by?, key?, missing?, revoked?, format?}`, `status` being `approved`, `unapproved`, `invalid`, `missing`, `moved`, or since phase 6 `revoked` or `unknown`, and its tag `service: true`; a proposed record that rules at the tip (as this clone has it) cover gets `approval: {required: true, rules}`, which `release.propose` and `release.obsolete` answer too, refusing nothing for rules; a record no rule covers has no `approval`. `release sync` never creates or moves a tag of a record under rules, listing them as `left_to_service`. `ryucad review approvals [PR]` (`GET …/pulls/{n}/approvals`) and `ryucad review audit [--part P] [--since DATE] [--until DATE] [--format json|csv] [--out FILE]` (`GET …/audit`; `--out` implies CSV) are the service's clients. Approving is a GitHub review (`gh pr review --approve`) under the person's own token, which ryucad doesn't wrap.
- **Git.** The merge driver merges `approvals.rules` as one value and `approvals.keys` per key. Textconv gives each rule a line, numbered from 0 (`approvals.rules.0 = 2 of dave, erin, frank for motor-*, gearbox`), and each key one (`approvals.keys.<id> = <hex>`, with ` (revoked YYYY-MM-DD)` for a revoked one); `diff`'s `pdm.changes` covers them by pointer.
- **App.** The Releases tab gives each record under rules its approval: `Approved by alice, bob`, `Unapproved`, `Attestation invalid`, `Key revoked`, `Attestation too new`, `Not fetched` or `Tag moved`, with the approvers and when, the proposer and the key on hover, and a proposal `Needs 1 of alice, bob, carol`. The Part section's state line adds who approved the latest official release. Sync never touches the service's tags. The app reads only `release list`, never the service.
- **Testing.** Unit tests in `approvals` and `attest` (rules, globs, logins, teams, keys and their IDs, formats, `judge`, canonical bytes, a known-answer signature (RFC 8032's test 1), signing under `TEST_SEED` deterministic, every clause); `ryupdm/tests/api.rs`'s `approvals_verify_offline_in_any_clone` and `forged_moved_lightweight_and_unapproved_tags_are_told_apart`, on scratch repositories with tags the test key signed; ryucad's `approvals_from_the_cli` both ways, the `review approvals` and `review audit` scenarios against the fake service, and doctor, merge (`approvals_merge_rules_whole_and_keys_per_key`) and textconv tests; the `pdm` line of `tests/golden/rebuild.txt` (an attestation's bytes, its signature under the test key and four verdicts through `verify_message`, without Git, since commit hashes depend on Git's environment, so `release list` is checked by the CLI scenario instead); the `pdm` fuzz target, which reads `approvals` and tag messages; the app's `core::releases` tests and the window test `a_release_approved_by_the_services_tag_says_who_approved_it`.

## Multi-repo (decided in ryupdm phase 5)

The design is document 233 in the Coxswain planning project `ryucad-ryukei`; these are its phases 1 to 3, plans 5.A and 5.B, with the bump setting from 5.D. The app is Dependencies in the app below; the service's side is Dependencies on pull requests in `ryupdm-review.md`. A project depends on projects in other Git repositories and places their parts only at official release labels, locked to commits and read offline once fetched. Git is still the vault: no registry, no second store.

- **Files.** `ryucad.json`'s `dependencies` (`doc::deps`), by project ID: `{name, url, path}`. `name` is a part-ID-like handle, unique among them; files name a dependency by its ID only, so renaming one rewrites nothing else. `url` is one Git takes (`https`, `http`, `ssh`, `git`, `file`, `user@host:path`, an absolute path), on one line, with no password. `path` is the project's folder in the repository (`""` for its root). `forked_from: {project, commit}` is written only by `pdm new-id`. Either key makes the manifest format 3 (`files::MANIFEST_FORMAT`). A foreign instance writes `project` beside a label `rev` (`Rev::Foreign`, feature format 6); `working` there is `instance_foreign_working`. Inside a dependency's files a plain label is that dependency's own, and a label of the reading project is its own again (`Rev::seen_from`). A foreign part's item number is keyed `<project ID>:<part>` (`files::item_key`, part format 4). Files using none of these keep their formats. Faults: `dependency_invalid`, `project_id_duplicate` (the project's own ID listed as a dependency, as a fork not yet given its own lists its upstream), `dependency_missing`.
- **The lock.** `ryucad.lock` (`doc::lock`, kind `ryucad.lock`, format 1, committed), by project ID: every project the working files reach, direct or transitive, with `url` and `path` (the root's manifest wins, else the first project in `via` that names it), `release_branch`, `via` (the shortest chain from the root) and `labels` by `<part>/<label>`, each `{commit, content}`: the official commit and the record's content hash. It is a root file in the project revision, and a tagged piece of the revision of each part placing a foreign instance (other parts hash as before), never in content hashes. A write that adds or changes a foreign instance works the lock out first, from the cache alone (`deps::relock_keeping`), refusing only for the labels it adds or changes, with that label's fault (`dependency_not_fetched`, `label_not_official`, …): a label the lock already holds stays as it is when the cache can't read it, so it needs no fetch (doctor's `deps_lock` and `merge.status` use plain `deps::relock`, `deps update` `deps::relock_renewing`); every save of a part's features and `deps remove` then write it again in the same change when what the files reach moved (`deps::keep_lock`), deleting it when nothing foreign is placed. Labels the old lock holds keep their commits.
- **The cache.** `ryupdm::deps::Cache`: bare repositories in `RYUCAD_DEPS_DIR`, else `deps` in ryucad's cache folder (`ryucad::deps::cache`), which trimming never reaches, one per URL, shared by every project on the machine. A repository's folder is `<32 hex>.git`, the hex of BLAKE3 over the URL normalized (`deps::normalize`, `deps::folder`: no trailing `/` or `.git`, an `http(s)` scheme and host in lower case), and a fetch holds its lock file. A fetch takes the remote's `HEAD` (as `refs/ryucad/head`, `deps::HEAD_REF`), each asked-for project's release branch (named by its `ryupdm.json` at that `HEAD`, `main` by default) and `refs/tags/ryupdm/*`, incrementally, and pushes nothing.
- **Fetching.** `file://`, paths and SSH (the system `ssh`) use gix's own transports; `http(s)://` uses `deps::http`, a `gix-transport` client over ureq on rustls with ring, which the binary already had for `ryucad review` (gix's own HTTP backends are curl or reqwest). A read or write quiet for 60 s fails the fetch (`http::STALL`). Every fetch sets `gitoxide.credentials.terminalPrompt` false, so credentials come only from Git's credential helpers: gix otherwise asked for a username on `/dev/tty`, and a daemon or an agent on a terminal waited forever. ryucad also sets `GCM_INTERACTIVE=never` and `GIT_TERMINAL_PROMPT=0` for itself and every process it runs, unless they are set, so Git Credential Manager and helpers falling back to a terminal answer at once rather than wait on a sign-in nobody can give (#382). A failure is `dependency_fetch_failed` (exit 4) with the URL and Git's reason, never a credential; one for want of credentials says to sign in once with `git ls-remote <url>` in a terminal, which the helper keeps. Only `deps add`, `deps fetch` and `deps update` without `--offline` touch the network; the daemon fetches with its lock released (`deps::prepare`).
- **Reading.** A foreign label one of the project's own releases places (a part placed at its label) is read through the lock committed with that release when the working lock doesn't hold it, so `deps update` moving the working lock on doesn't move what a release placed (#309). `deps::read::Reader` reads a locked label at the lock's commit, under the dependency's `path`, as `Session::pinned_part` reads a local label at its commit. The record must exist (`label_not_found`), name the dependency's project ID (`dependency_project_mismatch`, as for a manifest at `path` with another ID), carry the lock's content hash, and still be official at that commit on the fetched release branch, else `dependency_rewritten`: a rewritten history is never followed silently, and `deps update` re-resolves once a person decides. A commit the cache lacks is `dependency_not_fetched`, naming the dependency and `ryucad deps fetch`. An obsolete label still places, with `instance_obsolete`.
- **Rebuild, export and release.** A foreign part rebuilds as a pinned local one does, held in the session's store by part and `Rev`. Its `OpKey`s are its own project's, so its stable names are the ones its repository builds; references reach its entities through occurrence paths, and mates connect to it. Its features share disk cache entries with any feature of the same inputs: the input hash already covers everything a result depends on, so the project ID isn't added (design 233 said it would be). Cycles are found over (project, part). Export makes it a product of its own (its PDM number, else its import's product, else `<dependency>:<part>`), its revision its label. An assembly placing foreign instances releases only when each is locked, fetched, official and not obsolete.
- **Commands.** Each a `proto` method; writes are logged, undoable and guarded by the project revision (`--expect`). `deps.add` (`ryucad deps add <url> [--path P] [--name N]`) fetches, reads the project's ID at the tip and names it from its folder or repository; a URL and path already listed, or a name already taken, is `duplicate_id`, a folder holding no project `dependency_project_mismatch`, and one holding this project's own ID, or an ID already a dependency under another URL (a fork not yet given its own ID and its upstream), `project_id_duplicate`. `deps.fetch` (`[<name>…]`) fetches the dependencies and every project the lock reaches through them, writing nothing in the project. `deps.list` gives each dependency and transitive project, fetched or not, its tip, the locked labels and the instances using them. `deps.parts` (`<name> [--part P]`) gives what a dependency has released: each part's number, name, kind and labels, latest first. `deps.update` (`[<name>…] [--part P] [--to LABEL] [--offline] [--dry-run]`) moves instances to their part's latest official, non-obsolete label, writes the lock, keeps assemblies current, and answers `moved` and `failing` (what builds now and wouldn't after), refusing nothing it can explain; a locked label whose release branch now makes it official at another commit (a rewritten history) is moved there and listed in `relocked`, `{project, dependency, part, label, from, to}`, in the dependencies it names and the projects the lock reaches through them (all, when it names none): `deps update` is the decision `dependency_rewritten` waits for (#377); `--offline` with nothing to move writes the lock again. `deps.outdated` lists every instance, the project's own included, at a label older than its part's latest (outside a repository its own labels are never outdated). `deps.remove` is `has_dependents` while anything needs the dependency. `feature.add` and `feature.edit` take `of` as `<dependency>:<part>` with a label. `deps.add`, `deps.fetch` and `deps.update` are long requests, a `fetch` phase counting repositories and stopped between them by a cancel (`ryu_session::job::Phase::Fetch`, plan 5.C).
- **BOMs.** `ryupdm::structure::Reader::with_others` takes an `Others`: `deps::read::Through` (the lock, the manifest's dependencies and the cache) or `structure::Fixed` (projects' files in memory, for property tests and fuzzing). Nodes from another project carry `project` and are kept by (project, commit, part); `Others::commit` names a label's locked commit first, so a node read once is used again. A release read at its commit brings in the lock committed beside it (`Others::learn`), so a release whose instances the working files dropped still reads. BOM rows are keyed by item key and gain `project` and `dependency` (the reading project's name for it, else another manifest's, else its ID); flat rows sort by part number, then dependency (the project's own first), part and revision; `bom_mixed_revisions` and `bom diff` pair rows by the key. A foreign part's properties come from its own `properties.json`, under the root project's columns. CSV gains its last column, `project`, only when the BOM holds another project's rows, so every other CSV is as it was (design 233 said always). Part numbers aren't checked across projects.
- **Where-used.** `where-used <dependency>:<part>` gives this project's uses of another's part. `--in <folder>…` (else the user preference `pdm.dependents`, up to 100 folders; `--no-dependents` skips it) also searches projects on disk whose lock names this project (`crate::dependents`: a folder holding a manifest is a project, any other is searched below it, but not inside projects, hidden folders, `target` or `node_modules`), their working files and their official releases read from their own repositories, side by side; rows gain `project`, `folder` and `name`, and a folder that doesn't read is a `problems` entry. A project reads its dependents' uses of its own labels from its own repository (`deps::read::Local`), so a library needn't fetch itself. `--org` asks the service (`review::where_used_org`: `GET /api/v1/where-used`, with `review.url` and its token; `project_id_missing` with no ID): CLI only, since the daemon mustn't hold its lock for a remote, so `bom.where_used` has no `org`.
- **`deps uses`.** `deps.uses` (`ryucad deps uses [--rev REV]`, offline, `where_used::placed_from_others`), `schema: 1`: `{schema, project, rev, commit?, working: [{assembly, places}], released: [{assembly, label, commit, places}], problems, released_note?}`, each place `{project, dependency, part, label, count, uses: [{via, count}]}` at any depth (`via` ends at the assembly placing it: one step is a direct use). The service indexes it.
- **Forks.** `pdm.new_id` (`ryucad pdm new-id [--expect REV]`) gives the project a new random ID and writes `forked_from: {project, commit}` (the old ID, `HEAD`), one logged, undoable change; it is refused outside a repository (`not_a_git_repo`), with no ID (`project_id_missing`, a code this phase added) and before the first commit (`rev_not_found`). Records naming `forked_from.project` are inherited: `release list` gives them apart as `inherited`, `check` and the commit guard don't call them `release_project_mismatch`, the fork's own assemblies may place them, and its labels continue past them. A dependent reads only records naming a dependency's current ID (`Reader::releases`), so it can't place a fork's inherited labels.
- **Check and doctor.** `check` adds `source: deps` findings (`ryucad::deps::findings`): the manifest's faults; `lock_invalid`, `dependency_unlocked` and `lock_unused`, a warning (`ryupdm::deps::lock::judge`, offline: labels the files reach that the lock lacks, and the reverse); each locked label the cache can't read (`dependency_not_fetched` with the command, which fails `check` since nothing reading it can be checked, `dependency_rewritten`, `dependency_project_mismatch`, `label_not_found`); and `instance_outdated`, a warning that never fails it. Doctor reports `dependency_invalid`, `project_id_duplicate`, `lock_invalid`, `dependency_unlocked` and `lock_unused`, `check` leaving out its copies; its repair `deps_lock` rewrites the lock from fetched objects, offline (deleting it when nothing is placed), offered only when every label can be locked, and `doctor.repair` reads the daemon's own cache.
- **Git.** `drivers::LINES` gains `ryucad.lock merge=ryucad diff=ryucad text eol=lf` (it moved the `diff` golden section and `tests/golden/scale.txt`, which textconv and write `.gitattributes`). Textconv gives `dependency <name> = <id> <url> (path "")`, `forked_from = <id> at <commit>`, each lock project `project <name> = <id> <url> (path "") on <branch>` (with ` via a > b` when transitive) and each label `<name> <part>/<label> = <commit> content <hash>`, and a foreign instance `rev = <name>:<part> @ label B`, naming projects from the manifest at or above Git's working folder (`diff::textconv_named`, `names_near`), else by ID. The merge driver takes `ryucad.lock` (`merge::driven`), each dependency and each locked label one value, so two branches locking one label differently conflict there. `merge.status` lists `dependency_unlocked` where the merged lock is out of step with the merged files and a side's wasn't, blamed on both, with the repair `deps_lock`. `diff` gives a top-level `deps` block when a locked label differs: `added`, `removed` and `changed`, each `{project, dependency?, part, label, commit}` (`commit: {from, to}` when changed).
- **The bump setting.** `ryupdm.json` gains `dependencies: {bump: "none" | "pr"}` (`config::Bump`, format 2), written only when `pr` (`none` spelled out reads as none); `pdm configure --bump none|pr`, and `pdm.config` answers it. ryucad does nothing with it: the service reads it at the release branch's tip (see Dependencies on pull requests in `ryupdm-review.md`).
- **Testing.** Unit tests per module, `ryupdm::deps` against bare repositories over `file://` and `git http-backend`; `tests/deps.rs`'s `three_repositories_place_each_others_releases` (a library, a subassembly repository and a product: release, fetch, place, release, a rewritten history, a fork); `tests/cli.rs`'s `dependencies_from_the_cli` and `structure_across_projects_from_the_cli`, in process and through the daemon; `ryupdm/tests/structure_props.rs` over seeded projects placing each other's releases (`fixtures::projects`); the `structure` fuzz target and the `merge` target's lock (`0xf9`) and dependencies (`0xf8`) modes; the `deps` and `deps_structure` golden sections; `tests/assembly_bar.rs`'s bars over a dependency, with `RYUCAD_BARS=1` on cox-worker-2 (Ryzen 7 9700X, 8 cores, shared): 1,000 mates over 1,001 occurrences rebuilt in 33.5 ms from a dependency against 35.7 ms with the parts its own, the flat BOM 1.8 ms against 1.5 ms (both bars 1.25 times, which a loaded machine can miss: one run during a build gave 2.2 against 1.6), and where-used over 10 checkouts of 100 released assemblies cold in 74 ms (bar 1 s).
- **Limits.** Notices of newer releases are `deps outdated`, `check` and the service's; nothing is pushed or emailed. No vendoring, no pruning of the cache, and no hosts beyond what Git's transports reach.

No snapshot moved.

## Teams and revoked keys (decided in ryupdm phase 6)

The design is document 437 in the Coxswain planning project `ryucad-ryukei`; this is its phase 1, plan 6.A, built in ryucad #667. The service's side (membership from GitHub, team review requests, `team_unreadable`, the keys endpoint) is Organizations and teams on the service in `ryupdm-review.md`. Rules name GitHub teams as well as logins; the attestation the service signs says through which team each approval counted, so any clone still verifies it offline; and a key can be revoked, after which everything it signed proves nothing, whatever date it claims. Files and tags using none of this are byte for byte as before.

- **Teams in rules.** A rule's `from` takes `@<org>/<team-slug>` beside logins (`approvals::team_ok`, `approvals::team_org`): the organization a GitHub login, the slug 1 to 100 of `A-Z a-z 0-9 - _ .`; anything else starting with `@` is `approval_rule_invalid` at its pointer ("write @<organization>/<team-slug>"). Teams are named once per rule and compared without regard to case, as logins are; `Rule::teams` lists them and `Rule::names` matches a team as it matches a login. A team's size isn't known offline, so a rule naming one takes a `count` from 1 to `approvals::MAX_COUNT` (100); a rule of logins alone keeps 1 to its logins' number. `Rule::text` writes it as any rule (`3 of @acme/quality, dave for *`).
- **One organization, the owner's.** Every team in a file must be of one organization, checked offline when the file is read (`approval_rule_invalid` at the later team's pointer). `Approvals::check_owner(owner, at)` refuses teams of any organization but the repository owner's (`approval_rule_invalid`, `details.team` and `details.owner`): `pdm.configure` calls it when the clone's `origin` is a GitHub repository (`git::github_repo` of `Repo::origin_url`), and the service always does. Doctor and `check` don't, since a clone may not know its owner.
- **Counting.** `approvals::judge_with(rules, reviews, proposer, &dyn Teams)` takes a membership resolver: `Teams::membership(team, login)` answers `Membership::Member`, `NotMember` or `Unreadable`, and any `Fn(&str, &str) -> Membership` is one. `judge` is `judge_with` with `NoTeams` (no one is in any team), so every verdict over logins is as before. A rule counts distinct logins whichever entry admits them: a login named directly and through a team counts once. The proposer never counts, even through a team, and a change request from a login a team admits blocks. `Judgement` gains `via` (for each counted login, lower case, that a team admitted where that rule doesn't name it directly, those teams, sorted) and `unreadable` (the teams answered `Unreadable`, sorted: their members count for nothing, so a rule that needs one is never quietly met).
- **`via` in attestations.** `attest::Approval` gains `via`, a sorted list of teams, written only when non-empty: the teams through which the service counted that approval. `attest::FORMAT` is 2, and `Attestation::format` writes the lowest format that holds the attestation, 2 only when some approval has a `via`, so an attestation of logins is format 1 byte for byte as before. The signature domain stays `ryupdm.attestation.1\0` (`attest::DOMAIN`) at either format. Reading demands the declared format be that lowest one: a `via` in format 1, format 2 with no `via`, or a `via` that isn't a non-empty sorted list of distinct teams is `unreadable`.
- **Verifying `via` offline.** Every `via` must name a team the attestation's rules name, else `Invalid(Clause::Via(team))`, clause `via`. Membership itself is what the service's signature vouches for, as it vouches for the review: `verify_message` judges again with `judge_with` and a resolver built from the signed `via` lists (a login is in a team exactly when its approval's `via` says so). Without the `via`, a login a rule doesn't name directly is `not_met`.
- **Revoked keys.** An `approvals.keys` entry is `"<id>": "<64 hex>"` as before, or `"<id>": {"key": "<64 hex>", "revoked": "YYYY-MM-DD"}`. The day is checked by shape and range (`approvals::is_date`); a bad or missing `revoked`, another field or a bad key is `approval_rule_invalid` at its pointer (`/approvals/keys/<id>/revoked`). `Approvals::revoked` maps IDs to days. A revoked key stays in `Approvals::keys`, still trusted to recognise its own signature, which then verifies as revoked; `Approvals::to_json` writes the object form only for a revoked key.
- **Hosted revocations.** `attest::HOSTED_REVOKED` holds `(ID, YYYY-MM-DD)` pairs, empty now; each must be in `HOSTED_KEYS`, which never loses one (a unit test checks both). Revoking a hosted key takes a ryucad release, as a new key does. `attest::revoked(extra)` is the hosted list and `approvals.keys`' revoked entries. The service's `/.well-known/ryupdm-keys.json` lists the hosted ones as `status: revoked` with their day; no clone reads it.
- **Where revocations count.** A revocation counts when `approvals.keys` revokes the key at `rules_at` (where the record's rules were read) or at the release branch's tip as this clone has it, so revoking a key in a later commit reaches every older tag it signed. Trust stays at `rules_at`: a key only at the tip is still `unknown_key`. `history` reads the tip's revocations once (`judged`), and the verdict memo's key holds them.
- **Judging a tag, in order.** The message is split (`attest::split_message`: lightweight, no attestation, too large, unreadable); then the key and signature (`attest::check_signature`: `unknown_key`, `bad_signature`); then **revoked**; then **a newer format**; then the attestation's fields as before. `Expect` gains `revoked`. A good signature by a revoked key is `Verdict::Revoked {key, revoked}`, whatever `signed_at` says (a stolen key can backdate), and nothing after it is judged; a good signature on an attestation above `attest::FORMAT` is `Verdict::Unknown {key, format}`.
- **Findings.** Two new codes in `check::CODES`, both warnings, so `check` doesn't fail on them, each with `tag`, `official`, `key`, `rules` and `rules_at`: `release_attestation_revoked` (`revoked`, the day: "signed by key …, revoked on …: … stays official, but its approvals have no proof") and `release_attestation_unknown` (`format`: "newer than this ryucad reads (2): upgrade ryucad to judge it"). The record stays official: officialness is Git's, not the signature's.
- **`ryupdm.config` format 3.** Written when `approvals` names a team or holds a revoked key (`Approvals::format_3_at` gives the first such pointer), else as before (2 with `approvals` or `dependencies.bump`, else 1). A team or revoked key in a file declaring 2 or lower is `invalid_document` at its pointer ("teams and revoked keys need format 3: write the file at format 3 (pdm configure does)"), which doctor reports as other config faults. Format 4 went to release packages (phase 7).
- **Older ryucads.** One from before this phase reads a format 3 `ryupdm.config` as `format_too_new`, and a format 2 attestation as `release_attestation_invalid` (`unreadable`), not unknown, since its reader refused any format but 1: design 437 expected `release_attestation_unknown`, which this phase's ryucad is the first to answer for a newer format.
- **`release list`.** Still `schema: 1`. `approval.status` gains `revoked` (with `key` and `revoked`) and `unknown` (with `key` and `format`), and each of `approvers` gains `via` when the attestation has one.
- **Git.** Textconv gives a team in a rule's line as written (`approvals.rules.0 = 2 of @acme/quality, dave for *`) and a revoked key as `approvals.keys.<id> = <hex> (revoked YYYY-MM-DD)`. The merge driver is unchanged (`approvals.rules` one value, `approvals.keys` per key), so one side revoking a key and the other changing the rules merge cleanly at format 3, and two days for one key conflict at `/approvals/keys/<id>`.
- **The app.** The Releases tab (`core::releases::approval_line`, `approval_hover`) reads `Key revoked` (`revoked on <day>` and the key on hover) and `Attestation too new` (`format <n>: upgrade ryucad to judge it`), and an approver counted through a team `quinn via @acme/quality at …` on hover.
- **Testing.** `approvals` unit tests `rules_name_teams_beside_logins`, `teams_are_of_one_organization_the_owners`, `a_key_may_be_revoked_on_a_day`, `a_team_admits_its_members` (a fake resolver: members, counted once, the proposer, blockers, `via`, `unreadable`) and `rule_faults_point_at_their_field`; `attest`'s `an_approval_through_a_team_is_format_2`, `a_via_vouches_for_a_team_its_rules_name`, `a_revoked_key_proves_nothing_whatever_date_it_claims` and `a_newer_attestation_is_unknown_not_invalid`; `config`'s `teams_and_revoked_keys_need_format_3_and_write_it`; `ryupdm/tests/api.rs`'s `teams_and_revoked_keys_verify_offline_in_a_clone` (a team's rule, a tag approved through the team verified in a bare clone, then the key revoked at the tip and the tag `revoked`); ryucad's `approvals_are_configured_refused_and_removed`, `pdm_files_are_one_line_per_value`, `a_revocation_merges_with_new_rules_and_takes_format_3` and `tests/cli.rs`'s `approvals_from_the_cli` (the test key revoked at the tip: `release list` gives `revoked`, `release check` warns `release_attestation_revoked`, `check` passes); the golden section `pdm_teams` in `tests/golden/rebuild.txt` (a format 2 attestation's bytes and signature, and verdicts on it, on a `via` its rules don't name, under a revoked key with a backdated `signed_at`, and on a format 3 message); the app's `a_team_approval_and_a_revoked_key_say_so`; the `pdm` fuzz target.
- **Limits.** A revocation reaches a clone only through a ryucad release (`HOSTED_REVOKED`) or a commit to `approvals.keys`. Nothing is attested again: a tag is never moved, so releases a revoked key signed stay official with unproven approvals. Only `pdm configure` (given a GitHub `origin`) and the service check that a rule's teams are the owner's. A team's `count` is bounded by 100, not by its size.

## Release packages (decided in ryupdm phase 7)

The design is document 436 in the Coxswain planning project `ryucad-ryukei`; this is its plan 7.A (phases 1 and 2). The service's side (building on release, storing, signing, delivering, share links) is 7.B's, in `ryupdm-service`: Release packages on the service in `ryupdm-review.md`.

- **The package.** `ryupdm::package`: a deterministic zip, `<number>-<label>.zip` (`<number>` the PDM number made file-safe, else the part ID), holding `package.json` first (a `Manifest`, kind `ryupdm.package`, format 1, canonical JSON), `record.json` (the record's bytes at its official commit) and the files `packages.formats` names, in path order: `step/<number>-<label>.step` (AP242, mm), `drawings/<drawing>.pdf`, `drawings/<drawing>-<sheet>.dxf`, an assembly's `bom/indented.csv`, `bom/flat.csv` and `bom/bom.json` (both `bom.get` answers), and `render/iso.png` (1600×1200). The manifest names `built_with` (ryucad's version and the commit `ryucad version` gives, 12 hex in a release), the official `commit`, the record's `content` hash and `record` (its bytes' BLAKE3), every file's path, BLAKE3, size and media type, `parameters` (`formats`, `render`, `step`), an assembly's `children` (each part it places directly, at its label or `null` in work, with `package` always `null` in 7.A) and `warnings` (uncertain views) when there are any.
- **Keys.** `Manifest::key` is design 44's input key: BLAKE3 over length-prefixed `ryupdm.package.1`, `content`, `record`, the ryucad version and commit, and the parameters' canonical JSON. `Manifest::hash` (the package hash, what an attestation signs) is BLAKE3 of the canonical manifest with each child's `package` left out.
- **The zip** (`package::zip`). Written by hand over `miniz_oxide` (beside `ryuformats::zip`, which ryupdm can't link without the kernel): deflate at level 6, 1980-01-01 00:00, made by Unix with mode 0644, no extra fields, comments, data descriptors or ZIP64. Read back with every size bounded (`MAX_MANIFEST` 1 MiB, `MAX_FILE` 2 GiB, 65,535 entries), names unique, CRCs checked; anything else is `Unread`, never a panic.
- **Formats.** `ryupdm.json`'s `packages: {formats: [...]}` (`bom`, `dxf`, `pdf`, `render`, `step`), read sorted, the default every one but `dxf`; an unknown one is `packages_format_unknown` at its pointer. It needs config format 4 (design 261's rule: the next free format; ryupdm 6.A's teams and revoked keys took 3). `pdm configure --package-formats step,pdf,dxf,render` (`--default-package-formats` back), and `pdm.config` answers `packages`.
- **Building.** `ryucad release package <part> [--label L] [--out FILE.zip|DIR/] [--formats …]` (proto `release.package`, a long request, phase `package`, unit `files`): the label (else the part's latest official release) is resolved in the clone's history (`label_not_found`, `label_not_official` for a proposal, `release_obsolete`), and every file is built from the official commit through `export --rev label:L`, `drawing.export` and `render` at the commit, and `bom.get --rev label:L`. A file that fails, or a drawing finding of severity error (`drawing_view_failed`), refuses the whole package as `package_failed` with each failure; uncertain views are warnings in the answer and the manifest. Without `--out` the CLI writes `<number>-<label>.zip` into the current folder (`into`); `--out` ending in `/` (or an existing folder) writes the files unzipped. `--out` is never a project file (`export`'s rule), and a `DIR/` is never inside the project (`invalid_param` on `out`, its path compared with ASCII case folded as `export`'s is), since its files would be left there untracked; a zip may still be written there.
- **Verifying.** `ryucad release package verify FILE.zip [--rebuild]` (proto `release.package.verify`): every file's BLAKE3 and size against the manifest and nothing unlisted (`package::verify::files`), the record official at the manifest's commit with its bytes and content (`verify::release`), and the package tag when fetched. `verified` or `unattested` (warning `package_unattested`); anything else is `package_invalid` with its `clause` (`unreadable`, `no_manifest`, `manifest_unreadable`, `file_missing`, `file_changed`, `file_extra`, `record_mismatch`, `not_official`, `commit_mismatch`, `record_changed`, `wrong_project`, `wrong_content`, `rebuild_differs`, `tag_<release clause>`, `tag_hash`). `--rebuild` with another ryucad than `built_with` warns `package_built_with_other` and doesn't compare.
- **The package tag.** `ryupdm/<part>/<label>.package` at the official commit, annotated, its message a `ryupdm.package_attestation` (format 1: `built_with`, `commit`, `hash`, `label`, `part`, `project`, `record`, `signed_at`) in design 261's message and signature block, signed over `ryupdm.package_attestation.1\0` (`package::attest::DOMAIN`), so neither kind verifies as the other. The keys are a release tag's: `HOSTED_KEYS` and `approvals.keys` at the official commit's first parent. `attest::split_message` and `attest::check_signature` are what both kinds share. A key revoked where the record arrived or at the release branch's tip (ryupdm 6.A's revocations) makes the tag `revoked`: it proves nothing, so `release package verify` answers `unattested` with the warning `package_attestation_revoked`, and it is never an error. `release list` gives each official release `package: {tag: attested|invalid|revoked|missing, hash?, key?, built_with?, clause?, revoked?}`; `release check` reports `release_package_invalid` (an error) and never a missing one; `.package` tags aren't `release_tag_orphaned` while their release is official.
- **Clients.** `ryucad review package get <part> <label> [--out FILE]` (download through the service's signed link, then verify against the clone in process), `review package build` and `review package share [--days N]`: `GET`/`POST /api/v1/repos/{o}/{r}/releases/{part}/{label}/package` and `…/package/share`, whose service is 7.B's. There is no client for revoking a share link: the service revokes one through `DELETE …/package/share/{id}` only (plan 452, question 450), and `ryucad review package unshare <part> <label> <id>` over that route is ryucad's follow-up.
- **Testing.** `ryupdm` unit tests (`package::zip`: bytes pinned, bounds, CRCs, every truncation; the manifest's round trip, keys and hash; formats; paths; `verify`'s clauses; package attestations and domain separation; config format), ryucad's `package::tests` (A and B packaged from their own commits with their own title blocks, refusals, an assembly's children and BOM, verify and tampering, tags under trusted and untrusted keys), `tests/cli.rs`' `packages_from_the_cli` both ways and the review scenario's package routes, the `packages` golden section (every file but the record, and the manifest with commits left out, one thread and four), and the `pdm` fuzz target's package modes.

## Properties from STEP files (decided in ryucad phase 24)

- **Imports fill declared properties.** A STEP import fills `material` and the custom properties `ryupdm.json` declares from the file's material and user-defined attributes, judges them three ways on re-import, and never overwrites a person's value silently (`import_property_conflict`).
- **File properties.** Undeclared attributes are file properties: read-only, read from the committed bytes, never in `properties.json`.
- **No new types.** No property types or dimensions were added: a mass maps only to a `number`, in kg.
