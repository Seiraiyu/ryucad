## Hosted review (decided in ryupdm phase 2)

The design is document 65 in the Coxswain planning project `ryucad-ryukei`; its plans are 2.A to 2.H. Plan 2.A built the public hooks in this repo. Plans 2.B to 2.G built the service in the private repo `Seiraiyu/ryupdm-service`, whose `README.md` and `deploy/README.md` say how to build, test and deploy it. The paid part stays private: only what is useful without the service lands here.

- **Public hooks.** `render --rev REV` renders a revision; `--frame REV` (repeatable, `working` for the working files) frames those revisions' models too, so before and after renders share a camera; `--compare REV` paints faces new and changed since `REV` and ghosts its model with gone faces in the removed colour, the colours the app's compare view takes from `render` (the `compare` golden section, apart from `render`'s). `diff`, `inspect`, `release list` and `mesh` answer `"schema": 1`, as `check` does, with its rule: adding a field is not a change, changing or removing one is.
- **`ryucad review`.** `crate::review`, CLI only (it talks to a service, not to the session): `status`, `threads [--open]`, `comment <REF> <TEXT> [--pr] [--commit]`, `reply`, `resolve`, `reopen`, `update` (Merge in) and `renders --out DIR`, each a call to the service's `/api/v1` through a blocking `ureq` client on rustls. Its ring provider is the binary's C beyond mimalloc, a choice `crates/ryucad/Cargo.toml` explains; the kernel crates stay pure Rust. The PR is the current branch's by default (`GET /repos/{o}/{r}/pulls?branch=`), the repo `origin`'s GitHub URL, the token `RYUCAD_REVIEW_TOKEN`, else `GH_TOKEN`/`GITHUB_TOKEN`, else `gh auth token`, and the service the `review.url` preference (`https://review.seiraiyu.com`; `RYUCAD_REVIEW_URL` overrides it). The API's codes become `review_<code>` (exit 1); `review_unreachable` and `review_failed` exit 4, and a code this build doesn't know is `review_failed` with the service's in `details.service_code`. Tested against a fake service (`tests/review.rs`, `tests/fake_review`).
- **The interface.** The service runs the released `ryucad` binary (`--no-daemon`) for every rebuild, check, diff, mesh, render, merge and (since plan 3.D) BOM, pinned by its `RYUCAD_VERSION` (v0.5.0 at phase 2's end), and never reimplements a rule. It links neither `ryucad-doc` nor `ryupdm`: it reads the `schema: 1` outputs with serde types of its own and refuses any other schema. So a change here reaches it only when that pin moves, and changing or removing a field of a versioned output, a `review_` code or a `render` option breaks it: add, or give the output a new schema.
- **The service.** One Rust binary (`server`, `worker`, `migrate`): axum, Postgres 17 for state and the job queue (`FOR UPDATE SKIP LOCKED`, leases, three attempts), and artifacts by content key in a filesystem store (an S3 store is built for later). Builds (`ryupdm.build.3`, `ryupdm.build.4` since plan 3.D: the ryucad release and the project folder's Git tree), comparisons (`ryupdm.compare.2`, `.3` since 3.D) and merges (`ryupdm.merge.1`: the release and the head and base commits) are BLAKE3-keyed and shared across PRs, pushes and repos. Each step runs in a fresh Docker container: UID 10001, `--network none`, a read-only root, `--cap-drop ALL`, `no-new-privileges`, 4 CPUs, 8 GiB, 512 PIDs and 10 minutes, with the clone (whole, since ryucad reads history offline) and the output folder its only writable mounts; 2 GiB of disk is measured after each step, not enforced. Steps use the worker's Git config (no hooks, ryucad's drivers, `ryupdm[bot]`), never get an installation token, and once one has run in a clone the worker's own Git never touches that clone again.
- **On the pull request.** Two check runs, concluded together per head: `ryucad / check` (fails when `check --against` fails; findings, the feature diff, the PDM block, annotations on feature files) and `ryucad / merge` (`success`, `failure`, or `action_required` with a **Merge in** button when GitHub's line merge conflicts and ryucad's doesn't). One sticky comment per PR carries both verdicts, before and after renders of each changed part (1200×900, `iso`, the after one with `--compare`) as 30-day signed links, and the open threads.
- **Merge validation and Merge in.** The merge job checks out the PR's head and merges its base in (so the head is the first parent and "ours" is the PR's side, the reverse of design 65's wording), with ryucad's driver forced by `.git/info/attributes`, runs `merge status` in every project, and when the merge is clean commits it as `ryupdm[bot]` and keeps it as a bundle. Merge in (the check's button, the PR page, `POST …/merge-in`, `ryucad review update`) needs a person whose GitHub permission can push the head branch (an App's `ghs_` token is `forbidden`), refuses with `head_moved`, `base_moved`, `fork_not_installed` or `merge_unavailable`, and pushes exactly the bundled commit, never forced and never to a base.
- **Viewer, threads and API.** Server-rendered askama pages with htmx, built to the owner's mockups (`design/web/`): landing, repository, PR and commit pages in the app's three looks, light and dark, and a TypeScript WebGL2 view that decodes `ryucad.mesh.1`, paints the comparison, ghosts the base and picks on the CPU. Sign-in is GitHub OAuth into a signed cookie that holds no token; a private repo's pages ask GitHub for the login's collaborator permission with the installation's token (cached 5 minutes), and a repo the service doesn't know is `not_found`. Threads pin to an entity's reference (`<part>/<founder>/<hex>`, a part, a feature, or a sketch entity `<part>/<sketch>/<entity>`) and are re-resolved at each head by stable name only: the same reference stands, otherwise the thread is outdated, `removed_by` a feature or `part_removed`. Markdown is pulldown-cmark with raw HTML dropped. `/api/v1` (`crates/service/openapi.json`, served at `/api/v1/openapi.json`) takes a person's GitHub token, named by `GET /user` and checked as the pages check, or an App's installation token for the repos it reads; it adds `unauthenticated`, `not_in_beta`, `invalid_request`, `github_unreachable` and `merge_unavailable` to design 65's codes. The audit log records thread actions, tag writes and every Merge in with where it came from.
- **Release tags.** A push to a release branch the service knows (the default branch, or one a project's `release list` named) runs `release list` at the tip and creates each official record's lightweight tag `ryupdm/<part>/<label>` on GitHub; a tag found elsewhere is `release_tag_moved` on the next check, and no tag is ever moved or deleted.
- **Deployment.** The LXC `ryupdm-1` under Docker Compose, Postgres local to it, served at `review.seiraiyu.com`, invite-only by an allow-list (`RYUPDM_ALLOW`) and free in the beta. A deploy is a `v*` tag on the service's `main`: CI, both images to GHCR, then the ARC runner writes the host's secrets from GitHub secrets, migrates, restarts, and runs `scripts/e2e.sh checks beta pages threads merge` against the permanent fixtures `Seiraiyu/ryupdm-e2e` and `Seiraiyu/ryupdm-e2e-beta`. Phase 2 ended at `v0.3.0-pre.5`; v0.3.0 belongs to the service-release roadmap (design 116).
- **Testing and limits.** Here: the `compare` golden section, `schema` in each output's tests, and `ryucad review` against the fake service with every code mapped. In the service: unit and Postgres tests, a fake GitHub, workers on real ryucad and real Git repositories, the sandbox asserted from `docker inspect` in CI, the viewer's decoder against `mesh.rs`'s vectors, page snapshots, and the e2e on real GitHub at every deploy; the fixture's 1,000-hole block and 20-part project took 7 min 52 s cold and 13 s warm (report 102). The codes the service added after 2.A have codes of their own: `review_not_in_beta`, `review_invalid_request` and `review_merge_unavailable` (its `reason` under `service`) exit 1, `review_github_unreachable` exits 4 (#151). Limits: the sandbox is Docker in an unprivileged LXC (gVisor or Kata come with k3s); the viewer gives assemblies no compare paint and sketch entities no pin; one render per part; a press of the check run's button on GitHub and the signed-in pages are checked live only by a person (the e2e signs in nowhere).

## BOMs on pull requests (decided in ryupdm phase 3)

The design is document 180 in the Coxswain planning project `ryucad-ryukei`; this is its phase 6, plan 3.D, built in the private repo `Seiraiyu/ryupdm-service`.

- **What the service reads.** `bom` (indented and flat), `bom diff` and `where-used`, `schema: 1` (see Structure and BOMs in `ryupdm.md`), read by serde types of the service's own (`crate::bom`), as every other output is. Adding a field to them is safe; changing or removing one, or the root rule (one root answers, several are `invalid_param` with `details.roots`), breaks the service.
- **Jobs.** The build (`ryupdm.build.4`) finds the project's roots with `ryucad bom` and no part. One root answers with its BOM, several get a step each, and none (a project of plain parts) means no BOM. It keeps `bom` (the roots, the refusal's envelope, or `{"unsupported": true}`), `bom/<root>` (indented), `bom_flat/<root>`, and `where_used/<part>` for every part the roots' BOMs place below the root. The where-used runs share one sandbox step: `sandbox::Program::RyucadEach` runs one command per part inside one container (`EACH_SCRIPT`, the parts in `RYUPDM_EACH`, each a ryucad ID since they are split on spaces; envelopes and exit codes go to `/out/each/<part>.json` and `.exit`, read back only as plain files), and exit 4 for any part retries the job. The comparison (`ryupdm.compare.3`) keeps `bom_diff` and `bom_diff/<root>`, base to head, with roots judged at the head only, so a root the PR deletes shows as a removed part. The key bumps made every cached build and comparison again once.
- **An older ryucad.** A ryucad without `bom` answers `usage` with "unrecognized subcommand" (exit 2). The step records `{"unsupported": true}` and runs no other BOM step, and no comment section, check line or tab appears, so the service deploys with such a ryucad unchanged. Any other refusal keeps its envelope, and the check already says why.
- **Check and comment.** `ryucad / check`'s summary gains one line per root whose BOM changed, `BOM: 1 added, 1 removed, 2 changed`, naming the root (`BOM of **frame**: …`) when there are several. It never changes the conclusion: `check --against` already fails on a BOM's errors. The sticky comment gains `#### BOM changes · <project> · <root>` (the project left out at the repository's root) per changed root: the counts, then a table of flat rows (`+` added, `−` removed, `~` changed). A changed row says what changed: `revision A → B`, `quantity 0.6 m → 1.2 m`, each revising property, the rest counted (`1 other property`), else `item numbers`. The first 20 rows are inline, the rest under `<details><summary>N more</summary>`.
- **The BOM tab.** Each project section of the PR and commit pages has a tab bar, **3D** | **BOM**, of server-rendered links (`?tab=bom&project=<path>&root=<root>`, with `&flat=1` and `&used=<part>`) that keep the page's other query; 3D stays the default. The tab (`web::bom`) has an Indented/Flat toggle, a root choice when there are several, the columns Level, Item, Number, Name, Part, Revision, Quantity, Make/buy and State, findings and problems above the table, each line's problem beside it, and lines inside a bought assembly weak. On the PR page it is painted as the app paints a compare: added lines (and everything under an added assembly) new, changed lines changed with `<new> (was <old>)` cells, removed lines weak after their parent's last line (in the flat BOM, last), under `Compared with <base>: n added, n removed, n changed` and the legend; the commit page paints nothing. Choosing a line's part shows its where-used under the table. It uses only classes `app.css` has, so no asset hash moved, and the pages run nothing: they read the jobs' outputs.
- **ryucad builds.** `RYUCAD_VERSION` names a release: `deploy.yml` refuses any value that isn't `X.Y.Z` (a pre-release too), so production never runs a commit build. The sandbox image also takes `RYUCAD_VERSION=commit:<40 hex>` and builds that ryucad from source. `ci.yml`'s `RYUCAD_COMMIT` (overridable by `workflow_dispatch`'s `ryucad_commit`) is built once and shared; `test` runs as a matrix over the pinned release and the commit (fmt and clippy in the release leg only), and `images` builds and tests both sandboxes. `scripts/e2e.sh --ryucad X.Y.Z|commit:<40 hex>` picks the e2e's local ryucad, and its `bom` stage (a second pin placed in the fixture's `assembly/rig`, then the check's line and the comment's rows) is left out of the deploy's stages until a pinned release has `bom`. The BOM fixtures come from `scripts/bom-fixtures.sh`, which refuses a ryucad without `bom`.
- **Testing and limits.** Unit tests of the readers, the comment section and the check line, Postgres tests of the jobs' outputs, workers against both ryucads, page snapshots of both tabs, `tests/sandbox.rs`'s `each_steps_run_in_one_container` in both images, and `e2e-selftest.sh` with both ryucads. Limits: every placed part's where-used runs in one container under one step's wall time, and the parts travel in one environment variable, so a project of several thousand parts could pass the 128 KiB limit on one string; BOMs aren't in `/api/v1`; the commit sandbox image pulls the Rust image even for a release; the live BOM e2e waits for a pinned release with `bom`.
