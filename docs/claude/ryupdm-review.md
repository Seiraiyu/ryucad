## Hosted review (decided in ryupdm phase 2)

The design is document 65 in the Coxswain planning project `ryucad-ryukei`; its plans are 2.A to 2.H. Plan 2.A built the public hooks in this repo. Plans 2.B to 2.G built the service in the private repo `Seiraiyu/ryupdm-service`, whose `README.md` and `deploy/README.md` say how to build, test and deploy it. The paid part stays private: only what is useful without the service lands here.

- **Public hooks.** `render --rev REV` renders a revision; `--frame REV` (repeatable, `working` for the working files) frames those revisions' models too, so before and after renders share a camera; `--compare REV` paints faces new and changed since `REV` and ghosts its model with gone faces in the removed colour, the colours the app's compare view takes from `render` (the `compare` golden section, apart from `render`'s). `diff`, `inspect`, `release list` and `mesh` answer `"schema": 1`, as `check` does, with its rule: adding a field is not a change, changing or removing one is.
- **`ryucad review`.** `crate::review`, CLI only (it talks to a service, not to the session): `status`, `threads [--open]`, `comment <REF> <TEXT> [--pr] [--commit]`, `reply`, `resolve`, `reopen`, `update` (Merge in) and `renders --out DIR`, each a call to the service's `/api/v1` through a blocking `ureq` client on rustls. Its ring provider is the binary's C beyond mimalloc, a choice `crates/ryucad/Cargo.toml` explains; the kernel crates stay pure Rust. The PR is the current branch's by default (`GET /repos/{o}/{r}/pulls?branch=`), the repo `origin`'s GitHub URL, the token `RYUCAD_REVIEW_TOKEN`, else `GH_TOKEN`/`GITHUB_TOKEN`, else `gh auth token`, and the service the `review.url` preference (`https://review.seiraiyu.com`; `RYUCAD_REVIEW_URL` overrides it). The API's codes become `review_<code>` (exit 1); `review_unreachable` and `review_failed` exit 4, and a code this build doesn't know is `review_failed` with the service's in `details.service_code`. Tested against a fake service (`tests/review.rs`, `tests/fake_review`).
- **The interface.** The service runs the released `ryucad` binary (`--no-daemon`) for every rebuild, check, diff, mesh, render, merge and (since plan 3.D) BOM, pinned by its `RYUCAD_VERSION` (v0.5.0 at phase 2's end), and never reimplements a rule. It reads the `schema: 1` outputs with serde types of its own and refuses any other schema. Until plan 4.B it linked neither `ryucad-doc` nor `ryupdm`; since then it links them for approvals only (see Approvals on pull requests). So a change here reaches it only when that pin moves, and changing or removing a field of a versioned output, a `review_` code or a `render` option breaks it: add, or give the output a new schema.
- **The service.** One Rust binary (`server`, `worker`, `migrate`): axum, Postgres 17 for state and the job queue (`FOR UPDATE SKIP LOCKED`, leases, three attempts), and artifacts by content key in a filesystem store (an S3 store is built for later). Builds (`ryupdm.build.3`, `ryupdm.build.4` since plan 3.D: the ryucad release and the project folder's Git tree; `ryupdm.build.5` since plan 5.D, see Dependencies on pull requests), comparisons (`ryupdm.compare.2`, `.3` since 3.D) and merges (`ryupdm.merge.1`: the release and the head and base commits) are BLAKE3-keyed and shared across PRs, pushes and repos. Each step runs in a fresh Docker container: UID 10001, `--network none`, a read-only root, `--cap-drop ALL`, `no-new-privileges`, 4 CPUs, 8 GiB, 512 PIDs and 10 minutes, with the clone (whole, since ryucad reads history offline) and the output folder its only writable mounts; 2 GiB of disk is measured after each step, not enforced. Steps use the worker's Git config (no hooks, ryucad's drivers, `ryupdm[bot]`), never get an installation token, and once one has run in a clone the worker's own Git never touches that clone again.
- **On the pull request.** Two check runs, concluded together per head by the report (since plan 4.B a third, `ryucad / release`, created with them and concluded by the approvals job after the report; see Approvals on pull requests): `ryucad / check` (fails when `check --against` fails; findings, the feature diff, the PDM block, annotations on feature files) and `ryucad / merge` (`success`, `failure`, or `action_required` with a **Merge in** button when GitHub's line merge conflicts and ryucad's doesn't). One sticky comment per PR carries their verdicts (a third row for `ryucad / release` since 4.B), before and after renders of each changed part (1200×900, `iso`, the after one with `--compare`) as 30-day signed links, and the open threads.
- **Merge validation and Merge in.** The merge job checks out the PR's head and merges its base in (so the head is the first parent and "ours" is the PR's side, the reverse of design 65's wording), with ryucad's driver forced by `.git/info/attributes`, runs `merge status` in every project, and when the merge is clean commits it as `ryupdm[bot]` and keeps it as a bundle. Merge in (the check's button, the PR page, `POST …/merge-in`, `ryucad review update`) needs a person whose GitHub permission can push the head branch (an App's `ghs_` token is `forbidden`), refuses with `head_moved`, `base_moved`, `fork_not_installed` or `merge_unavailable`, and pushes exactly the bundled commit, never forced and never to a base.
- **Viewer, threads and API.** Server-rendered askama pages with htmx, built to the owner's mockups (`design/web/`): landing, repository, PR and commit pages in the app's three looks, light and dark, and a TypeScript WebGL2 view that decodes `ryucad.mesh.1`, paints the comparison, ghosts the base and picks on the CPU. Sign-in is GitHub OAuth into a signed cookie that holds no token; a private repo's pages ask GitHub for the login's collaborator permission with the installation's token (cached 5 minutes), and a repo the service doesn't know is `not_found`. Threads pin to an entity's reference (`<part>/<founder>/<hex>`, a part, a feature, or a sketch entity `<part>/<sketch>/<entity>`) and are re-resolved at each head by stable name only: the same reference stands, otherwise the thread is outdated, `removed_by` a feature or `part_removed`. Markdown is pulldown-cmark with raw HTML dropped. `/api/v1` (`crates/service/openapi.json`, served at `/api/v1/openapi.json`) takes a person's GitHub token, named by `GET /user` and checked as the pages check, or an App's installation token for the repos it reads; it adds `unauthenticated`, `not_in_beta`, `invalid_request`, `github_unreachable` and `merge_unavailable` to design 65's codes. The audit log records thread actions, tag writes and every Merge in with where it came from.
- **Release tags.** A push to a release branch the service knows (the default branch, or one a project's `release list` named) runs `release list` at the tip and creates each official record's lightweight tag `ryupdm/<part>/<label>` on GitHub; a tag found elsewhere is `release_tag_moved` on the next check, and no tag is ever moved or deleted. Since plan 4.B a record under approval rules gets a signed annotated tag instead (see Approvals on pull requests).
- **Deployment.** The LXC `ryupdm-1` under Docker Compose, Postgres local to it, served at `review.seiraiyu.com`, invite-only and free in the beta: by an allow-list (`RYUPDM_ALLOW`) until phase 6, then by each organization's `access`, set with `ryupdm-service org` (Organizations and teams on the service). A deploy is a `v*` tag on the service's `main`: CI, both images to GHCR, then the ARC runner writes the host's secrets from GitHub secrets, migrates, restarts, and runs `scripts/e2e.sh checks beta pages threads merge` against the permanent fixtures `Seiraiyu/ryupdm-e2e` and `Seiraiyu/ryupdm-e2e-beta`. Phase 2 ended at `v0.3.0-pre.5`; v0.3.0 belongs to the service-release roadmap (design 116).
- **Testing and limits.** Here: the `compare` golden section, `schema` in each output's tests, and `ryucad review` against the fake service with every code mapped. In the service: unit and Postgres tests, a fake GitHub, workers on real ryucad and real Git repositories, the sandbox asserted from `docker inspect` in CI, the viewer's decoder against `mesh.rs`'s vectors, page snapshots, and the e2e on real GitHub at every deploy; the fixture's 1,000-hole block and 20-part project took 7 min 52 s cold and 13 s warm (report 102). The codes the service added after 2.A have codes of their own: `review_not_in_beta`, `review_invalid_request` and `review_merge_unavailable` (its `reason` under `service`) exit 1, `review_github_unreachable` exits 4 (#151). Limits: the sandbox is Docker in an unprivileged LXC (gVisor or Kata come with k3s); the viewer gives assemblies no compare paint and sketch entities no pin; one render per part; a press of the check run's button on GitHub and the signed-in pages are checked live only by a person (the e2e signs in nowhere).

## BOMs on pull requests (decided in ryupdm phase 3)

The design is document 180 in the Coxswain planning project `ryucad-ryukei`; this is its phase 6, plan 3.D, built in the private repo `Seiraiyu/ryupdm-service`.

- **What the service reads.** `bom` (indented and flat), `bom diff` and `where-used`, `schema: 1` (see Structure and BOMs in `ryupdm.md`), read as schema-1 JSON (`crate::bom`; only the envelope is typed), as the diff is. Adding a field to them is safe; changing or removing a field the service reads (`part`, `children`, `rev`, `quantity`, …), or the root rule (one root answers, several are `invalid_param` with `details.roots`), breaks it.
- **Jobs.** The build (`ryupdm.build.4`; `.5` since plan 5.D) finds the project's roots with `ryucad bom` and no part. One root answers with its BOM, several get a step each, and none (a project of plain parts) means no BOM. It keeps `bom` (the roots, the refusal's envelope, or `{"unsupported": true}`), `bom/<root>` (indented), `bom_flat/<root>`, and `where_used/<part>` for every part the roots' BOMs place below the root. The where-used runs share one sandbox step: `sandbox::Program::RyucadEach` runs one command per part inside one container (`EACH_SCRIPT`, the parts in `RYUPDM_EACH`, each a ryucad ID since they are split on spaces; envelopes and exit codes go to `/out/each/<part>.json` and `.exit`, read back only as plain files), and exit 4 for any part retries the job. The comparison (`ryupdm.compare.3`) keeps `bom_diff` and `bom_diff/<root>`, base to head, with roots judged at the head only, so a root the PR deletes shows as a removed part. The key bumps made every cached build and comparison again once.
- **An older ryucad.** A ryucad without `bom` answers `usage` with "unrecognized subcommand" (exit 2). The build's step records `{"unsupported": true}` and runs no other BOM step (the comparison still runs its one `bom diff` and keeps `{"unsupported": true}` as `bom_diff`), and no comment section, check line or tab appears, so the service deploys with such a ryucad unchanged. Any other refusal keeps its envelope, and the check already says why.
- **Check and comment.** `ryucad / check`'s summary gains one line per root whose BOM changed, `BOM: 1 added, 1 removed, 2 changed`, naming the root (`BOM of **frame**: …`) when there are several. It never changes the conclusion: `check --against` already fails on a BOM's errors. Only compared projects carry a BOM diff, so a project new in the PR gets no check line or comment section. The sticky comment gains `#### BOM changes · <project> · <root>` (the project left out at the repository's root) per changed root: the counts, then a table of flat rows (`+` added, `−` removed, `~` changed). A changed row says what changed: `revision A → B`, `quantity 0.6 m → 1.2 m`, each revising property, the rest counted (`1 other property`), else `item numbers`. The first 20 rows are inline, the rest under `<details><summary>N more</summary>`. A changed root with no flat rows gets no table, only "Only the structure changed: no part's total moved."
- **The BOM tab.** Each project section of the PR and commit pages has a tab bar, **3D** | **BOM**, when its build has a BOM (not for a project without a root assembly, a build from an older ryucad, or one from before 3.D): server-rendered links (`?tab=bom&project=<path>&root=<root>`, with `&flat=1` and `&used=<part>`) that keep the page's `head` and `threads=all` and drop the rest of its query; 3D stays the default. The tab (`web::bom`) has an Indented/Flat toggle, a root choice when there are several, the columns Level, Item, Number, Name, Part, Revision, Quantity, Make/buy and State, findings and problems above the table, each line's problem beside it, and lines inside a bought assembly weak. On the PR page it is painted as the app paints a compare: added lines (and everything under an added assembly) new, changed lines changed with `<new> (was <old>)` cells, removed lines weak after their parent's last line (in the flat BOM, last), under `Compared with <base>: n added, n removed, n changed` and the legend; the commit page paints nothing. Choosing a line's part shows its where-used under the table. It uses only classes `app.css` has, so no asset hash moved, and the pages run nothing: they read the jobs' outputs.
- **ryucad builds.** `RYUCAD_VERSION` names a release: `deploy.yml` refuses any value that isn't `X.Y.Z` (a pre-release such as `0.6.0-pre.1` is refused too), so production never runs a commit build. The sandbox image also takes `RYUCAD_VERSION=commit:<40 hex>` and builds that ryucad from source. `ci.yml`'s `RYUCAD_COMMIT` (overridable by `workflow_dispatch`'s `ryucad_commit`) is built once and shared by the `test` legs (the `images` commit leg builds it again in `docker/sandbox.Dockerfile`'s `commit` stage); `test` runs as a matrix over the pinned release and the commit (fmt and clippy in the release leg only), and `images` builds and tests both sandboxes. `scripts/e2e.sh --ryucad X.Y.Z|commit:<40 hex>` picks the e2e's local ryucad, and its `bom` stage (a second pin placed in the fixture's `assembly/rig`, then the check's line and the comment's rows) is left out of the deploy's stages until a pinned release has `bom`. The BOM fixtures come from `scripts/bom-fixtures.sh`, which refuses a ryucad without `bom`.
- **Testing and limits.** Unit tests of the readers, the comment section and the check line, Postgres tests of the jobs' outputs, workers against both ryucads, page snapshots of both tabs, `tests/sandbox.rs`'s `each_steps_run_in_one_container` in both images, and `e2e-selftest.sh` with both ryucads. Limits: every placed part's where-used runs in one container under one step's wall time, and the parts travel in one environment variable, so a project of several thousand parts could pass the 128 KiB limit on one string; BOMs aren't in `/api/v1`; the sandbox image pulls the Rust image (its `commit` stage's) even for a release; the live BOM e2e waits for a pinned release with `bom`.

## Approvals on pull requests (decided in ryupdm phase 4)

The design is document 261 in the Coxswain planning project `ryucad-ryukei`; this is its phase 4, plan 4.B, built in the private repo `Seiraiyu/ryupdm-service`. The open side (rules, attestations, verification and the clients) is Approvals in `ryupdm.md`.

- **Linking ryupdm.** The service links `ryupdm` and `ryucad-doc` as Git dependencies at a ryucad commit or release tag, and `ed25519-dalek` 2, for two things only: `approvals::judge` (since phase 6 `approvals::judge_with`, given GitHub's team memberships), the one ryupdm rule it calls rather than running ryucad (a pure function over rules and reviews, run on every review without a sandbox), and `ryupdm::attest`'s types, canonical bytes and message, so `attest::Signer` signs byte for byte as `attest::sign` does (a test checks it). Every other rule still comes from the pinned ryucad binary. Linking brings gix and ryukei into the service's build, so `docker/service.Dockerfile` builds the dependencies in a layer keyed only by the manifests and `Cargo.lock`, cached through GHA under the `service` scope, which only runs that aren't pull requests write.
- **An older ryucad.** At start a worker asks its ryucad `pdm configure --no-approvals` outside any project (`approvals::supported`): one without approval rules refuses the argument (`usage`), and the service then posts no `ryucad / release` and signs nothing, so tags stay lightweight and it deploys unchanged on such a ryucad. Without a signing key, or when GitHub names no account that proposed it, it leaves a ruled record's tag alone (`unsigned`).
- **Reviews.** The App subscribes to `pull_request_review` (no new permission, so installations aren't asked again). An `approvals` job reads the PR's reviews from GitHub: each reviewer's latest review that approves, requests changes or was dismissed stands, comments don't count, and a dismissed review is none (`approvals::fold`). Only a PR whose base is a project's release branch collects approvals. The proposals and their rules come from `release list` at the head, the rules read at the base's tip. An approval is bound to the record, not the head: it counts while the record's bytes at the commit it reviewed are its bytes at the head, so a push that changes the record needs new approvals and one that doesn't keeps them. A change request from a login a rule names (since phase 6, or a member of a team it names) blocks, whatever it reviewed, until that reviewer approves or it is dismissed.
- **`ryucad / release`.** A third check run on every head, once the worker's ryucad has approval rules, so a team can make it required without it ever hanging: `success` (no proposal under rules, every one met, or a PR not into a release branch), `action_required` (`Awaiting approval: 1 of 2`: proposals whose rules are met, of those under rules) or `failure` (a blocker, or records or rules that couldn't be read). Its summary lists each proposal, its rules, who approved at which commit, approvals that saw another version of the record, who is still needed, blockers, the reviews requested and the logins (since phase 6, teams) GitHub wouldn't request, and whether the PR changes `approvals` (since phase 6, with whether CODEOWNERS gives `ryupdm.json` an owner). The sticky comment gains a row for the check and a line per proposal.
- **Review requests.** For each head's proposals under rules, the service asks GitHub for a review from each login a rule names (since phase 6, each team too, as `team_reviewers`) that it hasn't asked on that PR (`review_request`) and whose review doesn't already stand, never the author, so GitHub notifies them. Requests are never withdrawn.
- **Signed tags.** On a push to a release branch, each newly official record under rules (judged at its official commit's first parent) is attested: the PR that brought it (GitHub's pulls-for-commit), its reviews as they stood at its `merged_at` (`approvals::submitted_by`, so an approval given after the merge counts for nothing), judged, signed, and made with GitHub's Git data API (a tag object whose tagger is `ryupdm[bot]`, then its ref). Rules met give `approved`; a bypassed check or a direct push gives `unapproved`. Records without rules keep their lightweight tags, a tag already present is left alone, and a ryupdm tag that is lightweight or doesn't verify is a `release_attestation_invalid` banner on the repository's page. A failure to sign or tag fails the tags job, which is retried as any job is, and leaves the record official and untagged meanwhile.
- **Keys.** `RYUPDM_SIGNING_KEY` is the Ed25519 seed as exactly 64 lower-case hex digits, a GitHub secret: `deploy.yml` refuses any other value and writes it to the host as `/etc/ryupdm/secrets/signing-key` (`RYUPDM_SIGNING_KEY_FILE`). `GET /.well-known/ryupdm-keys.json` lists the public keys by ID, the current one and the retired ones (`attest::RETIRED`, which never loses one); since phase 6 a key in ryupdm's `HOSTED_REVOKED` is listed as `revoked`, with its day. Rotating: add the new public key to ryucad's `HOSTED_KEYS`, release ryucad, move the old key to `RETIRED`, then switch the secret.
- **Audit and the release index.** New audit events: `review_counted`, `changes_requested`, `review_dismissed`, `rules_met`, `attestation_signed`, `tag_created` and `release_bypassed` (outcome `release_unapproved`), kept for the life of the installation. Migration 0007 adds `review`, `review_request`, the run's `ryucad / release` columns and its judgement (`approvals`), a signed tag's `outcome`, and `release`: every official record as `release list` at the release branch's tip last said, after the tags job ran, with its tag's status, proposer, approvers and rules. The next push rebuilds it, so it can be rebuilt from the tags.
- **Pages and API.** `/{o}/{r}/releases`: each part's labels, newest first, with kind, official commit, proposer, approvers and when, outcome and whether the tag verifies, filtered by part and date. `/api/v1` (`schema: 1`, under the pages' access checks, OpenAPI updated): `GET /repos/{o}/{r}/pulls/{n}/approvals` (`202` while the head is being judged; `judged: false` on a ryucad without rules), `GET /repos/{o}/{r}/releases[?part=&since=&until=]` and `GET /repos/{o}/{r}/audit[?part=&since=&until=&format=json|csv]`, which gives the events above and the tag events `tag.create` and `tag.moved`.
- **e2e.** `scripts/e2e.sh`'s `approvals` stage, on `Seiraiyu/ryupdm-e2e`'s `approvals/` project under one rule naming a reviewer account other than the proposer's, whose token is the secret `RYUPDM_E2E_REVIEWER_TOKEN` (a GitHub App can't approve): `ryucad / release` waits, the reviewer's approval turns it green, the merge makes an annotated tag that a fresh clone's `release list` reads as approved by the reviewer, with `release check` reporting nothing of it. Then the bypass: a separate project, `bypass/` (record `blocker A`), released on a branch of its own, `e2e-bypass`, made from main each run; merged there with no approval, its tag says `unapproved`, which a clone reports as `release_unapproved`, while main stays clean. The branch and `ryupdm/blocker/A` are deleted when the run ends. It is skipped without the token, refuses a local ryucad without `--approvals`, and joins the deploy's stages once a pinned ryucad release has approval rules.
- **Testing and limits.** Unit tests of folding, record binding and `submitted_by`; snapshots of the check's conclusions and summaries and of the CSV; a fake GitHub for review requests, the Git data API's annotated tags and pulls-for-commit; Postgres tests of the release index and the audit events; the keys endpoint; worker tests (`the_worker_knows_whether_its_ryucad_has_approvals`, `merged_releases_under_rules_get_tags_a_clone_verifies`, where a fresh clone's `ryucad release check` verifies the service's tag, and `an_approval_after_the_merge_counts_for_nothing`). The approvals tests run in CI's ryucad commit leg, which is opt-in (`gh workflow run ci.yml -f ryucad_commit=<40 hex>`) while the pinned release has no approval rules; the release leg runs them as a check that rules are absent. Limits: reviewers were logins, not teams, until phase 6 (Organizations and teams on the service); approving after the fact and revoking an approval are out of scope, and revoked keys came with phase 6; who may change `approvals` is flagged in the check (since phase 6 with a CODEOWNERS note), not gated.

## Dependencies on pull requests (decided in ryupdm phase 5)

The design is document 233 in the Coxswain planning project `ryucad-ryukei`; this is its phase 5, plan 5.D, built in the private repo `Seiraiyu/ryupdm-service` (its ryucad part, the bump setting, is in Multi-repo in `ryupdm.md`). Builds read the dependencies their locks name from mirrors the worker fetched, an index of what every project places from others answers organization-wide where-used, and a newer release in a dependency opens a notice and, where a project opts in, a bump pull request.

- **Linking.** `ryupdm` and `ryucad-doc` are linked at a ryucad commit that has `dependencies.bump` (until a release holds it, then at its tag) for the rules the service mustn't redo: the mirror's name (`ryupdm::deps::folder`, `normalize`), the settings (`config::Config`, `Bump`), label order (`label::index`), the lock and the manifest (`doc::lock::Lock`, `files::Manifest`).
- **An older ryucad.** At start a worker asks its ryucad `deps list` outside any project (`Worker.deps`): one without dependencies answers `usage`, and the service then fetches no mirrors and keeps no uses, notices or bumps, so every job runs as before and it deploys unchanged on such a ryucad.
- **Which are fetched.** The worker reads each project's `ryucad.lock` at the job's commits before any step (`deps::locks`), and fetches a URL only when it names a repository on `RYUPDM_GITHUB_WEB`'s host (`https://`, `http://`, `ssh://git@` and `git@host:` forms) that the `repo` table holds under the job's own installation, matched without regard to case (`deps::readable`), from GitHub with that installation's token. Any other URL is left out, and ryucad's own `dependency_not_fetched` names it.
- **Mirrors.** Bare repositories at `<RYUPDM_SCRATCH>/deps/<folder>` (`deps::folder`'s `<32 hex>.git`), laid out as ryucad's cache (`refs/ryucad/head`, the release branches the locks name and each project's own, `refs/tags/ryupdm/*`), fetched with Git's CLI (the token in a header from the environment, `ls-remote` first so only refs the remote has are asked for) under a lock file per mirror. Never pruned; `deploy/README.md` says how to empty them. A fetch that fails fails the job, which is retried as any job is: a transient failure is never kept in a build.
- **The sandbox.** Every step gets `RYUCAD_DEPS_DIR=/deps` and only its job's mirrors, each mounted read-only at `/deps/<folder>` (`sandbox::DEPS_DIR`), so the sandbox keeps `--network none` and never sees another installation's mirrors. Build, compare, merge, tags and bump jobs fetch their mirrors before any step.
- **Keys.** Builds are `ryupdm.build.5`: the release, the project's tree and the sorted lock URLs that were left out, so installing the App on a dependency rebuilds a build that said `dependency_not_fetched` rather than serving it forever. Comparisons are keyed by their builds; merges keep `ryupdm.merge.1`.
- **The index.** Migration 0008 adds `project_index`, `dependency_use`, `dependency_notice` and the `bump` job kind. The tags job (every push to a release branch) runs `ryucad deps uses` for each project at the tip and replaces its rows, with the project's ID, settings and dependencies (`index::store`); one that fails keeps the rows it last gave. Not in builds: only release-branch tips are indexed, and nothing reads a pull request's uses. It can be rebuilt from the repositories.
- **Where-used.** `GET /api/v1/where-used?project=&part=[&label=][&direct=true]` (`api::deps::where_used`, `schema: 1`) answers `ryucad where-used`'s shape, each row with `repo`, `commit` and `path` (the placing project's folder: one repository may hold several): `working` from release-branch tips, `released` from their official releases with `state` (`released`, `superseded` or `obsolete`, from 4.B's release index in the placing project's scheme). `direct` keeps one-step uses. Only repositories the caller may read are answered, checked as the pages check; a bad parameter is `invalid_request` with `details.parameter`. `ryucad where-used --org` is its client. The viewer has no part pages, so each part on the Releases page gains a Used by line instead.
- **Notices.** One open notice per (dependent repository, project, dependency project), its rows `{part, from, to}`: an instance an assembly at the dependent's release-branch tip places itself, at a label older than its part's latest official, non-obsolete one in the dependency's scheme (`notices::moves`). The dependency is the repository the dependent's manifest URL names, under the same installation, so a repository copying another's project ID raises none. The tags job works them out again for the project pushed, both as a dependent and as a dependency (`notices::refresh`); a notice whose rows change is updated in place, and one left with none closes. They show as a banner on the repository's page, in `GET /api/v1/repos/{o}/{r}/notices`, and as one line under the project in `ryucad / check`'s summary (`Newer releases: lib p A → B, lib q A → C`), which never changes its conclusion. Only a project's own instances are noticed: `deps update` moves only those.
- **Bump pull requests.** Where the project's `ryupdm.json` at the tip says `dependencies.bump: "pr"`, a `bump` job runs per notice whose rows changed, queued once beside one running. It clones the tip, fetches the mirrors (and up to three more that `deps update` names as `dependency_not_fetched`), runs `ryucad deps update <name> --offline` in the sandbox and, when something moved, commits there as `ryupdm[bot]` and keeps a bundle. The worker pushes the bundled commit, never forced, to the new branch `ryupdm/bump/<name>/<12 hex>` (BLAKE3 over the moves, `bump::branch`) through a fresh shallow fetch, as Merge in pushes, and opens a pull request into the release branch titled `Move to <name> <part> <label>[, …]`, its body the moves and `failing`. Nothing moved opens nothing, and the notice keeps why (`bump_error`). A newer bump comments on the notice's earlier open one with a link and closes it, deleting its branch only when it starts `ryupdm/bump/` and GitHub's compare shows every commit authored and committed by the bot (`bump::all_ours`). Audit events `bump.opened` and `bump.superseded`. The App needed no new permission: it already had Contents and Pull requests read and write.
- **e2e.** `scripts/e2e.sh`'s `deps` stage, on `Seiraiyu/ryupdm-e2e`'s `deps/` project, which places the part `pin` of the private library `Seiraiyu/ryupdm-e2e-lib` (seeded by `scripts/e2e-seed.sh --lib`; the App must be installed on it) and opts in to bumps: a new release of `pin` on the library's `main` opens a notice and a bump pull request whose `ryucad / check` passes, and `ryucad where-used pin --org` from the library finds the fixture. The bump pull request is closed and its branch deleted when the run ends; the library keeps its releases. It needs `--ryucad` with dependencies, and joins the deploy's stages once a pinned ryucad release has them.
- **Testing and limits.** Unit tests of the lock reader, the URL filter, the index's rows, notices' moves and the bump's branch, title and body; the API's `organization_where_used` and `a_repos_notices` over Postgres; `tests/sandbox.rs`'s `mirrors_are_read_only_in_the_sandbox`; `tests/review_cli.rs`'s `org_where_used_against_the_service`; worker tests `builds_read_dependencies_from_mirrors`, `pushes_index_what_projects_place_from_others`, `a_newer_release_in_a_dependency_opens_a_notice`, `opted_in_projects_get_bump_pull_requests`, `a_newer_bump_supersedes_the_open_one` and `the_worker_knows_whether_its_ryucad_has_dependencies`, against a fake GitHub; page snapshots of the banner and Used by. The dependency tests skip against a ryucad without dependencies, as the pinned release (0.7.0) is, so they run only in CI's ryucad commit leg, which is opt-in (`gh workflow run ci.yml -f ryucad_commit=<40 hex>`, the commit the service links ryupdm at: `ff521934`) while the pinned release has no dependencies. Limits: GitHub only, and only the job's installation; mirrors are never pruned; the tags job fetches only the tip's lock, so an older release whose lock named another URL reads its foreign rows with what ryucad couldn't read in `problems`; notices cover direct dependencies only.

## Organizations and teams on the service (decided in ryupdm phase 6)

The design is document 437 in the Coxswain planning project `ryucad-ryukei`; this is its phases 2 and 3, plan 6.B, built in the private repo `Seiraiyu/ryupdm-service`, whose `deploy/README.md` says how it is run (Organizations and access). The open side (teams in rules, an approval's `via`, revoked keys) is Teams and revoked keys in `ryupdm.md`. The GitHub account an installation is on becomes an organization the service knows, its access set by the operator instead of `RYUPDM_ALLOW`; its members, owners and teams are GitHub's, read with the App's *Organization: Members (read)* permission, and the service keeps no roles of its own.

- **Linking.** `ryupdm` and `ryucad-doc` move to plan 6.A's merge (ryucad `bbc7e91e`): the approvals job calls `approvals::judge_with` with the team memberships it asked GitHub for (`approvals::Known`, which implements ryupdm's `Teams`), and `/.well-known/ryupdm-keys.json` (`attest::keys`) lists a key in ryupdm's `HOSTED_REVOKED` as `{"status": "revoked", "revoked": "<day>"}`. The Releases page's chip reads `Key revoked` or `Newer attestation` (`Chip::release`).
- **The organization row.** Migration 0009 adds `organization` (keyed by the GitHub account ID `installation.account_id` already holds; `login`, `kind` `org` or `user`, `access` `off`, `beta` or `paid`, `cache_cap` in bytes, `created_at`), `repo.excluded`, `audit.organization_id` (with `audit.installation_id` nullable and the `operator` actor kind), `usage`, `review.via` and `pending_seed`. Every installation event records its account (`org::seen`: a new one is `off`), and `organization.renamed` renames the organization, its installations and its repos (`org::renamed`). `installation.allowed` is no longer read, kept with a default of `false` so the older image still runs after a rollback. Design 437's `installation.organization_id` wasn't needed.
- **Access.** Webhooks, pages, `/` and the API read the organization's `access` and `repo.excluded` (`org::repo_on`): `off` or an excluded repo gets no checks and the private-beta comment as before, and its pages `not_in_beta`; `beta` and `paid` get everything. The operator sets it on the host: `ryupdm-service org list` (login, kind, access, cache cap, installations, repos, excluded), `org set <login> [--access off|beta|paid] [--cache-cap 50GiB|none]` (`org::parse_bytes`, listed back by `org::format_bytes`), `org exclude <owner/name>` and `org include <owner/name>`; `org` logs to stderr, so its stdout is only its answer. Each change is an audit row with actor `operator` (`audit::record_org`, `Actor::Operator`): `org.access` (`{from, to, cache_cap}`), `repo.exclude`, `repo.include`.
- **The seed.** `ryupdm-service migrate` (`db::migrate_seeding`), while migration 0009's `pending_seed` row `access_seed` is there, turns each `RYUPDM_ALLOW` login's organization `beta` and excludes each `!owner/name` repo, as the operator (`org::seed`). The seed and the row's deletion are one transaction, so a seed that fails changes nothing and the next `migrate` tries again, and one that succeeded never runs again. A name with nothing installed is skipped with a warning. Afterwards the server and worker read `RYUPDM_ALLOW` only to warn at start that it is ignored (`Config.allow_env`).
- **Members and owners.** `GET /orgs/{org}/memberships/{login}` with an installation token asked only for `permissions: {members: read}` (`GitHub::members_token`, `GitHub::members`): `active` with role `admin` is an owner, `active` with `member` a member, anything else (pending, 404, the login now another account's) an outsider (`org::role`, `org::Role`). A personal account's one member and owner is the account itself. GitHub's 422 to that token request (the permission not accepted) is `Role::Unreadable`. Answers are kept 5 minutes by (organization, user) (`web::access::Cache.roles`, `access::TTL`).
- **Who learns an organization is here.** `api::orgs::org_for` and the page settle this first (`web::organization::known_to`): anyone, when the organization has a public repo installed (`web::organization::visible`); otherwise only someone who reads one of its repos. To everyone else every refusal is `not_found`, so neither `not_in_beta` nor `members_unreadable` (whose link names the installation) reveals a private organization, and an outsider gets `not_a_member` only when the organization is visible (design 437 gave it to anyone reading a repo). An App's installation token is never a member.
- **API.** `GET /api/v1/orgs/{org}` (`schema: 1`: `login`, `id`, `kind`, `access`, `role` `owner` or `member`, and the `repos` the caller sees), `GET /orgs/{org}/usage[?month=YYYY-MM]` and `GET /orgs/{org}/audit[?part=&since=&until=&format=json|csv]` (owners only); `openapi.json` has the three. New codes, all 403: `not_a_member`, `owner_only` and `members_unreadable` (`details.accept_url`, the installation's settings page, `Org::accept_url`). A bad `month` or `format` is `invalid_request` with `details.parameter`. `ryucad review` has no client for these yet and doesn't map the three codes.
- **The organization page.** `/{org}` (`web::organization::organization`, `templates/organization.html`, from the existing templates and `app.css`): the repositories as `/` lists them (open, failing, Merge in available, last run), this month's usage, an owner chip and, for owners, `/{org}/audit.csv` (`web::organization::audit_csv`). A member sees the installed repos that aren't excluded and are public or ones GitHub says they read (`web::organization::repos`); owners see every one. Signed out or an outsider: not found; `off`: `not_in_beta`. When members can't be read it shows only the `members_unreadable` banner, linking to the permission. The cache section is plan 6.C's (The shared cache on the service).
- **Usage.** `usage` rows by organization, month (its first day, UTC) and repo (`0` the organization's own): `committers` (GitHub user IDs), `build_seconds`, `artifact_bytes`, and `cache_bytes`, `cache_reads` and `cache_writes` (6.C's). Committers are the authors of a PR's commits (`GET …/pulls/{n}/commits`, up to GitHub's 250), read by the `report` job, bots (`type` `Bot` or a login ending `[bot]`) left out (`usage::committers`); build seconds the wall time of a job's sandbox steps (`Worker.sandbox_ms`), counted when it ends; artifact bytes those a job newly stores (`put_artifact`). All go through `usage::add`, and counting never fails a job. The API (`usage::month`, `Month::to_json`) gives members the totals with `private_committers` (the intended pricing's unit), and owners also `repos`. Nothing is enforced from usage but 6.C's cache cap, and nothing is billed.
- **The organization's audit.** `audit::record` fills `organization_id` from the installation's account, so the export is one query (`api::orgs::events`): the release events of every repo of the organization, as `…/repos/{o}/{r}/audit` gives one repo's, plus its own (`org::EVENTS`: `org.access`, `repo.exclude`, `repo.include`, and 6.C's `cache_token.created`, `cache_token.revoked`, `cache.trimmed`), oldest first; as JSON with `repo` on each event, or CSV with columns `at,repo,event,part,label,kind,project,pull,commit,actor,outcome,target` (`api::orgs::COLUMNS`, file `<org>-audit.csv`).
- **Teams in `judge`.** Before judging, the approvals job asks GitHub who of the PR's reviewers is in each team the release branch's rules name (`approvals::teams`, `Worker::memberships`): `GET /orgs/{org}/teams/{slug}/memberships/{login}` with the members token (`org::team_membership`), `active` a member, pending or 404 not, kept 5 minutes by (installation, team, login) in `Worker.teams`. `approvals::stand` takes the memberships (`&dyn Teams`): a team member's review is the rule's as a named login's is (bound to the record, stale, or a blocking change request). A rule naming another organization's team is refused (`Approvals::check_owner`, `approval_rule_invalid`: `@globex/quality is a team of globex, but the repository is acme's`), so `ryucad / release` fails as for rules that don't read.
- **`team_unreadable`.** When the installation hasn't accepted *Members (read)*, every team the rules name is unreadable (`Known.unreadable`): approvals through it count for nothing and the rule is unmet, never quietly met, said before anyone reviews as a `:warning: ``team_unreadable``: GitHub won't say who is in @acme/locked: …` line in `ryucad / release`'s summary.
- **`via`.** `Standing` gains `via` (each counted login and the teams it counted through where no rule names it directly) and `unreadable`. The check's table reads `quinn at ``1a2b3c4`` via @acme/quality`, and `GET …/pulls/{n}/approvals` gives each approval's `via` and each proposal's `unreadable`. After each judgement `Worker::record_via` writes `review.via` for every approving review: the union of its teams over the PR's proposals, `'{}'` for none, `NULL` for a review no 6.B judgement saw. The tags job signs those `via`s into the attestation (format 2; one of logins only stays format 1), asking GitHub now only for a review that judgement never saw, so a member leaving the team after the merge changes nothing (design 437 said teams as they stood at `merged_at`).
- **Team review requests.** A team a rule names is requested once per PR as `team_reviewers` by its slug (`approvals::request_body`), so GitHub notifies its members, and kept in `review_request` as `@org/slug`, lower case. A team GitHub refuses (422: no access to the repo) gets a line of its own: `GitHub wouldn't request a review from the team … (no access to this repository?)`.
- **The CODEOWNERS note.** When a PR changes `approvals`, `ryucad / release`'s summary also says whether the base's CODEOWNERS gives that project's `ryupdm.json` an owner. GitHub reads the first of `codeowners::PLACES` that exists (`.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`), patterns read as GitHub reads them (`codeowners::owners`: gitignore's, last match wins, a line without owners unowns), kept per project in `approvals::check::Owners`. The summary names the file and its owners, or warns `No code owner reviews changes to ``ryupdm.json``` and suggests `/<path>/ryupdm.json @<owner>/<release-team>` and requiring code owners' reviews in the branch's protection. It never changes the conclusion: who may change `approvals` is GitHub's to gate.
- **Uninstalling.** The hourly sweep (`housekeeping::sweep`, `Swept.organizations`) deletes an organization once none of its installations is left (they go 30 days after `installation.deleted`) and the row is a day old, with its usage and its own audit rows.
- **The App's settings.** *Organization permissions: Members (read)* and the *Organization* event, which every installation is asked to accept. Until one does, its page shows the banner, the API answers `members_unreadable`, and a rule naming one of its teams is unmet with `team_unreadable`; nothing else changes for it.
- **e2e.** `scripts/e2e.sh`'s `beta` stage relies on `ryupdm-service org exclude` (the seed of `!Seiraiyu/ryupdm-e2e-beta`). The `org` stage, with `GH_TOKEN`, is in the deploy's stages: `GET /api/v1/orgs/<owner>` names the organization `beta` or `paid`, the token's role and the fixture (`org: page`); its usage answers for this month (`org: usage`); its audit answers JSON (`org: audit`) and CSV with the `repo` column (`org: audit csv`), a note instead when `GH_TOKEN`'s account isn't an owner. The `teams` stage needs a service and a local ryucad that read teams in rules, `E2E_REVIEWER_TOKEN` and `E2E_TEAM` (a team holding the reviewer): on the fixture's `teams/` project under `1 of $E2E_TEAM`, `ryucad / release` waits and the team is asked; the reviewer's approval turns it green; once merged, a fresh clone's `release list` reads the tag as approved via the team. Without `E2E_TEAM` it is a note. It joins the deploy's stages once a pinned ryucad release reads teams.
- **Testing.** Postgres and unit tests: `db`'s `organizations_usage_and_the_operator` and `a_failed_seed_is_tried_again`; `org`'s `the_allow_list_seeds_access_once`, `the_operator_lists_and_sets`, `sizes_read_as_the_operator_writes_them`, `sizes_are_written_as_they_are_read`, `members_and_owners_are_githubs`, `an_organization_is_found_by_its_live_installation` and `team_memberships_are_githubs`; `github`'s `members_tokens_read_members_only`; `events`' `installations_are_organizations_off_until_set` and `reviews_of_an_organization_turned_off_queue_nothing`; `web::access`'s `the_organizations_access_and_excluded_repos`; `usage`'s `committers_are_authors_and_no_bots` and `usage_adds_up_by_organization_month_and_repo`; `housekeeping`'s `an_organization_goes_with_its_last_installation`; `attest`'s `revoked_keys_are_published_as_revoked`. The API's `an_organization_for_its_members`, `an_organization_whose_members_cant_be_read`, `an_organizations_usage` and `an_organizations_audit_across_its_repos` (snapshot `org_audit.csv`); the page's `an_organizations_page_for_its_members` and `a_personal_account_and_unreadable_members`; `approvals`' `memberships_known_before_judging` and `a_team_is_asked_as_a_team`; `approvals::check`'s `teams_in_the_summary`, `changed_rules_say_who_owns_them` and `the_codeowners_file_found_is_the_one_named`; `codeowners`' `patterns_as_github_reads_them`. Worker tests against the fake GitHub's memberships and teams (`set_member`, `set_team`, `members_unreadable`): `a_checked_pull_request_counts_its_usage`, `teams_approve_releases`, `a_team_github_wont_read_is_unmet` and `another_organizations_team_is_refused`. The team tests skip against a ryucad without teams in rules (`ryucad_has_teams`), so they run in CI's ryucad commit leg (`gh workflow run ci.yml -f ryucad_commit=<40 hex>`) until a pinned release has them.
- **Limits.** Invite-only: every new installation's organization starts `off` until the operator sets it, on the host only. Teams work only once the pinned ryucad reads them, since a rule naming one needs `ryupdm.json` format 3. Only the repository owner's teams are read. Memberships, owners and teams are GitHub's as of up to 5 minutes ago. Committers are counted from pull requests only. No roles, accounts or SSO of the service's own.

## Release packages on the service (decided in ryupdm phase 7)

The design is document 436 in the Coxswain planning project `ryucad-ryukei`; this is its plan 7.B, built in the private repo `Seiraiyu/ryupdm-service`, whose `deploy/README.md` says how it is run. The open side (the package, building and verifying it, the package tag and the clients) is Release packages in `ryupdm.md`. The service never assembles a package: it runs the pinned `ryucad release package` in its sandbox, so its package and a clone's rebuild are the same bytes.

- **An older ryucad.** At start a worker asks its ryucad `release package verify` of a file that isn't there, outside any project (`worker::has_packages`): one without packages refuses the subcommand (`usage`), and the service then queues no packages and shows none, so it deploys unchanged on such a ryucad.
- **Which releases.** The tags job, after a push to a release branch, queues one `package` job per record that became official in it (ruled or not, `packages::queue_new`), keyed by repo, project, part and label. Obsolete records get none. Earlier releases are packaged only on request. Package jobs run at the queue's lowest priority, behind every PR's jobs, and a job may wait (`job.not_before`) for its retry.
- **The job.** It fetches the official commit with tags and the dependency mirrors (`deps::locks`), reads the record and `ryupdm.json` there to work out the input key (`packages::Inputs::key`, design 44's key as `Manifest::key` gives it), and reuses a built package with that key whose zip the store still holds, with no step. Otherwise one step: `ryucad --no-daemon release package <part> --label <L> --out /out/package.zip`, under the sandbox's limits but with its own wall time, `RYUPDM_PACKAGE_TIMEOUT` (30 minutes by default; `Step::with_wall`). The zip goes into the store under the key ryucad answered (`application/zip`).
- **States.** A `package` row per release (migration 0010): `queued`, `building`, `built`, `failed` (ryucad refused, with its error: deterministic, never retried by itself, and built again only by another ryucad than `built_with`), `limit` (a sandbox limit or a fault: retried 1, 5 and 30 minutes later, then left for a request). It keeps the key, the package hash, the size, `<number>-<label>.zip`, `built_with`, ryucad's answer and its warnings.
- **The package tag.** For each built package, the service signs a `ryupdm.package_attestation` with its signing key (`attest::Signer`, over `ryupdm.package_attestation.1\0`, byte for byte as `ryupdm::package::attest` signs) and creates `ryupdm/<part>/<label>.package` at the official commit through the Git data API, as release tags are made. The row's `tag` is `created`, `present` (a tag already there, left alone), `unsigned` (no signing key: stored and listed, never tagged) or `failed` (GitHub refused: the next push to the release branch tries again, `packages::untagged`). The release index keeps each release's package tag as `release list` verified it at the tip (`package_tag`, `package_clause`, `package_hash`).
- **Retention.** Housekeeping never sweeps a zip that a `package` row names, however long unused: a package is what was sent. A row goes with its installation or when a repo admin deletes it. A built package whose zip the store lost is queued again on its next download (API, page or share link), and is `failed` with `package_lost` if the rebuild gives another hash.
- **Delivery.** `/api/v1` (`schema: 1`, under the pages' access checks, OpenAPI updated): `GET /repos/{o}/{r}/releases/{part}/{label}/package[?project=]` (the row, and a signed link valid for 10 minutes when built), `POST …/package` (a repo admin: build one that has none, or retry a `limit` or a refused one; `202` when queued), `DELETE …/package` (a repo admin: forget it and its share links), `POST …/package/share` (a repo writer: `days` 1 to 30, 7 by default) and `DELETE …/package/share/{id}` (a repo writer: revoke). `GET …/releases` gives each release's `package`. A share link is `/share/{id}` signed with `RYUPDM_URL_KEY`, downloaded with no sign-in until it expires or is revoked (then `403`), each use counted. Every link is the server's signed `/artifacts/{key}`, which redirects to a presigned GET when the store is S3. The Releases page has a Package column (the zip and its size, building, failed with ryucad's error on hover, or none) and the package tag's verdict beside the release tag's.
- **Audit.** `package_built`, `package_failed`, `package_signed` and `tag_created` (for `.package` tags), `package_requested`, `package_deleted`, `package_downloaded`, `package_shared` and `package_share_revoked`. A download through a share link has the link as its actor (`share`), and one from a public repo's page by someone signed out is `anonymous`.
- **Metrics.** `ryupdm_package_bytes` (the built zips, each key once) and, on a folder store (`RYUPDM_STORE=fs`), `ryupdm_artifacts_volume_bytes{kind="size"|"used"}`, which `deploy/alerts.yml`'s `RyupdmArtifactsVolumeFull` reads (over 80% for 30 minutes).
- **Revoking from ryucad.** The `ryucad review package` clients build, get and share, but don't revoke: revoking is the API's `DELETE …/package/share/{id}` (plan 452, question 450). `ryucad review package unshare <part> <label> <id>` over that route is the follow-up for ryucad.
- **e2e.** `scripts/e2e.sh`'s `packages` stage, on `Seiraiyu/ryupdm-e2e`'s `packages/` project (a plate with one drawing, put on `main` by the first run): a PR proposing the plate's next label, merged, gets its release tag and then its `.package` tag at the official commit; `ryucad review package get` downloads and verifies it; a fresh clone's `release package verify --rebuild` gives the same bytes; a share link downloads with no token and is refused once revoked. It needs `--ryucad` with packages, and joins the deploy's stages once a pinned ryucad release has them. Its `packages: docker sandbox` row is design 436's sandbox test on the deployed worker.
- **Testing.** Unit tests of the states and retries, the key, the queue's order (`packages_go_last_and_wait_their_turn`), share-link signing and expiry, retention (`packages_are_kept_while_their_release_is`) and the metrics; the API's `a_releases_package_and_building_one`, `a_lost_package_is_queued_again`, `share_links_download_until_revoked_or_expired` and `the_releases_list_says_each_releases_package` over Postgres; the Releases page's snapshot; `sandbox::tests::a_step_may_have_a_wall_time_of_its_own` with the process runner; worker tests `the_worker_knows_whether_its_ryucad_has_release_packages` and `official_releases_are_packaged_stored_tagged_and_reused`, where a fresh clone's `release package verify` accepts the service's tag; and, with Docker, `tests/sandbox.rs`'s `packages_build_in_the_sandbox` (the package step under `--network none` with the package timeout, then verified there), which skips on an image whose ryucad has no packages. The package tests run in CI's ryucad commit leg (`gh workflow run ci.yml -f ryucad_commit=<40 hex>`) until a pinned release has packages.
