## Annotations in the daemon (decided in ryucad phase 19)

The design is document 374 in the Coxswain planning project `ryucad-ryukei`; this is its plan 19.A (phases 1 to 3).

- **Files.** `annotations/<id>.json` at the project's root, one file each (kind `ryucad.annotation`, format 1, `doc::annotation`): `id`, `by` (`{participant, kind}`: the participant's name as `participant.list` gives it, `human` or `agent`), `at` (UTC to the second, `YYYY-MM-DDTHH:MM:SSZ`), `status` (`open`, `in_progress`, `done`, `rejected`), `claimed_by` (set exactly while `in_progress`), `pins` (`{ref, point_m?}` or `{part, point_m}`, in meters), `comment` (required unless it carries a change), `view` (a named view's fields), `change` (`{request, rough, base, writes, after}`, whose `base` and `writes` name only files a model edit writes: `ryucad.json`, `ryucad.lock`, `materials.json`, `parameters.json`, `ryupdm.json` and `parts/**/*.json`, so an annotation arriving by a merge or written by hand never has `annotation.apply` write into `.git`, `.gitattributes` or `imports/`; `doc::annotation::is_proposable_path`), `replies` by `r1`, `r2`, … one past the largest, and `resolution` (`{by, at, note, applied}`, set exactly while `done` or `rejected`; a rejection gives its reason). Every key is written, `null` where it has nothing. IDs are 10 characters of RFC 4648 base32 from 50 random bits (`annotation::new_id`), or a fixed sequence from `RYUCAD_ID_SEED`; the clock is `RYUCAD_NOW` when that is a time. Sessions track the folder (notifications, the activity log, undo) and Git revisions read it, but no revision counts it: the project's and parts' revisions, release content hashes and rebuilds never read an annotation, so an agent's `--expect` never conflicts with one.
- **Derived states.** Never written, worked out from the working files each time they are asked for (`annotation::derive`, `entry`): `outdated` (pins that don't resolve now, each `{pin, ref, code, was?, removed_by?, candidates?}`), `applied` (only with a change: every file it writes is those bytes in the working files, or an annotation whose change stands on it, its `after` at any depth, is applied, having written over it) and `stale` (only of a change not applied: a file it touches isn't, with its unapplied `after` chain laid over the working files, the bytes its `base` records; `{path, base, now}`). `applied` is derived because `annotation.apply --keep-open` leaves an annotation open with no resolution.
- **Git.** `drivers::LINES` gains `annotations/*.json merge=ryucad diff=ryucad text eol=lf` (it moved the `diff` golden section and `tests/golden/scale.txt`, which textconv and write `.gitattributes`). The merge driver merges an annotation per key, `by`, `view` and `change` one value each, but `status`, `claimed_by` and `resolution` go together (changed differently on both sides they are one conflict at `/status`, never a done annotation claimed), and replies merge per reply: both sides number a new reply one past the largest, so theirs' takes the next free ID where ours took it, and a reply both changed differently is a `value` conflict. Textconv gives `by`, `claimed_by`, each pin, the change's method (`(rough)`, `after …`) and the files it writes, each reply and the resolution a line, the request last; `diff` gives a top-level `annotations` block (`added`, `removed`, `changed` by JSON pointer) when any differs. Doctor reports an annotation that doesn't read (or holds another ID) as `invalid_document`, one not canonical `non_canonical`, anything else in the folder `unknown_file`; pins that no longer resolve are the listing's `outdated`, not an issue.
- **The capture.** The session is a request's write target: `Session::write_json`, `write_bytes`, `remove_file`, `read_file`, `read_text`, `project_revision` and `check_project_revision` write and read the folder, or a capture session's record of the files. `Session::capturing(files)` is a session over `files` whose writes are kept (`captured`) and read back as if on disk, a reload taking them in (`after_change` lets go of the results they made stale, as the folder's changes do). `annotation::tests::proposable_handlers_write_through_the_session` reads ryucad's sources and fails on a free write function (`write_json(`, `write_atomic(`, `remove_file(`, `fs::write(`, `remove_dir_all(`…) outside the files no proposable request reaches (`activity.rs`, `cli.rs`, `drivers.rs`, `review.rs`, `export.rs`, `doctor.rs`, `validate.rs`, `worktree.rs`, `import/plan.rs`) and lines marked `// no session:`.
- **Proposals.** `annotation.propose` (`{request: {method, params}, comment?, pins?, rough?}`) runs a request of `annotation::propose::PROPOSABLE` (the 18 model edits: features, sketches, parameters, assembly moves, appearance, materials, properties, item numbers, named views, explodes) through `server::dispatch` in a capture session over its proposer's draft: the working files with the proposer's open changes laid over them, each after those its `after` names, then by `at`, then ID, a change laid only while its `base` still matches (a stale change would put back bytes someone has since changed). What it would have written becomes the change: each file's content (`null` for a deletion) in `writes`, its BLAKE3 as the draft had it in `base`, and `after` the laid changes touching the same files. Anything else is `invalid_param` naming the method; a refusal is the request's own; a request that changes nothing is `operation_no_effect`; none of them makes an annotation. The answer is the annotation and the request's own answer.
- **Revisions and apply.** `annotation:<id>` is a revision everywhere one is taken (`Session::at`, `files_at`): the working files with the change and its unapplied chain laid over them, kept with the revisions by a hash of those files; `annotation_not_found` for an ID there isn't, `invalid_param` for one with no change. A stale one still answers, with an `annotation_stale` warning in the result's `warnings` (`files`), lifted into the CLI's envelope for `diff`, `inspect`, `mesh`, `render`, `mass` and `interference`; a rebuild's answer is raw text (#533) and carries none. `annotation.apply` (`id`, `keep_open`, `expect`) checks every step of the chain, then the change itself, against the files as the steps before leave them (`annotation_stale` naming the first and its files, before anything is written), writes them in order and closes each `done` (`resolution.applied: true`) unless `keep_open`: one logged, undoable change; `operation_no_effect` when it is applied already.
- **Lifecycle, CLI and notifications.** `annotation.create` (pins resolved against the author's draft; `camera` or `with_view`), `annotation.list` (`status`, `part`, `by`, `open`; newest first, `schema: 1`, files that don't read under `faults`), `annotation.show` (pins resolved with their kind and what `inspect` gives now, the change's files), `annotation.reply`, `annotation.claim` (`annotation_claimed` naming who holds it), `annotation.resolve` (`note`), `annotation.reject` (`reason`, required), `annotation.reopen` (the resolution kept as a reply), `annotation.edit` and `annotation.delete` (their author's while open and unclaimed, `annotation_claimed` or `invalid_param` otherwise; anyone deletes a closed one); every write but `list` and `show` is a logged, undoable change, guarded by the file's BLAKE3 (`expect`, `conflict`). The author is the connection's participant, else the agent named by `as` (`--as`, `RYUCAD_PARTICIPANT`), else `agent`. CLI `ryucad annotations add|propose|list|show|reply|claim|apply|resolve|reject|reopen|edit|delete`, whose help is `annotation::ETIQUETTE`: how an agent works through annotations (list the open ones when it starts, ask before acting on ones it wasn't asked about, claim, diff and render the revision, apply or edit, reply, resolve or reject with a reason, `watch --topic annotations`), shown again in the app's Driving ryucad from an agent window; never enforced. `annotation.changed` (topic `annotations`) gives each annotation added or changed as listings give it, its derived states included, and the IDs `removed`, worked out only while anyone watches and the files moved.
- **Modes.** `live::Mode` (`view`, `annotate`, `edit`) is participant view state, `mode` in `participant.changed`, `view` on every hello. `participant.mode` (`ryucad mode view|annotate|edit`) sets the caller's own participant only: no request sets another's, so an agent never puts a person's window into Direct edit; `no_live_session` in process. `server::answer_live` refuses a human participant's request its mode doesn't allow, before it runs: annotation writes (`Request::annotates`) need `annotate` or `edit`, every other write (`mutates`, undo and `annotation.apply` included) `edit` (`Request::needs`); `participant_mode` with the participant, its `mode` and what it `needs`. Reading is never refused, and an agent's mode, or a connection that said no hello, refuses nothing. A refused request prepares nothing without the lock (`Serve::prepare` takes the live session and the caller), so a View-mode human's `deps.add` or `deps.update` fetches nothing. `export` needs no mode (the window exports in View), so its `out` may never be a project file whoever asks: a path the session tracks (`session::tracked`: the root files, `parts/`, `releases/`, `imports/`, `annotations/`) or one through a dot folder (`.git`) is `invalid_param` at `out`; elsewhere in the project folder it writes as before (a departure from the review's "anywhere inside the project folder", agreed with the coxswain: `ryucad export p --out p.step` in the project is the natural use). The app's window sets Direct edit when it connects (`core::link`), so it writes as before until 19.B gives it its modes.
- **Testing.** `ryu-doc`'s `annotation_codes_are_the_agents_to_fix`; `doc::annotation`'s round trip, faults by pointer, newer format and IDs; `annotation::tests` (IDs and the clock, `outdated`, `stale` and `applied`, unreadable files, the source guard, the lifecycle, authors, listings, the etiquette); `annotation::propose::tests` (drafts in order, every proposable request captured byte for byte as it would be written, proposals standing on earlier ones, refusals, `annotation:` revisions and their warning, apply's chain, staleness and `keep_open`); `session.rs`' tracking, capture and revision tests; `merge.rs`' replies and status tests and `drivers.rs`' line; `diff.rs`' textconv and diff; `doctor.rs`' `annotations_that_dont_read_are_reported`; `server.rs`' `annotations_are_announced_with_their_derived_states`, `a_participant_sets_its_own_mode` and `a_humans_writes_are_refused_outside_their_mode_and_an_agents_never`, `an_export_never_writes_over_a_project_file_whoever_asks` and `a_view_mode_humans_dependency_fetch_is_refused_before_it_fetches`; `doc::annotation`'s `a_change_writes_the_files_model_edits_write`; `tests/cli.rs`' `annotations_from_the_cli` and `modes_from_the_cli` both ways (`Pair` sets `RYUCAD_ID_SEED` and `RYUCAD_NOW`); `tests/daemon.rs`' `a_human_writes_only_in_the_mode_that_allows_it`; the `annotations` golden section (proposals over the showcase, their writes, bases and `annotation:` rebuilds, one thread and four); the app's `the_agents_window_gives_the_annotation_etiquette`; the `merge` fuzz target's `0xf1` mode (every clean merge reads as an annotation).
