## Annotations in the daemon (decided in ryucad phase 19)

The design is document 374 in the Coxswain planning project `ryucad-ryukei`; this is its plan 19.A (phases 1 to 3).

- **Files.** `annotations/<id>.json` at the project's root, one file each (kind `ryucad.annotation`, format 1, `doc::annotation`): `id`, `by` (`{participant, kind}`: the participant's name as `participant.list` gives it, `human` or `agent`), `at` (UTC to the second, `YYYY-MM-DDTHH:MM:SSZ`), `status` (`open`, `in_progress`, `done`, `rejected`), `claimed_by` (set exactly while `in_progress`), `pins` (`{ref, point_m?}` or `{part, point_m}`, in meters), `comment` (required unless it carries a change), `view` (a named view's fields), `change` (`{request, rough, base, writes, after}`, whose `base` and `writes` name only files a model edit writes: `ryucad.json`, `ryucad.lock`, `materials.json`, `parameters.json`, `ryupdm.json` and `parts/**/*.json`, so an annotation arriving by a merge or written by hand never has `annotation.apply` write into `.git`, `.gitattributes` or `imports/`; `doc::annotation::is_proposable_path`), `replies` by `r1`, `r2`, … one past the largest, and `resolution` (`{by, at, note, applied}`, set exactly while `done` or `rejected`; a rejection gives its reason). Every key is written, `null` where it has nothing. IDs are 10 characters of RFC 4648 base32 from 50 random bits (`annotation::new_id`), or a fixed sequence from `RYUCAD_ID_SEED`; the clock is `RYUCAD_NOW` when that is a time. Sessions track the folder (notifications, the activity log, undo) and Git revisions read it, but no revision counts it: the project's and parts' revisions, release content hashes and rebuilds never read an annotation, so an agent's `--expect` never conflicts with one.
- **Derived states.** Never written, worked out from the working files each time they are asked for (`annotation::derive`, `entry`): `outdated` (pins that don't resolve now, each `{pin, ref, code, was?, removed_by?, candidates?}`), `applied` (only with a change: every file it writes is those bytes in the working files, or an annotation whose change stands on it, its `after` at any depth, is applied, having written over it) and `stale` (only of a change not applied: a file it touches isn't, with its unapplied `after` chain laid over the working files, the bytes its `base` records; `{path, base, now}`). `applied` is derived because `annotation.apply --keep-open` leaves an annotation open with no resolution.
- **Git.** `drivers::LINES` gains `annotations/*.json merge=ryucad diff=ryucad text eol=lf` (it moved the `diff` golden section and `tests/golden/scale.txt`, which textconv and write `.gitattributes`). The merge driver merges an annotation per key, `by`, `view` and `change` one value each, but `status`, `claimed_by` and `resolution` go together (changed differently on both sides they are one conflict at `/status`, never a done annotation claimed), and replies merge per reply: both sides number a new reply one past the largest, so theirs' takes the next free ID where ours took it, and a reply both changed differently is a `value` conflict. Textconv gives `by`, `claimed_by`, each pin, the change's method (`(rough)`, `after …`) and the files it writes, each reply and the resolution a line, the request last; `diff` gives a top-level `annotations` block (`added`, `removed`, `changed` by JSON pointer) when any differs. Doctor reports an annotation that doesn't read (or holds another ID) as `invalid_document`, one not canonical `non_canonical`, anything else in the folder `unknown_file`; pins that no longer resolve are the listing's `outdated`, not an issue.
- **The capture.** The session is a request's write target: `Session::write_json`, `write_bytes`, `remove_file`, `read_file`, `read_text`, `project_revision` and `check_project_revision` write and read the folder, or a capture session's record of the files. `Session::capturing(files)` is a session over `files` whose writes are kept (`captured`) and read back as if on disk, a reload taking them in (`after_change` lets go of the results they made stale, as the folder's changes do). `annotation::tests::proposable_handlers_write_through_the_session` reads ryucad's sources and fails on a free write function (`write_json(`, `write_atomic(`, `remove_file(`, `fs::write(`, `remove_dir_all(`…) outside the files no proposable request reaches (`activity.rs`, `cli.rs`, `drivers.rs`, `review.rs`, `export.rs`, `doctor.rs`, `validate.rs`, `worktree.rs`, `import/plan.rs`) and lines marked `// no session:`.
- **Proposals.** `annotation.propose` (`{request: {method, params}, comment?, pins?, rough?}`) runs a request of `annotation::propose::PROPOSABLE` (the 18 model edits: features, sketches, parameters, assembly moves, appearance, materials, properties, item numbers, named views, explodes) through `server::dispatch` in a capture session over its proposer's draft: the working files with the proposer's open changes laid over them, each after those its `after` names, then by `at`, then ID, a change laid only while its `base` still matches (a stale change would put back bytes someone has since changed). What it would have written becomes the change: each file's content (`null` for a deletion) in `writes`, its BLAKE3 as the draft had it in `base`, and `after` the laid changes touching the same files. Anything else is `invalid_param` naming the method; a refusal is the request's own; a request that changes nothing is `operation_no_effect`; none of them makes an annotation. The answer is the annotation and the request's own answer.
- **Revisions and apply.** `annotation:<id>` is a revision everywhere one is taken (`Session::at`, `files_at`): the working files with the change and its unapplied chain laid over them, kept with the revisions by a hash of those files; `annotation_not_found` for an ID there isn't, `invalid_param` for one with no change. A stale one still answers, with an `annotation_stale` warning in the result's `warnings` (`files`), lifted into the CLI's envelope for `diff`, `inspect`, `mesh`, `render`, `mass` and `interference`; a rebuild's answer is raw text (#533) and carries none. `annotation.apply` (`id`, `keep_open`, `expect`) checks every step of the chain, then the change itself, against the files as the steps before leave them (`annotation_stale` naming the first and its files, before anything is written), writes them in order and closes each `done` (`resolution.applied: true`) unless `keep_open`: one logged, undoable change; `operation_no_effect` when it is applied already.
- **Lifecycle, CLI and notifications.** `annotation.create` (pins resolved against the author's draft; `camera` or `with_view`), `annotation.list` (`status`, `part`, `by`, `open`; newest first, `schema: 1`, files that don't read under `faults`), `annotation.show` (pins resolved with their kind and what `inspect` gives now, the change's files), `annotation.reply`, `annotation.claim` (`annotation_claimed` naming who holds it), `annotation.resolve` (`note`), `annotation.reject` (`reason`, required), `annotation.reopen` (the resolution kept as a reply), `annotation.edit` and `annotation.delete` (their author's while open and unclaimed, `annotation_claimed` or `invalid_param` otherwise; anyone deletes a closed one); every write but `list` and `show` is a logged, undoable change, guarded by the file's BLAKE3 (`expect`, `conflict`). The author is the connection's participant, else the agent named by `as` (`--as`, `RYUCAD_PARTICIPANT`), else `agent`. CLI `ryucad annotations add|propose|list|show|reply|claim|apply|resolve|reject|reopen|edit|delete`, whose help is `annotation::ETIQUETTE`: how an agent works through annotations (list the open ones when it starts, ask before acting on ones it wasn't asked about, claim, diff and render the revision, apply or edit, reply, resolve or reject with a reason, `watch --topic annotations`), shown again in the app's Driving ryucad from an agent window; never enforced. `annotation.changed` (topic `annotations`) gives each annotation added or changed as listings give it, its derived states included, and the IDs `removed`, worked out only while anyone watches and the files moved.
- **Modes.** `live::Mode` (`view`, `annotate`, `edit`) is participant view state, `mode` in `participant.changed`, `view` on every hello. `participant.mode` (`ryucad mode view|annotate|edit`) sets the caller's own participant only: no request sets another's, so an agent never puts a person's window into Direct edit; `no_live_session` in process. `server::answer_live` refuses a human participant's request its mode doesn't allow, before it runs: annotation writes (`Request::annotates`) need `annotate` or `edit`, every other write (`mutates`, undo and `annotation.apply` included) `edit` (`Request::needs`); `participant_mode` with the participant, its `mode` and what it `needs`. Reading is never refused, and an agent's mode, or a connection that said no hello, refuses nothing. A refused request prepares nothing without the lock (`Serve::prepare` takes the live session and the caller), so a View-mode human's `deps.add` or `deps.update` fetches nothing. `export` needs no mode (the window exports in View), so its `out` may never be a project file whoever asks: a path the session tracks (`session::tracked`: the root files, `parts/`, `releases/`, `imports/`, `annotations/`) or one through a dot folder (`.git`) is `invalid_param` at `out`, judged with ASCII case folded and each name's trailing dots and spaces dropped on every platform (Windows and macOS would write `RYUCAD.JSON` or `Parts/p/part.json` over the project's own, Windows `ryucad.json.`); an existing `out` is also judged by its canonical path (8.3 names, Unicode case folds), and an NTFS stream suffix (`ryucad.json::$DATA`) is dropped, so a name the file system resolves to a project file is refused too (#581); elsewhere in the project folder it writes as before (a departure from the review's "anywhere inside the project folder", agreed with the coxswain: `ryucad export p --out p.step` in the project is the natural use). The app's window sets Direct edit when it connects (`core::link`), so it writes as before until 19.B gives it its modes.
- **Testing.** `ryu-doc`'s `annotation_codes_are_the_agents_to_fix`; `doc::annotation`'s round trip, faults by pointer, newer format and IDs; `annotation::tests` (IDs and the clock, `outdated`, `stale` and `applied`, unreadable files, the source guard, the lifecycle, authors, listings, the etiquette); `annotation::propose::tests` (drafts in order, every proposable request captured byte for byte as it would be written, proposals standing on earlier ones, refusals, `annotation:` revisions and their warning, apply's chain, staleness and `keep_open`); `session.rs`' tracking, capture and revision tests; `merge.rs`' replies and status tests and `drivers.rs`' line; `diff.rs`' textconv and diff; `doctor.rs`' `annotations_that_dont_read_are_reported`; `server.rs`' `annotations_are_announced_with_their_derived_states`, `a_participant_sets_its_own_mode` and `a_humans_writes_are_refused_outside_their_mode_and_an_agents_never`, `an_export_never_writes_over_a_project_file_whoever_asks` and `a_view_mode_humans_dependency_fetch_is_refused_before_it_fetches`; `doc::annotation`'s `a_change_writes_the_files_model_edits_write`; `tests/cli.rs`' `annotations_from_the_cli` and `modes_from_the_cli` both ways (`Pair` sets `RYUCAD_ID_SEED` and `RYUCAD_NOW`); `tests/daemon.rs`' `a_human_writes_only_in_the_mode_that_allows_it`; the `annotations` golden section (proposals over the showcase, their writes, bases and `annotation:` rebuilds, one thread and four); the app's `the_agents_window_gives_the_annotation_etiquette`; the `merge` fuzz target's `0xf1` mode (every clean merge reads as an annotation).

## What the daemon gives the window (decided in ryucad phase 19)

The design is document 374 in the Coxswain planning project `ryucad-ryukei`; this is its phase 4, plan 19.B (story 4.1).

- **Drafts.** `draft:<name>` is a revision everywhere one is taken (`session::DRAFT`, `Session::draft_files`, `server::files_at`): the working files with the human participant `name`'s open, unapplied proposed changes laid over them in order, exactly as `annotation.propose` lays them (`annotation::propose::laid`), so what a window draws is what its next proposal stands on. Answers name it `{rev, draft, annotations}` (the IDs laid); someone with no open changes has the working files as a draft; `draft:` alone is `invalid_param`. A draft's session is kept among the revisions by the files' hash, as an `annotation:<id>`'s is (`Session::at_files`, which both share). A change's `after` names only earlier changes touching the same files, so `annotation:<last>` isn't the whole draft once a person suggests changes to two parts: hence a revision of its own (question 283).
- **Reads at a revision.** `feature.show`, `param.list`, `props.get`, `sketch.get`, `path.get` and `sweep.get` take `rev` (CLI `--rev`), as `inspect`, `mesh.get` and `rebuild` do, so the window's forms and drawings read the draft; `feature.show`'s `revision` is the revision's, so a proposal made from a form read at the draft is guarded by it.
- **Pins in renders.** `display.annotations` (a user preference, default true) says whether the app draws pins. `render --annotations` (proto `annotations`, default false) draws each open annotation's pins that carry a point, on the rendered part and its occurrences (an occurrence's pin point is in its own part's frame, placed by the occurrence's pose as drawn), a dot in `render::ANNOTATION` with its number (`Geometry::add_marker`). A marker's number is its annotation's place among the open ones, oldest first, from 1 (`annotation::markers`), the same as the app's. No render without `--annotations` moved a pixel.
- **Testing.** `annotation::propose::tests::a_persons_draft_is_a_revision` and `forms_and_drawings_read_a_draft`; `annotation::tests::markers_number_open_annotations_oldest_first`; `server::tests::renders_draw_annotations_only_when_asked`; `config`'s overlay preferences; `tests/cli.rs`'s parity test. No golden hash moved.

## Controlled edits (decided in ryucad phase 19)

The design is document 374 in the Coxswain planning project `ryucad-ryukei`; this is its phase 5, plan 19.C.

- **The daemon.** `assembly.move` and `assembly.solve`'s moves take `about` (three quantities: the point in the assembly's frame the turn's axis runs through; the instance's origin when left out; refused alone, `invalid_param` at `about`; CLI `--about`). `assembly.solve` takes `rev` (any revision a read takes, a person's `draft:` included, named in the answer's `rev`; CLI `--rev`) and `mates` (each a mate's fields as `feature.add` takes them, run as `feature.add` in a capture session over the files at `rev` and solved with the rest, never written; a refusal is `feature.add`'s own with `pointer` `/mates/<i>`, its own pointer kept as `field`; CLI `--mate JSON`, repeatable). No feature format moved and no golden hash.
- **Move and turn handles** (`core::mover`, `edit.move`, a toolbar toggle and on instance rows and occurrences' entities). On one selected instance of the shown assembly that `Model::movable` lets move (else no handle, and the status line says why): three arrows and three rings at the middle of its drawn boxes, in the triad's colours, along the assembly's axes or, with Own axes, the instance's. A drag snaps (1 mm in metric default units, 0.1 in in imperial ones, 15° a turn; Shift a tenth) and previews (`assembly.solve` with `component`, at the drawn revision, when the value changes, one at a time, at most every `DRAG_EVERY`); letting go leaves the value field open, focused and its text selected (question 333): Enter sends `assembly.move` (a turn with `about` the middle), Esc drops the value and its preview, a second Esc the tool. A click on a handle opens the field at 0. Typed text reads as a quantity (bare: the default unit, or degrees). Instances only: datums and sketches' placements are typed in their forms (question 334; a departure from design 374, which named them).
- **The Mate dialog** (`core::mating`, `ui::mate`, `edit.mate`, Edit > Mate… and the same context menus). A face, edge or vertex picked on each of two instances (`pick::Filter::connectors`; picks never select, and one the dialog refuses, such as a second pick on the first's instance, is said in it), a form, its angle and distance, Flip (`b_offset.flip`). Every change previews (`assembly.solve` with `mates` at the drawn revision, its poses drawn as a drag's); the daemon's refusal shows in the dialog and disables Add (Suggest in Annotate), which sends `feature.add`. Esc closes it before it clears the selection.
- **Rough drags.** In Annotate the freehand drag's `assembly.move` is proposed with `rough: true` and the comment `Move about here` (`workspace::ROUGH_COMMENT`); when the proposal answers, the window chooses its annotation, puts the comment in the Annotations tile's Edit box and opens the tile (`Workspace::wants_tile`). In Direct edit it writes as before.
- **Modes.** Each is a request through `Workspace::send`, so 19.B's gate proposes it in Annotate, refuses it in View and writes it in Direct edit; `edit.move` and `edit.mate` are disabled in View.
- **Testing.** `assembly.rs`' `a_turn_about_a_point_swings_the_origin_round_it`, `mate.rs`' `a_solve_previews_a_turn_about_a_point` and `a_solve_previews_a_mate_without_writing_it`, `annotation::propose`'s `a_solve_reads_a_draft`, `tests/cli.rs`' `controlled_edits_from_the_cli` both ways; `core::mover`, `core::mating` and `core::command` unit tests; `tests/workspace.rs`' `the_move_tool_previews_and_writes_a_typed_move` and `the_mate_dialog_previews_and_adds_a_mate`; `tests/annotations.rs`' `a_freehand_drag_in_annotate_is_a_rough_suggestion_with_a_comment_to_edit`; window tests `a_typed_move_by_the_handle_is_written_in_direct_edit_and_proposed_in_annotate`, `a_dragged_ring_previews_and_esc_drops_the_value_then_the_tool`, `a_fixed_instance_shows_no_handles_and_says_why`, `a_mate_is_picked_previewed_and_added_from_its_dialog` and `the_mate_dialogs_add_waits_for_both_picks_and_esc_closes_it`.

## Redline marks in the daemon (decided in ryucad phase 20)

The design is document 423 in the Coxswain planning project `ryucad-ryukei`; this is its plan 20.A (phases 1 to 3).

- **Files.** An annotation gains `marks` (`doc::redline`): `{part, list}`, `part` the model they were drawn on (the frame `view` is in), each mark `{kind, in, …, touches}`: `line`, `arrow` (tail, tip), `ellipse` and `rectangle` (two opposite corners), `stroke` (2 to 2,048 points, closed when its ends meet), `text` (one point, one line of 1 to 120 characters). In the view (`in: view`, `xy_m` in metres in the plane through the view's target square to its line of sight, `x` right, `y` up), or a stroke on the faces (`in: face`, `on` an occurrence or solid of `part`, `points_m` in that part's frame). At most 64 marks, coordinates within the size box, no styles. Format 2 of the annotation file only when it has marks: a file with none is format 1 byte for byte, so no stage 19 file or golden moved. Marks need a `view`. Faults are `invalid_document` at the mark's pointer.
- **Touches.** Worked out once, when marks are written, from the annotation's view over the author's draft: the render scene (`server::render_scene`, split from `render`) is built with entity tags (`render::Tags`) and rasterized by `render::pick` into the nearest face, the nearest visible edge or sketch curve within 6 pixels and the nearest visible vertex or sketch point within them, ranked as the window's picker ranks them, 600 pixels high and as wide as the marks need (at least 800). A line's or arrow's ends take what is picked there; an ellipse, rectangle or closed stroke the faces under most of its inside; an open stroke the edges, else faces, it passes over; a face stroke the faces under its points; text nothing (at most 16 a mark, most first). Touches given with a mark are kept, each checked to resolve in the draft. The pick pass leaves out the author's participant's hidden set and cuts with the view's section planes. Marks are never moved when the model changes; an annotation is `outdated` while a touch doesn't resolve (`outdated_marks`, by mark and touch, with the resolver's own code: `not_found` for a name the session never learnt, `reference_unresolved` for one it did; a touch given that doesn't resolve is refused with the same code).
- **Reading.** `annotation.show`, `create` and `edit` answer each mark in words (`redline::words`: points in the plane and in the model's frame, an arrow's length and direction, a box, each touch resolved now); listings and `annotation.changed` give a summary (`{part, count, kinds}`, and since 20.B `list`, the marks themselves, for the window to draw). `render --annotation <id>` renders its view with its pins (numbered by their place in it) and marks, at any revision; `--annotations` draws open annotations' marks too. View marks are on a new overlay pass (`render::Overlay`: lines and arrowheads 3 pixels wide, drawn over everything, never cut; text as notes on a box), face strokes depth-tested lines; each in its author's participant colour (`render::participant`, which the app now re-exports), closed annotations' at 40%. No other render's pixels moved.
- **CLI.** `annotations add|edit --marks JSON|@FILE`, shorthands `--arrow`, `--line`, `--ellipse`, `--rectangle` (`X1,Y1:X2,Y2`) and `--text X,Y=TEXT` in the default unit (sent in that order after the JSON's), `--model PART`, `add --of VIEW` (a named view as the annotation's view), `edit --no-marks`; `render --annotation ID` (`usage` with a camera or view). No new method or error code.
- **Git.** Textconv gives each mark a line in millimetres with its touches; the merge driver takes `marks` as one value; diff lists marks' changes by pointer; doctor reports marks that don't read as `invalid_document`; the merge fuzz target's `0xf1` mode adds and removes marks.
- **Testing.** `doc::redline` and `doc::annotation` unit tests; `render::pick`'s and the overlay's; `redline`'s (the plane, outlines, the pick size, drawing); `annotation` tests over a drilled plate from a corner (each kind's touches, a face stroke, touches given, limits, shorthands, a draft's touches, outdated through a touch, words); `server`'s render tests; `tests/cli.rs`' `redlines_from_the_cli` both ways; the `redlines` golden section (5.2 s in a debug build on cox-worker-1, an Intel Xeon E5-2650 shared at a load of about 14, 2026-11-10); the merge fuzz target ran 10,532 inputs in 61 s with no find.
