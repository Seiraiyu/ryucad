## Diff and check (decided in ryucad phase 3)

The design is document 48 in the Coxswain planning project `ryucad-ryukei`; these are its phases 1 and 2, plan 3.A.

- **Sources and revisions.** `doc::source::Source` lists folders and reads files; `Project::load_from` loads from the folder or from files in memory alike, faults and revisions included (empty folders aren't in Git). `git::revision` resolves a revision expression with gix (`rev_not_found` otherwise; outside a repository `not_a_git_repo`) and gives the project's files there (the manifest, `.gitattributes`, everything under `parts/`) and the project folder's tree. `rebuild`, `mesh.get` and `inspect` take `rev` (CLI `--rev`), `working` meaning the files on disk: the session answers from a frozen session over that revision, one of `session::REVISIONS` (4) kept by tree, most recently used first, which never reads the disk and starts from the working files' caches, so only what differs is rebuilt. Answers name the `commit`.
- **Textconv.** `ryucad git textconv <file>` (plain text, not JSON: Git reads it as the file) prints a header (kind, a feature's type, format), then one sorted line per value (`extent.length = 15 mm`, references as `<feature>/<name>`, arrays of values on one line); a part lists its features one per line in order; a sketch gives each entity and constraint a line and its positions last, apart. Anything that isn't JSON comes back as it is.
- **Registration.** `ryucad init` writes `.gitattributes` in the project folder, a project file the session tracks, so its repair is logged and undoable. `ryucad git install` writes the driver entries (this binary, single-quoted, forward slashes) to the repository's config, `--global` to the user's; the installers run the global one when Git is there. It is CLI only, as `init` is: no session, and the app has no use for it. `doctor` reports `gitattributes_missing` (repaired by adding the lines, keeping the rest) and `git_drivers_missing` in a repository. Plan 3.B added the merge driver and the hooks (see Merge below).
- **Diff.** `diff` (`ryucad diff [--from REV] [--to REV] [--part] [--model] [--positions] [--all]`; `HEAD` and `working` by default) compares two revisions' files as JSON, so broken files and expressions show as written: the manifest by pointer; per part its order (`added`, `removed`, `moved`: those kept outside the longest run both keep), its parameters as written, each feature `added`, `removed`, `changed` or `same` with `changes` by JSON pointer (arrays as one value), a sketch by entity and constraint (`positions` summarised as `changed`/`same`, listed with `--positions`), a file that doesn't read as `invalid`. `--model` rebuilds both and adds, under each feature whose result differs, `model`: each side's result and, for bodies, the faces, edges and vertices `gone`, `new` and `changed` (by the bits of their geometry and boundary) and the box; for sketches, state and freedom. A renamed face is one gone and one new.
- **Check.** `check` (`ryucad check [part] [--against REV]`) rebuilds from nothing and reports findings: `doctor`'s issues (`source: doctor`; stale sketches are among them), `feature_failed`, `faces_intersect` and `cannot_check` (from `check_intersections`), `mesh_faults` at normal quality, and `cache_mismatch` where the session's cache differs from the fresh rebuild. Any error fails it with `check_failed` (exit 1), the report in its details. With a part it keeps the project's own issues and that part's. `--against` adds `diff --model` from that revision to the working files. A merge left unfinished fails it: conflict records are `doctor`'s `merge_conflict`, paths Git left unmerged `unmerged_path`. Release findings join it (`source: release`; see Local PDM below).
- **Testing.** Unit tests per module (sources, revisions, textconv, structural and model diffs, check), real repositories in tests (`git` with a fixed identity, and in the CLI scenario fixed dates so two repositories' commits match), `git install` with an isolated `HOME`, the installer tests, and the `diff` section of `tests/golden/rebuild.txt`.

## Merge (decided in ryucad phase 3)

The design is document 48 in the Coxswain planning project `ryucad-ryukei`; these are its phases 3 and 4, plan 3.B.

- **Driver.** `.gitattributes` gives `ryucad.json`, `ryupdm.json`, `parts/**/*.json` and `releases/**/*.json` `merge=ryucad diff=ryucad text eol=lf` (`eol=lf` keeps them canonical where Git for Windows would check them out with CRLF; an earlier ryucad's lines are replaced), and `.gitattributes` itself `text eol=lf` (issue #101); `merge.ryucad.driver` is `'<ryucad>' git merge-driver %O %A %B %P`, written with the textconv entry. `ryucad git merge-driver` (CLI only, prints nothing) merges three versions with `merge::bytes`: files that are JSON (canonical or not: an agent writing a file on one line merges as the CLI's writes do; issue #52), of one kind, without a conflict record and no newer than this build reads merge by value (`merge::merge`) and come out canonical; anything else merges as lines (`merge::text`, an in-process diff3 on a longest common subsequence after common ends, Git's `<<<<<<< ours` markers) and always exits 1. It never rebuilds and never reads other files.
- **Rules.** Each file is walked in base, ours and theirs by key: one side changed takes it, both alike takes it, otherwise a conflict ("changed" includes added and removed); arrays and references (`{feature, name}`) are one value. A feature whose `type` changes on either side is one value; two different files added at one path are an `id_collision`. `part.json`'s list merges by identity: base's features both keep in base's order, a feature one side moved (outside the longest run it keeps) at that side's place, each side's additions after everything that preceded them on that side, ours first at one spot; moved differently, moved and removed, moved where the other side's moves break its side's order, or added by both at different places is an `order` conflict at `/features/<id>`, its sides' places as `{"after": id}` or `{"first": true}`. Sketches merge entities and constraints by ID and field; positions (`m`, `r_m`) never conflict (the side that moved them, ours if both); removed on one side and changed, or named by what the other side left, is `delete_edit` (ours' value in place, so a removal theirs made comes back); two different members under one ID are `id_collision`. Release and obsolete records are whole files. The result's `format` is the lowest that holds it (`files::feature_format` from the JSON alone).
- **Conflict record.** A conflicted file is ours' value at each conflict plus a top-level `conflicts` object by JSON pointer: `{kind, base, ours, theirs}` with absent sides left out; a whole file's sides are whole files. Loading fails that file with `merge_conflict` (pointers in the details); a conflicted manifest fails every part but the project still opens; `doctor` reports `merge_conflict`.
- **Merge state.** `git::Repo::merge_state` reads `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` and `REBASE_HEAD` (during a rebase): ours is `HEAD`; theirs and base are the other head and the merge base, the picked commit and its parent, or for a revert the reverted commit's parent from the reverted commit. Inside the hook Git runs before committing a merge it made itself, before it writes `MERGE_HEAD`, the heads come from `GIT_REFLOG_ACTION` (`merge <commit>`, or for a pull `FETCH_HEAD`'s heads for merging). Octopus merges are `merge_unsupported`; outside a merge requests are `not_merging`. `unmerged` reads the index's stages.
- **Status.** `merge.status` (`ryucad merge status`) lists conflicts with a stable ID (`<path>#<pointer>`, or `#merge_broke`, `#sketch_stale`, `#rename_merged`), kind (`validate::KINDS`), files, `concerns` (part, feature, entities, parameter, references), `cause` (`ours`, `theirs` or `both`), choices and planned repairs: records' entries; unmerged paths (`modify_delete`, `merge_unparsed`; a deletion carried out counts as settled, a kept file stays listed until staged, since it looks as Git left it); `rename_merged` (Git's merge follows renames by default, and Git 2.47 even with `merge.renames=false`, so a feature one side added whose merged content is what merging it with a feature that side deleted and the other changed gives is reported, with repairs `restore` and `drop`); `merge_broke` (it rebuilds base, ours, theirs and the merge, sides through `Session::at`: a feature that built on a side and fails in the merge, blamed on the other side when its changes reached what the feature reads; one failing only through another the merge broke is listed under it (`also`), one already failing on a side is `already_failing` and doesn't block, one failing through a conflicted file is left to the structural conflict, and a feature no side has (work the merge didn't bring) is listed as `already_failing` with `failed_on: []` and doesn't block (#207)); and `sketch_stale` (current on the sides, stale in the merge; repair writes the solved file); and `import_misplaced` beside `assembly_stale`: an imported fixed instance its file's bytes place elsewhere in the merge but not on the sides, with the repair `place` (#206). Files settled but not staged are `unstaged`, as is every project file whose working copy differs from the index (a conflict record `git add`ed and then settled), which the hook would refuse; `untracked` lists the unstaged files the index holds at no stage. The status is kept by `validate::key` (the merge, the index's stamp, a digest of the working files).
- **Renumbering.** An `id_collision`'s repair (`renumber`) gives theirs' feature the first free `<id>-<n>` (ryucad's own rule) or theirs' sketch entity one past the largest with its prefix, rewrites what the merge has from theirs (a node equal to theirs' and not ours') that names it (sweeps' `sketch`, `loops` and `axis`, sketch members' points, references), lists a feature where theirs lists it (after ours' where both put it), and maps theirs' references through `diff::match_names`: theirs built as committed and renumbered, each body's faces, edges and vertices paired by exact geometry. Not one to one, no repair.
- **Resolve.** `merge.resolve` (`ryucad merge resolve <id> --ours|--theirs|--value JSON|--repair ID [--expect REV]`) settles a batch in order in memory and writes all or nothing, guarded by part revisions (`conflict`), conflicts (`conflict_not_found`) and repair IDs (`repair_conflict`); one logged, undoable change. A record entry takes the value (an order conflict a place), the entry leaves the record (the record with its last entry); a modify/delete or unparsed file takes a side's stage (a feature file kept is listed where that side lists it, one deleted unlisted). It never touches the index.
- **Hooks.** `ryucad git install` (and `init` in a repository) writes the same hook as `pre-merge-commit` (Git committing a merge itself) and `pre-commit` (someone committing a merge or cherry-pick Git stopped; rebase steps run neither): `exec '<ryucad>' merge status --hook`, which checks every project in `HEAD` and the merged commit, in process, prints what is unresolved and exits 1, and exits 0 at once outside a merge. The check reads the work tree, so it also refuses while a project file differs from the index (changed, deleted or new and not staged: `git::Repo::unstaged`), since the commit would take the index's. Someone else's hook, or a `core.hooksPath` folder, is left alone and reported with the line to add (`git_hook_foreign`, `git_hook_missing`). The clone's own setup also sets `merge.renames=false` (decided 2026-10-24, issue #44; Git 2.47 ignored it, 2.50 honours it): feature files are small and alike, so Git took a delete and an add for a rename and merged past the driver. It is never written to the global config, which every repository reads. `doctor` counts it under `git_drivers_missing`, and both that and a missing hook (not a `core.hooksPath` one) offer the repair `git_install`, which runs `ryucad git install` in the clone: Git's config and hooks, not project files, so it isn't logged or undoable.
- **Session.** `publish` sends `merge.changed` (topic `merge`) with `{merging, status}` when the key changes; `{merging: false}` when it ends.
- **Testing.** `merge.rs` unit tests per rule, `tests/merge_props.rs` (no change gives the other side, same change, disjoint changes commute, outputs canonical and conflicted ones refused), the `merge` fuzz target (raw bytes, or edits of a sketch, list or parameters file), `validate` and `check` tests over real repositories with the driver simulated, `tests/merge.rs` through Git itself (merge, rebase, cherry-pick, pull, a project below the root, rename following, the hooks), a CLI scenario both ways with undo, and the `merge` section of `tests/golden/rebuild.txt`. Limits: a squash merge commits without a merge state; criss-cross histories use one merge base; Git's line merge of files the driver doesn't get (drivers not installed) isn't detected as a renamed merge.

## Compare view and conflict panel (decided in ryucad phase 3)

The design is document 48 in the Coxswain planning project `ryucad-ryukei`; this is its phase 5, plan 3.C.

- **Compare state.** A participant compares the working files against a Git revision or not (`live::Participant::compare`, the revision as given, in `participant.changed`). `compare.set` (`ryucad compare REV`, `--off`) changes `participant`'s, else the one human's (an agent shows a person what it did; `ambiguous_participant` with several), else the caller's; the revision must name a commit holding the project (`rev_not_found`, `not_a_git_repo`; `working` is `invalid_param`). `compare.get` gives the revision and the commit it names now. A window takes its compare from its participant, so an agent's `ryucad compare HEAD` and the window's own menu go the same way, and a reconnected window tells the new session again.
- **What is shown.** The window reads `diff --model` from the revision to the working files (`core::compare`), again after every `model.changed`, one at a time. Only bodies whose results differ take part: their faces are painted new or changed (over the chosen feature, under selections), bodies added or failing at the revision new as a whole, and the revision's body is ghosted (`mesh.get` at the diff's commit, one body per request): translucent, pushed back by the fraction edges are pulled forward so coplanar faces show the model, with faces gone from the working files in the removed colour. Unchanged bodies would only fight the model for pixels. The tree marks features `[added]`, `[changed]`, `[rebuilt]` (only its result differs), `[moved]`, `failed at REV (code)`, lists those only the revision has as `[removed]`, and the property panel lists a chosen feature's changes. A gone face is picked in the ghost where nothing of the model is nearer (`Hit::rev`): described and copied, never selected. `render --compare` paints and ghosts an assembly's occurrences the same way (#135).
- **Entering one.** View > Compare with HEAD, Compare with… (a typed revision), Stop comparing; a Compare button per commit in the History tab; a bar above the viewport while comparing, with the counts and the colours.
- **Conflict panel.** The window asks `merge.status` when it opens and follows `merge.changed`; `not_merging` and `not_a_git_repo` mean no merge. At the top of the right panel, each conflict shows its kind, what it concerns, its sides, its cause, Take ours / Take theirs and each planned repair (a `merge.resolve` with the revision of its part the window last saw; a refusal reads the status again and keeps saying why), and Show (chooses the feature and marks the sketch entities); a value is typed with the CLI's `--value`, and `merge_broke` is fixed in the model. Settled files waiting for `git add` and features already failing are listed, with a reminder that ryucad never stages or commits. The title says `(merge in progress)` and the status line the summary. Conflicts are titled `<kind> in <part>/<feature>` (#212); untracked project files are listed apart from settled ones.
- **Testing.** Unit tests of the diff reading, ghost picking and resolutions; `tests/compare.rs` and `tests/merge.rs` against real daemons and real repositories (`Project::committed`, `diverged`); window tests for both; the scene test draws a ghost; the snapshot gains `compare-lavapipe.png`. The app's font has no `→`: change lines say `->`.

## The material library in Git (decided in ryucad phase 10)

The design is document 198 in the Coxswain planning project `ryucad-ryukei`; this is its phase 2, plan 10.A.

- **Attributes.** `drivers::LINES` gains `materials.json merge=ryucad diff=ryucad text eol=lf`; existing projects report `gitattributes_missing` until doctor's repair adds it. The line moved the `diff` golden section's hash (it textconvs `.gitattributes`). Appearance, views and explodes (plans 10.C and 10.D) live under `parts/**/*.json`, which the existing line covers; a root `parameters.json` (plan 10.E) will need a line of its own.
- **Textconv, merge, diff.** Textconv gives each material one line (`materials.steel = density 7850 kg/m^3, colour #888888`) and the default its own; the merge driver merges the library by material and field (`merge::newest` knows its format, so a newer one merges as lines); `diff` lists library changes by pointer at the top level (`materials.changes`), never under `--model`, since no result changes.
- **Testing.** `diff.rs` and `merge.rs` unit tests, `drivers.rs`'s line counts, the `merge` fuzz target's `0xfd` mode (densities set, materials removed, the default moved on either side).

## Named views in Git (decided in ryucad phase 10)

The design is document 198 in the Coxswain planning project `ryucad-ryukei`; this is its phase 4, plan 10.B.

- **Files.** `parts/<part>/views/<id>.json` lies under `parts/**/*.json`, whose attributes line it shares: no new line, and no golden hash moves. Sessions track it (three levels under `parts/`) and Git revisions read it (`project_blobs` walks `parts/` whole).
- **Textconv, merge, diff.** Textconv gives a view one line per field (its points on one line each); the merge driver merges views by field (`merge::newest` knows the kind's format), a point one value, so two people moving the eye conflict and one moving the eye while the other widens the field of view doesn't; `diff` gives a part with views on either side a `views` block: `added` and `removed` IDs and `changed` by pointer, never under `--model`. Doctor reports a view that doesn't read (or takes a standard view's name) as `invalid_document`, one not written canonically `non_canonical`, anything else in `views/` `unknown_file`.
- **Testing.** `diff.rs`, `merge.rs` and `doctor.rs` unit tests, and the `merge` fuzz target's `0xfc` mode (eyes and targets moved, fields of view changed, projections switched on either side).
