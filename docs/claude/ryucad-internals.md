## Internals and scale (decided in ryucad phase 27)

The design is document 541 in the Coxswain planning project `ryucad-ryukei`: ryucad made cheaper to change without changing anything it does (#482, #555). Plan 27.A is its phase 1; 27.B to 27.F add their sections here.

- **The CLI is in the library.** `ryucad::cli` (`crates/ryucad/src/cli.rs`) with its entry point `cli::main`, and `ryucad::process`: `STACK` (8 MiB) and `start`, the process setup (transparent huge pages off on Linux, #236; Git's credential prompts off, #382; the CLI on a thread of `STACK`), `unsafe` because it sets environment variables before any thread starts. `src/main.rs` names the allocator (mimalloc on Linux and macOS) and calls `process::start(cli::main)`; so does ryucad-app's example `ryucad-test`, so the two are one program. `lib.rs`'s `extern crate self as ryucad;` keeps the CLI's `ryucad::…` paths.
- **The app's tests' `ryucad` (#555).** Cargo rebuilt `ryucad` in every app test process, and again in the next `cargo` outside it, because `ring`'s build script watches `CARGO_MANIFEST_DIR`: the test's own `cargo build -p ryucad` inherited the app's from `cargo test`, so ring, rustls, ureq, ryupdm and ryucad rebuilt both ways (about 8 s each on bc2 and davids-m4, even for a `--no-run` with nothing changed). `crates/ryucad-app/tests/common::ryucad()` now takes, in order: `ryucad` beside the tests under `RYUCAD_TEST_PREBUILT` (CI's partitions); `examples/ryucad-test` when `common::built_after` finds nothing it is built from newer (every crate's `src`, `build.rs` and `Cargo.toml` but the app's `src`, the example, the app's manifest, the workspace's manifest and lock file) and `check_build` accepts it; else `cargo build -p ryucad` (a run filtered to one `--test` builds no examples), with the variables `cargo test` set for the test (`CARGO_PKG_*`, `CARGO_MANIFEST_*`, `CARGO_BIN_EXE_*`, `CARGO_CRATE_NAME`, `CARGO_PRIMARY_PACKAGE`, `CARGO_TARGET_TMPDIR`) removed, so it builds what a shell's `cargo` would. The link time order of a test binary and the example in one Cargo run is arbitrary, so neither's time judges the other. `RYUCAD_TEST_TIMING` prints which and how long. `ryucad_beside_app()` builds the one `ryucad-app --smoke` finds beside itself. CI's window-test job builds the example first. Bar: the second and later test binaries of one `cargo test -p ryucad-app` under 1 s; measured on bc2 (cox-worker-3): max 19 ms over 30 binaries, and a no-change `--no-run` and the link test 0.16 s and 0.19 s (8 to 9 s before); davids-m4: 14 ms (the first binary of the run 2.8 s, macOS's first start of a fresh program), and 0.2 s and 0.25 s (8 and 10 s before). `build.rs`'s Git watches were not the cause and are unchanged.
- **ryucad's `tests/common`.** `call`, `must` and `project()` (an empty part `p`, millimetres), taken by the 30 integration test files that carried the same text. Seven keep their own because theirs differ: `corpus.rs` and `step.rs` (`call` gives a bad request back as an error), `step_bar.rs` and `sweeps.rs` (`call` panics), `reference_bar.rs`, `sheet_metal_flat_bar.rs` (`must` names the part) and `drawing_props.rs` (`must`'s message).
- **The server split (27.B).** `server/` is the request lifecycle and a router. `server/mod.rs` holds `init`, `handle`, `handle_live`, `answer_live` (binary answers), `handle_safely`, `handle_job`, `handle_job_raw`, `prepare`, `prepare_job`, `publish`, `settle` and `tick`. `server/route.rs` is `dispatch`, one `match` whose arms only call a handler. The handlers live in one module per domain: `part`, `feature`, `view`, `assembly`, `pdm`, `git`, `annotation`, `cache` and `session`, plus the `crate::` modules that already answered their requests (`crate::release`, `crate::deps`, `crate::drawing`, …). The tests of `server.rs` are `server/tests.rs`, and their harness (`fresh`, `call`, `call_live`, `drain`, the fixtures and `RENDER_BUDGET`) is `crate::testing`; the session-write scan (`annotation`'s `proposable_handlers_write_through_the_session`) skips both, as it skipped the inline `mod tests`. What other modules borrowed from `server` lives outside it:
  - `crate::part`: IDs, revision checks, a part's features and kind, proposed parts, `part_report`;
  - `crate::save`: `save`, the one write path for a part's files, atomic and synced;
  - `crate::geometry`: `geom_json`, `normal_to_face`;
  - `crate::budget`: `mesh_budget`, `render_budget`;
  - `crate::scene`: display meshes, occurrences, model points and a render's scene, which annotations and release packages also render through;
  - `crate::diff`: the `diff` request.

  `testing`'s `nothing_outside_the_server_names_more_than_its_entry_points` holds the direction: outside `server/`, code names only the lifecycle's entry points (`SERVER_ENTRY`). The old paths stayed as re-exports while ryucad 27 ran, and 27.F removed them. Their new uses of an old path fail the scan, which names the new home.
- **Feature kinds (27.C).** A feature type's request handling is one kind behind `crate::feature::FeatureKind`, registered once in `feature::KINDS` (its order is `feature.types`' order). A kind owns one or more `type`s (`types`) and says the request fields each takes (`fields`, `given.only`'s list), the body it needs and whether it founds one (`body`), how a request becomes its feature, new or edited (`from_given`, through a `Write`: the session, the part, the `Given`, and `Place::New` or `Place::Edit`), its report (`report`; `feature::report` adds `id` and `type`; its old path `server::feature_report` went with 27.F), and its own checks against the rebuild (`check`, through a `Check`). Defaulted hooks hold what `feature.add` and `feature.edit` did per type in their shared order: `before_targets` (a pattern's targets, a mirror's solid and operation, an insert's newest label), `acts_without_operation` (a hole), `take_given` (a tweak's `face`, a flange's length, a primitive's `radius`), `default_target` (tweaks, shells, flanges), `before_revision` (an insert's edit), `refuse_others` (a primitive's own message, an import's refusal first), `rechecks` and `always_checked`. Kinds whose logic already had a module implement it there (`tweak`, `datum`, `path`, `along`, `loft`, `surface`, `body`, `sheet_metal`); the rest are `feature/<kind>.rs`, beside the shared helpers in `feature/mod.rs` (`Given`, placements, `solids_before`, `check_sweep`). File formats stay in `ryucad-doc`. `FEATURE_TYPES` is gone: every registered type gets the early `wrong_part_kind` before its fields are read (17 types didn't, a drift).
  - Adding a type: its file struct in `ryucad-doc` (and its name in `unknown_type`'s list), a kind (or a type in an existing kind's `types`), its row in `what_each_type_needs_and_founds`, and the kind in `KINDS`. A new `FeatureFields` field goes in some kind's `fields`. The tests fail otherwise: `every_type_has_exactly_one_kind` (against ryucad-doc's list), `every_type_a_kind_owns_parses_as_that_type`, `every_field_a_kind_lists_is_a_request_field`, `every_request_field_is_taken_by_some_kind` (serde's own field list, renames included) and the body table.
  - `feature.types` (`ryucad feature types [<type>]`) is the registry read back for agents: `{"types": [{"type", "fields", "body", "founds"}]}`, `body` `solid`, `sheet` or null (what holds whatever the fields say), `founds` `always`, `when_new`, `when_both_kept` or `never`; an unknown type is `unknown_feature_type`. `feature add --help` ends with the registry's types (`feature::type_list`, set on clap's command in `cli::main`). The CLI's `FieldArgs` and `to_fields` stay hand-written: some flags mean different fields by type.
- **Rebuild through kinds (27.D).** A kind's `rebuild` is its rebuild step (required), through a `RebuildCx` (the part, its solids, the feature's ID, the results before it, a join's or cut's kept own body `tool`, the `Run`), answering an `Outcome` (the result, and the own body for the cache). `rebuild_with` and `build_feature` only ask the kind (`kind_of(f).rebuild`, `.alone`; `alone` builds a primitive and every other kind refuses with its old internal error), and `kind::bodies_read` asks `reads` (design 388's table, its rows in the kinds; the default is a combine's targets). The nine body-making types (primitives, extrude, revolve, sweep, loft, planar, thicken, mirror, hole) answer `rebuild::body_step`, the one shared step: read the targets, take the kept own body or build it (`own_body`; a hole's tools are built there, at its points, so `build_body` still names the hole), found a solid or apply it. Each type's builder lives with its kind (`build_primitive`, `build_boolean`, the blend's groups and errors, `build_pattern`, `build_sweep` with its axes and errors in `feature/extrude.rs`, the split's sides in `body.rs`, `delete_body` in `feature/delete_body.rs`); `rebuild.rs` keeps what kinds share (`read`, `apply`, `ToolBody`, the boolean's errors and origins, `finish`), the loop, the hashes and the caches. Per type in `rebuild.rs`, on purpose: `input_hash`'s through-all extrude and hole sizes (cache keys mustn't move), `rebuild_part_in`'s insert and instance (models from outside the part) and its disk policy. `FeatureKind::body` holds whatever the fields say, so it can't replace `bodies_read`; `what_each_body_read_wants_agrees_with_the_types_table` holds the two together, and `the_rebuild_matches_on_no_type` scans `rebuild_with`, `build_feature` and `bodies_read`. Their old paths (`rebuild::check_blend`, `body::delete_body`/`delete_report`) went with 27.F.
  - Adding a type now also means its `rebuild` (the build fails without it), `own_body` if it answers `body_step`, `alone` if it should refuse in its own words, and `reads` when it reads bodies other than a combine's targets.
- **The session's caches (27.E).** `Session` keeps what defines it: the project, its stamps and watch, the store (rebuilds, models, summaries, the budget), the epoch, pins and the dependency state (`pinned_parts`, `deps_cache`, `deps_reader`, `prefetched`, `foreign_pins`), names learnt, labels, cycles, revisions, worktrees' stamps, the sink, the job and the heal and edit budgets, every field private (`job()`/`set_job()`, `heal_budget()`, `edit_budget()`, `store()` (read only; `put_holes` keeps a part's holes), `caches()`/`caches_mut()`; `the_session_and_its_caches_show_no_field` holds it). What it keeps only to answer faster is `session::Caches` (`src/session/caches.rs`), its fields private too. By content (meshes, flats, interference, clearance, mass and blend verdicts, projections, sections, sweeps): keyed by what they were made from, never stale, each bounded by its own cap when filled; `x()` to read, `x_mut()` to fill, `verdicts_mut()` for a sweep's two. By state (merge status, the release branch, release states and results, ryupdm's structure, worktree counts, merge previews, a revision's warnings): keyed by what they read, and the getters (`merge_status(key)`, `releases(key)`, `kept_states(key)`, `preview(key)`, `worktree_changes(key)`, `release_result(content)`) give an entry only for the key read now. `Caches::changed(Moved)` is where a move lets entries go: `Files` and `Budget` let nothing go (the store's rebuilds, which a change makes stale, are the session's, let go in `after_change`, `let_results_go` and `trim`), `Fetched` keeps only the project's own structure, `Worktrees` only the counts listed. `Caches::mesh_bytes` and `Caches::verdicts` are what the budget counts of it; a trim lets go of rebuilds, never cache entries. A revision's session takes `for_revision` (the owner's verdicts, projections, sections, sweeps and structure cloned, maps of `Arc`s; meshes afresh over the disk; no state). No key, entry or lifetime changed: the rules were recorded as tests on main first. A new cache goes into `Caches` with its rule, never onto `Session`. Scale, `RYUCAD_BARS=1` at 10,000 parts on cox-worker-3, main against the branch: warm daemon 4.7 and 4.3 s (main 4.6 and 4.3), a request that builds nothing 1.1 and 1.0 ms (1.2, 1.1), an edit heard 133 and 124 ms (125, 122), peak 4794 and 4766 MiB (4786, 4772): within main's spread, every bar met but the daemon's peak memory, which main misses too (#854).

## Fuzzing in CI (decided in ryucad phase 30)

- **The build guard (30.A).** `ci.yml`'s `fuzz targets build` runs `cargo check --manifest-path fuzz/Cargo.toml --bins` on every pull request, on the pinned stable toolchain (only cargo-fuzz's sanitizer flags need nightly), with its own cache (`fuzz -> target`, saved by main). Every one of the 41 targets is checked, the six the nightly doesn't run too. Before it, nothing built `fuzz/` on a pull request, and four build breaks (#188, `appearance`, `drawings`, `hole_standards`) each surfaced only at 03:17 the next night. Measured in its PR: 61 s cold (43 s of it the check), beside the PR's slowest job (windows-latest 1/3) at 32 min; warm: measured after merge. It moves to `full.yml` if it can't stay under ten minutes.
- **A red night files itself (30.A).** `fuzz.yml` builds each target (`cargo fuzz build`) apart from its run, so a build failure is told from a find; a failed job uploads `fuzz-report-<target>` (target, kind, libFuzzer's `SUMMARY` line), with kinds `build failure`, `crash`, `out of memory`, `timeout`, `setup failure` and `failure without a libFuzzer summary`. A job whose runner died (lost communication) can't upload one, so the `issues` job also files every failed job without a report, as `runner lost, no report`, from the run's job list. The `issues` job (`issues: write`, `actions: read`) keeps one open issue per red target, `fuzz nightly: <target> red`, labelled `fuzz` and `bug`, with the run, kind and artifact; a later red night comments on it. It sets no milestone (the coxswain triages) and never closes one: the fix does. It runs on main, or on a dispatch with `file_issues`. A dispatch's `targets` (a JSON list) runs fewer targets than the nightly's 35. Tested in 30.A's PR: #856 opened, commented on twice (a crash and a build failure), and closed by hand.
- **Regression tests live with the crate (design 600).** A crash a target finds is fixed in its crate, with a test in that crate's `tests/fuzz_regressions.rs` replaying the input byte for byte, and the input in `fuzz/corpus/<target>/` when small. ryudfm's (30.A: the `odb` round trip, see `ryudfm.md`) runs in PR CI with the rest of its tests.
- **The app's workspace (27.F).** `ryucad-app`'s `core::workspace` is a lifecycle and a router over fourteen sub-states, each a field of `Workspace` holding its own state:
  - `model` (`core::model::Model`, which took the loading, made faces, sweeps, sheets and flat view);
  - `forms`, `parameters`, `drawings` (the Drawings `Tile`), `activity`, `branches` (with Git's merge), `deps` (with the picker);
  - `pdm` (releases, PDM settings, properties, where-used, the BOM; the design's "releases");
  - `annotations` (with the Markup bar), `comparing`;
  - `session` (mode, participants and what this window's participant shows, settings, doctor, cache);
  - `assembly` (drags, Move, Mate, interference and clearance only when asked, explodes, motions);
  - `view` (named views, appearance, sections, Measure, Mass);
  - `exchange` (import, export).

  `Workspace` itself keeps the link, the window's errors, toasts, progress, camera sharing and reconnecting. A sub-state's requests are `Workspace` methods in its file (`core/workspace/<sub>.rs`): a write refused by the window's mode is still answered before `send` returns. Each is sent under a `Route` (one variant per sub-state holding its own `Asked`, plus `Proposal` and `Quiet`), and `Workspace::answer` hands the answer to that sub-state's `answer` (`the_workspace_answers_only_by_routing`), which touches only its own fields. It records what else must happen as `Effect`s (`route.rs`): a failure, a redraw, the model's previews, marks and level of detail, a read to send, or a `Then` (one variant per workspace method an answer may call), which `Workspace::apply` carries out in order after it. Every read an answer sends goes through `send` as before, and `gate` never refuses a read, so deferring them moved no refusal. A lost daemon resets each sub-state through its `on_lost`. The property panel's per-type forms are `core/edit/<kind>.rs`, named as ryucad's feature kinds: `extrude`, `blend`, `hole`, `pattern`, `mate`, `datum`, `sweep` (ryucad's `along`), `loft`, `body`, `sheet_metal`, `surface`, `tweak`. Each implements `edit::FeatureForm` (`read` from its type's `feature.show`, its fields, dirty, revert, what it gives `feature.edit`, the refusal pointers it owns). `Form` keeps one `Option` per kind, which the panel reads, and asks the one that is set (`every_type_reads_at_most_one_kinds_form`). The tree's icons ask the same modules (`edit::icon`), and `tree::type_icon` keeps the types with no form. A new feature type's form is a module there with its `FeatureForm` impl and `icon`, one field on `Form` and one line each in `Form::kinds`/`parts_mut`. A new request is a variant of its sub-state's `Asked`, and a new field goes on its sub-state, never on `Workspace`.
