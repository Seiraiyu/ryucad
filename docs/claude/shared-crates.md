## Shared crates (decided in ryueda phase 0)

The design is document 157 in the Coxswain planning project `ryucad-ryukei`; this is its plan 0.A. ryueda reuses ryucad's file vocabulary and session plumbing without ryucad's file kinds, the kernel or each other's protocols.

- **`ryu-math`.** `ryukei::math` moved as it was (`libm`, hardware `sqrt`); `ryukei` re-exports it, so kernel code, `clippy.toml` and every golden hash are unchanged. `ryu-doc`'s expressions use it, so the file formats get the same bits without the kernel.
- **`ryu-doc`.** `canonical`, `id` (`Id`, `ProjectId`, the instance path's step syntax), `source` (with `plain`, `relative` and `write_atomic`), `units`, `expr` and `error` moved unchanged; `ryucad-doc` re-exports them under their old paths. `error::Code` stays one enum for every product, so codes stay unique.
- **Electrical units.** `Dim` gains powers of mass, time and current, with eight named electrical dimensions (`Dim::ELECTRICAL`: voltage, current, resistance, capacitance, inductance, frequency, power, time). `Quantity::electrical(text, dim)` reads a literal with an SI prefix (`3.3 V`, `100nF`, `4.7 kOhm`, `µ` and `Ω` as well; written `100 nF`, `4.7 kOhm`, `2.2 uH`), with no default unit and no expressions: electrical units are never names in expressions, so no parameter name (`s`, `ms`, `ohm`) is reserved by them, and `Dim::parse` reads only the names it always has.
- **`ryu-session`.** Generic over a `Product` marker (ryucad's is `ryucad::Cad`): its name and runtime variable, what participants point at (`Target`), what else a window shows (`View`: ryucad's camera, compare, focus and hidden set), what subscribers were told (`Seen`) and its topics (`notify::Topics`). `prefs::Schema` adds the config variable and which keys a preferences file may hold; `Serve` adds the manifest, the idle variable, the session, the requests (`client::Call`), the version and when two are the same build, and how requests are parsed, classified (`daemon::Control`), answered and settled. Requests are answered one at a time under one lock, but slow work a request can do apart (`Serve::prepare`: ryucad's display meshes the cache lacks for `mesh.get` of the working files) runs with the lock released and is handed back under it, so a window fetching meshes doesn't hold up agents (#91). Each module is the code ryucad had, generalised; ryucad names the types for itself (`ryucad::live::Live` is `Live<Cad>`, `ryucad::client::Daemon` is `Daemon<Cad>`), keeps its free functions as wrappers, and keeps what is its own (its `View` and `Seen`, `CadLive`'s setters, its topics, its preference keys, `open`, undo's write order and folder cleanup). Folder, socket and pipe names, messages, codes and JSON are as they were.
- **Products apart.** A version names its product (ryucad's JSON holds `ryucad`). A client that meets a daemon of its own product but another build replaces it, as before; one that meets another product's daemon refuses with `daemon` and never asks it to stop.
- **Testing.** Each module's tests moved with it, run against a test product (`ryu_session::testing`); ryucad's own tests, CLI scenarios both ways and every golden hash are unchanged; new tests pin a participant's JSON, electrical literals and that electrical units reserve no parameter names, the preferences file of another product, and the client's refusal of another product's daemon.
- **`ryu-part21`** (plan 0.B). ryustep's exchange structure (`part21`: parse, write, `Param`, `Part`, `File`, `Header`, `Instance`, `Record`) and `StepError` moved as they were into a crate with no kernel, which ryustep re-exports as `ryustep::part21` and `ryustep::StepError`; `part21::write`'s refusals are its own `WriteError::Unwritable`, which ryustep's `WriteError` takes in (`From`). ryueda checks its 3D models parse with it. Golden hashes and every ryustep test are unchanged.
- **`ryu-standards`** (ryucad 28.A). Engineering standards data for every ryu product: metric, unified and pipe thread standards (`thread`, `iso_metric`, `unified`, `pipe`), drill series and tap-drill rules (`drill`, `tap`) and ISO 286 limits and fits (`fit`, moved unchanged from `ryucad::drawing::fit`). Only what the owner's ruling allows is built in (design 533, question 657): values computed from published formulas (unified limits checked against every row of public-domain FED-STD-H28/2B, whose one differing value wins, cited; metric limits from ISO 965-1's formulas alone, since H28/21B prints none), and plain facts (sizes and pitches as ISO 261's selection is commonly tabulated, cross-checked against H28/21B Table XXI.1); nothing copied from a paid ISO, ASME or DIN table, and no fastener clearances or pipe-thread diameters, which a project's own table supplies. Every value is integer nanometres (ISO's micrometres and ASME's ten-thousandths of an inch are both whole) with a `Source`, and there is no float in the crate: fractional powers are decided by exact integer comparisons. It has no dependencies at all (`tests/deps.rs`), and `tests/sources.rs` checks every built-in value names its source.

## ryu-git (decided in ryueda phase 4)

The design is document 518 in the Coxswain planning project `ryucad-ryukei`; this is its phase 1, plan 4.A.

- **What it holds.** ryucad's Git plumbing that knows nothing of parts: `repo` (`Repo`: open, revisions, files at a commit, any folder of a commit (`file_at`, `files_at`, `tree_at`), `merge_state`, `unmerged`, `unstaged`, `untracked`, `merge_base`, the stamps, history, worktrees; `merging_projects`) and `drivers` (attribute lines, driver entries, `git install`, `merge.renames=false` in the clone, the shared hook). It depends on `ryu-doc`, `ryu-session` (for `fresh::Files`), `gix` and `serde_json`, never on a product.
- **Products.** A product implements `ryu_git::Layout` (its name, manifest, root files, folders, and which paths are project files) on its marker (`ryucad::Cad`, `ryueda::Eda`) and gives a `drivers::Drivers` (its config keys, whether it has a merge driver and a hook line). ryucad keeps its paths: `ryucad::git::Repo` is `ryu_git::Repo<Cad>`, `ryucad::drivers::*` wrap ryu-git's with ryucad's lines. Answers, files and golden hashes didn't move.
- **The shared hook.** One `pre-merge-commit` and `pre-commit` per clone, marked `# ryu: …`, holding a `# <product>` line and that product's `'<binary>' merge status --hook` per installed product, in name order, the last `exec`'d, so a product's failure stops the commit. ryucad's own hook (its `# ryucad:` header) is ryu's and is rewritten into the block on the next install. A hook of someone else's counts as running a product's check when a line runs `merge status --hook` and its program isn't another ryu product. `core.hooksPath` folders are never written.
- **Later.** The per-key value walk, the conflict record, list order and the in-process diff3 move into `ryu_git::value` with ryueda's merge driver (plan 4.C).
- **Testing.** `ryu-git`'s own tests against a toy product (`testing::Toy`) and real repositories; ryucad's tests where they were.
