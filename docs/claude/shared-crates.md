## Shared crates (decided in ryueda phase 0)

The design is document 157 in the Coxswain planning project `ryucad-ryukei`; this is its plan 0.A. ryueda reuses ryucad's file vocabulary and session plumbing without ryucad's file kinds, the kernel or each other's protocols.

- **`ryu-math`.** `ryukei::math` moved as it was (`libm`, hardware `sqrt`); `ryukei` re-exports it, so kernel code, `clippy.toml` and every golden hash are unchanged. `ryu-doc`'s expressions use it, so the file formats get the same bits without the kernel.
- **`ryu-doc`.** `canonical`, `id` (`Id`, `ProjectId`, the instance path's step syntax), `source` (with `plain`, `relative` and `write_atomic`), `units`, `expr` and `error` moved unchanged; `ryucad-doc` re-exports them under their old paths. `error::Code` stays one enum for every product, so codes stay unique.
- **`ryu_doc::files` (ryueda 10.A).** `Obj`, `invalid`, `header_in(v, kind, newest, product)`, `conflicted_in(v, at, product)`, `without_conflicts` and `CONFLICTS`, and `units::snap_origin`, moved down from `ryucad-doc`, which re-exports them at their old paths, its `header` and `conflicted` naming ryucad. A `<product>.feature`'s `type` is kept in a conflict's details for the product named. `ryucad-doc`'s no-op `migrate` went with them.
- **Electrical units.** `Dim` gains powers of mass, time and current, with eight named electrical dimensions (`Dim::ELECTRICAL`: voltage, current, resistance, capacitance, inductance, frequency, power, time). `Quantity::electrical(text, dim)` reads a literal with an SI prefix (`3.3 V`, `100nF`, `4.7 kOhm`, `µ` and `Ω` as well; written `100 nF`, `4.7 kOhm`, `2.2 uH`), with no default unit and no expressions: electrical units are never names in expressions, so no parameter name (`s`, `ms`, `ohm`) is reserved by them, and `Dim::parse` reads only the names it always has.
- **`ryu-session`.** Generic over a `Product` marker (ryucad's is `ryucad::Cad`): its name and runtime variable, what participants point at (`Target`), what else a window shows (`View`: ryucad's camera, compare, focus and hidden set), what subscribers were told (`Seen`) and its topics (`notify::Topics`). `prefs::Schema` adds the config variable and which keys a preferences file may hold; `Serve` adds the manifest, the idle variable, the session, the requests (`client::Call`), the version and when two are the same build, and how requests are parsed, classified (`daemon::Control`), answered and settled. Requests are answered one at a time under one lock, but slow work a request can do apart (`Serve::prepare`: ryucad's display meshes the cache lacks for `mesh.get` of the working files) runs with the lock released and is handed back under it, so a window fetching meshes doesn't hold up agents (#91). Requests take the lock in arrival order (`daemon::fifo::Fifo`, #849); a request with nothing to prepare keeps the lock it took, so it keeps its turn. A watched daemon's publishes are coalesced (`publish::Coalesce`: `Serve::publish_ms`, quiet and max, 150 and 1,000 ms by default), and its time is summed by method (`timings::Timings`, `daemon.status {timings}`, `Control::Status { timings }`). ryueda and ryudfm mark nothing, so their watchers settle every `poll_ms` as before. Each module is the code ryucad had, generalised; ryucad names the types for itself (`ryucad::live::Live` is `Live<Cad>`, `ryucad::client::Daemon` is `Daemon<Cad>`), keeps its free functions as wrappers, and keeps what is its own (its `View` and `Seen`, `CadLive`'s setters, its topics, its preference keys, `open`, undo's write order and folder cleanup). Folder, socket and pipe names, messages, codes and JSON are as they were.
- **Products apart.** A version names its product (ryucad's JSON holds `ryucad`). A client that meets a daemon of its own product but another build replaces it, as before; one that meets another product's daemon refuses with `daemon` and never asks it to stop.
- **Testing.** Each module's tests moved with it, run against a test product (`ryu_session::testing`); ryucad's own tests, CLI scenarios both ways and every golden hash are unchanged; new tests pin a participant's JSON, electrical literals and that electrical units reserve no parameter names, the preferences file of another product, and the client's refusal of another product's daemon.
- **`ryu-part21`** (plan 0.B). ryustep's exchange structure (`part21`: parse, write, `Param`, `Part`, `File`, `Header`, `Instance`, `Record`) and `StepError` moved as they were into a crate with no kernel, which ryustep re-exports as `ryustep::part21` and `ryustep::StepError`; `part21::write`'s refusals are its own `WriteError::Unwritable`, which ryustep's `WriteError` takes in (`From`). ryueda checks its 3D models parse with it. Golden hashes and every ryustep test are unchanged.
- **`ryu-standards`** (ryucad 28.A). Engineering standards data for every ryu product: metric, unified and pipe thread standards (`thread`, `iso_metric`, `unified`, `pipe`), drill series and tap-drill rules (`drill`, `tap`) and ISO 286 limits and fits (`fit`, moved unchanged from `ryucad::drawing::fit`). Only what the owner's ruling allows is built in (design 533, question 657): values computed from published formulas (unified limits checked against every row of public-domain FED-STD-H28/2B, whose one differing value wins, cited; metric limits from ISO 965-1's formulas alone, since H28/21B prints none), and plain facts (sizes and pitches as ISO 261's selection is commonly tabulated, cross-checked against H28/21B Table XXI.1); nothing copied from a paid ISO, ASME or DIN table, and no fastener clearances or pipe-thread diameters, which a project's own table supplies. Every value is integer nanometres (ISO's micrometres and ASME's ten-thousandths of an inch are both whole) with a `Source`, and there is no float in the crate: fractional powers are decided by exact integer comparisons. It has no dependencies at all (`tests/deps.rs`), and `tests/sources.rs` checks every built-in value names its source. Since ryucad 28.B: external thread classes for ISO metric (g and h at grades 4, 6 and 8, by ISO 965-1's formulas; unified external classes aren't built in, since H28/2B prints no external limits), lookups by side (`Thread::internal`, `major_max`, `basic_minor`), `Big`'s sums and differences, and `drill::nearest`.

## The racy window sized to the timestamp (decided in release 10.A, #1050)

- **Why.** `fresh::Stamps::scan` trusts a file whose time and length match its stamp only when the time is a window older than the last scan; otherwise it reads the file again (racy-git). The window was 2 s for every file. ryueda's bar generates its design and talks to its daemon within 2 s, so every request re-read every file: on windows-latest 12,168 reads in 24 refreshes (all ~507 files each time), `session.refresh` 17.4 ms a request against a 2.2 ms walk (bars.yml run 45352005367), since each read of a just-written file can wait on Defender. Linux paid it too, cheaply. An agent that writes and reads within 2 s pays the same.
- **The rule.** `racy_window(modified)`: 2 s (`RACY`) when the time has no sub-second part (FAT and exFAT, HFS+, coarse network shares, or a time that happens to fall on a whole second), else 100 ms (`RACY_FINE`: NTFS's 100 ns, ext4's and APFS's ns). A file is trusted when its time and length match and its time is before the last scan's own clock minus that window, so a time later than the scan's clock (skew, a stamp in the future) is never trusted.
- **What it trusts, and why.** A write after the read that took the stamp gets a time at least a clock tick later, so once that read came a tick after the time, an unchanged time and length prove the bytes unchanged. Fine-grained file systems stamp with the clock's tick, not their resolution (about 15.6 ms on Windows, 1 to 10 ms on Linux), so the window is 100 ms rather than 10 ms: a tick with room for a little skew. The trade-off: a network share with sub-second times whose server clock runs more than 100 ms from the client's can let a same-tick, same-length rewrite pass unseen, where the old rule needed more than 2 s of skew. This process's own writes get no special trust.
- **What moved.** Files read, not answers: ryucad's, ryueda's, ryudfm's and ryuplm's freshness and session tests are unchanged. `Stamps::last_reads` counts the last scan's reads; ryueda's `refresh_changes` gives `refresh.list`, `refresh.scan` and `refresh.reads` in `daemon status --timings`, which its bar prints. `bars.yml` takes `windows-latest` (hosted, indicative).
- **Not this.** At 100,000 files the walk itself costs (#1018): file events narrowing the scan, as ryucad's session does, are its fix, not a window.

## ryu-git (decided in ryueda phase 4)

The design is document 518 in the Coxswain planning project `ryucad-ryukei`; this is its phase 1, plan 4.A.

- **What it holds.** ryucad's Git plumbing that knows nothing of parts: `repo` (`Repo`: open, revisions, files at a commit, any folder of a commit (`file_at`, `files_at`, `tree_at`), `merge_state`, `unmerged`, `unstaged`, `untracked`, `merge_base`, the stamps, history, worktrees; `merging_projects`) and `drivers` (attribute lines, driver entries, `git install`, `merge.renames=false` in the clone, the shared hook). It depends on `ryu-doc`, `ryu-session` (for `fresh::Files`), `gix` and `serde_json`, never on a product.
- **No install from a checkout (#920, v0.9.2).** The local config and the hooks are the clone's common ones, which every linked worktree shares, and `git install` writes the binary's absolute path into both. A binary inside a checkout of that clone (its work tree, the main one or any linked worktree: a `target/` build) goes when that checkout does, and every other worktree's commits then fail on the hook. So `drivers::install_with` (what `install` is, for this binary) writes nothing for such a binary and answers `{scope: local, skipped: binary_in_checkout, warning}`; `--global` is unchanged, and the doctor's `git_install` repair carries the skip. Paths are compared as given and canonical (macOS's `/private/var`).
- **Products.** A product implements `ryu_git::Layout` (its name, manifest, root files, folders, and which paths are project files) on its marker (`ryucad::Cad`, `ryueda::Eda`) and gives a `drivers::Drivers` (its config keys, whether it has a merge driver and a hook line). ryucad keeps its paths: `ryucad::git::Repo` is `ryu_git::Repo<Cad>`, `ryucad::drivers::*` wrap ryu-git's with ryucad's lines. Answers, files and golden hashes didn't move.
- **The shared hook.** One `pre-merge-commit` and `pre-commit` per clone, marked `# ryu: …`, holding a `# <product>` line and that product's `'<binary>' merge status --hook` per installed product, in name order, the last `exec`'d, so a product's failure stops the commit. ryucad's own hook (its `# ryucad:` header) is ryu's and is rewritten into the block on the next install. ryuplm joined `PRODUCTS` in ryuplm 0.A: the header names its install too, and a hook with the earlier two-product header is still read as the shared one. A hook of someone else's counts as running a product's check when a line runs `merge status --hook` and its program isn't another ryu product. `core.hooksPath` folders are never written.
- **Values** (plan 4.C). `ryu_git::value` holds the merge's product-free half, moved from ryucad unchanged: `Kind` (`value`, `delete_edit`, `order`, `id_collision`, and ryueda's `layout_pending`), `Conflict`, `Merged` and the record under `CONFLICTS` (`record`, `escape`, `unescape`, `child`), `Walk` over a product's `Rules` (`atom`: pointers merged as one value; `whole`: values merged as one value wherever they sit), `order` of a list of IDs at a given pointer with `place` and `moved`, `put` and `set_at` for settling, and `text` (the in-process diff3) with `Outcome`. ryucad re-exports them at its old paths (`ryucad::merge::Walk` and the rest, `merge::order` at `/features`, `validate::put`), its rules `Rules { atom: <per kind>, whole: is_reference || is_connector }`; no answer, file or golden moved.
- **Testing.** `ryu-git`'s own tests against a toy product (`testing::Toy`) and real repositories; ryucad's tests where they were.

## ryu-app (decided in ryueda phase 3)

The design is document 519 in the Coxswain planning project `ryucad-ryukei`; this is its phase 3, plan 3.C.

- **What it holds.** The desktop shell `ryucad-app` had that names no product: `fonts` (Inter, JetBrains Mono, Phosphor, in `crates/ryu-app/fonts/` with their licences), `icon` (Phosphor's and the glyph table), `style` (looks, palettes, high contrast, `vision` for colour tests, the selection and hover colours), `command` (`Command<C>`, generic over what context menus target, with `Category`, `Scope`, `Kind` and the `const fn` builders), `keys` (`Chord`, `Keymap<R: Registry>`, `consume`), `palette` (matching and recent commands over a registry), `layout` and `shell` (`ui.layout` read and written, and the egui_tiles tree, over a `layout::Spec`: tiles, homes, default and centre), `toast` (`Toasts<W: Words>`), `people` (`Person<V: View>`, which dereferences to its view both ways, `People<V>`, the People strip) and `status` (the look and connection labels), `link` (`Link<A: Client>`, `find`, `check_build`) and `canvas` (the 2D camera, wheel and pan, curve cutting, hit tests and culling). It depends on egui, egui_tiles, `ryu-math`, `ryu-doc`, `ryu-session` and serde_json, never on eframe, a product or the kernel (`tests/deps.rs`).
- **How a product uses it.** One marker type implements the shell's traits (`ryucad_app::core::product::Ryucad`: `keys::Registry`, `toast::Words`, `link::Client`), and the product's modules name the generic types for it (`core::keys::Keymap` is `Keymap<Ryucad>`, `core::link::Link` is `Link<Ryucad>`, `core::people::Person` is `Person<CadView>`). Whole modules are re-exported under their old paths (`ui::fonts`, `ui::icon`, `ui::style`'s glob). So ryucad's code and tests kept their paths; only three toast tests changed, from struct literals to `Toasts::with`.
- **In ryu-session.** The chord syntax (`chords`: `chord_ok`, `key_names`, `command_id_ok`, `MODIFIERS`, `MAX_CHORDS`) and the participant and highlight colours (`colours`) moved from `ryucad::config` and `ryucad::render`, which re-export them, so a daemon checks `ui.keys` and a render paints participants without egui.
- **Testing.** Each module's product-free tests moved with it and gained a toy product (a registry, a spec, words, a view). ryucad's tests stayed where they were and passed unchanged. The window pictures (`tests/looks.rs`) were kept at the base commit (`RYUCAD_PICTURES_KEEP`) and compared pixel for pixel after every move (`RYUCAD_PICTURES_SAME`) on lavapipe. Two runs of one build differ only in the Activity tile's newest row (a fresh annotation's age and random file name) in `annotate`, `direct` and `redlines`, so the exact compare leaves that row out (`VARIES`); lavapipe once moved 11 viewport edge pixels on one run that a rerun didn't repeat.

## ryu-review (decided in ryupdm phase 8)

The design is document 667 in the Coxswain planning project `ryucad-ryukei`; this is its phase 2, plan 8.A.

- **What it holds.** The hosted review service's client, moved out of `ryucad::review` unchanged: `Client` (ureq on rustls, `get`, `post`, `download`), `refusal` (the service's codes as `review_*`), `token_from`, `escape`, `github_repo`, `url_ok`, `where_used` (schema 1 only), a clone's `Session<L: ryu_git::Layout>` (origin, branch, its pull request) and the shared `Action`s (status, threads, comment, reply, resolve, reopen, update, renders, approvals) with `run`. `testing::Fake` (feature `testing`) is the stand-in service every product's tests use. It depends on `ryu-doc`, `ryu-git`, `serde_json` and `ureq`, never on a product (`tests/deps.rs`).
- **Products.** A product is a `Product`: its binary and version (the user agent), its URL and token variables (`RYUCAD_REVIEW_URL`, `RYUEDA_REVIEW_TOKEN`) and its `review.url` preference. `ryucad::review` keeps its paths, `Action`, audit and packages, codes and answers; `ryueda review` has the shared actions and `where-used --org`. A render row names a `part` (ryucad) or a `block` and `sheet` (ryueda), and `format: "svg"` saves as `.svg`.
- **Testing.** Its own tests against the fake; ryucad's `tests/review.rs` unchanged through a re-export; ryueda's `tests/review.rs`.
- **The ledger** (ryuplm 2.B, design 936): `refusal` maps the service's `part_number_taken` to `Code::PartNumberTaken`. `testing::Fake::serve(handler)` answers from a handler (`Fake::start`'s fixed routes are built on it), and `testing::Ledger::start(slug)` is a stateful stand-in for the ledger's four routes (sequences by template, reservations by catalogue, bindings a test sets, a refusal for every call), used by ryuplm's tests and bar.

## ryu-gerber (decided in ryueda 5.C)

- **What it is.** Gerber X2 and Excellon written from `ryu-board`'s shapes, product-neutral; it depends on `ryu-board` alone (`tests/deps.rs`). ryueda's `board export` writes through it; ryudfm's stage 6 adds its readers here. Its `testing` feature is a reader of exactly what it writes, not a general reader.
- **Gerber.** `%FSLAX46Y46*%` in mm: a nanometre is one unit, coordinates exact; ±9,999.999999 mm (`Error::OutOfRange`). File attributes `.GenerationSoftware`, `.SameCoordinates`, `.FileFunction`, `.FilePolarity`; `.AperFunction` per aperture and region; `.N`, `.P`, `.C` per item, deleted after it. A region is flashed only when it is exactly the `Round`, sharp `Rect` or `Oval` standard symbol on its box with an integer centre (`flash_of`, cyclic edge equality; a full circle is the same contour from any start); otherwise a region with true arcs (`G75`). Round pens draw; square-pen segments become their hulls; regions with holes, square pens on arcs, pens of no width and swept pens are refused. A layer that would define no aperture defines one unused `C,0.010000`, since readers take a file with no `%AD` for RS-274D.
- **Excellon.** KiCad's dialect: `M48`, X2 comments, `FMAT,2`, `METRIC`, tools by diameter then function, holes by drill, `T0`, `M30`; mm with as few decimals as are exact. Slots `G85` or routed (`SlotForm`), the caller's choice.
- **Testing.** Unit tests per module; `tests/read_back.rs` (hand-made layers, 400 seeded symbols at every quarter turn, drills in both forms, refusals); the golden `tests/golden/ryu-gerber.txt` (`UPDATE_GOLDEN=1 cargo test -p ryu-gerber --test determinism`), in the CPU-levels job.
