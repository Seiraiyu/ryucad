# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ryucad is CAD built for AI agents to drive, not primarily for humans clicking in a GUI. FreeCAD was rejected because it performs poorly on large assemblies, and its kernel, OCCT, is a main reason. This project builds its own kernel, **ryukei**, and the long-term target is Parasolid-level capability.

The project is in its early stages. Roadmap phases 0 (foundations: deterministic math, the tolerance model, exact predicates, interval arithmetic, the test harness), 1 (topology core: flat-array B-rep bodies, Euler operators, the validity checker, stable names, the five primitives), 2 (geometry: rational NURBS, the ellipse, pcurves, derivatives, global projection), 3 (tessellation: certified, watertight, parallel meshing, and the first OCCT comparison) 4 (sweeps: validated profiles, extrude, revolve, swept and spun surfaces) and 5 (analytic booleans, design 32: pcurves on every fin, cavities, certified intersections, the self-intersection check, and unite, intersect and subtract of solids with any number of tools) are done. Phase 6 (blends, design 43) is done: pipes, the surface a rolling ball sweeps, and their certified intersections (plan 6.A), edge blends and chamfers (plan 6.B), corners (plan 6.C), and booleans on blend faces, the self-intersection check beside tangent faces, and comparisons with OCCT and SMLib (plan 6.D). Phase 7 (interop: STEP read and write, healing imported geometry) comes next. See design 14 (ryukei roadmap) in the Coxswain planning project `ryucad-ryukei`. On the application side, ryucad phase 0 (projects of feature files, deterministic rebuild of the primitives, the agent CLI, the session daemon, releases and installers) is done, and so is phase 1 (design 28): the live session, the activity log and undo, settings, Git history, display meshes, renders and `doctor` in the daemon, and the desktop app, `ryucad-app`, with its installers. Phase 2 (parametric parts, design 36) is done: parameters and expressions and stage 1 of the sketch solver `ryusketch` (plan 2.A), sketch features and extrude and revolve (plan 2.B), references and incremental recompute (plan 2.C), and sketches, labels and the parameter panel in the app and stage 2 of the solver (plan 2.D). Phase 3 (the Git-native workflow, design 48) is done: any revision loaded and rebuilt, readable `git diff`, `ryucad diff` and `ryucad check` (plan 3.A), the merge driver and merge validation (plan 3.B), and the app's compare view and conflict panel (plan 3.C). ryupdm phase 0 (the data model, design 44) is decided: identity, properties, revisions and release records are below; local PDM (ryupdm phase 1) builds them.

Above the kernel sit ryucad, the application (feature files in Git, the agent CLI, a live viewer humans watch but don't model in, assemblies at scale), and ryupdm, product data management (revisions, releases, where-used, BOM, hosted review; PDM only, not PLM). ryupdm is the likely business; ryukei and ryucad may be open sourced. Their roadmaps are designs 20 (ryucad) and 21 (ryupdm), design 23 lines up all three, and design 22 is the business plan.

## Layout

- `crates/ryukei`: the B-rep geometry kernel (library).
- `crates/ryusketch`: the 2D constraint solver for sketches (library). It depends on `ryukei` only for `math`.
- `crates/ryucad-doc`: ryucad's file format (`doc`, `units`, `expr`, `error`), split out so ryupdm can read projects; `ryucad` re-exports each under its old path.
- `crates/ryupdm`: local product data management (library): the PDM settings, part properties and, later, revisions and releases. It reads projects through `ryucad-doc` and never calls the kernel, a session or the app.
- `crates/ryucad`: the application layer and binary.
- `crates/ryucad-app`: the desktop app, a client of the daemon (`core`: link, model, people, navigation, picking, forms; `ui`: the egui window and the wgpu scene).
- `packaging/`: what the installers register: the Linux desktop entry and project MIME type, and the macOS launcher's AppleScript.
- `crates/ryukei-testkit`: test-only helpers (exact references, seeded inputs, golden hashes, Euler operator sequences, sweeps and booleans from bytes, random NURBS). Never a runtime dependency.
- `crates/ryukei-bench`: divan benchmarks, and the comparisons behind its `occt` and `smlib` features: `cxx` shims over a system OCCT 7.8 and over `libsmlib`, the kernel of NVIDIA's USD BRep built from a pinned commit. The devcontainer installs both.
- `fuzz/`: cargo-fuzz targets, outside the workspace (nightly only).
- `install.sh`, `install.ps1`: the installers, also published with each release. `scripts/` holds their tests and the release smoke test.
- Design documents, roadmaps and plans live only in the Coxswain planning project `ryucad-ryukei` (`cox doc list`), never as markdown in the repo, so there is one copy of each.

ryupdm code will live in this monorepo too; the repo may be split later if parts are open sourced.

The boundary between the two crates is deliberate. ryukei works on single bodies (geometry, topology, booleans, blends, tessellation) and must not depend on documents, assemblies, or agents. Large-assembly performance (instancing, lazy loading, caching, incremental recompute) and the agent interface live in ryucad. Keep both in this repo until the kernel API settles.

## Kernel principles

- **Parasolid-level is the goal.** Supporting analytic surfaces first (planes, cylinders, cones, spheres, tori, and fillets between them) only sets the order of work, not the scope. Never hard-code analytic-only assumptions into the core types. Analytic surfaces are fast special cases of a general surface/curve representation that NURBS will slot into.
- **Tolerant modeling from day one.** Edges and vertices carry their own tolerances.
- **Data-oriented topology.** Store topology in flat arrays referenced by IDs, not reference-counted pointer graphs like OCCT's. This makes models cheap to copy, cache-friendly, and shareable across instances.
- **Parallel from the start.** Design operations so independent work (tessellation, separate bodies, recomputing independent parts) can run concurrently.
- **Stable names for faces and edges.** Agents need references to faces and edges that survive a rebuild. FreeCAD's "toponaming" problem is the failure to avoid.
- **Deliberate numerical precision.** Decide explicitly which calculations must be exact and which can use floating point with tolerances.
- **Identical results on every platform.** The same model must produce the same result on every OS and CPU. Don't use the platform's own math functions (`f64::sin` and similar) where results must match; use a portable implementation such as the `libm` crate. Use fused multiply-add only explicitly, never fast-math, and only portable or runtime-selected SIMD. Otherwise booleans can succeed on one OS and fail on another, and saved test results won't match across machines.
- **CPU-only.** The kernel needs 64-bit floats and branch-heavy code, which GPUs handle poorly, so performance comes from the memory layout and running on many cores. GPU work (viewer, rendering for agents, clash detection) belongs in ryucad. CI uses software renderers for it.
- **Keep C++ kernels out of the default build.** Put OCCT and SMLib behind a Cargo feature or in a separate bench crate, so the default build has no C++ dependency on any platform.
- **Robustness through testing at scale.** Use a corpus of real models, randomly generated and mutated operations, checks that the topology stays valid after every operation, comparison of results against OCCT and SMLib, and benchmarks against OCCT's numbers. OCCT and SMLib may serve as references and benchmark baselines, and as a temporary fallback (in ryucad, preferring SMLib) for operations ryukei can't do yet, but never as the long-term kernel. See "Reference kernels" in design 14 (ryukei roadmap).
- **Port SMLib's algorithms, not its numerics.** SMLib (NVIDIA's USD BRep, Apache 2.0) may be ported into ryukei. Keep its NOTICE and credit it in the ported file. Topology decisions still go through `ryukei::predicates`, `ryukei::interval` and `tol`, never SMLib's float tests.

## Numerics (decided in phase 0)

The design is document 12 in the Coxswain planning project `ryucad-ryukei`.

- **Units and tolerances.** Model space is SI meters. `ryukei::tol` fixes `LINEAR_RESOLUTION` = 1e-8 m, `ANGULAR_RESOLUTION` = 1e-11 rad and a size box of ±500 m for every body. Per-entity `Tolerance` values are never below the resolution. Unit conversion and larger models are ryucad's job.
- **Precision policy.** Decisions that change topology or classification (side of a plane, inside a circle or sphere, ordering) use exact or certified predicates (`ryukei::predicates`, `ryukei::interval`), never a raw float sign. Geometric values (coordinates, parameters, distances, constructed points) are f64 compared through `tol`, never with `==`. Predicates take their f64 inputs as exact. An uncertain interval sign must be escalated or resolved by an explicit tolerance rule, never guessed.
- **Determinism.** Kernel code gets transcendental functions only from `ryukei::math`; `clippy.toml` bans the `f64` versions and `mul_add`. `tests/golden/determinism.txt` holds the bit-exact hashes that every CI platform and CPU level must reproduce. When you change results on purpose, regenerate it and review the diff.

## Topology (decided in phase 1)

The design is document 15 in the Coxswain planning project `ryucad-ryukei`.

- **Storage.** A `ryukei::topo::Body` holds flat arrays of regions, shells, faces, loops, fins, edges and vertices, plus its curves, surfaces and pcurves, all referenced by typed `u32` IDs. Each edge has a ring of fins (Parasolid style), so sheets and non-manifold bodies fit later; phase 1 builds and accepts manifold solids only. A solid region has one outer shell and any number of void shells (cavities). Deleting leaves a tombstone; IDs are never reused until `Body::compact()`, which returns a `Remap`. Closed edges have exactly one vertex; periodic faces have no seam edges (a sphere or torus is one face with no loops).
- **Editing.** Topology changes only through `ryukei::euler`: MVFS/KVFS, MVS (a shell in an existing solid region; KVFS undoes it), MEV/KEV, MEF/KEF, KEMR/MEKR, KFMRH/MFKRH, SEMV/JEKV, MVR/KVR, plus `set_point`/`set_curve`/`set_surface`/`set_pcurve`. Operators check every precondition before writing (on `Err` the body is unchanged) and decide no geometry; the caller passes it.
- **Geometry.** Curves and surfaces live in the body's own arrays and may be shared by several edges or faces; see Geometry below.
- **Names.** Faces, edges and vertices carry a 128-bit `name::Name`: SipHash-2-4 of the caller's `OpKey`, the entity's `Role` and its parents' names. A split retires the parent's name and names both children; every operation returns a `Journal` of the changes. The kernel never invents keys; resolving an agent's reference through the journal is ryucad's job.
- **Validity.** `check::check_topology` holds after every Euler operator (debug builds assert it); `check::check` adds geometry and orientation and holds for finished bodies (primitives assert it). `check::check_intersections` adds that faces meet only at shared edges and vertices (see Intersections below); it runs in tests and fuzzing, not after every operator.

## Geometry (decided in phase 2)

The design is document 17 in the Coxswain planning project `ryucad-ryukei`.

- **Types.** `geom::Curve` (line, circle, ellipse, NURBS), `geom::Surface` (plane, cylinder, cone, sphere, torus, NURBS) and the pcurve type `geom::Curve2` (line, circle, ellipse, NURBS in a surface's `(u, v)` plane) are `#[non_exhaustive]` enums, `Clone` but not `Copy`. Analytic variants are fast paths with closed forms. A NURBS sits behind an `Arc` and never changes once built, so cloning a body shares it; its Bézier pieces are built on first use in a `OnceLock` that takes no part in equality or the dump. Fins carry pcurves (see Pcurves and cavities below).
- **NURBS.** Rational, degree 1 to 25, with a `KnotVector` that is clamped or periodic (distinct knots plus multiplicities). Constructors reject bad input with `Error::InvalidNurbs(NurbsError)`, `NonFinite` or `OutsideSizeBox`; collapsed control rows (poles) are allowed. `refine`, `split` and `to_clamped` return clamped splines; `transformed` takes a `Rigid`. Every analytic type converts exactly (`to_nurbs`), with a `Reparam` relating the parameters.
- **Derivatives.** `eval` gives derivatives up to second order. Tangents and normals are `Option`: a NURBS judges vanishing on derivatives scaled to its domain, and gives the limit normal at a pole. Principal curvatures are measured against the natural normal, positive where the surface bends towards it.
- **Projection.** `project` returns a point within `LINEAR_RESOLUTION` of the true global minimum, and among minima that close, the lowest parameter. The search works on the Bernstein coefficients of `(S - p)·S'` per Bézier piece: one sign means no stationary point, one sign change means exactly one (curves); surfaces add an interval Newton step and a depth limit, then Newton's method. Domain boundaries, kinks and creases (knots of multiplicity `degree`) are searched as curves, and every candidate must be a genuine local minimum. Degenerate splines (folds, collapsed patches, poles) are where this breaks: the property tests and the `nurbs` fuzz target pin the cases found so far.
- **Bodies.** Euler operators, the checker, `compact` and the dump accept every variant. The checker measures distances through `project`, bounds NURBS by their hulls, requires edge intervals inside a clamped curve's domain, and lets a closed edge lie on a clamped curve whose ends meet. A face with no loops is still only allowed on an analytic sphere or torus.

## Tessellation (decided in phase 3)

The design is document 19 in the Coxswain planning project `ryucad-ryukei`.

- **API.** `mesh::tessellate(&Body, &MeshParams) -> Result<BodyMesh, Error>`. `MeshParams` has an absolute `chord` (at least `10 × LINEAR_RESOLUTION`), an `angle` in `(0, π/2]`, an optional `max_edge`, and a `max_triangles` budget (50M by default). Bad parameters are `InvalidMeshParams`; a runaway request is `MeshTooLarge`, refused from an estimate before faces are meshed, and again if the real count passes the budget.
- **Guarantee.** Every face is within `chord` of its triangles both ways (two-sided Hausdorff), plus the local edge tolerance near tolerant edges. The bounds are certified, never sampled: `geom::{CurveBound, SurfaceBound}` bound second derivatives and turning rates over a parameter range (closed forms for analytic types, interval arithmetic on Bézier pieces for NURBS, differencing the whole piece before cutting it down), and a triangle passes when `M R² / 2 <= chord` (Waldron's bound, `R` the smallest enclosing circle in the face's scaled parameter plane). The normal turns at most `angle` across a triangle, except that the angle test is waived for pieces smaller than `chord` (features under the tolerance, and poles or apexes where the normal has no limit).
- **Structure.** Edges are sampled once (bisection until the curve and every adjacent face are satisfied, with an exact sample at every seam crossing) and shared, so the mesh is watertight by index. Each face is a constrained Delaunay triangulation on exact `orient2d`/`incircle` in its parameter plane scaled by powers of two (so scaling is exact), cut at seams (the domain start of a periodic direction) into one period, with collapsed rows (poles, apexes) as sides whose points weld to one position. Refinement is longest-edge bisection; a face never splits a boundary segment itself but asks its edge for a sample, and is meshed again (up to twelve rounds; after three, an edge still asked about is halved all along, so the asking stops). An edge's first segments are checked at their middle, so an arc of half a turn or more round a periodic face can't be mistaken for the short way round. A vertex whose neighbours meet one welded position in two runs (a "pinch" at a pole or across a seam) is repaired by flips or splits before assembly.
- **Output.** `BodyMesh`: welded `positions` (body vertices, then edge samples, then face points), per-face `corners` (position, unwrapped `(u, v)`, outward normal), triangles counterclockwise from outside, `FaceMesh` ranges by `FaceId`, `EdgePolyline`s by `EdgeId`, and `faults`. A face that can't meet the guarantees (`EdgeOffSurface`, `BadDomain`, `RefinementStalled`, `BoundaryNotResolved`) is left out and reported; `check_mesh` verifies indices, winding and that every welded edge has exactly two opposite uses.
- **Parallelism and determinism.** `ryukei` depends on `rayon`: edges, then faces, run on the current pool; each is a pure function and results are gathered in ID order, so the mesh is the same bits on any number of threads. Golden hashes pin meshes across platforms.
- **Doubly periodic faces.** A face with loops that leave one direction unwound (a torus band between two circles, a pipe's elbow) meshes that direction as open, wrapped from just below the face by its loops' orientation, when the loops leave a tenth of a turn clear. Otherwise (a face whose loops are all holes, a band spiralling round a torus, one within a tenth of a turn of that) both directions stay periodic, with seams in gaps between the loops' sampled extents (`uv::gap`, which sees spans running past the period's end); a ring that fits between one direction's seams but not the other's is cut at the seam it crosses, as on a cylinder. Loops winding both ways, or fitting neither way, are `BadDomain`.
- **Slivers.** Booleans make faces meeting in wedges thinner than the chord. Where two faces draw one chord between boundary points (both inside, or one as a loop segment), both are meshed again with it split (`refine::chords`), so the welded mesh stays manifold. Where two loop segments cross (edges of a sliver closer than their samples' sagitta), the face asks both edges for samples there. An edge alone in a loop with one other gets its middle when it would have no inner samples. A seam crossing is only accepted where the curve really lies on the seam (a long segment's side test can flip half a period away instead).
- **Limits.** Closed directions are periodic ones only (a clamped NURBS face whose ends meet is `BadDomain`). A ring through a pole never winds round its free direction (the jump along the pole is free, and with half a turn across it the nearest period is a tie), and a jump that crosses a seam is cut there; a ring through two poles (a sphere's wedge) takes the stretch between them by the face's orientation. A feature thinner than the chord (a torus tube) can stall refinement. Meshes are not FEA-quality, and ryukei makes about 1.5 to 18 times OCCT's triangles at the same chord.

## Sweeps (decided in phase 4)

The design is document 27 in the Coxswain planning project `ryucad-ryukei`.

- **Profiles.** `sweep::Profile` is a `Frame` and loops of trimmed `Curve2` segments (`t1 < t0` runs a segment backwards), each segment and loop carrying a caller key (`SegmentKey`, `LoopKey`, 128-bit, unique in the profile). `ValidProfile::new` checks structure, ranges and closure (gaps up to `LINEAR_RESOLUTION`), then certifies that segments are more than `LINEAR_RESOLUTION` apart except at their shared ends (rational Bézier pieces with a `1e-10` m rounding slack, cone tests at joints; uncertain counts as touching), signs each loop's area by an explicit rule, and nests loops by winding number into lumps with holes, outer loops counterclockwise. Failures are `Error::InvalidProfile(ProfileError)`, naming the keys. A whole period of a periodic curve must be its loop's only segment.
- **Operations.** `sweep::extrude(key, &profile, dir, start, end)` and `sweep::revolve(key, &profile, Axis, start, end)` make one body with a solid region per lump, built through Euler operators (`sweep/build.rs`) and named from the caller's keys. Extrude takes any direction more than `ANGULAR_RESOLUTION` from the profile's plane (snapped to the normal within it). Revolve's axis lies in the profile's plane; a span within `ANGULAR_RESOLUTION` of 2π is a full turn with no caps. The profile may touch the axis at segment ends or lie along it, never cross it or touch it inside a segment; in a full turn, holes and the stretches of a loop between two axis contacts that another stretch spans enclose cavities and become void shells, and a lone touch is refused (`PinchedOnAxis`). Parameter faults are `Error::InvalidSweep(SweepError)`.
- **Surfaces.** Sides are analytic wherever exact (plane, cylinder, cone, sphere, ring torus), otherwise `Surface::Extrusion` (a planar curve along a direction) or `Surface::Revolution` (a curve in the frame's xz half-plane turned about z; poles only at a clamped curve's ends, closed genus 0 with poles at both ends, 1 for a periodic curve). Both keep their generating curve, project exactly through it, and convert exactly to NURBS. A revolve's sides measure their angle from opposite the middle of a partial turn, so no face meets a surface's seam.
- **Topology and names.** Periodic sides have no seams; a full turn's profile vertices sweep closed circles; a vertex on the axis is a body vertex only at an apex (a side meeting the axis at an angle), not at a pole. Names (`name::SweepRole`) come only from the sweep's key and the caller's keys: a side from its segment, a cap from its lump's outer loop and its end, a cap edge from its cap and side, a lateral edge and its vertices from the segments either side of the profile vertex. Editing dimensions or rotating a loop's start renames nothing; adding a segment renames only what sat where its new vertex is.
- **Limits.** Extrude and revolve cost grows with the square of a loop's segment count (MEF walks the loop): about 70 ms at 1,000 segments.

## Pcurves and cavities (decided in phase 5)

The design is document 32 in the Coxswain planning project `ryucad-ryukei`; these are its phases 0 and 1.

- **Pcurves.** Every fin of a finished body has a `topo::Pcurve`: a `Curve2` in the body's `curves2` array and an affine map `s = map[0] + map[1] t` from the edge's parameter to the pcurve's, so the face's surface takes the pcurve to within the edge's tolerance of the edge at the same parameter. New fins start without one; operators keep pcurves while they stay valid (SEMV shares them, JEKV needs them equal) and drop them when a fin's face changes surface or its edge changes curve (`set_surface`, `set_curve`, KEF and KFMRH across surfaces). `check::check` reports `MissingPcurve` and `PcurveOffEdge` (sampled, like the other edge checks).
- **Exact pcurves.** `pcurve::exact` finds them from the geometry: on a plane (or a NURBS parallelogram) a line, circle, ellipse or NURBS maps to the same kind of curve; on any other surface an edge along a parameter line (circles round an axis, rulings, a swept surface's generator) is a `Line2` with an affine parameter, read from projections a quarter and three quarters along. A candidate counts only if it fits at 17 samples. `pcurve::fill` gives every fin without one its pcurve, or fails with `Error::NoPcurve`; primitives and sweeps call it before their final check, and so must anything that builds a body by hand. Intersection curves bring fitted pcurves (see Intersections below).
- **Meshing.** An edge sample's `(u, v)` on a face comes from its fin's pcurve; only a fin without one still inverts the point with `project`.
- **Cavities.** A cavity is a void shell in its solid region, made with MVS; its faces point into it. For all-planar solids the checker wants exactly one shell enclosing positive volume and the others negative. An empty body (only the outer void region) is sound and meshes to nothing.

## Intersections (decided in phase 5)

The design is document 32 in the Coxswain planning project `ryucad-ryukei`; these are its phases 2 and 3.

- **Certified roots.** `geom::bernstein` and `geom::bernstein2` hold polynomials by interval Bernstein coefficients, rounded outward; roots are certified by sign (one sign excludes, a certified monotone piece holds one root) and what rounding can't decide is reported unresolved, never guessed. Krawczyk's test (`bernstein2::krawczyk`) certifies unique solutions of 2×2 systems.
- **Implicit forms.** Each analytic surface has a polynomial `f` in its frame (`intersect::implicit`, degree 1, 2 or 4) whose factoring bounds the distance from the surface by a multiple of `|f|`. A cone's form holds both nappes; what lies on the other nappe is dropped everywhere. Every certified distance adds `intersect::SLACK` (1e-10 m) for floating-point evaluation.
- **Curve–surface.** `intersect::curve_surface` substitutes a curve's exact rational Bézier pieces (`geom::chain3`) into the implicit form: simple roots are crossings; a piece or stretch certified within the tolerance touches, a point if under 100 tolerances long (a tangency's rounding zone), a stretch `On` the surface if longer; near misses and crossings closer than the tolerance are one contact by rule; sides come from certified signs, and contacts reaching an end of the interval snap to it.
- **Surface–surface.** `intersect::surface_surface` decides coincidence by rule (`intersect::coincide`), meets closed-form pairs exactly (`ss_exact`: coaxial pairs by their meridians, plane sections including plane–cone conics as rational quadratics in the cone's angle and, where a plane nearly along a cylinder's axis cuts an ellipse centred outside the size box, that ellipse's stretches in the region, parallel cylinders, equal crossing cylinders, cones sharing an apex) and traces the rest: the simpler surface's exact NURBS patches go into the other's implicit form, cells are excluded, regular (a graph) or singular, side crossings are certified once per piece of a line, and each singular cluster must hold one critical point (Krawczyk) on the curve. Where seams make that uncertain the trace retries with the surface turned about its own axis. Traced branches are fitted as cubic Hermite NURBS with pcurves on both surfaces by one parameter (`intersect::fit`), every span certified by the implicit forms and a Taylor bound, the worst bound the tolerance (refused past 10 × resolution). Every branch carries pcurves on both surfaces (exact where `pcurve::exact` finds them) and is cut at sphere poles and cone apexes; slivers under 10 tolerances are points.
- **Faces.** `intersect::point_in_face` is on a vertex or edge within tolerance, else a certified ray aimed at the face's own pcurves, the first transversal crossing deciding by the loop's side. `geom::intersect2::crossings` meets plane curves (same carriers in closed form, else a certified polynomial system; overlaps over 100 tolerances). `intersect::face_face` trims surface intersections to both faces by cutting at the edges' curve–surface hits; coincident faces give the rims of their overlap. A face on a swept or NURBS surface takes part only certified apart from the other face, else `Unsupported`.
- **Self-intersection check.** `check::check_intersections` intersects every pair of faces whose boxes overlap (`intersect::broad`, a box tree over `face_box`), in parallel: `FacesCross` unless they meet only along a shared edge or at a shared vertex, `FacesOverlap` for coincident faces overlapping in an area, `CannotCheck` for pairs it can't intersect, including every pair where a face on a swept surface meets its neighbours (design 32 leaves swept surfaces to phase 8). Faces tangent along an edge they share are certified apart beside it instead (see Booleans on blends below). Out of a vertex both faces have, a stretch inside at most one of them is benign for `sqrt(2 × size × reach)`, how long surfaces meeting tangentially stay within the reach: a tangent wedge's tip.
- **Testing.** `tests/intersect_props.rs` checks curve–surface and surface–surface results against sampling, `tests/point_in_face.rs` point in face against the mesh; the primitive and sweep tests run the self-intersection check; the `intersect` fuzz target puts surface pairs on a coarse grid, the `sweep` target runs the check on every body, and `tests/fuzz_regressions.rs` replays what it has found (through `ryukei_testkit::sweep_bytes`). Golden hashes cover intersections (`intersections` section).
- **Limits.** Pairs of swept or NURBS faces that meet, tangency along a whole curve in the traced case, and curves through a patch corner in every turn of the parameterization are `Uncertain` or `Unsupported`: about 1–2% of grid-placed analytic pairs in the `intersect` fuzz target are refused this way.

## Booleans (decided in phase 5)

The design is document 32 in the Coxswain planning project `ryucad-ryukei`; these are its phases 4 to 6.

- **API.** `boolean::boolean(key, op, &target, &[Tool { key: ToolKey, body, place: Rigid }]) -> Result<(Body, Journal), Error>` unites, intersects or subtracts any number of placed tools in one pass; the tools act as their union. Refusals are `Error::InvalidBoolean(BooleanError)`: `DuplicateToolKey`, `OutsideSizeBox`, `Unsupported` (a non-analytic face that meets another), `Uncertain` (an intersection, ordering or classification rounding can't decide) and `NonManifold` (kept faces meeting at an edge or a point only), naming faces by their names. `Error` is no longer `Copy`.
- **Pipeline.** `place` moves the tools (`Body::transformed`); `table` intersects every pair of faces of different operands whose boxes overlap, cuts every edge with the faces it may meet, and clusters every point found into global vertices (closer than the sum of their tolerances; a touching point reaches 100 tolerances, the touch rule, and snaps to an edge's end within that), never merging two vertices of one operand. Edges and stretches are carriers, cut at their vertices; carriers known to run together share them, and their pieces between two vertices are one global edge with a pcurve on every face that uses it. `split` walks each face's arcs in its parameter plane (darts ordered by angle about the outward normal, tangent ties by where they go a little way out, poles and apexes ordered by the surface's directions), lifts the cycles (stretches along a pole's line between chains count as crossings), and groups them: outer boundaries and holes by certified winding numbers, bands by where winding cycles cross a line across them, caps at poles and apexes. `classify` makes one certified ray cast (`intersect::point_in_body`) per group of pieces joined across untouched own edges and per other operand whose box holds its point; pieces on another operand's face are `On` it. `select` applies the design's table. `build` grows each shell through Euler operators from the vertex rotations the kept pieces' fans give (MEV, `mev_reversed`, MEF, MEKR, KFMRH), builds a shell found to be a void again by MVS in the region around it (a lone shell is never a void), and fills tolerances to cover rounding at joints. `merge` joins faces either side of an edge on one surface (KEF), removes edges with one face both sides (KEMR, or MFKRH then KEF for a closed edge alone in two loops, where a tool touched a periodic face all round) and lone vertices no operand had (KVR), and joins edges on one line or circle (JEKV, sharing pcurves first).
- **Names.** Target entities kept whole keep their names; tool entities are `Placed` under a `Tool` name from the boolean's key and the `ToolKey`, so copies never collide and moving a tool renames nothing; split faces are `Piece`s named by their cutters, cut edges `Cut`s, new edges and vertices `IntersectionEdge`/`IntersectionVertex` by the faces meeting there, merged ones `Merged`, with an ordinal only where names still collide. `Event::Split` and `Event::Merged` are n-ary; `Event::Placed` records every renamed tool entity.
- **Guarantees.** Nothing is built until every intersection, split and classification has succeeded. Results pass `check::check`, `check_intersections` and mesh without faults (debug builds assert `check`; release builds run `check_topology` and report `Topology(Inconsistent)`). One thread and many give the same bits.
- **Testing.** `tests/booleans.rs` and `tests/boolean_corpus.rs` check exact volumes (a plate's hole, a lens, the Steinmetz solid, torus and cone cuts, flush, coaxial, tangent and coincident cases, cavities, refusals) and `tests/boolean_names.rs` the names and journal; `tests/boolean_props.rs` checks the set identities on random placed primitives and sweeps, in release only (minutes in a debug build), replaying the cases it found first; the `boolean` fuzz target puts primitives on a coarse grid (`ryukei_testkit::boolean_bytes`); golden hashes cover booleans (`booleans` section). In the devcontainer, `ryukei-bench`'s `booleans` test checks ryukei against OCCT's exact volumes, with SMLib beside them.
- **Performance.** A block minus 1,000 through-cylinders takes about 0.55 s on one thread, against OCCT's 1.1 to 1.3 s; single traced pairs (crossed cylinders, a cone and a ball) are 3 to 5 times slower than OCCT's.
- **Limits.** A traced branch whose points come out of order along the curve (seen near a cone's apex) is refused by the fit as `Uncertain`, as are the cases the intersection limits list. Equal crossed cylinders unite only to a pinch at their tangent points (`NonManifold`). The `boolean` fuzz target still finds results the mesher refuses: a cone, a block and a torus whose middle plane is the cone's base intersect into faces whose loop segments keep crossing however much they are refined (`BadDomain`; work item #532 has the bytes).

## Pipes (decided in phase 6)

The design is document 43 in the Coxswain planning project `ryucad-ryukei`; these are its phases 0 and 1, plan 6.A.

- **Surface.** `Surface::Pipe` (behind an `Arc`) is `P(s, θ) = c(s) + r (cos θ e₁ + sin θ e₂)`: a circle of radius `r` about each point of a spine (an ellipse or a NURBS; along a line or a circle a fillet is a cylinder or a torus instead) in the plane normal to it. Its frame is anchored on an analytic surface: `e₁` points from the spine towards its foot on the anchor, made perpendicular to the tangent, and `e₂ = e₁ × t`, so `θ = 0` is where the ball touches the anchor, the seam `θ = ±π` is opposite it, and the natural normal points away from the spine along `P_s × P_θ`. `Pipe::new` certifies it regular over the whole spine in interval arithmetic (speed, one side of the anchor and clear of its axis, centre, core circle or apex, a defined frame, `r κ < 1`), else `Degenerate`. A closed spine gives a closed tube (genus 1, a face with no loops). A pipe has no exact NURBS form (`to_nurbs` is `Degenerate`); `Pipe::to_nurbs_within` gives one within a certified tolerance, for export (see Booleans on blends below). A chamfer between curved rails is an exact ruled NURBS (`NurbsSurface::ruled`), with no surface type of its own.
- **Jets.** `geom::jet` carries a value with its gradient and Hessian in two variables over `f64` or intervals, by the product and chain rules. A pipe is written once over jets: evaluation with exact second derivatives, and over interval jets enclosures over cells. Its derivative bounds go through its frame, which depends on `s` alone (see Booleans on blends below). Curves gained third derivatives (`Curve::jet3`) and enclosures of them over a range (`Curve::jet_box`).
- **Offsets and projection.** `Surface::offset(d)` moves the analytic surfaces and pipes along their natural normals keeping their parameters (`None` for NURBS and swept surfaces; `Degenerate` where it collapses). Projection onto a pipe goes through every stationary point of the distance to its spine (`NurbsCurve::stationary`, maxima too) and its ends.
- **Intersections.** `intersect::pipe_surface` meets a pipe with an analytic surface: the implicit form over the pipe's jets, `F = f ∘ P`, enclosed over cells (mean value and second order forms) and traced in the pipe's parameter plane as `ss_trace` traces patches (excluded, regular or singular cells; crossings solved once per piece of a line, the wrapping lines folded together; Krawczyk on `∇F` for singular points; retries with the grid shifted in `θ` and `s`), then fitted with the pipe's side read through its distance from its spine and certified by its pcurve bound. A tangency along a whole curve is `Uncertain` at once; two pipes, or a pipe and a NURBS or swept surface, are `Unsupported`. `intersect::curve_pipe` solves `(C - c)·c' = 0`, `|C - c|² = r²` in the curve's and the spine's parameters (cells halved along the parameter that adds more to the enclosures), with `curve_surface`'s rules for contacts, touches, ends and sides. `surface_surface` and `curve_surface` hand pipes to these, so booleans and `check_intersections` take pipe faces (see Booleans on blends below).
- **Testing and limits.** `tests/pipes.rs` (tubes and a bent cylinder against Pappus's volume and area, face boxes, `pipe_surface` end to end), `tests/pipe_props.rs` (seeded random surfaces and lines against sampling; release only, its own CI step), golden hashes (`pipes` section).

## Blends (decided in phase 6)

The design is document 43 in the Coxswain planning project `ryucad-ryukei`; these are its phases 2 and 3, plan 6.B.

- **API.** `blend::blend(key, &body, &[EdgeBlend { edge, kind }])` rounds each named edge (`BlendKind::Fillet { radius }`) or bevels it (`BlendKind::Chamfer(Chamfer::{Equal, Distances, DistanceAngle})`, setbacks along the faces, a named face first) where it is convex and fills it where it is concave: a new body and a journal. Refusals are `Error::InvalidBlend(BlendError)`, made before anything is built, naming entities by name. `blend::tangent_chain(&body, edge)` gives the chain through an edge, for ryucad's propagation.
- **Pipeline.** `spec` resolves names, sizes and faces (analytic or pipe); `convex` certifies how each edge bends (the sign of `(n₀ × n₁) · d` over interval pieces: convex, concave, or smooth where the normals agree, `ConvexityChanges` or `Uncertain` otherwise) and when edges meet tangentially (within `ANGULAR_RESOLUTION`, plus four times a fitted curve's tolerance over its end piece); `chain` classes every vertex of a blended edge: a closed edge alone, an end (three edges, the third face cutting the blend off), a join (two tangent blended edges alone) or a smooth join (tangent, sharing a face, a smooth third edge between their other faces). Any other vertex (corners, ends with more edges) is `Unsupported` naming it, a blended edge tangent to an unblended one `OpenTangentChain`, tangent edges blended differently `SizeChangeAlongChain`. Each chain is planned in parallel (`plan`): cut at smooth joins into segments, one blend face each, its new rails all on one rail face (the shared face at smooth joins, else the lower-named face).
- **Fillets.** The spine is the branch of the faces' offsets towards the material (`Surface::offset`) through the ball touching both faces at the edge's middle (Newton), run along the chain; offsets keep their parameters, so its pcurves are the rails' pcurves. Rails are lines or circles in closed form along a line or circle spine, else the face along the pcurve (`intersect::fit_along`, certified by the pcurve bound). The surface is a cylinder (seamed opposite the section) along a line, a torus along a circle, else a pipe anchored on an analytic face, on a closed fitted spine made periodic (`NurbsCurve::bezier_periodic`); Forward at a convex edge, Reversed at a concave one. Earlier fillets, pipes included, are supports: the chain through an earlier fillet's end joins smoothly at its rails.
- **Chamfers.** A rail is the point at its setback from the edge in each normal plane, on the face; sections follow the edge's line, circle or ellipse, or the faces' intersection through a fitted edge. Along a line between planes or cylinders and a circle round coaxial faces the rails are exact and the chamfer a plane, cylinder or cone; otherwise both rails are fitted on shared knots by the edge's parameter (`intersect::fit_on`, certified by the faces' implicit forms) and the chamfer is the ruled NURBS between them, periodic all round. `DistanceAngle` sets the other setback to `d sin θ / sin(α + θ)`, only where the wedge `α` is the same all along (planes along a line, coaxial faces along a circle; else `Unsupported`, and `α + θ ≥ π` is `BadSize`).
- **Ends, joins, overflow.** At an end each rail crosses its cut (the crossing nearest the vertex) and the end curve is the branch of the blend surface and the end face through both crossings, the arc nearer the vertex. A plain join cuts the other face's rail where the ball passes the vertex; at a smooth join the segments meet where the ball touches the smooth edge (a chamfer's section through the vertex), and the section arc (a line for a chamfer) divides their faces. Before building, every rail and end curve is met with its face's edges in the face's parameter plane: touching only at its ends, only the edges it ends on; new curves on one face meet only end to end within a chain; no other loop of the face or other chain's curve lies in a strip a blend takes. Otherwise `Overflow { edge, face }`; offsets that collapse, tori that aren't rings and pipes that fold are `RadiusTooLarge`.
- **Rebuild.** A blended edge becomes its blend's rail on its other face; only the rail-face rail is new. An open chain splits the rail face's cut at each end (SEMV), cuts the blend face off along the rails (MEV between segments, MEF), moves its vertices along the other faces' cuts and smooth edges, turns the rail face's cut stretches into end curves, and splits the blend face at sections (MEF, or MEKR on a closed chain's two-loop strip). A closed path starts from a spur (MEV) where the rail face has no other loop, else from a spoke to another loop (MEKR, split by SEMV), so no loop ever moves (MFKRH would split the shell); KEMR removes it. `euler::start_loop_at` first makes the far side keep the loop's first fin, so the face's other loops stay there. Edges at plain joins on one curve are joined again (JEKV). Pcurves come from the plan, exact or fitted (a rail's on a pipe from its known parameters, `intersect::fit_pcurve_by`); tolerances cover the gaps.
- **Names.** A blend face is named from the blended edges it replaces (sorted), a rail from its blend face and the face it rolls on, an end edge from its blend face, the end face and the vertex taken away, a section from its two blend faces (sorted), every vertex on a blend face from its edges (sorted); trimmed faces and shortened edges keep their names. The journal has `Event::Replaced { old, new }` for each blended edge and each vertex taken away (by the blend faces now there), `Created` for new edges and vertices, `Modified` for changed faces and edges. Resizing or moving a blend renames nothing.
- **Testing and limits.** `tests/blends.rs` and `tests/chamfers.rs` check exact volumes (box edges, rims, holes, a boss's foot, a slot's top all round, tubes, chains across earlier fillets, pipes and ruled bands) and refusals; `tests/blend_names.rs` the names and journal; `tests/blend_props.rs` 48 seeded random primitives (release only, as are the pipe and ruled cases, each file its own CI step); golden hashes (`blends` section). Corners are below; a ruled chamfer can't end on a face and a chamfer can't lie on a pipe face (NURBS and pipe intersections, phase 8).

## Corners (decided in phase 6)

The design is document 43 in the Coxswain planning project `ryucad-ryukei`; this is its phase 4, plan 6.C.

- **Classes.** Where blended edges meet at angles at a vertex of three edges: two sharing a face and bending the same way, the third left sharp, trim each other (`blend::trim`); three fillets of one radius bending one way meet in a ball (`blend::corner`); three chamfers are mitred (`blend::mitre`); three fillets where one is larger than the other two, or the only one bending its way, the other two alike, are rolled (`blend::stage`). Two larger fillets and a smaller one (the small ball would round a crease that vanishes), three sizes, fillets with a chamfer, a mitre whose point leaves a chamfer, and edges bending opposite ways sharing a face are `Unsupported` naming the vertex. One blended edge at a vertex of four or more edges is a fan: the other faces cut the blend off in turn.
- **Geometry.** A ball corner's centre is on all three offsets (Newton's method); each fillet ends at the ball's section normal to its spine, and the corner face is that sphere, its seam and poles away from the sections. A trim follows the branch of the two blend surfaces' intersection that leaves the point where their rails cross on the shared face towards the vertex (two branches cross there, both surfaces touching that face); the blend whose rail on its other face that branch reaches first ends on it all along, and the other also ends in an end curve on that face, to where its own rail crosses the sharp edge, unless both reach the sharp edge at one point. A mitre runs from each pair's rail crossing to the point all three chamfers share. A fan's end curves run between the blend's crossings with the edges between the end faces.
- **Rebuild.** The edges between blend faces at a corner are built round the vertex before the chains: a triangle of sections for a ball (SEMV, MEV and MEF, by how many blended edges become rails on each face), a tree of pieces split off the vertex's edges and spurs for a trim or a mitre (`grow`). Every blended edge still becomes its rail on its other face, and each chain's path runs to the vertex on its rail face; the path's closing MEF keeps the face's other loops on the side away from the blended edges, found by walking the loop. A fan cuts a triangle off each end face but the last and merges it into the rail face (MEF, KEF). Faces keep the names they had before the blend, read from the faces the edges were resolved on.
- **Stages.** A rolled corner's first fillet is built in an earlier stage, as if the others were not blended (an end on the third face); in the next stage the other two run on into its end curve tangentially and it is blended with them, joined smoothly at the first fillet's rails. Chains wait for every chain built first at one of their corners, the two rolling over one corner go together, and a cycle is `Unsupported`; each later stage has a key derived from the blend's. The journal is composed: names a stage made and a later one took away never appear, and the vertex is replaced by the faces that replaced its end curve too.
- **Names.** A corner face from the vertex and the faces it touches, sorted (`BlendRole::Corner`); edges between a blend face and a corner face, between two trimmed blends and between mitred chamfers are `Section`s of the two faces; a trim's end curve and a fan's are `End`s. The vertex is `Replaced` by the faces there.
- **Ends.** An end curve is the arc of the blend surface's meeting with the end face that lies on the blend face (scored against the section through its middle, `plan::on_face`), not the arc nearer the vertex. A closed branch fitted as a clamped spline (a pipe cut all round, a small fillet's spine round a pipe's end) has its start moved off the stretch a blend needs, its pcurves with it (`blend::seam`), and pcurves that still don't cover an arc are fitted again. A fitted curve is tangent within its tolerance over the whole piece an end lies in, and overflow leaves out the stretch where a curve ending tangentially on an edge stays within the tolerances of it. So the chain round a pipe fillet's end cut off askew builds.
- **Testing and limits.** `tests/corners.rs` checks exact volumes (a box's corner, every edge, every corner alone, a cavity's concave balls, trims of fillets and of a fillet and a chamfer by integration, mitres, rolls by Pappus, a block's foot rolled round its rounded edges, three stages against the same done by hand, a fillet up to a pyramid's apex against booleans) and refusals; `tests/blend_names.rs` the corner names and journals; `tests/corner_props.rs` 96 seeded random boxes and sweeps (release only, as are the slow corner cases, each file its own CI step); golden hashes (`corners` section). A concave fillet ending on a face that doesn't run on past it overflows (6.B), so a concave corner rolls only over a convex first fillet; a fillet rolled round an end arc twice its radius is a horn torus (`RadiusTooLarge`); a long blend face a millimetre wide meshes slowly at a fine chord.

## Booleans on blends and hardening (decided in phase 6)

The design is document 43 in the Coxswain planning project `ryucad-ryukei`; these are its phases 5 and 6, plan 6.D.

- **Pipe bounds.** A pipe's frame depends on `s` alone, so enclosures of the spine's and the frame's first and second derivatives are tabulated once per stretch of spine (`Pipe::frames`, halved until each enclosure is narrow to an eighth of its size, built on first use), and every derivative bound over a box (`derivative_bound`, `first_bound`) is a lookup with `cos` and `sin` of the box's angles. Certifying a rail's pcurve on a pipe dropped from 1.5 s to about 0.1 s.
- **Pipes in booleans.** `curve_surface` meets a pipe through `curve_pipe` and `surface_surface` a pipe and an analytic surface through `pipe_surface`, so `face_face`, the boolean table and `point_in_body` take pipe faces: holes and cuts through any fillet. Two pipes, or a pipe with a NURBS or swept face, that meet stay `Unsupported`.
- **Beside.** `intersect::beside` (and `face_beside` for a face of a body) certifies that a face of an analytic surface or a pipe (`geom::sheet::Sheet`: the surface's point over jets) keeps off another analytic surface `f` outside a strip round curves where they touch: `F = f ∘ P` is enclosed over parts of the face's parameter box (seam-aware: the shortest stretch round a periodic direction), halved breadth first, and a part is left out when the rails' pieces (exact Bézier hulls, grown by `1e-12` so neighbours meet, moved by whole periods) cover it within `strip / |P_u|` across, when it lies within the strip of a rail's end or a given vertex, or when no boundary piece meets it and its middle is outside the face. Every other part must be signed (32,768 parts at most).
- **The self-intersection check.** Faces tangent along an edge they share (normals within a millionth of a radian at its middle) are first certified apart, and traced only if that fails: they pass when either keeps off the other's surface beside it, the more curved first, or when both lie either side of the plane of a planar shared edge (a section: a circle, an ellipse, or a NURBS whose control points lie within its tolerance of a plane), with a strip `sqrt(2 × size × reach)` wide, the touch rule's tangent wedge. Pairs a trace can't settle that share an edge or a vertex are tried the same way. An edge both faces use is never cut with the other face's surface: its ends are the only cuts. Blend, chamfer, corner and pipe results now check clean, except a fillet rolling on an earlier pipe fillet (two pipes along a rail: neither has an implicit form) and, rarely, two fillets of different radii trimmed against each other (their cylinders cross inside a face and their intersection has a node where the rails cross; 1 of 144 seeded cases).
- **NURBS form.** `Pipe::to_nurbs_within(range, tolerance)` returns a NURBS, `[Reparam::Identity, Reparam::Angle]`, and its certified bound: each section the exact rational quadratic turn, its eight control points cubic Hermite along `s`, spans halved until `h² / 8` times the enclosed difference of second derivatives is within the tolerance. `Surface::to_nurbs` stays exact-only.
- **References.** `ryukei-bench` fillets and chamfers through OCCT's `BRepFilletAPI_MakeFillet`/`_MakeChamfer` and SMLib's `SmFilletExecutive` (fillets only: SMLib measures chamfers as a chord), each kernel picking its own edges and faces from points (`BenchBlend`). `tests/blends.rs` (devcontainer) checks box edges, a rounded box, a rim and the three chamfers against exact volumes and a pipe fillet against OCCT's, and races a plate's 1,000 hole rims on one thread: about 0.2 s against OCCT's 7 s (the bar: ryukei must be faster). Single blends are slower than OCCT's: every edge of a box 60 ms against 10, a boss's pipe fillet 1.7 s against 3 ms.
- **Testing.** `tests/blend_booleans.rs` (a rounded rim halved and drilled against Pappus, a pipe fillet halved by its symmetry planes and drilled; the pipe cases release only, its own CI step); the seeded blend and corner tests run the self-intersection check; the `blend` fuzz target blends primitives, sweeps and boolean results from bytes (`ryukei_testkit::blend_bytes`): every result a typed refusal or a body that checks clean and meshes; golden hashes (`blend_booleans` section); `benches/blend.rs` and `blend_kernels.rs`.

## Persistence (decided 2026-10-16)

A ryucad model is a folder of canonical text feature files in a Git repo, one per feature or object, rebuilt deterministically by ryukei. Git provides history, branches and merges; ryucad supplies CAD-aware diff and merge drivers, and features reference topology by stable name. Derived data (bodies, meshes, renders) is a cache, never committed. ryupdm builds on the same repos rather than a second store. This follows the freecad-spike (github.com/Seiraiyu/freecad-spike) GO verdict, without FreeCAD.

## ryucad (decided in ryucad phase 0)

The design is document 24 in the Coxswain planning project `ryucad-ryukei`.

- **Projects.** A project is a folder: `ryucad.json` (format, default unit), then `parts/<part>/part.json` (the ordered feature list) and `parts/<part>/features/<feature>.json`. Every file is canonical JSON (`doc::canonical`): sorted keys, one value per line, shortest round-trip numbers, LF, a trailing newline, written atomically. `format` is versioned per file kind; newer is refused with `format_too_new`. Part and feature IDs are `^[a-z0-9][a-z0-9_-]{0,62}$`, not a Windows device name, and never change. Derived data never goes into the project.
- **Units.** Quantities are strings with units (`"10 mm"`), kept as written; bare numbers take the project's default unit and are written explicitly. ryucad converts to meters only when it calls ryukei, by one f64 multiplication. Output reports `{"value", "m"}`.
- **Rebuild.** Each phase 0 feature is one primitive with its own body. Its `OpKey` is `OpKey::from_bytes("ryucad.feature\0<part>\0<feature>")`, so editing parameters or placement never renames anything. Placement is `origin` plus `z` and `x` axes (`Rigid::from_frame`). Features rebuild in parallel, are collected in order, and every body passes `check::check`. `tests/golden/rebuild.txt` holds ryucad's bit-exact hashes.
- **Agent interface.** The `ryucad` CLI prints one JSON document (`{"ok", "result" | "error", "warnings"}`) and exits 0, 1 (the agent can fix it), 2 (usage), 3 (no usable project) or 4 (not the agent's fault). Error codes (`error::Code`) are stable and never reused. Warnings are only the envelope's strings: a protocol result that carries `warnings` (`history.log`, `config.get`; JSON-RPC has no envelope) has them moved there by the CLI. A part's `revision` (a hash of the files that define it) guards writes through `--expect`.
- **Daemon.** One per project (`ryucad daemon run`), started by the CLI on demand, serving newline-delimited JSON-RPC 2.0 (`proto`) on a Unix socket in a private runtime folder or an owner-only named pipe. The runtime folder never follows `$TMPDIR`, which agent sessions, sudo and launchd set differently: macOS uses the user's temporary folder from `confstr`, other Unix `XDG_RUNTIME_DIR`, else `/tmp`. It checks file freshness before every request (size and time from the directory listing, then content, which it keeps for the activity log), reloads only the parts whose files changed (all of them when the manifest did), and caches rebuilds by revision. A daemon of another version is replaced; a request that was never delivered runs in process with a warning; `--no-daemon` or `RYUCAD_NO_DAEMON=1` skips it. CLI tests run every scenario both ways.
- **Persistence and releases.** Models are the feature files in Git. Releases are static binaries for x86_64/aarch64 Linux (musl, with mimalloc), aarch64 macOS and x86_64 Windows, with `SHA256SUMS`; the installers verify them and install to `~/.ryucad/bin`.

## Live session (decided in ryucad phase 1)

The design is document 28 in the Coxswain planning project `ryucad-ryukei`.

- **Use model.** Agents model; humans watch, point, judge and nudge. Parity: everything the app can do is a `proto` method with a CLI command (a test fails otherwise), and a human's edit goes through the same request, with `expected_revision`, as an agent's. State lives in five layers: the model and project knowledge in Git, org standards (later, ryupdm), user preferences in the OS config folder, and session state in the daemon. A setting goes in Git only if someone checking out a commit needs it to rebuild or understand the model.
- **Participants.** A connection says `session.hello` as a human (an app window, gone with its last connection) or an agent (reused by name across CLI calls: `--as`/`RYUCAD_PARTICIPANT`, `agent` by default, kept 10 minutes). Each has its own selection, camera, highlights (style `pending`/`changed`/`note`, replaced by style and label) and status. "The human" is the one human attached; with several, `ambiguous_participant`. Entity references are `<part>/<feature>/<32 hex>` everywhere and never resolve to a nearest match; references that stop resolving drop out after a rebuild.
- **Notifications.** `subscribe` turns a connection into a subscription; each has a queue drained by its writer thread, and past 1000 queued it gets one `resync`. Notifications carry state: `model.changed`, `project.changed`, `config.changed`, `participant.changed`, `activity.appended`, and only changes made after subscribing. While anyone is subscribed, the daemon runs its freshness check every `daemon.poll_ms` (250 ms). `ryucad watch` lets an agent wait for them.
- **Activity and undo.** The daemon logs every change it makes (who, the method, each file before and after) and every change it sees behind its back (`external`, not undoable), keeping 1000 entries or 64 MiB. `undo`/`redo` restore files only if every touched file is still as the entry left it (else `undo_conflict`), and are logged themselves. The log is memory only; Git is the history, read with `gix` (no commits, no network; see Diff and check for the config ryucad writes).
- **Settings.** A fixed schema in `config`: `default_unit` in `ryucad.json` (a logged, undoable file change guarded by the project revision), everything else in `preferences.json` under the OS config folder (`RYUCAD_CONFIG_DIR` overrides it); a file that can't be read is reported, used as defaults, and kept as `.bak` when next written; a preference set to its default is removed, so it reads as the default.
- **Meshes and renders.** Display meshes come from `display.quality` (chord a fraction of the body's diagonal), cached by body hash and quality, missed bodies meshed in parallel. `mesh.get` answers JSON, or with `transfer: binary`, `ryucad.mesh.1` bytes after the response line (`binary: {encoding, length}`); renders are always bytes. `render` is a CPU rasterizer in `ryucad::render`: twice the size averaged down, parallel bands, f32 pixel arithmetic, normal display quality and a fixed theme whatever the user's preferences, so its pixels are golden-tested on every platform. Cameras that frame the model (renders, `camera --view/--fit`, the app's first view, standard views and Zoom to fit) fit its mesh points, not its box: centred as the view sees them (in perspective, the extremes each way at equal angles), with a margin, at the view's aspect where it is known (square for `camera`, whose followers may be any shape).
- **Doctor.** `doctor` reads the folder directly (it works with no manifest; a folder with parts but no manifest is `project_damaged`) and reports 20 issue codes, each with planned repairs: exact file changes, an ID with a hash of the files involved (`repair_conflict` if they changed), and parameters (`unit`, `order`). Repairs restore from Git `HEAD` where they can, and never rename (that would change stable names).

## Desktop app (decided in ryucad phase 1)

The design is document 28 in the Coxswain planning project `ryucad-ryukei`; the plan is the phase 1.B plan there.

- **Process.** `ryucad-app` is eframe (egui on winit and wgpu), all Rust. It is a client of the project's daemon and nothing else: it depends on the `ryucad` library for `proto` and `client`, never touches project files (a damaged project is repaired by running `ryucad doctor`) and never calls ryukei. It starts daemons from the `ryucad` binary beside it, else on `PATH`, which must be the same build: the same ryucad, ryukei, commit and protocol (`VersionInfo::same_build`; the target differs on Linux, where the app is glibc and the CLI static musl). `RYUCAD_APP` names the app for `ryucad open`.
- **Connections.** Two per window, as one human participant named `<OS user> (window n)`: requests on a thread, notifications on a `client::Subscription`, which wakes its own reader when dropped so a closed window leaves the session. A lost daemon greys the window, which reconnects with backoff and loads again.
- **Model.** Parts and features from `rebuild` reports (which give each feature's `type`), meshes fetched as `ryucad.mesh.1` one body per request and kept by body hash, so an unchanged body is never fetched twice. Cameras move with `view::{orbit, pan, zoom}` and are shared at most every 150 ms; matrices are made relative to a reference point near the model so f32 GPU positions stay precise.
- **Drawing.** The scene renders with wgpu into a texture of its own (MSAA when the adapter can), shown as an egui image and read back in tests; each body uploads once per hash, and selections, highlights and hover paint over faces from a per-frame buffer at equal depth. Picking is a CPU ray cast on faces and screen distance for edges and vertices (vertex over edge over face, nothing hidden). Edges are pulled towards the eye by 0.1% of their distance, along their sight line, and the near plane stays at least far/1000, so hidden edges stay hidden close up; egui samples a plain (not sRGB) view of the scene's sRGB texture, so the window shows the colours drawn. The window's look is the `ui.style` preference (`drafting`, the default, `graphite` or `studio`; `ui::style::Look`): predefined palettes, corners and spacing for egui's light and dark styles, the same layout in each, no shadows, and `ui.theme` picks the mode. The viewport's background is the style's in a light theme and one shared grey in a dark one (the styles' dark viewports sit too close to edges). Picking judges an edge's visibility at its own pixel, with a perspective-correct point. Navigation: an orbit turns about the model under the press (else the middle of the view, else the model's middle); the wheel zooms towards the model under the cursor, over the background towards the cursor at the depth of the model's middle, and zooming at a point puts the target on the view axis at that point's depth, so it stays by the model. On a trackpad (scrolls in points not from a wheel) two fingers pan, Shift+two fingers orbit, a pinch zooms; on macOS Ctrl+click is a right-click and the SolidWorks pan is Cmd+middle. Hardware adapters first, else a software one (lavapipe, WARP) with a note in the status line.
- **Writes.** The property panel saves through `feature.edit` against the revision `feature.show` read it at (`feature.show` now returns it); a conflict reloads the form and lists what changed. Settings go through `config.set`; preference writes hold a lock file, since every project's daemon shares `preferences.json`, and the daemon (not the app) puts a project first among the recent ones when a window says hello.
- **Tests.** App tests run against real daemons, building `ryucad` themselves; drawing tests skip without an adapter unless `RYUCAD_REQUIRE_GPU` is set (CI sets it on Linux, with lavapipe, and Windows). Window tests drive the real app with `egui_kittest`, whose accessibility check means every control needs a name. The viewport snapshot is lavapipe's, compared within a tolerance.
- **Packaging.** Release archives carry `ryucad` and `ryucad-app` (plus `share/` files on Linux and macOS); installers install both unless `RYUCAD_NO_APP=1`, and register "Open in ryucad" on folders (Windows, per user), a desktop entry and `ryucad.json` MIME type (Linux), and an AppleScript launcher compiled at install time into `~/Applications/ryucad.app` (macOS, unsigned).

## Parameters and expressions (decided in ryucad phase 2)

The design is document 36 in the Coxswain planning project `ryucad-ryukei`; this is its phase 1.

- **Expressions.** Anywhere a quantity goes, a string may be an expression (`ryucad::expr`): literals with units (`3 mm`, `15 deg`; angles are `deg` and `rad`), parameter names (`[a-z_][a-z0-9_]{0,62}`, not a unit, function or `pi`), `+ - * / ^`, parentheses and the functions in `expr::FUNCTIONS`, all from `ryukei::math`. A string that is only a number takes the default unit, as in phase 0; inside an expression a bare number is a plain number, so `wall + 3` is `unit_mismatch`. Values carry a dimension (`units::Dim`, powers of length and angle); syntax faults are `invalid_quantity` with a byte `position`. Text is kept token for token with canonical spacing (`2 * wall + 3 mm`), and output adds `"expr": true` to a quantity that isn't a literal.
- **Parameters.** `parts/<part>/parameters.json` (kind `ryucad.parameters`) holds a part's parameters, each an expression over the others (`expr::Env`; cycles are `parameter_cycle`). The part's revision covers it. Features are evaluated against it when the part loads, so `Quantity` holds its value; a feature whose parameter is missing or broken fails alone. A feature with any expression is written at feature format 2, one with only literals at 1.
- **Protocol.** `param.list`, `param.set`, `param.delete` (refused with `has_dependents` while anything reads it; the file goes with its last parameter) and `param.rename` (rewrites every expression that reads it, in one logged change). Writes refuse values that don't evaluate or that would break a feature that loads now.

## Sketch solver (decided in ryucad phase 2)

The design is document 36 in the Coxswain planning project `ryucad-ryukei`; these are its phases 2 and 7, stages 1 and 2 of the solver.

- **Sketches.** `ryusketch::Sketch` holds points, lines, arcs (counterclockwise, radius `|start - center|`) and circles by caller IDs, and the constraints in `Constraint`; `fixed` points and circles are constants (projected geometry). Positions lie in ryukei's size box (±500 m), radii at most 500 m, lengths at most `MAX_LENGTH` (1000 m): past it f64 can't resolve `SOLVE_TOL`. `solve` validates it, then returns the sketch with solved positions and a `Report`; a solve that leaves the box hasn't converged.
- **System.** Coincident points and concentric centers are merged before solving (a coincidence closing a loop is redundant by structure); everything is scaled by a power of two (exact); each constraint becomes residuals written once over forward-mode dual numbers, so the Jacobian is exact. Lengths hold within `SOLVE_TOL` (1e-10 m), angle-like residuals within `ANGLE_TOL` (1e-12), whatever the scale. A constraint that reads the direction of a line shorter than `SOLVE_TOL` never holds: a collapsed line has no direction.
- **Solving.** Damped least-norm Gauss-Newton from the stored positions, so free geometry moves as little as it can and roots don't flip; steps are capped at half the sketch's size, radii stop at zero, and the solver aims at a quarter of the tolerance. A sketch that already holds returns the same bits with `changed` false.
- **Stage 2.** Each connected component is split by its Dulmage-Mendelsohn decomposition (`blocks`: a Hopcroft-Karp matching of equations to variables, Tarjan's components in dependency order): an over-determined part, square blocks, an under-determined part, solved one after another by the same steps over their own variables. A piece that doesn't converge sends the component back to stage 1 from where it started; `solve_whole` is stage 1 alone, for comparisons. The decomposition is structural only: it never decides a rank.
- **Report.** Degrees of freedom and what moves come from the rank and null space of the Jacobian; minimal redundant and conflicting sets from its left null space, cut down one constraint at a time. Stage 2 reads them from the pieces when they are clean (the over part of full column rank, every square block of full rank, the under part of full row rank, all judged against the whole Jacobian's scale): the null space is then the under part's and the left null space the over part's. Otherwise (a dependency only the values show: two horizontal lines also made parallel) it reads the whole component, as stage 1 does. Profiles' closed loops and open chains come from shared points, never positions.
- **Testing and limits.** `tests/props.rs` (random polygons and slots), `tests/stages.rs` (stage 2 against stage 1: the same report on the corpus, and positions within 50 tolerances for well-conditioned well-defined sketches; two independent solves of a sketch with nearby roots may each find either), golden hashes (`tests/golden/solve.txt`, in the `cpu-levels` job), the `sketch` fuzz target (stage 2 converges wherever stage 1 does, and both diagnose a solved sketch alike) and benchmarks. A dimensioned polygon of 1,000 entities solves in about 2 ms (stage 1: 0.8 s), 10,000 in about 20 ms; an under-determined part is still one dense piece.

## Sketch features and sweeps (decided in ryucad phase 2)

The design is document 36 in the Coxswain planning project `ryucad-ryukei`; these are its phases 3 and 4, plan 2.B.

- **Features.** `doc::files::Feature` is an enum: `Primitive` (phase 0's types, `PrimitiveType`), `Sketch`, `Extrude`, `Revolve`. Sketches and sweeps are feature format 2. Quantities may be angles (`units::Field`): a bare number in an angle field is degrees.
- **Sketch files.** A sketch lies on an origin plane (`plane`: `xy`, `yz`, `zx`, `x` along the first axis) or a `placement`. Entities (`point` with `m`, `line`, `arc` counterclockwise, `circle` with `r_m`, `construction` on curves) and constraints (`a`, `b`, `about`, and a `value` expression for dimensions) are objects keyed by ID; IDs are unique across both, generated as `p3`, `l2`, `a1`, `ci4`, `c7`, `d4`. Positions are solver state, f64 meters with `-0` written as `0` (`sketch::clean`), so a write and a read give the same bits. Validation goes through `ryusketch::Sketch::validate`, its faults mapped to the file's IDs and pointers.
- **Solving.** `ryucad::sketch::solve` maps IDs to `u32`s in ID order. Stored positions that already hold come back with the same bits and rebuild uses them as stored; otherwise the sketch is stale, rebuilt from positions solved in memory with a `sketch_stale` warning (in the rebuild result and the CLI envelope); one that can't hold is `sketch_unsolved`. A sketch's rebuild output (`rebuild::Output::Sketch`) has no body: the rebuild report gives its state, dof and staleness instead of a hash, and it has no mesh.
- **Editing.** `sketch.edit` applies a batch of ops (`add`, `remove`, `set`, `move`) with one solve and writes the solved positions, or refuses the whole batch (`sketch_overconstrained`, `sketch_unsolved`, `has_dependents` for a curve's point or what a sweep names); what was moved is held where it was put for a first solve, so it stays there if the rest can follow. Removing an entity removes the constraints that name it. `sketch.solve` reports without writing, for the sketch or a proposed batch; `sketch.get` gives positions in both frames and per-entity and per-constraint states. Writes keep sketches current (see References and recompute below). Staleness from outside is never written behind anyone's back: `doctor` reports `sketch_stale` and its repair writes the solved file.
- **References.** `<part>/<sketch>/<entity>` names a sketch entity in selections, highlights and framing (`entity::Target`). An extrude or revolve names a sketch listed before it: `feature.add`/`edit` refuse a missing sketch (`not_found`), one that isn't a sketch (`reference_wrong_kind`), one after it (`reference_forward`), and entities it doesn't have; `feature.delete` of a swept sketch is `has_dependents`, `feature.move` that would put a sweep before its sketch `reference_forward`.
- **Sweeps.** Profiles come from the solve report's closed loops (`ryucad::profile`), all or those holding a chosen entity; segment keys are SipHash of `ryucad.sketch\0<part>\0<sketch>\0<entity>`, loop keys the same over the loop's anchor: the first of the points where its curves join in natural order (`p2` before `p10`; a lone circle's anchor is the circle), and generated IDs are one past the largest, never a gap, so dimensions, extents, which way lines run and new segments or fillets rename nothing but what sat where a segment joins; removing the anchor point renames both caps and every cap edge. Extrude is along the sketch's normal (`blind`, `symmetric`, `reverse`); revolve about a line of the sketch (`angle` up to 360 deg or `full`, `symmetric`). A sweep whose sketch failed is `dependency_failed`. Kernel faults come back in the sketch's terms: `profile_invalid` with `entities`, `invalid_extent`. `inspect` gives every sweep entity an `origin` (its sketch entity, cap and loop, or the entities either side of it), derived by recomputing the sweep's names from ryucad's keys (`Name::from_u128`, the one ryukei API this phase added); bounds and display meshes of sweeps come from the body's faces.
- **Testing.** `tests/sweeps.rs` (names across edits, `check_intersections`, thread count), the `sweeps` section of `tests/golden/rebuild.txt`, CLI scenarios both ways, and the `feature` fuzz target, which solves sketch files and checks the result is current.

## References and recompute (decided in ryucad phase 2)

The design is document 36 in the Coxswain planning project `ryucad-ryukei`; this is its phase 5, plan 2.C.

- **References.** A feature refers to a face, edge or vertex of an earlier feature of its part by stable name only: `{"feature", "name"}` in files (`doc::reference::Reference`), `<part>/<feature>/<name>` in requests and output. `reference::resolve` finds exactly the entity with that name or fails: `not_found`, `reference_forward`, `dependency_failed`, `reference_wrong_kind` (a sketch, or the wrong kind of entity), `reference_unresolved` (the name is gone; with `role` and `reference`, and `was: {kind, from}` when the session has seen the name: the session remembers every name of every body it built). Never a nearest match, never a signature.
- **Uses.** A sketch on a planar face (`face`, with an optional vertex `origin` and straight edge `x`; proto and CLI `face`, `face_origin`, `face_x`, `""` for the default): the face's outward normal, the part origin and `x` (or `y` when `x` is along the normal) projected onto it. Projected entities: any point, line, arc or circle may carry `projected`; a vertex fixes a point, a straight edge a line's points, a circle parallel to the sketch a circle's centre and radius or an arc's points (counterclockwise in the sketch); the solver holds them fixed (`sketch::Context`), and `add` makes a projected curve's points when they are left out. Edges neither straight nor a parallel circle, or that project to a point, are `projection_unsupported`. Extrude `up_to` a planar face parallel to the sketch or a vertex, plus an `offset` of either sign (`invalid_extent` if not parallel or no further than the sketch). Revolve about a straight edge in the sketch's plane (`invalid_extent` off it). Writes check that references resolve to the right kind now; geometry is rebuild's.
- **Graph.** A feature's inputs (`graph::inputs`) are its swept sketch and its references' features, always earlier in the list; its depth orders the rebuild, each depth in parallel. `feature.delete` of anything another feature reads is `has_dependents`, `feature.move` that would put a reader before its input `reference_forward`; `feature.list` gives each feature's `uses`.
- **Recompute.** Each result is keyed by a BLAKE3 hash of its inputs: ryucad's and ryukei's versions, the feature as written (canonical, units explicit), the values of the parameters it reads, and each input's place and result hash. The session keeps each part's results by feature (`rebuild::Cache`) and reuses every unchanged one; bodies are shared behind an `Arc`. `tests/recompute.rs` checks incremental equals full over random edits at 1 and 8 threads.
- **Keeping sketches current.** `param.set`, `feature.edit` and `sketch.edit` note which sketches are current before they write and write back, solved, those the write left stale, in the same logged change (`sketches` in the response); one that now fails is reported and left. `doctor` judges sketches that read other features by rebuilding their part, and its repair's files include everything they read.
- **Testing.** Unit tests per reference use, `tests/recompute.rs`, the `references` section of `tests/golden/rebuild.txt` (bodies pass `check_intersections` too), a CLI scenario both ways, and the `feature` fuzz target, which builds each file after a box and a sketch.

## Sketches in the app and renders (decided in ryucad phase 2)

The design is document 36 in the Coxswain planning project `ryucad-ryukei`; this is its phase 6, plan 2.D.

- **Drawing.** `ryucad::sketch_view` says how a solved sketch is drawn, for `sketch.get`, `render` and the app alike: each curve a polyline in model space (lines exactly, arcs and circles in pieces of at most the display quality's angle, never under 8 to a turn), each point a dot, each entity in its solve state (`well`, `under`, `over`, `failing`), and each dimension a label: its value as written, with `= <value> <default unit>` (degrees for angles) when it isn't a literal, placed beside what it measures (4% of the sketch's size off a line's middle, past a circle at 45°, along an angle's bisector). `sketch.get` takes a `quality` (the user's by default) and adds `polyline` to curves and `label` to dimensions.
- **Renders.** `render` draws sketches (`sketches`, default true; CLI `--no-sketches`) in fixed state colours (`render::SKETCH_*`), construction curves dashed on screen (6 on, 4 off), points as dots, highlighted sketch entities in their highlights' colours, and with `labels` each dimension's label. Golden: the `sketch_drawing` section.
- **App.** The window fetches each sketch's `sketch.get` when its part's revision moves (and when the display quality or default unit does) and draws it in the scene, depth-tested and pulled towards the eye as edges are: curves as bands two points wide, points as squares, so a sketch on a face shows and one behind a solid hides. Sketch points pick like vertices and curves like edges (`Target::Sketch`); a sketch chosen in the tree is framed and painted. `display.sketches` (default true) turns sketches, their labels and their picking off. Every sketch is drawn, whatever reads it.
- **Labels and forms.** Dimension labels are drawn where no face hides their anchor; clicking one opens its value in the property panel, saved with `sketch.edit` (`set`) against the revision `sketch.get` read; a conflict reloads and says what changed, as the feature form does.
- **Parameters and the tree.** The parameter panel shows the chosen feature's part (else the first part): each parameter as written, its value and what reads it, editable, with a row to add one, saved with `param.set` against `param.list`'s revision. Rebuild reports give each feature's `uses`, and the tree shows them under each feature, with a sketch's state and freedom and a failure's code.
- **Testing.** `tests/sketches.rs` and `tests/params.rs` against real daemons; window tests pick a sketch line, edit a dimension and a parameter, and read the tree; the viewport snapshot has a sketch on the box. lavapipe crashes when window tests draw in parallel (in the devcontainer, and on the CI runners from 2026-10-22), so each window test holds one lock (`one_at_a_time`) for its whole run.

## Diff and check (decided in ryucad phase 3)

The design is document 48 in the Coxswain planning project `ryucad-ryukei`; these are its phases 1 and 2, plan 3.A.

- **Sources and revisions.** `doc::source::Source` lists folders and reads files; `Project::load_from` loads from the folder or from files in memory alike, faults and revisions included (empty folders aren't in Git). `git::revision` resolves a revision expression with gix (`rev_not_found` otherwise; outside a repository `not_a_git_repo`) and gives the project's files there (the manifest, `.gitattributes`, everything under `parts/`) and the project folder's tree. `rebuild`, `mesh.get` and `inspect` take `rev` (CLI `--rev`), `working` meaning the files on disk: the session answers from a frozen session over that revision, one of `session::REVISIONS` (4) kept by tree, most recently used first, which never reads the disk and starts from the working files' caches, so only what differs is rebuilt. Answers name the `commit`.
- **Textconv.** `ryucad git textconv <file>` (plain text, not JSON: Git reads it as the file) prints a header (kind, a feature's type, format), then one sorted line per value (`extent.length = 15 mm`, references as `<feature>/<name>`, arrays of values on one line); a part lists its features one per line in order; a sketch gives each entity and constraint a line and its positions last, apart. Anything that isn't JSON comes back as it is.
- **Registration.** `ryucad init` writes `.gitattributes` in the project folder, a project file the session tracks, so its repair is logged and undoable. `ryucad git install` writes the driver entries (this binary, single-quoted, forward slashes) to the repository's config, `--global` to the user's; the installers run the global one when Git is there. It is CLI only, as `init` is: no session, and the app has no use for it. `doctor` reports `gitattributes_missing` (repaired by adding the lines, keeping the rest) and `git_drivers_missing` in a repository. Plan 3.B added the merge driver and the hooks (see Merge below).
- **Diff.** `diff` (`ryucad diff [--from REV] [--to REV] [--part] [--model] [--positions] [--all]`; `HEAD` and `working` by default) compares two revisions' files as JSON, so broken files and expressions show as written: the manifest by pointer; per part its order (`added`, `removed`, `moved`: those kept outside the longest run both keep), its parameters as written, each feature `added`, `removed`, `changed` or `same` with `changes` by JSON pointer (arrays as one value), a sketch by entity and constraint (`positions` summarised as `changed`/`same`, listed with `--positions`), a file that doesn't read as `invalid`. `--model` rebuilds both and adds, under each feature whose result differs, `model`: each side's result and, for bodies, the faces, edges and vertices `gone`, `new` and `changed` (by the bits of their geometry and boundary) and the box; for sketches, state and freedom. A renamed face is one gone and one new.
- **Check.** `check` (`ryucad check [part] [--against REV]`) rebuilds from nothing and reports findings: `doctor`'s issues (`source: doctor`; stale sketches are among them), `feature_failed`, `faces_intersect` and `cannot_check` (from `check_intersections`), `mesh_faults` at normal quality, and `cache_mismatch` where the session's cache differs from the fresh rebuild. Any error fails it with `check_failed` (exit 1), the report in its details. With a part it keeps the project's own issues and that part's. `--against` adds `diff --model` from that revision to the working files. A merge left unfinished fails it: conflict records are `doctor`'s `merge_conflict`, paths Git left unmerged `unmerged_path`. Release records join it in ryupdm phase 1.
- **Testing.** Unit tests per module (sources, revisions, textconv, structural and model diffs, check), real repositories in tests (`git` with a fixed identity, and in the CLI scenario fixed dates so two repositories' commits match), `git install` with an isolated `HOME`, the installer tests, and the `diff` section of `tests/golden/rebuild.txt`.

## Merge (decided in ryucad phase 3)

The design is document 48 in the Coxswain planning project `ryucad-ryukei`; these are its phases 3 and 4, plan 3.B.

- **Driver.** `.gitattributes` gives `ryucad.json`, `ryupdm.json`, `parts/**/*.json` and `releases/**/*.json` `merge=ryucad diff=ryucad text eol=lf` (`eol=lf` keeps them canonical where Git for Windows would check them out with CRLF; an earlier ryucad's lines are replaced); `merge.ryucad.driver` is `'<ryucad>' git merge-driver %O %A %B %P`, written with the textconv entry. `ryucad git merge-driver` (CLI only, prints nothing) merges three versions with `merge::bytes`: files that are canonical, of one kind, without a conflict record and no newer than this build reads merge by value (`merge::merge`) and come out canonical; anything else merges as lines (`merge::text`, an in-process diff3 on a longest common subsequence after common ends, Git's `<<<<<<< ours` markers) and always exits 1. It never rebuilds and never reads other files.
- **Rules.** Each file is walked in base, ours and theirs by key: one side changed takes it, both alike takes it, otherwise a conflict ("changed" includes added and removed); arrays and references (`{feature, name}`) are one value. A feature whose `type` changes on either side is one value; two different files added at one path are an `id_collision`. `part.json`'s list merges by identity: base's features both keep in base's order, a feature one side moved (outside the longest run it keeps) at that side's place, each side's additions after everything that preceded them on that side, ours first at one spot; moved differently, moved and removed, moved where the other side's moves break its side's order, or added by both at different places is an `order` conflict at `/features/<id>`, its sides' places as `{"after": id}` or `{"first": true}`. Sketches merge entities and constraints by ID and field; positions (`m`, `r_m`) never conflict (the side that moved them, ours if both); removed on one side and changed, or named by what the other side left, is `delete_edit` (ours' value in place, so a removal theirs made comes back); two different members under one ID are `id_collision`. Release and obsolete records are whole files. The result's `format` is the lowest that holds it (`files::feature_format` from the JSON alone).
- **Conflict record.** A conflicted file is ours' value at each conflict plus a top-level `conflicts` object by JSON pointer: `{kind, base, ours, theirs}` with absent sides left out; a whole file's sides are whole files. Loading fails that file with `merge_conflict` (pointers in the details); a conflicted manifest fails every part but the project still opens; `doctor` reports `merge_conflict`.
- **Merge state.** `git::Repo::merge_state` reads `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` and `REBASE_HEAD` (during a rebase): ours is `HEAD`; theirs and base are the other head and the merge base, the picked commit and its parent, or for a revert the reverted commit's parent from the reverted commit. Inside the hook Git runs before committing a merge it made itself, before it writes `MERGE_HEAD`, the heads come from `GIT_REFLOG_ACTION` (`merge <commit>`, or for a pull `FETCH_HEAD`'s heads for merging). Octopus merges are `merge_unsupported`; outside a merge requests are `not_merging`. `unmerged` reads the index's stages.
- **Status.** `merge.status` (`ryucad merge status`) lists conflicts with a stable ID (`<path>#<pointer>`, or `#merge_broke`, `#sketch_stale`, `#rename_merged`), kind (`validate::KINDS`), files, `concerns` (part, feature, entities, parameter, references), `cause` (`ours`, `theirs` or `both`), choices and planned repairs: records' entries; unmerged paths (`modify_delete`, `merge_unparsed`; a deletion carried out counts as settled, a kept file stays listed until staged, since it looks as Git left it); `rename_merged` (Git's merge follows renames by default, and Git 2.47 even with `merge.renames=false`, so a feature one side added whose merged content is what merging it with a feature that side deleted and the other changed gives is reported, with repairs `restore` and `drop`); `merge_broke` (it rebuilds base, ours, theirs and the merge, sides through `Session::at`: a feature that built on a side and fails in the merge, blamed on the other side when its changes reached what the feature reads; one failing only through another the merge broke is listed under it (`also`), one already failing on a side is `already_failing` and doesn't block, one failing through a conflicted file is left to the structural conflict); and `sketch_stale` (current on the sides, stale in the merge; repair writes the solved file). Files settled but not staged are `unstaged`. The status is kept by `validate::key` (the merge, the index's stamp, a digest of the working files).
- **Renumbering.** An `id_collision`'s repair (`renumber`) gives theirs' feature the first free `<id>-<n>` (ryucad's own rule) or theirs' sketch entity one past the largest with its prefix, rewrites what the merge has from theirs (a node equal to theirs' and not ours') that names it (sweeps' `sketch`, `loops` and `axis`, sketch members' points, references), lists a feature where theirs lists it (after ours' where both put it), and maps theirs' references through `diff::match_names`: theirs built as committed and renumbered, each body's faces, edges and vertices paired by exact geometry. Not one to one, no repair.
- **Resolve.** `merge.resolve` (`ryucad merge resolve <id> --ours|--theirs|--value JSON|--repair ID [--expect REV]`) settles a batch in order in memory and writes all or nothing, guarded by part revisions (`conflict`), conflicts (`conflict_not_found`) and repair IDs (`repair_conflict`); one logged, undoable change. A record entry takes the value (an order conflict a place), the entry leaves the record (the record with its last entry); a modify/delete or unparsed file takes a side's stage (a feature file kept is listed where that side lists it, one deleted unlisted). It never touches the index.
- **Hooks.** `ryucad git install` (and `init` in a repository) writes the same hook as `pre-merge-commit` (Git committing a merge itself) and `pre-commit` (someone committing a merge or cherry-pick Git stopped; rebase steps run neither): `exec '<ryucad>' merge status --hook`, which checks every project in `HEAD` and the merged commit, in process, prints what is unresolved and exits 1, and exits 0 at once outside a merge. The check reads the work tree, so it also refuses while a project file differs from the index (changed, deleted or new and not staged: `git::Repo::unstaged`), since the commit would take the index's. Someone else's hook, or a `core.hooksPath` folder, is left alone and reported with the line to add (`git_hook_foreign`, `git_hook_missing`). `merge.renames` isn't written (decided when Git ignored it; Git 2.56 honours it).
- **Session.** `publish` sends `merge.changed` (topic `merge`) with `{merging, status}` when the key changes; `{merging: false}` when it ends.
- **Testing.** `merge.rs` unit tests per rule, `tests/merge_props.rs` (no change gives the other side, same change, disjoint changes commute, outputs canonical and conflicted ones refused), the `merge` fuzz target (raw bytes, or edits of a sketch, list or parameters file), `validate` and `check` tests over real repositories with the driver simulated, `tests/merge.rs` through Git itself (merge, rebase, cherry-pick, pull, a project below the root, rename following, the hooks), a CLI scenario both ways with undo, and the `merge` section of `tests/golden/rebuild.txt`. Limits: a squash merge commits without a merge state; criss-cross histories use one merge base; Git's line merge of files the driver doesn't get (drivers not installed) isn't detected as a renamed merge.

## Compare view and conflict panel (decided in ryucad phase 3)

The design is document 48 in the Coxswain planning project `ryucad-ryukei`; this is its phase 5, plan 3.C.

- **Compare state.** A participant compares the working files against a Git revision or not (`live::Participant::compare`, the revision as given, in `participant.changed`). `compare.set` (`ryucad compare REV`, `--off`) changes `participant`'s, else the one human's (an agent shows a person what it did; `ambiguous_participant` with several), else the caller's; the revision must name a commit holding the project (`rev_not_found`, `not_a_git_repo`; `working` is `invalid_param`). `compare.get` gives the revision and the commit it names now. A window takes its compare from its participant, so an agent's `ryucad compare HEAD` and the window's own menu go the same way, and a reconnected window tells the new session again.
- **What is shown.** The window reads `diff --model` from the revision to the working files (`core::compare`), again after every `model.changed`, one at a time. Only bodies whose results differ take part: their faces are painted new or changed (over the chosen feature, under selections), bodies added or failing at the revision new as a whole, and the revision's body is ghosted (`mesh.get` at the diff's commit, one body per request): translucent, pushed back by the fraction edges are pulled forward so coplanar faces show the model, with faces gone from the working files in the removed colour. Unchanged bodies would only fight the model for pixels. The tree marks features `[added]`, `[changed]`, `[rebuilt]` (only its result differs), `[moved]`, `failed at REV (code)`, lists those only the revision has as `[removed]`, and the property panel lists a chosen feature's changes. A gone face is picked in the ghost where nothing of the model is nearer (`Hit::rev`): described and copied, never selected.
- **Entering one.** View > Compare with HEAD, Compare with… (a typed revision), Stop comparing; a Compare button per commit in the History tab; a bar above the viewport while comparing, with the counts and the colours.
- **Conflict panel.** The window asks `merge.status` when it opens and follows `merge.changed`; `not_merging` and `not_a_git_repo` mean no merge. At the top of the right panel, each conflict shows its kind, what it concerns, its sides, its cause, Take ours / Take theirs and each planned repair (a `merge.resolve` with the revision of its part the window last saw; a refusal reads the status again and keeps saying why), and Show (chooses the feature and marks the sketch entities); a value is typed with the CLI's `--value`, and `merge_broke` is fixed in the model. Settled files waiting for `git add` and features already failing are listed, with a reminder that ryucad never stages or commits. The title says `(merge in progress)` and the status line the summary.
- **Testing.** Unit tests of the diff reading, ghost picking and resolutions; `tests/compare.rs` and `tests/merge.rs` against real daemons and real repositories (`Project::committed`, `diverged`); window tests for both; the scene test draws a ghost; the snapshot gains `compare-lavapipe.png`. The app's font has no `→`: change lines say `->`.

## PDM data model (decided in ryupdm phase 0)

The design is document 44 in the Coxswain planning project `ryucad-ryukei`. Nothing of it is built yet; ryupdm phase 1 (local PDM) implements it.

- **Identity.** A part is (project ID, part ID): the project ID is 128 random bits in `ryucad.json` (`project`, manifest format 2), kept across moves and forks; the part ID is the folder ID, which never changes. A part number is a property, never identity. A deleted part's ID stays reserved while any release record names it (`part_id_retired`).
- **Files.** `ryupdm.json` at the root (kind `ryupdm.config`: `revisions` scheme, `release_branch`, `part_number.pattern`, custom property schema) and `parts/<part>/properties.json` (kind `ryupdm.properties`): core properties `number`, `name`, `description`, `material`, `uom`, `make_buy`, plus declared custom ones with a `type`, `required` and `revising` (default true). Undeclared keys, bad values and duplicate numbers are per-part faults; a part with one still rebuilds but can't be released.
- **Revisions.** Per part, labelled by the project's scheme (`letters` per ASME Y14.35, `numeric`, `numeric2`), never typed. States: released and obsolete are recorded, superseded and `modified` are derived; work in progress is just commits. Editing a released part is work towards the next revision.
- **Release records.** `releases/<part>/<label>.json` (and `<label>.obsolete.json`), append-only, naming the content hash, the revising properties' values, the rebuilt body hashes and the build, never a commit. A record can be written on any branch and is official from the first commit on the release branch's first-parent chain whose tree holds it (`origin/<branch>` if it exists, else the local branch). Tags `ryupdm/<part>/<label>` are derived from records; `release sync` makes and repairs them locally, ryucad's only Git write. Signing is left to Git.
- **Content hash.** BLAKE3 (64 hex) over length-prefixed pieces: `ryupdm.content.1`, the manifest's `default_unit`, `part.json`, each listed feature's ID and bytes, then `parameters.json` if present. It excludes the rest of the manifest, `properties.json` and `ryupdm.json`, so none of those make a released part look modified.
- **Repo and service.** The repo is the source of truth for releases and (phase 4) approvals; the service keeps review state, comments, its audit log and rebuildable indexes. Derived data, release packages included, is a content-addressed cache, never Git or LFS.
- **Code.** A `ryupdm` crate over a new `ryucad-doc` crate (ryucad's file format split out of `ryucad`); `ryucad` depends on both and exposes PDM as `proto` methods and CLI commands. ryupdm never calls the kernel, daemon or app.
